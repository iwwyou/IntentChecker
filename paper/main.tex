\abstract{
Smart contract development lacks the mature debugging infrastructure available in traditional software engineering.
In particular, numeric logic errors---where program behavior diverges from developer intent---are difficult to address.
Whether such errors are present depends on the developer's intended numeric behavior, which is not expressed in the code itself.
Existing detection tools, designed to operate from source code alone in a testing context, rely on pre-defined vulnerability patterns and offer no mechanism for developers to declare and validate numeric intent during development.
Errors not covered by these patterns therefore have no practical way of early prevention.
This paper presents IntentChecker, a development-time intent validation tool for Solidity that operates at multi-contract single-transaction scope and shifts the detection target from pre-defined patterns to developer-defined intent.
We propose an intent model with two types: @During for intended relationships at specific program points within a function, and @Post for intended relationships after function execution.
A validation engine then checks whether the intervals computed by abstract interpretation satisfy the declared intent and reports a validation result together with a risk score.
We evaluate IntentChecker on real-world numeric logic errors and show that it provides a detection signal complementary to existing pattern-based tools, with analysis latency suitable for interactive development.
}

\keywords{Solidity, Numeric Logic Error, Debugging Assistant, Intent Model, Intent Validation}

\section{Introduction}

The debugging toolchain available to smart contract developers remains far less mature than what traditional software engineering provides, and the immutability of deployed contracts further amplifies the cost of bugs that go undetected~\citep{flyinointment}.
This immaturity is particularly acute for numeric logic errors---bugs in which a function executes without raising any compile-time or runtime exception but nevertheless produces values that violate the developer's intended numerical behavior.
Because correctness hinges on what the developer intended for a given computation---information that the source code does not capture---compilers, type checkers, and generic static analyzers are structurally blind to this class of bugs.
A recent empirical study~\citep{defisecurity} confirms this in practice: practitioners identified logic errors as the most difficult vulnerability type to detect, and reported that existing security tools are least effective against them.

Several recent tools---most notably NumScout~\citep{numscout} and GPTScan~\citep{gptscan}---explicitly target numeric logic errors.
These tools face an \textbf{inherent difficulty of the detection paradigm} rather than a mere engineering gap.
First, without access to the developer's actual intent, any detector must fall back on a curated catalog of codified patterns (e.g., division-in-path, operator order, wrong checkpoint order).
Second, because these catalogs are necessarily incomplete, tool coverage is orthogonal: error patterns targeted by GPTScan are missed by NumScout, and vice versa, and no single tool can be expected to unify them.
These are not failures of any specific tool but structural consequences of attempting to detect intent-dependent bugs without an explicit representation of that intent.

Compounding the above difficulty is a second, \textbf{temporal} limitation.
Both NumScout and GPTScan are designed to run over completed code in auditing or testing contexts, after the function under inspection is fully written.
At edit time, when the developer's intent is still fresh in mind and iteration cost is lowest, there is currently no tool that lets the developer declare ``I expect variable $v$ to stay within range $R$ at this point'' and immediately see whether that intent is consistent with the abstract execution of the function being written.
This edit-time gap is the central problem this paper addresses.

Our starting point for closing this gap is SolQDebug~\citep{solqdebug}, our previously published interactive debugger for Solidity.
SolQDebug provides the missing piece of infrastructure: an interactive parser and an incremental control-flow-graph builder that together drive interval-domain abstract interpretation at statement-level granularity, accepting developer-supplied range annotations (@StateVar, @LocalVar) to inject symbolic inputs.
However, SolQDebug only observes variable intervals; it does not validate any intended relationships between them, and its analysis scope is restricted to a single contract and a single transaction.
SolQDebug's own conclusion explicitly leaves numerical defects detection for future work.
This paper realizes that future work.

We present IntentChecker, a development-time intent validation tool that builds on SolQDebug's interactive analysis infrastructure and adds three contributions.
First, we introduce an intent model---a formal specification language consisting of two annotation types that align with the stages of variable flow in a function body, together with a denotational semantics that maps each clause to a tri-valued validation outcome against the abstract states produced by the interpreter. @During annotations specify intended relationships that must hold at specific program points within a function, while @Post annotations specify intended relationships that must hold after the function completes execution.
Second, we develop a validation engine that maps each annotation clause to an interval-domain comparison and produces a graded signal of Satisfied, Violated, or Warning, together with a separately computed risk score on a 0--10 scale and the sub-intervals in which the intent may be violated.
The underlying comparison primitive is mathematically proved sound against the set-theoretic specification of the intent model and cross-validated against brute-force ground truth across all possible topological configurations of two integer intervals.
Third, we extend SolQDebug's analysis scope from single-contract to multi-contract single-transaction, adding support for inherited contracts, library delegatecalls, interface-typed variables, and a practically useful arithmetic subset of inline assembly, and we introduce a new @IReturn debug annotation that injects range bindings into interface call return values, preserving the same ``unknown value, developer-specified range'' semantics already used by SolQDebug's existing debug annotations.

To ground our motivation in concrete numbers, we analyzed 1,023 non-trivial functions from DAppSCAN-source~\citep{dappscan} (see Table~\ref{tab:variable_distribution}) and found that numeric variable types appear in 82\% of these functions, with uint alone used in 78\%.
Since numeric computations form the core of smart contract business logic---handling token transfers, fee calculations, and balance updates---explicitly specifying developer intent for these operations is both necessary and, as our evaluation shows, practical.

We evaluate IntentChecker on 89 real-world numeric logic errors drawn from Web3Bugs~\citep{exploitablebugs} and NumScout~\citep{numscout}.
The evaluation organizes itself around three research questions: the extent to which IntentChecker can surface real-world numeric logic errors through its graded signal (RQ1), the intent model's expressibility ceiling for cases that require bug awareness (RQ2), and how IntentChecker's feedback compares with existing pattern-based detection tools in terms of signal characteristics, latency, and coverage complementarity (RQ3).
Importantly, our positioning with respect to existing tools is complementary rather than competitive: IntentChecker fills a distinct place in the development workflow by enabling intent-driven validation during editing, and is intended to coexist with auditing-time detectors rather than replace them.

\smallskip
\noindent\textbf{Contributions.}
\begin{itemize}
    \item We identify an unfilled gap in current Solidity tooling: the absence of a development-time mechanism for declaring and validating numeric intent, and we show that this gap is not a minor engineering oversight but a structural consequence of how existing numeric logic detection tools are designed (§\ref{sec:background}).
    \item We present an intent model with a formal denotational semantics defining each clause form as a tri-valued outcome against abstract states, together with a validation engine whose interval comparison primitive is proved sound against the semantics and cross-validated against brute-force ground truth, producing a graded signal (Satisfied / Warning / Violated) with a separately computed risk score and violated region (§\ref{sec:design}).
    \item We extend SolQDebug's single-contract single-transaction analysis scope to a multi-contract single-transaction scope that handles inheritance, libraries via delegatecall, interfaces, and a subset of inline assembly, and we introduce the @IReturn debug annotation to bridge the remaining cross-deployment gap (§\ref{sec:prelim}).
    \item We evaluate IntentChecker on 89 real-world numeric logic errors and position it against NumScout and GPTScan along three axes---signal characteristics, per-case latency, and coverage complementarity---demonstrating that the three tools occupy distinct points in the development/auditing timeline rather than forming a single comparison along detection accuracy (§\ref{sec:evaluation}).
\end{itemize}

\section{Background}\label{sec:background}
\subsection{Numeric Logic Errors in Solidity}

Recent research has identified various numeric-related weaknesses in smart contracts~\citep{numscout,gptscan,flyinointment,exploitablebugs,defiattacks}.
Building on these findings, numeric logic errors can be defined as follows:

\begin{definition}[Numeric Logic Error]
Bugs that allow transactions to complete successfully without compile-time or runtime exceptions,
but violate the developer's intended numerical or state relationships during function execution.
\end{definition}

These errors can manifest in different execution contexts.
Single-transaction errors occur within the execution of a single function call---where computation, function calls, and output generation happen in one atomic sequence.
In contrast, multiple-transaction errors only emerge through sequences of function calls, requiring analysis of inter-function dependencies and contract-level invariants.
Examples of multiple-transaction errors include Risky First Deposit and Price Oracle Manipulation~\citep{gptscan, exploitablebugs}, where attackers exploit state changes across multiple function invocations.

This paper focuses on single-transaction function execution, as this aligns with the development-phase validation model where developers can immediately verify individual function behaviors against their intentions.
The representative single-transaction numeric logic error patterns identified in prior work are summarized below:

\begin{itemize}
    \item \textbf{Div In Path}~\citep{numscout}: Division results used in conditions can lead to unexpected control flow due to integer truncation.

    \item \textbf{Operator Order Issue}~\citep{numscout}: Arithmetic order matters: a/b*c $\neq$ a*c/b due to intermediate truncation.

    \item \textbf{Exchange Problem}~\citep{numscout}: Rounding errors in exchange calculations may result in zero output despite valid input, or receiving tokens without payment.

    \item \textbf{Precision Loss Trend}~\citep{numscout}: Integer division's inherent truncation tends to favor one side, potentially misaligning with protocol intent.

    \item \textbf{Minor Amount Retention}~\citep{numscout}: Integer division in distributions leaves remainders unallocated to any recipient, causing permanent lock.

    \item \textbf{Erroneous Accounting}~\citep{gptscan, exploitablebugs}: Incorrect implementation of business model formulas introduces errors that accumulate into substantial losses. Representative sub-patterns include:
    \begin{itemize}
        \item Wrong Interest Rate Order: Balance calculations using outdated or prematurely updated interest rates yield incorrect results.
        \item Wrong Checkpoint Order: Incorrect ordering between state updates and checkpoints leads to reward miscalculation.
    \end{itemize}

    \item \textbf{Inconsistent State Updates}~\citep{exploitablebugs}: A required state variable update is omitted, causing subsequent calculations to use stale values. For example, failing to accrue interest before a balance query produces incorrect results.

    \item \textbf{Greedy Contract}~\citep{flyinointment}: Contract can receive funds but lacks proper logic to withdraw them, causing permanent lock.

\end{itemize}

Despite their diversity, these error patterns share a common root: the actual behavior diverges from what the developer intended.
A straightforward consequence is that any tool that hopes to flag such bugs reliably must reason about the intended behavior, not only the written code.
The next subsection examines how existing tools handle---or rather, fail to handle---this requirement.

\subsection{Limitations of Current Work}

Several tools explicitly target numeric logic errors.
NumScout~\citep{numscout} catalogs six numerical defect patterns (Div In Path, Operator Order Issue, Exchange Problem, Precision Loss Trend, Minor Amount Retention, and Profit Opportunity) and detects them through LLM-pruned symbolic execution.
GPTScan~\citep{gptscan} addresses a different group of logic vulnerabilities, including several accounting-related patterns, by combining GPT-based scenario matching with lightweight program analysis.
Other works~\citep{accountingerrors,smartinv} take closely related approaches.
These tools represent the current state of the art and have meaningfully advanced the field.
However, when viewed through the lens of the problem defined in §\ref{sec:background}.1, they share two structural limitations that are not engineering oversights but rather direct consequences of their design.

\smallskip
\noindent\textbf{(1) Operation context: post-hoc auditing rather than development.}
Existing numeric logic error detection tools are designed to run over completed code, and are positioned within auditing or testing workflows.
They accept a contract (or a set of contracts) and emit findings as a report.
They do not run inside the developer's editor as code is being written, nor do they accept developer-supplied specifications about the intended behavior of the function currently under the cursor.
As a consequence, the developer's intent is not part of the input at all.
Any detector operating in this context must recover intent indirectly: either by hard-coding intent assumptions as ``patterns'' that describe what buggy code looks like (NumScout), or by asking a language model to infer intent from code, comments, and public documentation (GPTScan, SmartInv~\citep{smartinv}).
Both strategies work only to the extent that the assumed intent coincides with the actual developer intent in the specific contract being analyzed.

\smallskip
\noindent\textbf{(2) Approach: pattern-based coverage is orthogonal across tools.}
Because the operation context rules out direct access to intent, each tool must commit to a fixed catalog of patterns.
These catalogs are necessarily incomplete: NumScout's six numerical defect patterns and GPTScan's accounting-related patterns target disjoint regions of the bug space.
A bug matching a NumScout pattern is, in general, not matched by GPTScan, and vice versa.
The problem is not that one catalog is better than the other; it is that neither catalog can be extended to cover all intent-dependent bugs, because intent itself is not expressible as a static pattern over code.
This orthogonality means that ``adding another pattern-based tool'' cannot in principle converge on full coverage.

\smallskip
\noindent\textbf{These two limitations are structural, not tool-specific.}
We emphasize that we do not characterize the above limitations as failures of NumScout or GPTScan.
Both tools are well-engineered within the design space they chose.
The point is that the design space itself---post-hoc pattern-based detection without explicit intent input---has an upper bound, and the field has largely reached it.
To go further, one must either enlarge the input (ask the developer to supply their intent) or move the tool earlier in time (run it during editing, when the developer is still available to supply that intent).
The approach taken in this paper is to do both.

\subsection{Proposed Overview}\label{sec:proposed-overview}

The structural limitations above suggest a complementary direction rather than a competing one.
If existing detectors cannot see the developer's intent, a tool that sits in the editor and explicitly asks the developer to declare their intent can fill the remaining space without contradicting the existing tools' strengths.
Our prior work, SolQDebug~\citep{solqdebug}, already provides much of the infrastructure needed for such a tool: an interactive parser, an incremental control-flow graph, and interval-domain abstract interpretation that accepts developer-supplied range annotations (@StateVar, @LocalVar) and produces line-level feedback as code is being written.
What SolQDebug does not do is validate any intended relationships between the computed intervals, and its analysis scope is confined to a single contract and a single transaction.

IntentChecker takes SolQDebug as its foundation and adds three things.
First, it introduces an intent model---two annotation types, @During and @Post, together with a grammar of clauses that lets developers declare what numeric relationships should hold at specific program points and after function execution, and a denotational semantics that assigns each clause a tri-valued validation outcome against the abstract states produced by the interpreter.
Second, it introduces a validation engine that reads the intervals computed by the extended abstract interpreter, compares them against the declared intent, and produces a graded result: Satisfied when the intent holds for all values in the intervals, Violated when it fails for all values, and Warning when it holds for some and fails for others.
Each result is accompanied by a risk score on a 0--10 scale and, for non-Satisfied results, by the sub-interval in which the intent may be violated.
Third, it extends the analysis scope to cover multi-contract single-transaction code: inherited contracts, libraries invoked via using directives and delegatecall, interface-typed variables, and a practically useful arithmetic subset of inline assembly.
To handle return values from interface calls whose implementation code is unavailable, we introduce @IReturn, a new debug annotation that uses the same ``inject a range at an unknown point'' semantics already used by SolQDebug's existing @StateVar and @LocalVar annotations.

Given an intent clause $l \mathrel{op} r$ where $l$ ranges over interval $L$ and $r$ ranges over interval $R$, the validation result is deterministically categorized into one of three states:

\[
  \textbf{Satisfied} \quad \Longleftrightarrow \quad
    \forall\, l \in L,\; \forall\, r \in R:\; l \mathrel{op}\, r \text{ holds}
\]

\[
  \textbf{Violated} \quad \Longleftrightarrow \quad
    \forall\, l \in L,\; \forall\, r \in R:\; l \mathrel{op}\, r \text{ fails}
\]

\[
  \textbf{Warning} \quad \Longleftrightarrow \quad
    \text{neither Satisfied nor Violated}
\]

Unlike warnings from pattern-based static analyzers, which are heuristic indicators that a known buggy shape may be present, IntentChecker's Warning is a precise statement: the declared intent holds for some combinations of values in $L$ and $R$ but not others, and the tool reports exactly which sub-intervals fall into the violating region.
In this sense IntentChecker is best understood as an awareness tool rather than a detector: its goal is not to pronounce ``this is a bug'' but to bring the developer's attention to the specific program points where the abstract execution cannot confirm the declared intent.
The next section describes the SolQDebug foundation and the scope extensions in detail, and Section~\ref{sec:design} presents the intent annotation grammar and the validation engine.

\section{Preliminaries: SolQDebug Foundations and Scope Extension}\label{sec:prelim}

This section reviews the parts of SolQDebug~\citep{solqdebug} that IntentChecker relies on and describes the scope extensions we introduce to support intent validation over realistic multi-contract Solidity code.
Readers familiar with SolQDebug may skip §\ref{sec:prelim}.1 and proceed directly to §\ref{sec:prelim}.2.

\subsection{SolQDebug Recap}\label{sec:prelim:recap}

SolQDebug is an edit-time debugging assistant for Solidity that provides statement-level feedback through interval-domain abstract interpretation.
It addresses two forms of inefficiency in traditional Solidity debugging: the temporal cost of the compile--deploy--setup--trace cycle in tools such as Remix IDE, and the iterative cost imposed by the non-reversible state model of the EVM.
Both inefficiencies are resolved by performing the entire analysis inside the editor, without contacting any blockchain node.

\smallskip
\noindent\textbf{Interactive parsing and incremental CFG.}
SolQDebug extends the Solidity ANTLR grammar with seven specialized entry rules that accept partial code fragments---a lone else branch, a function header without a body, a single statement inside an existing block, and so on.
As the developer types or edits code, only the affected region is re-parsed, and the corresponding nodes are inserted into an incremental control-flow graph via a line-to-node index.
Abstract interpretation then resumes from the edit point, reusing previously computed intervals for nodes whose inputs have not changed.

\smallskip
\noindent\textbf{Debug annotations and the ``unknown value, injected range'' semantics.}
Because abstract interpretation over completely unconstrained inputs produces overly conservative results, SolQDebug lets developers supply range information for variables whose actual values are unknown to the analyzer.
Two debug annotation families cover this role:
\begin{itemize}
    \item @StateVar---for global and state variables whose values are determined by prior transactions (e.g., totalSupply, a user's balance, a lending pool's reserves). SolQDebug has no way to know what value these variables hold at the start of the function being debugged; the developer declares a representative range instead.
    \item @LocalVar---for function parameters and locally declared variables whose values are determined by the caller or by earlier computation. This is how the developer specifies the test cases under which the function should be analyzed.
\end{itemize}
Both annotations share a single, unifying semantics: at each program point where the analyzer would otherwise have only $\top$ (``any value''), the developer explicitly injects a bounded range.
The analyzer then proceeds to compute intervals for downstream program points under that injected range, giving the developer a line-by-line view of how the function behaves for the chosen inputs.

\smallskip
\noindent\textbf{Output semantics: range in, range out.}
SolQDebug's output for each annotated path is a table of intervals---one per variable per line---reflecting what the abstract execution computed.
SolQDebug itself makes no judgment about whether these intervals are ``correct'': it neither compares them against any specification nor flags any of them as buggy.
It is, in the strict sense, a debugger: it shows the developer what happens, and leaves the interpretation to the developer.
IntentChecker's validation engine is precisely the layer that adds such interpretation on top of this ``range in, range out'' foundation.

\smallskip
\noindent\textbf{Analysis scope.}
SolQDebug's published scope is deliberately narrow: single contract, single transaction.
A function in the target contract is analyzed under the assumption that its state variables hold the values declared by @StateVar, and that only that function executes.
Inter-contract calls, inheritance, and library invocations are explicitly out of scope and are left to future work in the SolQDebug paper.
The next subsection describes how IntentChecker extends this scope to handle the realistic multi-contract code that real numeric logic errors tend to live in.

\subsection{Scope Extension for Multi-Contract Single-Transaction Analysis}\label{sec:prelim:extension}

Real-world numeric logic errors rarely occur in single-contract code: most of the Web3Bugs and NumScout benchmark cases involve inherited contracts, library calls, or interface-typed variables.
Validating intent over such code requires extending SolQDebug's analysis scope from single contract to multi-contract single-transaction, where a single atomic transaction may touch several contracts located in the same source file or its immediate dependencies, but is still confined to one execution step.
This subsection describes the four extensions required to make this scope practical: (a) a deployment-unit model for identifying which contracts share storage with the target, (b) library and using-directive handling, (c) interface-typed variables and the @IReturn debug annotation, and (d) a practically useful subset of inline assembly.

\smallskip
\noindent\textbf{(a) Deployment-unit scope.}
IntentChecker treats as ``in-scope'' everything that shares storage with the target contract in a single EVM execution: the target contract itself, all inherited parents resolved via C3 linearization, and any libraries invoked through delegatecall via Solidity's using for directive.
These all run under the same address(this) and over the same storage, so debug annotations on the target contract's state variables can be reused without reinterpretation whenever the analyzer steps into an inherited function or a library function.
External contracts---i.e., separately deployed contracts invoked through an address or an interface-typed variable---are out-of-scope by default, because their storage is a different deployment unit that SolQDebug's debug annotations cannot reach.
Extension (c) below describes how @IReturn allows a restricted form of data injection across this deployment boundary for view and pure interface calls.

\smallskip
\noindent\textbf{(b) Library and interface handling.}
For each Solidity construct in the target source file, IntentChecker pre-builds a dedicated CFG:
contracts are stored as ContractCFG, libraries as LibraryCFG, and interfaces as ContractCFG instances marked with a dedicated flag whose functions consist of an empty entry-to-exit body (interfaces carry no implementation).
When a using LibraryName for T directive is encountered, the corresponding LibraryCFG is attached to the declaring contract's set of using-libraries, and subsequent method-call resolution on values of type T walks this set to find the matching library function overload.
Inherited functions are resolved via the same C3 linearization order used by the Solidity compiler, ensuring that overrides behave as they would at runtime.
Library function bodies are analyzed in-place, reusing the debug annotations of the target contract since a library invoked via delegatecall shares storage with its caller.

\smallskip
\noindent\textbf{(c) @IReturn: Interface Return Value Debug Annotation.}
Interface-typed variables (e.g., IOracle oracle) present a structural problem that debug annotations on state or local variables cannot solve: the implementation code behind the interface is not present in the source file at all, so SolQDebug's abstract interpreter must return $\top$ for any value derived from an interface call.
This $\top$ then propagates into every downstream computation, defeating the purpose of intent validation for any function that reads an oracle or queries an external token contract.

Our observation is that this situation is semantically identical to the case that @StateVar and @LocalVar already handle.
In all three cases, the analyzer encounters a program point at which the actual value is unknown because its origin lies outside the analysis scope: @StateVar handles unknown storage values left behind by prior transactions, @LocalVar handles unknown inputs supplied by the caller, and a fourth kind of unknown---the return value of an interface call---can be handled by the same ``inject a developer-specified range at the unknown point'' mechanism.
This is consistent with the underlying philosophy of debugging: the developer chooses a particular execution path to inspect, declares the inputs relevant to that path, and observes the line-by-line output.
An interface return value is simply another input to the path under analysis; it only happens to originate from beyond a deployment-unit boundary rather than from a local variable or a storage slot.

We formalize this intuition as @IReturn, a new debug annotation that lets the developer bind a range to the return value of a specific interface function.
Two surface syntaxes are supported:
\begin{itemize}
    \item \textbf{Pattern A (variable-qualified).}
    // @IReturn oracle.getPrice() = [1000, 2000] binds the return value of getPrice on an interface-typed variable (oracle must be declared as some interface type).
    \item \textbf{Pattern B (explicit cast).}
    // @IReturn IOracle(oracleAddr).getPrice() = [1000, 2000] binds the return value of getPrice when the call is written as an explicit cast of an address variable to an interface type.
\end{itemize}
Both patterns may target structured return values, including struct members (...getReserves().reserve0) and tuple elements (...getPair()[0]), which we represent as an access chain so that a single return value can be partially specified and partially left as $\top$.

\smallskip
\noindent View/pure restriction.
@IReturn is restricted to view and pure interface functions.
The reason is that a state-modifying interface call would, in general, alter the state of the external contract whose implementation we do not have, and IntentChecker has no principled way to model the resulting storage mutation in the external deployment unit.
Allowing @IReturn on state-modifying calls would let the developer specify the return value but silently omit any side effect, producing a model that does not correspond to any real execution.
Restricting @IReturn to view/pure functions avoids this unsoundness: by definition, a view or pure call has no side effects, so binding its return value is a complete description of its observable behavior.

\smallskip
\noindent Registration.
Algorithm~\ref{alg:process-ireturn} describes how an @IReturn annotation is validated and registered.
Like @StateVar, @LocalVar, and @GlobalVar, @IReturn annotations are processed as part of the batch annotation phase: the developer writes all debug annotations, and the analyzer then interprets the target function from its start block with all registered values in effect.
The key difference is the view/pure check (line~4): if the target function is state-modifying, registration is rejected with a diagnostic, preventing the unsound model described above.

\begin{algorithm}[t]
\caption{ProcessIReturn: Annotation Registration}
\label{alg:process-ireturn}
\begin{algorithmic}[1]
\State \textbf{Input:} annotation $\mathit{contractVar}.\mathit{func}(\,).\mathit{chain} = \mathit{value}$
\State \textbf{Output:} updated IReturn registry $\mathcal{R}$, or error
\Statex
\State $I \gets$ resolve $\mathit{contractVar}$ to its declared interface type
\If{$I$ is undefined} \Return Error(``not an interface variable'') \EndIf
\State $f \gets$ look up $\mathit{func}$ in interface $I$
\If{$f$ is undefined} \Return Error(``function not in interface'') \EndIf
\If{$f$ is not view or pure}
    \State \Return Error(``@IReturn restricted to view/pure'')
\EndIf
\State $\mathcal{R}[(\mathit{contractVar},\; \mathit{func},\; \mathit{chain})] \gets \mathit{value}$
\end{algorithmic}
\end{algorithm}

\smallskip
\noindent Resolution at call sites.
When the abstract interpreter encounters an interface function call during analysis, it must decide whether to return $\top$ (no information) or a developer-specified value.
Algorithm~\ref{alg:resolve-ireturn} describes the resolution procedure.
The registered entries from Algorithm~\ref{alg:process-ireturn} are looked up as a short-circuit check before the interpreter would otherwise default to $\top$.
Two surface patterns are tried in order: Pattern~A matches by the variable name that holds the interface reference (e.g., oracle.getPrice()), and Pattern~B matches by the explicit interface cast (e.g., IOracle(addr).getPrice()).
If a match is found, the registered value is assembled---potentially following an access chain for struct members or tuple indices---and returned immediately, preventing $\top$ from propagating into downstream computations.

\begin{algorithm}[t]
\caption{ResolveIReturn: Interface Call Value Resolution}
\label{alg:resolve-ireturn}
\begin{algorithmic}[1]
\State \textbf{Input:} interface call expression $e = \mathit{base}.\mathit{func}(\ldots)$, IReturn registry $\mathcal{R}$
\State \textbf{Output:} resolved value or $\top$
\Statex
\Statex // Pattern A: variable-qualified (e.g., oracle.getPrice())
\If{$\mathit{base}$ is an identifier with interface type $I$}
    \State $\mathit{entries} \gets \{c \mapsto v \mid (\mathit{base}, \mathit{func}, c) \mapsto v \in \mathcal{R}\}$
    \If{$\mathit{entries} \neq \emptyset$}
        \State \Return \Call{Assemble}{$I$, $\mathit{func}$, $\mathit{entries}$}
    \EndIf
\EndIf
\Statex
\Statex // Pattern B: explicit cast (e.g., IERC20(addr).balanceOf())
\If{$\mathit{base}$ is a cast $I(\mathit{addr})$}
    \State $\mathit{entries} \gets \{c \mapsto v \mid (I, \mathit{addr}, \mathit{func}, c) \mapsto v \in \mathcal{R}\}$
    \If{$\mathit{entries} \neq \emptyset$}
        \State \Return \Call{Assemble}{$I$, $\mathit{func}$, $\mathit{entries}$}
    \EndIf
\EndIf
\Statex
\State \Return $\top$ \Comment{no registry match; fall back to default}
\Statex
\Function{Assemble}{$I$, $\mathit{func}$, $\mathit{entries}$}
    \If{$\mathit{entries}$ contains only the empty chain $()$}
        \State \Return $\mathit{entries}[()]$ \Comment{single scalar return}
    \EndIf
    \State $\mathit{retType} \gets$ load return type schema of $I.\mathit{func}$ from interface CFG
    \State $\mathit{val} \gets \top_{\mathit{retType}}$ \Comment{initialize with $\top$ of the declared type}
    \ForAll{$(c, v) \in \mathit{entries}$}
        \State set $\mathit{val}$ at access chain $c$ to $v$ \Comment{struct member or tuple index}
    \EndFor
    \State \Return $\mathit{val}$
\EndFunction
\end{algorithmic}
\end{algorithm}

\smallskip
\noindent\textbf{(d) Arithmetic-focused inline assembly support.}
Solidity's inline assembly (assembly \{ ... \}) is written in Yul and frequently appears in arithmetic-heavy code, particularly in high-precision fixed-point libraries such as FullMath or ABDKMath.
SolQDebug originally treated any inline assembly block as a single opaque region, leaving all affected variables at $\top$.
IntentChecker implements a dedicated Yul visitor that recognizes the subset of Yul used for arithmetic computation and translates it into the same expression IR used by the rest of the analyzer.
Concretely, the visitor supports variable declarations (let x := expr) and assignments (var := expr) inside a yulBlock, and maps the following Yul built-ins to their Solidity operator counterparts:
arithmetic add, sub, mul, div/sdiv, mod/smod, exp;
comparison lt/gt/slt/sgt/eq;
bitwise and, or, xor;
shifts shl, shr, sar;
the unary not and iszero;
and the three-argument mulmod and addmod, which are expanded into the corresponding Solidity expressions $(a \cdot b) \bmod n$ and $(a + b) \bmod n$.
This coverage is deliberately chosen to capture the arithmetic that high-precision libraries typically express in Yul to bypass Solidity's overflow checks, while avoiding the control-flow and memory features (if, for, switch, mload/mstore, sload/sstore) whose abstract semantics would require separate engineering beyond the scope of this paper.
Yul built-ins outside the supported subset (e.g., keccak256, call, log0) are handled conservatively by leaving their results at $\top$, preserving soundness.
Section~\ref{sec:discussion} discusses why we chose this particular subset and what the remaining unsupported features mean for the analysis.

\smallskip
\noindent\textbf{Summary.}
Taken together, these four extensions transform SolQDebug's single-contract single-transaction sandbox into an analysis scope that covers the ways modern Solidity contracts are actually structured: multiple contracts per source file, library-mediated arithmetic, oracle-style interface calls, and hand-written Yul for performance-critical fixed-point math.
All extensions preserve SolQDebug's ``range in, range out'' character; none of them introduce a notion of correctness on their own.
Building the intent validation layer on top of this extended analyzer is the subject of the next section.

\subsection{System Architecture}

Figure~\ref{fig:architecture} illustrates the overall architecture of IntentChecker.

\begin{figure}[t]
    \centering
    \includegraphics[width=\linewidth]{figure/architecture_drawio.png}
    \caption{System architecture of IntentChecker. Phases~1--2 (Parsing and Analysis Modules) are reused from SolQDebug; Phase~3 (Validation Module) is the core contribution of this work. The Validation Engine receives parsed intent clauses from the Parsing Module and computed intervals from the Analysis Module.}
    \label{fig:architecture}
\end{figure}

\smallskip
\noindent\textbf{Input.}
IntentChecker receives three types of input:
\begin{itemize}
    \item \textbf{Statement}---individual Solidity statements provided incrementally as the developer writes code.
    \item \textbf{Intent Annotation}---@During and @Post specifications expressing the developer's intended numerical relationships.
    \item \textbf{Debug Annotation}---variable initialization directives that provide concrete or symbolic value ranges at program points where the actual value is unknown to the analyzer. This category includes SolQDebug's original @GlobalVar (constructor-initialized storage variables), @StateVar (storage variables modified at runtime), and @LocalVar (function parameters and local variables), as well as the @IReturn annotation introduced in §\ref{sec:prelim:extension}(c) for interface call return values.
\end{itemize}

\smallskip
\noindent\textbf{Output.}
For each intent annotation, IntentChecker produces:
\begin{itemize}
    \item \textbf{Result}---a validation state of Satisfied, Violated, or Warning.
    \item \textbf{Risk Score}---a 0--10 scale score: $0.0$ for Satisfied, $10.0$ for Violated, and $0.1$--$9.9$ for Warning reflecting the severity of the potential violation.
    \item \textbf{Violated Region}---the specific sub-intervals where the intent may be violated, helping developers identify problematic input ranges.
\end{itemize}

\smallskip
\noindent\textbf{Internal Modules.}
The system builds upon SolQDebug~\citep{solqdebug}, whose Parsing Module, Analysis Module, and Snapshot Manager are reused as the basis for IntentChecker's extended analysis.
The Parsing Module uses ANTLR for syntax analysis of both Solidity source fragments and intent/debug annotation comments, and delegates to the official Solidity compiler for semantic validation.
The Analysis Module performs incremental abstract interpretation over the interval domain, updating the control-flow graph and variable states as each statement is processed, and handles the multi-contract scope extensions (inheritance, library resolution via using, interface-typed variables, and the arithmetic Yul subset) described in §\ref{sec:prelim:extension}.
For every library and interface referenced from the target source file, the Analysis Module either loads a pre-analyzed Dependency CFG---a serialized LibraryCFG or ContractCFG object produced once and cached---or constructs one on-the-fly when the source is locally available.
When a debug annotation is received, the Snapshot Manager preserves the current analysis state, allowing the system to apply temporary variable bindings, re-analyze affected code paths, and restore the original state afterwards; this mechanism is reused without modification for the new @IReturn annotation, since injecting a range at an interface call return site is mechanically the same as injecting one at a @StateVar declaration.

The Validation Engine (Phase~3) is IntentChecker's core contribution on top of this extended analyzer.
It receives two inputs from the earlier phases: parsed intent clauses from the Parsing Module, which encode the relational constraints declared in @During/@Post annotations, and computed variable intervals from the Analysis Module, which represent the abstract state of each variable at the annotated program point.
For each clause, it evaluates whether the declared intent holds by comparing the actual intervals against the specified constraints, producing the validation result, risk score, and violated regions as described above.

\subsection{Motivating Examples}

This section illustrates how IntentChecker addresses representative numeric logic errors, using three real-world cases from our evaluation benchmark (§\ref{sec:evaluation}).
The first two cases demonstrate mid-execution checks via @During annotations; the third demonstrates a post-execution check via @Post.

\subsubsection{Operator Order Issue (BoostToken)}

Listing~\ref{lst:compute-example} shows a fee-distribution function that divides before multiplying, causing integer truncation to silently reduce the transferred amount.
The developer intends the marketing wallet to receive $\lfloor\text{amount} \times 5 / 12\rfloor$, but amount.div(12).mul(5) truncates $\text{amount}/12$ first, losing precision when amount is not a multiple of~12.

\begin{lstlisting}[caption={BoostToken: operator order issue in fee distribution (simplified).}, label={lst:compute-example}]
function sendETHToTeam(uint256 amount) private {
    // @LocalVar amount = [68, 68]
    _devWalletAddress.transfer(amount.div(4));
    // @During transfer.arg[0] >= amount * 5 / 12
    _marketingWalletAddress.transfer(amount.div(12).mul(5));
    // @During transfer.arg[0] >= amount * 2 / 9
    _dipWalletAddress.transfer(amount.div(9).mul(2));
    _marketingWalletAddress2.transfer(amount.div(9));
}
\end{lstlisting}

The @During transfer.arg[0] >= amount * 5 / 12 annotation expresses the developer's intent that the actual transfer argument should be at least the mathematically correct share.
With amount\,=\,68, the correct value is $\lfloor 68 \times 5 / 12 \rfloor = 28$, but 68.div(12).mul(5) computes $\lfloor 68/12 \rfloor \times 5 = 5 \times 5 = 25$.
IntentChecker evaluates the annotation to $[25,25] \geq [28,28]$ and reports Violated with risk score~$10.0$.

\subsubsection{Exchange Rate Validation (Nokon)}

Listing~\ref{lst:transfer-example} shows a token purchase function where operator precedence causes the buyer to receive fewer tokens than the exchange rate warrants.

\begin{lstlisting}[caption={Nokon: exchange rate calculation with operator order issue (simplified).}, label={lst:transfer-example}]
function buy() public payable {
    // @GlobalVar msg.value = [50000000000500000, ...]
    // @StateVar presell = true
    require(presell, "presell is closed");
    uint256 amountToBuy = msg.value / ethRateFix
                          * calculateRate();
    // @During amountToBuy * ethRateFix >= msg.value * 250000
    balances[msg.sender] += amountToBuy;
}
\end{lstlisting}

The developer's intent is that amountToBuy should satisfy the exchange-rate invariant: the tokens received, times the rate denominator, should be at least the ETH paid times the rate numerator.
Because msg.value / ethRateFix truncates before multiplication, the invariant is violated for non-round input amounts.
The @During annotation captures this invariant directly, and IntentChecker reports Violated.

\subsubsection{Minting Invariant with Interface Call (Web3Bugs~\#78)}

Listing~\ref{lst:output-example} shows a rebasing vault's mint function.
The bug is that minted proxy tokens are computed from the total vault balance (including the just-deposited amount), which inflates the shares beyond the deposited amount when the redeem rate deviates from~1.

\begin{lstlisting}[caption={Web3Bugs \#78-H-02: vault mint with inflated proxy amount (simplified).}, label={lst:output-example}]
function mint(address to, uint256 amount)
    public override returns (uint256) {
    // @LocalVar amount = [500e18, 500e18]
    // @StateVar _totalSupply = [1000e18, 1000e18]
    // @StateVar _balances[to] = [0, 0]
    // @IReturn IERC20(baseToken).balanceOf()
    //   = [1500e18, 1500e18]
    uint256 _redeemRate = redeemRate();
    require(IERC20(baseToken).transferFrom(
        msg.sender, address(this), amount));
    uint256 baseBalance =
        IERC20(baseToken).balanceOf(address(this));
    uint256 proxy = (baseBalance * ONE) / _redeemRate;
    // @Post _balances[to] <= amount
    _mint(to, proxy);
}
\end{lstlisting}

The @Post \_balances[to] <= amount annotation expresses the invariant that no user should receive more shares than the tokens they deposited.
The @IReturn debug annotation injects a concrete balance (1500\,e18) for the external balanceOf call, which the analyzer would otherwise evaluate as $\top$ (§\ref{sec:prelim:extension}(c)).
With these annotations, IntentChecker computes the proxy amount and finds that it exceeds amount, reporting Violated.
This example demonstrates how @IReturn enables intent validation for functions that depend on external contract state.

\smallskip
These three examples---drawn from real bugs in the evaluation benchmark---illustrate the two temporal scopes of intent validation: mid-execution checks (@During with relational and argument constraints) and post-execution checks (@Post combined with @IReturn for external state injection).
The complete intent model supporting these annotations is defined in the following section.

\subsection{Intent Model}\label{sec:intent-model}

The intent model consists of two complementary components that together determine both what a developer can write and what the written annotation means as a validation judgment.
Section~\ref{sec:intent-syntax} fixes the concrete grammar of intent annotations and the informal meaning of each clause form, grouped by the two annotation types: @During, which checks conditions at specific program points within a function's execution, and @Post, which checks conditions after the function completes.
Section~\ref{sec:intent-semantics} then formalises how the validation engine evaluates an annotation against the abstract states produced by the interpreter, giving a denotational definition of each clause form as a tri-valued outcome in $\{S, V, W\}$.
Together, the syntax specifies the surface language available to developers, and the semantics specifies the mathematical object that every syntactic form denotes.

\smallskip
\noindent\textbf{Annotation Syntax Overview.}
Figure~\ref{fig:intent-grammar} presents the grammar of intent annotations.
Intent annotations are embedded in single-line comments, allowing them to coexist with Solidity code without affecting compilation.
Each annotation begins with a marker (@During or @Post) followed by one or more clauses.
Multiple clauses can be combined using logical operators: \&\& (conjunction) requires all clauses to hold, while || (disjunction) requires at least one clause to hold.

Intent values within clauses support arithmetic expressions using standard operators (+, -, *, /, \%), variable references with member and index access (e.g., balances[msg.sender]), numeric literals, and inline intervals written as [a, b] to represent value ranges directly.
Relational operators include <, >, <=, >=, ==, !=, as well as in and not in for interval membership tests.

\smallskip
\noindent\textbf{@During Annotation.}
The @During annotation specifies intended relationships at specific program points within a function's execution.
It supports the following clause types:

\begin{itemize}
    \item x(before relOp after)---compares the value of variable x immediately before and after an assignment statement. This validates that assignments modify variables as intended (e.g., balance(before > after) asserts that the balance decreases).

    \item x(assign relOp current)---compares the value being assigned to x against its current value. This is useful for validating incremental updates (e.g., counter(assign == current + 1)).

    \item func.arg[n] relOp value---validates the $n$-th argument passed to a function call, ensuring that function calls receive arguments satisfying specified constraints before execution proceeds.
\end{itemize}

\smallskip
\noindent\textbf{@Post Annotation.}
The @Post annotation specifies intended relationships that should hold after function execution completes.
It supports the following clause types:

\begin{itemize}
    \item x(entry relOp exit)---compares the value of variable x at function entry against its value at function exit. This validates function-level effects on state variables (e.g., totalSupply(entry == exit) asserts that total supply remains unchanged).
\end{itemize}

\smallskip
\noindent\textbf{Common Clauses.}
Both @During and @Post annotations share the following clause types:

\begin{itemize}
    \item returnExpression relOp value---validates the expression being returned against a specified value or range.

    \item return[n] relOp value---for functions returning multiple values (tuples), validates the $n$-th return value.

    \item x relOp PercentOf(y, p)---validates that x equals p percent of y, accounting for integer arithmetic. This is particularly useful for fee calculations and token distributions.

    \item x relOp ceil(y, d) and x relOp floor(y, d)---validate rounding behavior, where d specifies the divisor. These clauses help developers express intended rounding directions in division operations.

    \item x relOp y---general relational comparison between two intent values.

    \item x => y---implication clause, asserting that if condition x holds, then condition y must also hold. This enables conditional intent specifications.
\end{itemize}

\subsubsection{Semantics}\label{sec:intent-semantics}

We specify the meaning of intent annotations as a denotational function $\mathcal{V}\llbracket \cdot \rrbracket$ that maps each clause to a tri-valued validation outcome in $\{S, V, W\}$ (satisfied, violated, warning) under a validation context $\Gamma$.
Throughout this subsection we use the point-wise convention $\mathcal{V}\llbracket \varphi \rrbracket(\Gamma) = s$ to specify, for each syntactic form of $\varphi$, the state $s$ produced by applying the meaning function to context $\Gamma$.

\smallskip
\noindent\textbf{Abstract states and validation contexts.}
Let $\Sigma$ denote the space of abstract variable environments produced by the interval-domain abstract interpreter: each $\sigma \in \Sigma$ maps every program variable to an interval (or to a structured value whose leaves are intervals).
Let $\mathcal{I}$ denote the set of integer intervals.
A validation context $\Gamma$ is a record whose fields are listed in Table~\ref{tab:validation-context}; each clause kind uses only the subset of fields relevant to its form.

\begin{table}[t]

For a @During annotation, $\Gamma$ supplies $\sigma_{\text{pt}}$, $\sigma_{\text{before}}$, $\sigma_{\text{assign}}$, $\sigma_{\text{entry}}$, $R$, and $\mathcal{C}$; for a @Post annotation, $\Gamma$ supplies $\sigma_{\text{entry}}$, $\sigma_{\text{exit}}$, and $R$.
For clauses that may appear in either annotation type (the common clauses from Fig.~\ref{fig:intent-grammar}), we let $\text{ref}(\Gamma)$ denote the reference environment: $\text{ref}(\Gamma) = \sigma_{\text{pt}}$ under @During and $\text{ref}(\Gamma) = \sigma_{\text{exit}}$ under @Post.
This captures the rule that a common clause is evaluated at the annotated program point inside @During but at the function exit inside @Post.

\smallskip
\noindent\textbf{Well-formedness.}
We write $\Gamma \vdash \varphi : \mathbf{wf}$ to mean that clause $\varphi$ is well-formed under $\Gamma$: $\varphi$ parses against Fig.~\ref{fig:intent-grammar}, every variable referenced by $\varphi$ resolves in the relevant environment of $\Gamma$, and all clause-specific auxiliary data required by $\Gamma$ is present (a captured $\sigma_{\text{before}}$ for beforeAfter, a return-map entry for retExpr, a matching call expression in $\mathcal{C}$ for func.arg$[n]$, and so on).
The equations below define $\mathcal{V}\llbracket \varphi \rrbracket(\Gamma)$ only for well-formed inputs; clause forms whose auxiliary data is missing correspond to error paths in the implementation and lie outside the semantic claim.

Well-formedness is orthogonal to the informativeness of the input intervals themselves.
Debug annotations (@StateVar, @LocalVar, @IReturn), inherited from SolQDebug, are the mechanism by which developers supply bounded ranges for otherwise-unknown variables; without them, interval inputs may remain $\top$, and the comparison primitive defined below typically returns $W$ even though the semantics is still sound.
Debug annotations therefore raise the informativeness of validation results but are not a prerequisite for the semantics to be defined.

\smallskip
\noindent\textbf{Expression evaluation.}
Intent-value expressions (Fig.~\ref{fig:intent-grammar}, non-terminal intentValue) include ordinary arithmetic subexpressions, variable references with member and index access, interval literals $[a, b]$, and the DSL helpers PercentOf, ceil, and floor.
They are evaluated against a chosen environment $\sigma$ by a function
\[
\text{eval} : \Sigma \times intentValue \to \mathcal{I},
\]
which delegates to the interpreter's expression evaluator for ordinary subexpressions (inheriting soundness of interval arithmetic from the base analyzer) and to annotation-specific rules for DSL-only constructs.

\smallskip
\noindent\textbf{Comparison primitive.}
The core building block of the semantics is the set-theoretic comparison primitive
\[
\text{Cmp}^* : \mathcal{I} \times \text{Op} \times \mathcal{I} \to \{S, V, W\},
\]
defined as
\[
\text{Cmp}^*(L, \mathit{op}, R) \;=\;
\begin{cases}
S & \text{if } \forall l \in L,\ \forall r \in R:\ l \mathrel{\mathit{op}} r, \\[2pt]
V & \text{if } \forall l \in L,\ \forall r \in R:\ \neg(l \mathrel{\mathit{op}} r), \\[2pt]
W & \text{otherwise.}
\end{cases}
\]
For $\mathit{op} \in \{\text{in}, \text{not\,in}\}$, the set-membership interpretation replaces the pointwise comparison: $l \mathrel{\text{in}} r$ holds iff $l \in R$, regardless of the particular $r$, and not\,in is its complement.
By Theorems~\ref{thm:sound-gt}, \ref{thm:sound-eq}, \ref{thm:sound-in}, and Corollary~\ref{cor:state-consistency}, Algorithm~\ref{alg:interval-compare} implements $\text{Cmp}^*$ exactly via the closed-form expressions of Table~\ref{tab:op-formulas}.
The semantics thus has a sound computable realisation; conversely, $\text{Cmp}^*$ gives an algorithm-independent specification of what the validation engine is required to compute.

\smallskip
\noindent\textbf{Three-valued logic operators.}
Compound clauses combine sub-clauses via the connectives
\[
\wedge_K,\; \vee_K,\; \supset_K \;:\; \{S, V, W\}^2 \to \{S, V, W\},
\]
which coincide with Kleene's strong three-valued logic and match the combination tables of Table~\ref{tab:logic-combination}.
Treating $W$ as the third truth value ``unknown,'' $\wedge_K$ yields $S$ only when both arguments are $S$, yields $V$ whenever any argument is $V$, and yields $W$ otherwise; $\vee_K$ and $\supset_K$ are defined dually.

\smallskip
\noindent\textbf{Meaning function.}
The meaning function
\[
\mathcal{V}\llbracket \cdot \rrbracket \;:\; \text{Clause} \to (\text{Context} \to \{S, V, W\})
\]
is defined by cases on the syntactic form of $\varphi$, one equation per clause kind.

\smallskip
\noindent @During clauses.
\begin{align*}
\mathcal{V}\llbracket x(\text{before}\ \mathit{op}\ \text{after}) \rrbracket(\Gamma)
    &= \text{Cmp}^*\bigl(\text{eval}(\sigma_{\text{before}}, x),\; \mathit{op},\; \text{eval}(\sigma_{\text{pt}}, x)\bigr), \\[3pt]
\mathcal{V}\llbracket x(\text{assign}\ \mathit{op}\ \text{current}) \rrbracket(\Gamma)
    &= \text{Cmp}^*\bigl(\text{eval}(\sigma_{\text{assign}}, x),\; \mathit{op},\; \text{eval}(\sigma_{\text{pt}}, x)\bigr), \\[3pt]
\mathcal{V}\llbracket f.\text{arg}[n]\ \mathit{op}\ v \rrbracket(\Gamma)
    &= \text{Cmp}^*\bigl(\text{eval}(\sigma_{\text{pt}}, \text{arg}_n(f, \mathcal{C})),\; \mathit{op},\; \text{eval}(\sigma_{\text{pt}}, v)\bigr),
\end{align*}
where $\text{arg}_n(f, \mathcal{C})$ denotes the $n$-th argument expression of the call to $f$ located within the statements $\mathcal{C}$ at the annotated line.

\smallskip
\noindent @Post clauses.
\begin{align*}
\mathcal{V}\llbracket x(\text{entry}\ \mathit{op}\ \text{exit}) \rrbracket(\Gamma)
    &= \text{Cmp}^*\bigl(\text{eval}(\sigma_{\text{entry}}, x),\; \mathit{op},\; \text{eval}(\sigma_{\text{exit}}, x)\bigr).
\end{align*}

\smallskip
\noindent Common clauses.
The following equations apply uniformly to clauses appearing in either @During or @Post annotations; the reference environment $\text{ref}(\Gamma)$ selects $\sigma_{\text{pt}}$ or $\sigma_{\text{exit}}$ as appropriate for the enclosing annotation type.
\begin{align*}
\mathcal{V}\llbracket \text{returnExpression}\ \mathit{op}\ v \rrbracket(\Gamma)
    &= \text{Cmp}^*\bigl(R(\ell_{\text{ret}}),\; \mathit{op},\; \text{eval}(\text{ref}(\Gamma), v)\bigr), \\[3pt]
\mathcal{V}\llbracket \text{return}[n]\ \mathit{op}\ v \rrbracket(\Gamma)
    &= \text{Cmp}^*\bigl(R(\ell_{\text{ret}})[n],\; \mathit{op},\; \text{eval}(\text{ref}(\Gamma), v)\bigr), \\[3pt]
\mathcal{V}\llbracket e_l\ \mathit{op}\ e_r \rrbracket(\Gamma)
    &= \text{Cmp}^*\bigl(\text{eval}(\text{ref}(\Gamma), e_l),\; \mathit{op},\; \text{eval}(\text{ref}(\Gamma), e_r)\bigr),
\end{align*}
where $\ell_{\text{ret}}$ is the return-statement line selected by the annotation: in @During, the statement on the annotated line itself; in @Post, the join of all return values recorded in $R$.

\smallskip
\noindent Compound clauses.
\begin{align*}
\mathcal{V}\llbracket \varphi_1\ \text{\&\&}\ \varphi_2 \rrbracket(\Gamma)
    &= \mathcal{V}\llbracket \varphi_1 \rrbracket(\Gamma) \;\wedge_K\; \mathcal{V}\llbracket \varphi_2 \rrbracket(\Gamma), \\[3pt]
\mathcal{V}\llbracket \varphi_1\ \text{||}\ \varphi_2 \rrbracket(\Gamma)
    &= \mathcal{V}\llbracket \varphi_1 \rrbracket(\Gamma) \;\vee_K\; \mathcal{V}\llbracket \varphi_2 \rrbracket(\Gamma), \\[3pt]
\mathcal{V}\llbracket \varphi_1 \Rightarrow \varphi_2 \rrbracket(\Gamma)
    &= \mathcal{V}\llbracket \varphi_1 \rrbracket(\Gamma) \;\supset_K\; \mathcal{V}\llbracket \varphi_2 \rrbracket(\Gamma).
\end{align*}

\smallskip
\noindent\textbf{Connection to the algorithm.}
The validation engine of Section~\ref{sec:validation-engine} computes $\mathcal{V}\llbracket \varphi \rrbracket(\Gamma)$ by traversing the clause structure: for each atomic clause it invokes Algorithm~\ref{alg:interval-compare} with intervals selected according to the equations above; for each compound clause it applies the Kleene combination tables.
By Corollary~\ref{cor:state-consistency}, the state returned by Algorithm~\ref{alg:interval-compare} is exactly the state assigned by $\text{Cmp}^*$, so the engine's output agrees with the semantic definition on every well-formed input.
Algorithm~\ref{alg:interval-compare} additionally computes the true probability $p_{\mathit{true}}$, which Algorithm~\ref{alg:risk-score} consumes to rank warnings for presentation; risk scoring is therefore a downstream concern that does not affect the semantic claim.

\subsection{Validation Engine}\label{sec:validation-engine}

The Validation Engine validates developer-specified intent annotations against actual program behavior computed through abstract interpretation.
Given the CFG-based interval analysis from Section~\ref{sec:design}, the engine evaluates each annotation clause and determines whether the intended relationship holds across all possible execution states.

% ── (1) 검증 환경 ──────────────────────────────────────────────
To perform validation, the engine captures variable environments at specific program points:
\begin{itemize}
    \item before\_env: variable state immediately before a statement executes
    \item after\_env: variable state immediately after a statement executes (referred to as current in assign clauses)
    \item assign\_env: the value being assigned in an assignment statement
    \item entry\_env: variable state at function entry
    \item exit\_env: variable state at function exit, computed by joining all normal termination paths
\end{itemize}

% ── (2) 어노테이션별 검증 시점 ────────────────────────────────
\subsubsection{Validation Targets}
\noindent\textbf{@During Validation.}
The @During annotation is validated immediately after the associated statement executes:
\begin{itemize}
    \item var(before op after): compares before\_env against after\_env for variable var.

    \item var(assign op current): compares assign\_env against the current value of var.

    \item func.arg[n] op value: validates the $n$-th argument passed to the function call.
\end{itemize}

\smallskip
\noindent\textbf{@Post Validation.}
The @Post annotation is validated when function execution completes:
\begin{itemize}
    \item var(entry op exit): compares entry\_env against exit\_env for variable var.
\end{itemize}

\smallskip
\noindent\textbf{Common Clauses.}
The following clauses can be used in both @During and @Post annotations:
\begin{itemize}
    \item returnExpression op value: compares the return value against the evaluated value.

    \item return[n] op value: compares the $n$-th element of a tuple return value against value.

    \item $\mathit{exp}_1$ op PercentOf($\mathit{exp}_2$, p): compares $\mathit{exp}_1$ against $p$\% of $\mathit{exp}_2$.

    \item $\mathit{exp}_1$ op ceil($\mathit{exp}_2$, d) and $\mathit{exp}_1$ op floor($\mathit{exp}_2$, d): compares $\mathit{exp}_1$ against $\mathit{exp}_2$ rounded up or down to the nearest multiple of d.

    \item $\mathit{exp}_1$ op $\mathit{exp}_2$: general comparison between two expressions.
\end{itemize}

% ── (3) 검증 의미론 + Risk Score ──────────────────────────────
\subsubsection{State Determination and Risk Scoring}
The engine compares interval-domain values using Algorithm~\ref{alg:interval-compare}, which returns a pair $(\mathit{state},\, p_{\mathit{true}})$ where $\mathit{state}$ is one of three possible outcomes and $p_{\mathit{true}} \in [0, 1]$ is the true probability of the comparison holding under a uniform distribution assumption:
\begin{itemize}
    \item satisfied: the condition holds for all values in the intervals ($p_{\mathit{true}} = 1$).
    \item violated: the condition fails for all values in the intervals ($p_{\mathit{true}} = 0$).
    \item warning: the condition holds for some values but not others ($0 < p_{\mathit{true}} < 1$).
\end{itemize}

The state alone determines the semantic validation result (Section~\ref{sec:intent-semantics}); $p_{\mathit{true}}$ serves as a downstream quantitative signal used only to rank warnings for presentation.
Algorithm~\ref{alg:risk-score} transforms $(\mathit{state},\, p_{\mathit{true}})$ together with structural information about the violated region into a risk score on a 0--10 scale, where $0.0$ indicates a fully satisfied condition and $10.0$ indicates a definite violation.
For warning results, the engine classifies the violation pattern into three risk types based on the structure of the violated region: type~1 (single-direction, minor) maps to scores $0.1$--$3.3$; type~2 (single-direction violation) maps to $3.4$--$6.6$; and type~3 (bidirectional violation or equality operators) maps to $6.7$--$9.9$.
Within each band, the score is computed as $\mathit{base} + (1 - p_{\mathit{true}}) \times \mathit{span}$, so that lower $p_{\mathit{true}}$ yields a higher score within the band.

\begin{algorithm}[t]
\caption{Risk Scoring}
\label{alg:risk-score}
\begin{algorithmic}[1]
\State \textbf{Input:} $(\mathit{state},\, p_{\mathit{true}})$ from Algorithm~\ref{alg:interval-compare}, operator $op$, false-region summary $\mathit{regions}$
\State \textbf{Output:} $\mathit{risk\_score} \in [0.0, 10.0]$
\Statex
\If{$\mathit{state} = \mathit{satisfied}$}
    \State \Return $0.0$
\ElsIf{$\mathit{state} = \mathit{violated}$}
    \State \Return $10.0$
\EndIf
\Statex
\Statex // Warning case: classify and scale within band
\State $\mathit{risk\_type} \gets ClassifyRisk(\mathit{regions},\, op)$
\State $(\mathit{base},\, \mathit{span}) \gets BandOf(\mathit{risk\_type})$ \Comment{type~1: $(0.1, 3.2)$; type~2: $(3.4, 3.2)$; type~3: $(6.7, 3.2)$}
\State $\mathit{risk\_score} \gets \mathit{base} + (1 - p_{\mathit{true}}) \times \mathit{span}$
\State \Return $\mathit{risk\_score}$
\end{algorithmic}
\end{algorithm}

\noindent\textbf{Interval Comparison Algorithm.}
Algorithm~\ref{alg:interval-compare} presents the interval comparison procedure.
Given two integer intervals $L = [l_{\min}, l_{\max}]$ and $R = [r_{\min}, r_{\max}]$ with an operator $op$, the algorithm partitions $L$ into three regions under a uniform distribution assumption over both intervals:
\begin{itemize}
    \item $T_s$ (satisfied region): values of $L$ for which $l \mathrel{op} r$ holds for all $r \in R$.
    \item $T_v$ (violated region): values of $L$ for which $l \mathrel{op} r$ fails for all $r \in R$.
    \item $T_w$ (warning region): values of $L$ whose truth value depends on the actual value of $R$.
\end{itemize}

Table~\ref{tab:op-formulas} defines the early-return conditions and region sizes for each operator, where $n_L = l_{\max} - l_{\min} + 1$ and $n_R = r_{\max} - r_{\min} + 1$ denote the number of integer values in each interval.

\begin{algorithm}[t]
\caption{Interval Comparison}
\label{alg:interval-compare}
\begin{algorithmic}[1]
\State \textbf{Input:} Intervals $L = [l_{\min}, l_{\max}]$, $R = [r_{\min}, r_{\max}]$, operator $op$
\State \textbf{Output:} $(\mathit{state},\; p_{\mathit{true}})$ where $\mathit{state} \in \{\mathit{satisfied}, \mathit{violated}, \mathit{warning}\}$
\State $n_L \gets l_{\max} - l_{\min} + 1$, \; $n_R \gets r_{\max} - r_{\min} + 1$
\Statex
\Statex // Step 1: Early return for definite cases (Table~\ref{tab:op-formulas})
\If{SatisfiedCond($op$, $L$, $R$)}
    \State \Return $(satisfied,\; 1.0)$
\ElsIf{ViolatedCond($op$, $L$, $R$)}
    \State \Return $(violated,\; 0.0)$
\EndIf
\Statex
\Statex // Step 2: Region partitioning (Table~\ref{tab:op-formulas})
\State $|T_s|,\; |T_v| \gets$ per-operator formulas from Table~\ref{tab:op-formulas}
\State $|T_w| \gets n_L - |T_s| - |T_v|$
\Statex
\Statex // Step 3: Compute $p_{\mathit{true}}$
\If{$op \in \{\text{in},\; \text{not\,in}\}$}
    \State $p_{\mathit{true}} \gets |T_s| \;/\; n_L$
\ElsIf{$op \in \{=,\; \neq\}$ \textbf{and} $n_R > 1$}
    \State $p_{\mathit{true}} \gets |T_s| \;/\; (n_L \cdot n_R)$ \Comment{$=$ case; $\neq$: $1 - |T_v|/(n_L \cdot n_R)$}
\Else \Comment{$>,\; \geq,\; <,\; \leq$}
    \State $E_w \gets$ expected true count from $T_w$ via arithmetic series over $R$
    \State $p_{\mathit{true}} \gets (|T_s| + E_w) \;/\; n_L$
\EndIf
\State \Return $(warning,\; p_{\mathit{true}})$
\end{algorithmic}
\end{algorithm}

For the comparison operators ($>$, $\geq$, $<$, $\leq$), the warning region $T_w$ contains values of $L$ whose comparison result depends on the actual value of $R$.
Since Solidity operates on integers, for each $l \in T_w$ the number of $R$-values satisfying $l \mathrel{op} r$ forms an arithmetic sequence across the warning region.
The expected true count $E_w$ is therefore computed in closed form as $E_w = (a + b) \cdot |T_w| \;/\; (2 \cdot n_R)$, where $a$ and $b$ are the number of satisfying $R$-values for the smallest and largest elements of $T_w$, respectively.

For equality and inequality operators ($=$, $\neq$), each overlapping $L$-value has a $1/n_R$ probability of matching any particular $R$-value, rather than being a definite match.
The probability is therefore adjusted by the factor $1/n_R$.

\subsubsection{Algorithm Verification}\label{sec:alg-verification}

We establish the correctness of Algorithm~\ref{alg:interval-compare} in two complementary ways: a mathematical soundness proof showing that the closed-form expressions in Table~\ref{tab:op-formulas} compute $p_{\mathit{true}}$ exactly, and an empirical cross-validation against brute-force ground truth across a comprehensive battery of test cases.

\smallskip
\noindent\textbf{Definitions.}
Let $L = [l_{\min}, l_{\max}]$ and $R = [r_{\min}, r_{\max}]$ be nonempty integer intervals with $n_L = l_{\max} - l_{\min} + 1$ and $n_R = r_{\max} - r_{\min} + 1$. For an operator $op$, let
\[
N_{\mathit{sat}}(L, R, op) \;=\; \big|\{(l, r) \in L \times R : l \mathrel{op} r\}\big|
\]
denote the number of satisfying pairs. Under a uniform distribution over $L \times R$, the true probability of satisfaction is
\[
p_{\mathit{true}}(L, R, op) \;=\; \frac{N_{\mathit{sat}}(L, R, op)}{n_L \cdot n_R}.
\]
Algorithm~\ref{alg:interval-compare} is sound if its returned value $p_{\mathit{func}}$ equals $p_{\mathit{true}}$ for every well-formed input.

\smallskip
\noindent\textbf{Region partition.}
For $op \in \{>, \geq, <, \leq\}$, the algorithm decomposes $L$ into three disjoint regions instantiating the prose given earlier:
\begin{align*}
T_s &= \{l \in L : l \mathrel{op} r \text{ holds for all } r \in R\}, \\
T_v &= \{l \in L : l \mathrel{op} r \text{ fails for all } r \in R\}, \\
T_w &= L \setminus (T_s \cup T_v).
\end{align*}
The decomposition is exhaustive: for fixed $l \in L$, the truth value of $l \mathrel{op} r$ is monotonic in $r$, so it is either always true ($l \in T_s$), always false ($l \in T_v$), or transitions exactly once as $r$ ranges over $R$ ($l \in T_w$).

\begin{lemma}[Region sizes for $>$]\label{lem:region-gt}
For $op = ${} $>$, in the warning case ($l_{\min} \leq r_{\max}$ and $l_{\max} > r_{\min}$),
\[
|T_s| = \max(0,\, l_{\max} - r_{\max}), \qquad
|T_v| = \max(0,\, r_{\min} - l_{\min} + 1).
\]
\end{lemma}

\begin{proof}
$T_s = \{l \in L : l > r_{\max}\} = L \cap [r_{\max}+1, \infty) = [\max(l_{\min}, r_{\max}+1),\, l_{\max}]$, whose cardinality is $\max(0, l_{\max} - r_{\max})$. Similarly, $T_v = L \cap (-\infty, r_{\min}] = [l_{\min},\, \min(l_{\max}, r_{\min})]$, with cardinality $\max(0, r_{\min} - l_{\min} + 1)$.
\end{proof}

\begin{lemma}[Sum over $T_w$ for $>$]\label{lem:tw-gt}
Under the same assumptions, let $T_w = [l_w^-, l_w^+]$ and define $a = l_w^- - r_{\min}$, $b = l_w^+ - r_{\min}$. Then
\[
\sum_{l \in T_w} \big|\{r \in R : l > r\}\big| \;=\; \frac{(a + b)\, |T_w|}{2}.
\]
\end{lemma}

\begin{proof}
For $l \in T_w$ we have $r_{\min} < l \leq r_{\max}$, so $\{r \in R : r < l\} = [r_{\min},\, l - 1]$, with cardinality $l - r_{\min}$. Summing over $l \in T_w$ yields an arithmetic progression:
\[
\sum_{l = l_w^-}^{l_w^+} (l - r_{\min}) \;=\; \sum_{k = a}^{b} k \;=\; \frac{(a + b)(b - a + 1)}{2} \;=\; \frac{(a + b)\, |T_w|}{2}. \qedhere
\]
\end{proof}

\begin{theorem}[Soundness for $>$]\label{thm:sound-gt}
For $op = ${} $>$, $p_{\mathit{func}} = p_{\mathit{true}}$.
\end{theorem}

\begin{proof}
Case 1 ($l_{\min} > r_{\max}$). Every pair satisfies $l > r$, so $N_{\mathit{sat}} = n_L \cdot n_R$ and $p_{\mathit{true}} = 1$. Algorithm~\ref{alg:interval-compare} takes the satisfied early return and outputs $p_{\mathit{func}} = 1$.

Case 2 ($l_{\max} \leq r_{\min}$). No pair satisfies $l > r$, so $N_{\mathit{sat}} = 0$ and $p_{\mathit{true}} = 0$. The algorithm takes the violated early return and outputs $p_{\mathit{func}} = 0$.

Case 3 (warning case). Decompose
\[
N_{\mathit{sat}} \;=\; \sum_{l \in L} \big|\{r \in R : l > r\}\big| \;=\; \underbrace{|T_s| \cdot n_R}_{l \in T_s} \;+\; \underbrace{\textstyle\sum_{l \in T_w} (l - r_{\min})}_{l \in T_w} \;+\; \underbrace{0}_{l \in T_v},
\]
where the first term uses the fact that every $l \in T_s$ satisfies $l > r$ for every $r \in R$. By Lemma~\ref{lem:tw-gt}, the middle sum equals $(a + b)\, |T_w| / 2$. Dividing by $n_L \cdot n_R$ gives
\[
p_{\mathit{true}} \;=\; \frac{|T_s|}{n_L} \;+\; \frac{(a + b)\, |T_w|}{2\, n_L\, n_R} \;=\; \frac{|T_s| + E_w}{n_L},
\]
where $E_w = (a + b)\, |T_w| / (2\, n_R)$ is exactly the quantity computed by Algorithm~\ref{alg:interval-compare}. Hence $p_{\mathit{func}} = p_{\mathit{true}}$.
\end{proof}

\begin{corollary}[Soundness for $\geq, <, \leq$]\label{cor:sound-other}
The remaining comparison operators $op \in \{\geq, <, \leq\}$ admit symmetric proofs: the strict inequality is replaced by its non-strict counterpart, or the roles of $L$ and $R$ are swapped. The closed forms of $|T_s|$ and $|T_v|$ in Table~\ref{tab:op-formulas} arise from Lemma~\ref{lem:region-gt} via these substitutions, and the contribution from $T_w$ is computed by the same arithmetic-series argument as Lemma~\ref{lem:tw-gt}, yielding $p_{\mathit{func}} = p_{\mathit{true}}$ in each case.
\end{corollary}

\begin{theorem}[Soundness for $=$ and $\neq$]\label{thm:sound-eq}
For $op \in \{=, \neq\}$, $p_{\mathit{func}} = p_{\mathit{true}}$.
\end{theorem}

\begin{proof}
For $op = ${} $=$, each value $v \in L \cap R$ contributes exactly one satisfying pair $(v, v)$, and no other pair satisfies $l = r$. Hence $N_{\mathit{sat}} = |L \cap R|$ and
\[
p_{\mathit{true}}(=) \;=\; \frac{|L \cap R|}{n_L \cdot n_R}.
\]
When $n_R > 1$, Algorithm~\ref{alg:interval-compare} branches on $|T_s| / (n_L \cdot n_R)$, with $|T_s| = |L \cap R|$ from Table~\ref{tab:op-formulas}, matching $p_{\mathit{true}}$. The case $op = \neq$ follows by complementation: $p_{\mathit{true}}(\neq) = 1 - p_{\mathit{true}}(=) = 1 - |T_v| / (n_L \cdot n_R)$, which is exactly the complementary expression noted in Table~\ref{tab:op-formulas}.

When $n_R = 1$, the algorithm bypasses the dedicated $n_R > 1$ branch and falls through to the general comparison path. The warning region $T_w$ is then necessarily empty (since $|T_s| + |T_v| = |L \cap R| + (n_L - |L \cap R|) = n_L$), so $E_w = 0$ and the formula reduces to $|T_s| / n_L = |L \cap R| / n_L$. Direct calculation confirms this equals $p_{\mathit{true}}$ when $n_R = 1$: each $l \in L$ contributes one satisfying pair iff $l = r_{\min}$, giving $N_{\mathit{sat}} = |L \cap R|$ and $p_{\mathit{true}} = |L \cap R| / n_L$.
\end{proof}

\begin{theorem}[Soundness for in and not\,in]\label{thm:sound-in}
For $op \in \{\text{in}, \text{not\,in}\}$, $p_{\mathit{func}} = p_{\mathit{true}}$.
\end{theorem}

\begin{proof}
The semantics of in treats $R$ as a set: $l \in R$ holds iff $r_{\min} \leq l \leq r_{\max}$, independent of any particular $r$. Each $l \in L \cap R$ therefore yields $n_R$ satisfying pairs (one for every $r$), so $N_{\mathit{sat}} = |L \cap R| \cdot n_R$ and
\[
p_{\mathit{true}}(\text{in}) \;=\; \frac{|L \cap R| \cdot n_R}{n_L \cdot n_R} \;=\; \frac{|L \cap R|}{n_L} \;=\; \frac{|T_s|}{n_L},
\]
which matches the algorithm's branch for in. The case not\,in is the complement, $1 - p_{\mathit{true}}(\text{in})$.
\end{proof}

\begin{corollary}[State consistency]\label{cor:state-consistency}
Algorithm~\ref{alg:interval-compare} returns $(\mathit{state}, p_{\mathit{true}})$ where $\mathit{state}$ matches the set-theoretic definition of the comparison primitive $\text{Cmp}^*$ given in Section~\ref{sec:intent-semantics}: $\mathit{state} = \mathit{satisfied}$ iff every pair $(l, r) \in L \times R$ satisfies $l \mathrel{op} r$; $\mathit{state} = \mathit{violated}$ iff no pair does; and $\mathit{state} = \mathit{warning}$ otherwise.
\end{corollary}

\begin{proof}
By Theorems~\ref{thm:sound-gt}, \ref{thm:sound-eq}, and~\ref{thm:sound-in}, Algorithm~\ref{alg:interval-compare} computes $p_{\mathit{true}}$ exactly under the uniform distribution. The state branches are then determined by the boundary cases of $p_{\mathit{true}}$: $p_{\mathit{true}} = 1$ iff every pair satisfies the comparison (the set-theoretic satisfied condition), $p_{\mathit{true}} = 0$ iff no pair satisfies (the violated condition), and $0 < p_{\mathit{true}} < 1$ iff both satisfying and non-satisfying pairs exist (the warning condition). These three cases match the corresponding early-return and fall-through branches of the algorithm.
\end{proof}

\smallskip
\noindent\textbf{Compositional soundness.}
Compound clauses are built from atomic clauses via the connectives $\wedge$, $\vee$, and $\Rightarrow$, evaluated under the three-valued logic of Table~\ref{tab:logic-combination}. Treating warning as the third truth value ``unknown,'' these tables coincide with Kleene's strong three-valued logic, a standard result whose soundness with respect to its underlying classical interpretation is well known: a compound clause evaluates to satisfied (resp.\ violated) only when its classical reading would be true (resp.\ false) under every disambiguation of warning. By induction on clause structure, if every atomic sub-clause is evaluated soundly by Algorithm~\ref{alg:interval-compare}, the compound clause is evaluated soundly as well.

\smallskip
\noindent\textbf{Edge cases.}
Two boundary conditions deserve mention. (i) Empty intervals. An empty $L$ or $R$ corresponds to an infeasible execution path; the abstract interpreter prunes such branches before invoking Algorithm~\ref{alg:interval-compare}, so the algorithm is never called on empty inputs. (ii) Singleton right interval. When $n_R = 1$, the comparison operators $\{>, \geq, <, \leq\}$ reduce to standard pointwise tests handled by the early returns; the warning region $T_w$ degenerates to at most one element, and Lemma~\ref{lem:tw-gt} continues to hold (the arithmetic series is trivial). The equality operators $\{=, \neq\}$ with $n_R = 1$ are handled by Theorem~\ref{thm:sound-eq}. Together, Theorems~\ref{thm:sound-gt}, \ref{thm:sound-eq}, and~\ref{thm:sound-in}, Corollaries~\ref{cor:sound-other} and~\ref{cor:state-consistency}, and the compositional argument above establish that Algorithm~\ref{alg:interval-compare} computes $p_{\mathit{true}}$ exactly and returns a state matching $\text{Cmp}^*$ for every operator and every well-formed input.

\smallskip
\noindent\textbf{Empirical cross-validation.}
To guard against transcription errors and unforeseen edge cases in the formal development above, we additionally verified Algorithm~\ref{alg:interval-compare} on a comprehensive battery of test cases that exhaustively cover the topological configurations of two integer intervals.

\smallskip
\noindent\textbf{Verification method.}
For each of the eleven topological configurations, we generate five width profiles that systematically vary the interval sizes: Small (width 1--3), Medium (5--10), Large (20--50), Asymmetric-L ($|L| \gg |R|$), and Asymmetric-R ($|R| \gg |L|$).
Each configuration--profile pair is tested against all eight comparison operators ($>$, $\geq$, $<$, $\leq$, $=$, $\neq$, in, not\,in), yielding $11 \times 5 \times 8 = 440$ test cases.
For every test case, we compute the ground-truth probability $p_{\mathit{bf}}$ by exhaustively enumerating all $(l, r)$ integer pairs under a uniform distribution and compare it against the value $p_{\mathit{func}}$ returned by Algorithm~\ref{alg:interval-compare}.
A test passes when $|p_{\mathit{bf}} - p_{\mathit{func}}| < 0.001$.

\smallskip
\noindent\textbf{Result.}
All 440 test cases pass with an exact match between the brute-force ground truth and the algorithm output (Table~\ref{tab:rq1-results}).
The 100\% pass rate across all configurations and width profiles cross-validates the soundness proof above, confirming that the closed-form expressions of Table~\ref{tab:op-formulas} indeed compute $p_{\mathit{true}}$ for every possible relative position of two integer intervals, independent of their absolute sizes.

This completes the design and verification of IntentChecker's intent model and validation engine. The full implementation, together with the evaluation benchmark and scripts used in the following section, is publicly available~\citep{intentchecker}.

\section{Evaluation}\label{sec:evaluation}

The validation algorithm itself was already verified in §\ref{sec:alg-verification}, where we proved that the closed-form expressions of Table~\ref{tab:op-formulas} compute $p_{\mathit{true}}$ exactly and cross-validated this proof against brute-force ground truth across every topological configuration of two integer intervals.
The remaining questions concern IntentChecker's behavior on real-world code, the structural ceiling of its intent model, and its position relative to existing detection tools.
We address these questions through the following three RQs:

\begin{itemize}
    \item \textbf{RQ1 (Mitigation)}: When intent and debug annotations are provided based on bug report descriptions, can IntentChecker surface real-world numeric logic errors from the Web3Bugs and NumScout benchmarks via its graded Violated/Warning signal? For instances that the tool cannot handle, what is the structural reason, and how does this distribute across the limitation types defined in our taxonomy?
    \item \textbf{RQ2 (Annotation Model Expressibility)}: Among the instances that fail due to intent-model limitations rather than analysis-engine limitations, what fraction can the intent model express---and for those it can, how directly does the annotation capture the correct behavior? This question separates the model's expressibility ceiling from RQ1's empirical mitigation result, classifying each case as inexpressible, strongly expressible (the annotation encodes the correct value directly), or weakly expressible (the annotation detects that something is wrong, without stating the correct value).
    \item \textbf{RQ3 (Comparison with Existing Detection Tools)}: How does IntentChecker's feedback compare to that of ScType, GPTScan, and NumScout on the same set of bugs, in terms of (i) the detection model each tool employs (specification-driven vs.\ pattern-driven), (ii) per-case analysis latency, and (iii) coverage complementarity? The goal is to characterize where each tool sits in the detection landscape, not to argue numerical superiority.
\end{itemize}

\subsection{Experimental Setup}\label{sec:setup}

We construct a benchmark of 89 real-world numeric logic error instances drawn from three complementary sources, each contributing different error patterns under IntentChecker's scope (multi-contract / single-transaction).

\smallskip\noindent\textbf{NumScout (7 instances).}
NumScout~\citep{numscout} provides a curated collection of numeric logic errors mined from deployed BNB Smart Chain contracts.
We use the 95-sample subset distributed in NumScout's official repository (Experiment/95\_Samples\_Run), which the authors identify as their main case-level evaluation set.
We select one representative instance per pattern from the six numerical defect patterns enumerated in NumScout (Div In Path, Operator Order Issue, Exchange Problem, Precision Loss Trend, Minor Amount Retention, and Profit Opportunity), with two instances for Precision Loss Trend, yielding seven cases.
We target contracts with compiler pragma >=0.6---the minimum version supported by IntentChecker's Solidity front-end.
One selected contract carries an older 0.4.x pragma but uses only language constructs that are semantically identical under >=0.6 (no checked-arithmetic difference, no breaking syntax change in the analyzed function); we treat it as compatible with the supported subset.

\smallskip\noindent\textbf{Flyinointment (1 instance).}
We additionally include one Greedy Contract instance from the dataset of \citet{flyinointment}, which originally introduced the Greedy Contract pattern and is referenced in §\ref{sec:background}.1.
NumScout's pattern catalog does not include Greedy Contract, so this single instance is sourced separately to ensure pattern-level coverage of all the single-transaction error patterns described in §\ref{sec:background}.1.

\smallskip\noindent\textbf{Web3Bugs (81 instances).}
Web3Bugs~\citep{exploitablebugs} systematically collected and classified 493 high-severity vulnerabilities from Code4rena audit contests.
We restrict the candidate set to bugs whose execution context fits IntentChecker's scope, namely multi-contract single-transaction numeric logic errors.
This corresponds to (i) all bugs in categories S6-1 through S6-4 (Erroneous Accounting, 86 bugs), whose root causes are semantic errors in arithmetic or accounting logic and which the Web3Bugs authors confirm to be single-transaction, and (ii) the subset of S3-1 (Inconsistent State Updates) bugs whose root cause involves a numeric computation with a missing or stale state variable update.
We manually reviewed the 22 S3-1 bugs and retained the 11 instances meeting this criterion, excluding non-numeric cases such as approval resets and access-control omissions.
This yields 97 candidate instances.

We then exclude 16 instances whose target contracts contain inline assembly blocks---either directly in the target contract or in locally imported/inherited files---which cannot be processed by the abstract interpreter (the supported Yul subset is described in §\ref{sec:prelim:extension}).
After these exclusions, the final Web3Bugs subset contains 81 instances spanning Erroneous Accounting (72) and Inconsistent State Updates (9).

\smallskip\noindent\textbf{Exclusions.}
Of the 89 collected instances, 14 are excluded after manual inspection because they fall outside the definition of a development-time numeric logic error.
The exclusion categories are:
source already silently patched (E1, 2 cases);
checked-arithmetic revert under Solidity~$\geq$0.8 such that the program traps rather than returns a wrong value (E2, 2 cases);
duplicate audit findings on the same buggy site (E3, 2 cases);

required external libraries not provided in the audit package (E5, 2 cases);
bugs whose manifestation requires state changes across separate transactions and therefore fall outside our single-transaction scope (E6, 3 cases);

The remaining \textbf{75 instances} form the effective evaluation set used in RQ1--RQ3.

\smallskip\noindent\textbf{Methodology.}
For each of the 75 effective instances, we (1) analyse the audit report to understand the root cause,
(2) write an intent annotation that captures the expected numeric behaviour described in the report,
and (3) run IntentChecker to record whether it reports Satisfied, Violated, or Warning.
Cases that produce a non-Satisfied verdict are reported as mitigated in RQ1; cases for which no annotation can yield such a verdict are classified into the limitation taxonomy (§\ref{sec:rq1}) and analyzed for annotation expressibility in RQ2.

\subsection{RQ1: Mitigation}\label{sec:rq1}

\noindent\textbf{Setup.}
For each of the 75 effective benchmark instances (§\ref{sec:setup}), we (1) read the audit report and identify the buggy line(s), (2) write @During and/or @Post intent annotations that capture the expected numeric behavior described in the report, (3) supply the debug annotations (@StateVar, @LocalVar, @GlobalVar, and @IReturn) that the function needs to be analyzable under representative inputs, and (4) run IntentChecker on the resulting annotated source.
We record the verdict produced by the validation engine---Satisfied, Warning, or Violated---together with the risk score and violated region.
For instances where no annotation can yield a non-Satisfied signal, we further classify the structural reason according to the limitation taxonomy described below.

\smallskip
\noindent\textbf{Outcomes.}
Of the 75 effective instances, IntentChecker produces a Violated verdict on \textbf{20 cases} when supplied with annotations derived from the audit report.
The remaining 55 instances are classified as not\_detectable: IntentChecker cannot, given the structure of its analysis or its intent model, surface a non-Satisfied signal for them.
We first describe the 20 mitigated cases in detail (pattern coverage, annotation usage, and analysis time) and then present the limitation taxonomy for the 55 unmitigated cases.

\smallskip
\noindent\textbf{Pattern coverage of the 20 mitigated cases.}
The 20 mitigated instances cover 7 of the 8 single-transaction error patterns enumerated in §\ref{sec:background}.1: Div In Path, Operator Order Issue, Exchange Problem, Precision Loss Trend, Minor Amount Retention, Erroneous Accounting (with both Wrong Interest Rate Order and Wrong Checkpoint Order sub-patterns appearing), Inconsistent State Updates, and Greedy Contract.
Profit Opportunity is present in the benchmark but its representative case falls into the L4 category and is not mitigated.
This pattern-level distribution confirms that the mitigated cases are not concentrated in a single ``easy'' pattern but span the breadth of the taxonomy, suggesting that intent-based validation is a general technique rather than a coincidental match for one error class.

\smallskip
\noindent\textbf{Annotation model usage on the 20 mitigated cases.}
Table~\ref{tab:rq1-annotations} reports which intent clauses were used to surface the bug in each mitigated case.
Of the 20 cases, 12 use a @During clause (mid-execution checks) and 8 use a @Post clause (post-execution checks).
The single most common form is the simple relational comparison (intentValue relOp intentValue), used in 9 cases across both @During and @Post.
The two specialized @During forms---Before/After comparisons against an injection point, and func.arg[N] checks on argument values---are each used 2--3 times, and the specialized @Post forms (Entry/Exit, returnExpression, changed(\,)) account for the remainder.
This distribution suggests that the bulk of mitigation work in our benchmark is carried by the basic relational form, with the specialized clauses contributing on patterns that the basic form cannot capture (e.g., monotonicity over function execution, argument-level constraints, post-execution change detection).

To understand what drives the variation across cases, we collected six per-case complexity metrics---total source lines in the deployment unit, function count, control-flow branch count, loop count, debug annotation count, and external call count---and computed the Pearson correlation of each with the mean analysis time.
Figure~\ref{fig:rq1-scatter} plots each metric against analysis time.
Three observations emerge.
First, the strongest predictors are aggregate size measures: source lines ($r=0.87$), function count ($r=0.76$), and branch count ($r=0.72$).
The dominant cost is therefore the abstract interpreter's traversal of the deployment unit's control-flow graph, not any single feature local to the bug site.
Second, debug annotation count is also strongly correlated ($r=0.80$), reflecting that each debug annotation injects an additional state-evaluation point into the interpreter and thus contributes proportionally to total work.
Third, and perhaps counter-intuitively, loop count is only moderately correlated ($r=0.36$), and external call count only weakly so ($r=0.38$).
This contradicts the natural expectation that fixpoint iteration on loops would dominate analysis time.
Inspection of the mitigated set explains the gap: in several cases that contain loops, the widening of accumulator variables happens to occur on variables that do not flow into the intent annotation's value path, so the precision loss does not affect the verdict but the fixpoint iteration cost is still paid.
The cost is real, but it is not concentrated in the cases that succeed---those cases instead pay it as ``dead work'' alongside successful bug surfacing.
A future optimization that confines fixpoint iteration to the intent-relevant scope could reduce this overhead without changing detectability; we discuss this further in §\ref{sec:disc:tech}.

\smallskip
\noindent\textbf{Limitation type definitions.}
\begin{itemize}
  \item \textbf{L1a (Loop widening, 8).} Accumulator variables (+=, *=) inside fixpoint iteration are widened to $\top$, and both buggy and correct executions land in the same widened range.
  \item \textbf{L1b (Loop body granularity, 2).} The bug is exposed only at a specific point inside a loop body, but the analyzer summarizes loops by fixpoint result rather than by per-iteration trace, so no annotation point is available at the granularity needed.
  \item \textbf{L2a (Interface call return $\top$, 3).} The callee is reached only through an interface variable, the implementation is therefore unavailable, and @IReturn is inapplicable because the bug requires the return value of a state-modifying call.
  \item \textbf{L2b (External call, unknown external state, 1).} The implementation exists via dependency pre-analysis, but the callee's runtime storage state lies outside the deployment unit and the return value collapses to $\top$.
  \item \textbf{L3 (Unsupported construct, 7).} The bug-relevant value flows through an unsupported construct---abi.decode, opaque hash builtins, address(this).balance, or non-arithmetic Yul---which the analyzer treats as $\top$.
  \item \textbf{L4a (Inexpressible expected value, 10).} The intent annotation grammar can refer to in-scope arithmetic over existing variables, but the correct expected value depends on a new intermediate computation, an external contract's state, or a function call that does not appear in the program; no intentValue expression can be constructed.
  \item \textbf{L4b (No target storage variable, 8).} The buggy function (a view function, a pure function, a thin wrapper around external calls, or a library helper) does not modify any storage variable in the target contract, so no @Post clause has anything to attach to.
  \item \textbf{L4c (Magnitude-only difference, 1).} Buggy and correct code change the same state variable in the same direction; only the magnitude differs. changed(\,) and Entry op Exit both succeed in both versions, and IntentChecker's PostEntryExit clause does not currently admit arithmetic relations between Entry and Exit.
  \item \textbf{L4d (Invariant masked, 1).} A different statement in the same function already modifies the target state variable, so changed(\,) is satisfied in both versions. The actual invariant is a multi-variable arithmetic relation (e.g., a product invariant) which PostEntryExit cannot express.
  \item \textbf{L5a (Bug-awareness-required: missing code, 7).} A required statement (a function call, a state update) is omitted; the post-condition that would catch this is expressible, but knowing what is missing already presupposes knowing the bug.
  \item \textbf{L5b (Bug-awareness-required: wrong code, 7).} A required statement is present but uses the wrong identifier, operator, or struct field; the corrective annotation is expressible, but writing it requires knowledge of the correct form---and possessing that knowledge would have prevented the bug in the first place.
\end{itemize}

\smallskip
\noindent\textbf{Reading the limitation breakdown.}
Two top-level families emerge.
The L1--L3 limitations (21 instances combined) are properties of the underlying abstract interpreter: the analyzer assigns $\top$ to a value that should have been concrete enough to distinguish buggy from correct execution, and no developer annotation under the current model can recover that precision.
The L4--L5 limitations (34 instances) are properties of the intent model rather than of the analyzer: the abstract interpreter would distinguish the buggy and correct executions if the developer could express the right intent, but the current grammar either has no expression the developer could write (L4) or has one whose construction presupposes already knowing the bug (L5).
RQ2 examines this second family in detail, classifying each of the 34 cases by whether the intent model can express any awareness signal at all---and if so, how directly.

\subsection{RQ2: Annotation Model Expressibility}\label{sec:rq2}

\noindent\textbf{Setup.}
RQ1 partitioned the 55 not\_detectable cases into two top-level families: 21 cases that fail because the abstract interpreter loses precision (L1--L3, analysis-engine limitations) and 34 cases that fail because the intent model cannot express the right intent (L4--L5).
RQ2 examines the second family in detail.
The question is no longer ``did mitigation succeed?''---it did not, by construction---but rather: if a developer were already aware of the bug, could they at least express an annotation that the validation engine would surface as Violated or Warning?
This separates the model's expressibility ceiling from practical detectability, which depends on whether a developer would write that annotation in the first place.

\smallskip
\noindent\textbf{Three-tier classification.}
For each of the 34 L4--L5 cases we attempted to construct an annotation, assuming full bug awareness, that would yield a non-Satisfied verdict on the buggy code.
Each case is then placed into one of three tiers based on the strength of the resulting signal.

\begin{itemize}
  \item \textbf{Inexpressible (L4).} No annotation under the current grammar can yield a non-Satisfied verdict, even with full bug awareness. Either the correct value cannot be constructed from in-scope variables (L4a), the buggy function modifies no target storage (L4b), the difference is in magnitude only along the same direction (L4c), or another statement in the same function masks the change (L4d).
  \item \textbf{Expressible-Strong (L5, ``Direct'').} The annotation expresses the correct value or relation directly (a commonClause of the form intentValue relOp intentValue). The buggy version produces a clean Violated; the corrected version produces Satisfied. The annotation is essentially a fix-equivalent specification.
  \item \textbf{Expressible-Weak (L5, ``Indirect'').} The annotation captures only that some state variable changed---or did not change---in a particular direction (changed(var, true/false) or var(Entry relOp Exit)). The buggy version produces Violated because the change does not occur in the expected way, but the annotation does not encode the correct value, only its presence or polarity. We call this an awareness signal: it is enough to alert the developer that something is wrong, even though it does not tell them what the correct value is.
\end{itemize}

\smallskip
\noindent\textbf{Results.}
The three-tier classification of the 34 L4--L5 cases is summarized in Table~\ref{tab:rq2-tiers}.
Inexpressible cases account for 20 of 34 (59\%); Strong and Weak each account for 7 (21\% each).
Within the L5 group alone, all 14 cases are expressible---14 of 14, evenly split between Strong (7) and Weak (7)---which means the intent model can encode some awareness signal for every case where bug awareness is the only obstacle.
The Inexpressible tier maps exactly to the L4 sub-categories (L4a 10, L4b 8, L4c 1, L4d 1), confirming that L4 represents a hard expressibility ceiling rather than a question of developer awareness.

\smallskip
\noindent\textbf{Representative examples.}
We illustrate one case from each tier to show the qualitative difference in signal.

\noindent Inexpressible (L4a) --- web3bugs\_51\_H\_04 (SwapUtils.getYC). The bug is that when a swap crosses a target price, the StableSwap formula switches its amplifier coefficient mid-trade; the correct behavior is to split the swap at the crossing point and apply each amplifier to its sub-swap. Constructing this requires computing a split point $dx_1$ that does not appear anywhere in the program and that is not expressible as a closed-form arithmetic combination of in-scope variables (it is the solution to a Newton-method equation). No intentValue expression can capture the correct getY return, so the annotation grammar's intentValue == arithExpr form is unusable here.

\noindent Expressible-Strong (L5b) --- web3bugs\_113\_H\_05 (NFTPairWithOracle.\_lend). The buggy line is require(params.ltvBPS >= accepted.ltvBPS, ...); the correct comparison is <= (a lender wants the borrower's LTV to be at most their accepted ceiling). Under bug awareness, the annotation is direct:
\begin{verbatim}
// @During params.ltvBPS <= accepted.ltvBPS
\end{verbatim}
The buggy code admits inputs with params.ltvBPS > accepted.ltvBPS, which violate the annotation cleanly. The annotation is essentially the corrective require.

\noindent Expressible-Weak (L5a) --- web3bugs\_192\_H\_01 (Lock.extendLock). The function performs transferFrom for an additional \_amount but forgets to update the internal accounting variable totalLocked[\_asset]. Under bug awareness, the developer can write
\begin{verbatim}
// @Post totalLocked[_asset](Entry < Exit)
\end{verbatim}
which fires Violated on the buggy version (the variable does not change, so Entry == Exit) and is satisfied on a corrected version that adds totalLocked[\_asset] += \_amount. The annotation tells the developer that the variable was supposed to grow, but it does not tell them by how much---the precise increment \_amount is not present in the annotation. This is an awareness signal, not a fix-equivalent specification, and our grammar does not currently support intentValue expressions over the Entry value, which would be needed to encode the increment exactly.

\smallskip
\noindent\textbf{Implications.}
Two findings stand out.
First, the distinction between L4 and L5 is meaningful: L4's 20 cases are a hard ceiling that no amount of developer awareness can lift, whereas L5's 14 cases are a soft ceiling that the intent model already covers, contingent on whether the developer is aware.
Second, within L5, the 50/50 split between Strong and Weak suggests that for half of the awareness-conditional cases, the developer's annotation would express the actual fix, and for the other half it would express a coarser ``something must change here'' signal that nevertheless suffices to surface the bug.
Future grammar extensions that would enlarge the Strong tier and shrink Inexpressible---specifically, supporting (a) arithmetic expressions over Entry values in PostEntryExit, which would directly absorb several Weak cases by letting the developer write the exact increment, and (b) a returnExpression clause for view functions, which would absorb several L4b cases by giving view-only functions a meaningful annotation target---are concrete directions identified by this analysis and discussed in §\ref{sec:disc:tech}.

\subsection{RQ3: Comparison with Existing Detection Tools}\label{sec:rq3}

We compare IntentChecker against three state-of-the-art tools on the 20 mitigated cases from RQ1:
\textbf{ScType}~(ICSE~'24), a static type-checker that assigns financial types (token unit, scaling factor) to variables and detects type inconsistencies;
\textbf{GPTScan}~(ICSE~'24), an LLM-based multi-step pipeline that matches functions against ten DeFi-specific vulnerability rules (price manipulation, slippage, etc.); and
\textbf{NumScout}, a symbolic-execution engine that searches for five predefined numeric defect patterns (division-in-path, operator order, precision loss, exchange problem, profit opportunity).
Each tool was executed three times on the same machine; ScType and NumScout produce deterministic output, while GPTScan's LLM-based pipeline may vary across runs.

\smallskip
\noindent\textbf{NumScout execution adjustments.}
To run NumScout over our Web3Bugs subset we applied two classes of adjustments, both external to the bugs under study.
First, a source-level bug in NumScout's semantic analyzer (feature\_detector/semantic\_analysis.py, in the safeTransfer handler) raised UnboundLocalError on every contract reaching the relevant branch; we applied a minimal one-line fix (renaming an undefined local to the intended stack variable) so the tool could complete analysis.
Second, NumScout consumes EVM bytecode and fails with ``incomplete push instruction'' errors when the bytecode contains unresolved library placeholders (\_\_\$\ldots\$\_\_), which are emitted when a contract calls a public/external library function that would normally be linked at deploy time.
Two of our cases (51\_H\_02, Swap.rampTargetPrice; 77\_H\_01, Exchange.calculateLiquidityTokenQtyForSingleAssetEntry) use external libraries in this way.
For these two cases only, we produced a second copy of the target file in which every public/external library function was rewritten as internal, causing the compiler to inline the library body into the calling contract's bytecode rather than emit a placeholder.
This transformation is semantically equivalent at the operation level---the arithmetic instructions NumScout inspects (MUL, DIV, SUB, etc.), the storage accesses, and the control flow are preserved---so the defect patterns NumScout targets are unchanged; only the call-site mechanism (DELEGATECALL vs.\ inlined code) differs.
The modified files are kept separate from the originals used in the ScType and GPTScan experiments, and both modifications are restricted to the two cases noted above.

\smallskip
\noindent\textbf{Detection model.}
A key distinction among these tools is how the set of detectable bugs is defined.
GPTScan and NumScout operate on a pattern-driven model: each tool ships with a fixed catalog of vulnerability patterns (10 rules and 5 patterns, respectively), and only bugs matching those patterns can be detected.
When a new class of numeric error emerges, the catalog must be updated by the tool developers.
ScType is type-driven: it checks whether arithmetic operations preserve financial type consistency, which is more general than a fixed pattern catalog but still limited to errors expressible as type mismatches.
IntentChecker is specification-driven: developers write @During/@Post conditions describing intended behavior, and the tool verifies the implementation against those conditions via abstract interpretation.
This allows IntentChecker to target any numeric property expressible within its annotation grammar---including novel error patterns not yet cataloged by existing tools---but requires developer participation.
The grammar's expressibility ceiling was quantified in RQ2.

\noindent\textbf{Finding 2: complementarity with ScType.}
ScType provides the most direct comparison, as both tools target accounting errors and both require manual annotations (financial types for ScType, during/post conditions for IntentChecker).
Among the seven overlapping cases, ScType mitigated four: calcAsymmetricShare, calcLiquidityUnits (both in Vader Protocol's Utils.sol), transferFrom (WrappedIbbtcEth), and settleAccount (OptimisticLedger).
IntentChecker mitigated all seven.
The three cases that ScType could not mitigate (CDP.update, syncVaderPrice, \_calcPrincipalWithdrawable) are not type-inconsistency errors but rather value-level errors: the arithmetic uses correctly-typed operands but produces a numerically wrong result.
ScType's type-driven model cannot express the property ``this subtraction should yield the correct fee amount''; IntentChecker's specification-driven model can.
Conversely, ScType's type inference operates without requiring the developer to know the expected output value, which makes it applicable even when the developer does not have a specific numeric property in mind.
The two approaches are thus complementary: ScType catches type-level mismatches automatically, while IntentChecker catches value-level deviations when the developer can articulate the intended behavior.

The sub-10-second latency of IntentChecker makes it suitable for integration into CI/CD pipelines or interactive editor feedback loops, where developers expect near-instant responses.

\noindent\textbf{Summary.}
Each tool occupies a distinct position in the detection landscape:
pattern-driven tools (GPTScan, NumScout) offer fully automatic analysis but can only mitigate bugs within their predefined vulnerability catalogs;
type-driven analysis (ScType) generalizes beyond fixed patterns but is limited to errors expressible as type mismatches;
and specification-driven analysis (IntentChecker) can mitigate any property within its annotation grammar but requires developer participation.
The 20-case evaluation demonstrates that numeric logic errors---a class responsible for some of the highest-impact DeFi exploits---fall entirely outside the scope of pattern-driven tools and partially outside the reach of type-driven analysis, confirming the practical need for a specification-driven complement.

\subsection{Threats to Validity}\label{sec:threats}

\noindent\textbf{Internal validity.}
The intent and debug annotations used in RQ1 were authored by the researchers based on the audit report descriptions, not by the original contract developers.
A different annotator could plausibly write a slightly different annotation for the same bug, and a sufficiently weak annotation could fail to surface a bug that a stronger annotation would catch.
We mitigate this by deriving each annotation directly from the audit report's stated root cause and recording the exact annotation alongside each case in the supplementary material, allowing independent re-evaluation.

\smallskip
\noindent\textbf{External validity.}
Our 89-case benchmark is drawn from Web3Bugs (Code4rena audit findings) and NumScout (BNB Smart Chain), which together cover a substantial portion of publicly known numeric logic errors but are not exhaustive.
Findings may not generalize to numeric logic errors that arise in domains underrepresented by these two sources, such as zero-knowledge circuits or non-DeFi applications.

\smallskip
\noindent\textbf{Construct validity.}
RQ1's notion of ``mitigation'' relies on the validation engine producing a non-Satisfied verdict (typically Violated) for the annotated bug, rather than on a downstream measurement of developer behavior.
A non-Satisfied verdict on its own does not guarantee that a developer reading it would correctly diagnose and fix the bug; assessing that downstream effect is an important direction for future work.
In RQ3, GPTScan is marked as out of scope (N/A) rather than ``not mitigated'' because its rule set does not target numeric logic errors; this reflects a scope boundary, not a quality deficiency.
The ScType comparison is limited to seven overlapping cases for which type annotation files exist; results on the remaining thirteen cases may differ.
Two NumScout cases (51\_H\_02, 77\_H\_01) were evaluated on a variant of the target file in which public/external library functions were rewritten as internal to bypass NumScout's inability to handle unresolved library placeholders in compiled bytecode (§\ref{sec:rq3}).
Because this transformation only alters the call-site mechanism (inlined library code vs.\ DELEGATECALL) and preserves the arithmetic instructions, storage accesses, and control flow that NumScout's defect patterns inspect, we regard the comparison as fair for the specific pattern-level signal NumScout produces; we nevertheless note the modification explicitly so that readers interpreting Table~\ref{tab:rq3-mitigation} can account for it.

\section{Discussion}\label{sec:discussion}

\subsection{Annotation Authoring Burden and Future Automation}\label{sec:disc:burden}

IntentChecker's mitigation results in §\ref{sec:rq1} are conditional on the developer supplying intent and debug annotations.
This is by design---the entire approach is predicated on the developer making their intent explicit---but it nevertheless constitutes the tool's most significant practical limitation.
Two distinct kinds of effort are involved.

\smallskip
\noindent\textbf{Effort 1: writing intent annotations for unfamiliar code.}
The intent model assumes that the developer can articulate, in the grammar of @During/@Post clauses, what the function is supposed to do.
For code the developer wrote themselves a few minutes ago, this is unproblematic: the intent is still in the developer's head.
For code the developer is reviewing, modifying, or debugging without prior context, the intent must first be reconstructed from the surrounding code, comments, and external specifications, and only then can it be encoded as an annotation.
This reconstruction step is not free, and it is exactly the step that the L5 (bug-awareness-required) limitation in §\ref{sec:rq1} measures: when the correct intent is non-obvious, an annotation that captures it cannot be written without already knowing the bug.

\smallskip
\noindent\textbf{Effort 2: supplying debug annotations for realistic execution paths.}
Even for code whose intent is clear, IntentChecker can only analyze the path that the developer's debug annotations actually exercise.
@StateVar, @LocalVar, and @IReturn require the developer to choose representative ranges; choosing ranges that miss the buggy region produces a false negative, while choosing ranges that are too wide invites widening and produces uninformative Warning verdicts.
This is the standard cost of any annotation-based analysis and is well understood, but it remains a non-trivial barrier to adoption.

\smallskip
\noindent\textbf{The circularity objection.}
A natural question is whether writing a correct intent annotation already presupposes knowing the bug---in which case the tool would only confirm what the developer already knows.
The concern is legitimate, and our RQ2 analysis quantifies it precisely: 14 of the 34 intent-model limitation cases (L5) require bug awareness before the annotation can be written, confirming that for those cases, independent discovery through annotation alone is not realistic.
However, this circularity is not unique to IntentChecker; it is inherent in any specification-based approach, from formal pre/post-conditions to Scribble annotations to test oracles.
What differs across tools is how much of the specification burden falls on the developer.
For the 20 mitigated cases in RQ1, the annotations were derivable from the developer's own stated intent (e.g., ``this fee should equal $x$'', ``this balance should decrease after withdrawal'') without requiring knowledge of the specific bug.
The L5 cases, by contrast, identify the boundary where intent-driven annotation reaches its limit and external assistance---such as automated annotation suggestion---becomes necessary.
This observation directly motivates the LLM-assisted workflow described below: rather than expecting the developer to write all annotations from scratch, a suggestion layer can propose candidate annotations that the developer accepts, rejects, or refines, shifting the task from generation to validation and partially breaking the circularity.

\smallskip
\noindent\textbf{Future direction: LLM-assisted annotation suggestion and auto-repair.}
A natural way to lower both barriers is to combine IntentChecker with a large language model that observes the same source the developer is editing.
For intent annotations, the LLM could generate candidate @During/@Post clauses by reading the surrounding function, the contract's NatSpec comments, and the developer's recent commit messages, presenting the candidates as suggestions that the developer accepts or edits.
For debug annotations, the LLM could propose representative ranges based on the function's call sites elsewhere in the codebase or based on standard token decimals (e.g., 18 for most ERC20 tokens, 6 for USDC).
Beyond annotation suggestion, an LLM that has access to IntentChecker's Violated verdict and violated region could also propose code edits that move the violated region out of the reachable interval, effectively turning the awareness signal into a candidate fix.
We deliberately leave both directions as future work; what matters for this paper is that they are natural extensions enabled by, rather than blocked by, the current design.

\smallskip
\noindent\textbf{Developer study.}
This paper evaluates IntentChecker through structural analysis---what the tool can and cannot detect (RQ1), what the intent model can and cannot express (RQ2), and how the tool compares with existing detectors (RQ3)---rather than through a developer study measuring perceived usability or annotation intuitiveness.
A controlled study with Solidity-experienced participants would answer a complementary set of questions: whether developers find the annotation syntax natural, how long annotation authoring takes in practice, and whether the tool's feedback leads to faster bug discovery compared to existing debugging workflows.
Designing such a study requires careful attention to participant recruitment (sufficient Solidity expertise) and ecological validity (realistic development tasks rather than isolated code snippets), and we defer it to future work as an independent evaluation axis that builds on the structural foundation established here.

\subsection{Remaining Technical Limitations}\label{sec:disc:tech}

In addition to the annotation authoring burden discussed above, three classes of technical limitations remain in the current implementation.

\smallskip
\noindent\textbf{Multi-transaction invariants.}
IntentChecker's analysis scope is multi-contract but single-transaction.
A whole class of important numeric properties cannot be expressed within a single transaction because they relate quantities established by different transactions in the contract's lifetime.
The canonical example is the ERC20 conservation invariant totalSupply == sum(balances): any single function execution may temporarily increment one side and not the other, but across the entire transaction history the two must agree.
Another example is the price oracle manipulation pattern, where the buggy behavior only manifests when one transaction sets up state that a later transaction reads.
Validating such properties would require tracking state across transactions and aggregating across all balance entries, both of which lie outside the current single-transaction interval-domain analysis.
This is a known boundary of the development-time intent validation approach we have taken, and is more naturally addressed by post-hoc tools or formal verification frameworks that analyze entire contract lifecycles.

\smallskip
\noindent\textbf{Non-arithmetic Yul and other unsupported Solidity constructs.}
The arithmetic-focused Yul subset described in §\ref{sec:prelim:extension}(d) covers the cases where inline assembly is used as a faster substitute for high-precision integer arithmetic, which is by far the most common use case in DeFi libraries.
However, hand-written Yul that uses memory and storage opcodes (mload/mstore, sload/sstore), control flow (if, for, switch), or function definitions falls outside the supported subset and is conservatively treated as $\top$.
The same conservative treatment applies to a small number of Solidity constructs that the abstract interpreter does not model: abi.decode from raw bytes, keccak256, address(this).balance (whose value depends on the EVM-level execution context rather than on tracked state), and other built-ins whose results depend on opaque cryptographic or VM-level operations.
Bugs whose buggy/correct distinction depends on the precise value produced by such constructs are correspondingly out of IntentChecker's reach (these account for the L3 cases in Figure~\ref{fig:rq1-limitations}).
Extending the Yul visitor to handle memory and storage opcodes and the abstract interpreter to handle a wider set of opaque builtins is a meaningful but bounded engineering task.

\smallskip
\noindent\textbf{Soundness bounded by debug annotation scope.}
IntentChecker's analysis is sound within the ranges declared by debug annotations: when the validation engine reports Satisfied, the declared intent provably holds for every combination of values in those ranges---this follows from the set-theoretic definition of the comparison primitive (§\ref{sec:intent-semantics}) and the soundness results of §\ref{sec:alg-verification} applied pointwise to each clause.
The guarantee does not extend outside those ranges.
A bug that only manifests at the boundary of a parameter's representable values, but not in the range the developer chose for @LocalVar, will not appear in any verdict.
This is an inherent characteristic of debugging tools---traditional debuggers also only execute the inputs the developer provides---and we encourage developers to use representative ranges and to iteratively refine them when Warning results draw attention to specific sub-intervals.

\smallskip
\noindent\textbf{Value-level intent vs.\ logic-level intent.}
A broader observation from the limitation taxonomy is that IntentChecker's intent model operates at the value level: it can express whether a variable's value satisfies a numeric relationship (``this fee should be at least $x$'', ``this balance should decrease''), but it cannot express whether the right computation was performed in the first place.
The 20 mitigated cases in RQ1 are precisely the cases where a value-level assertion suffices to distinguish buggy from correct execution.
The L4 cases reveal the boundary: in L4a (10 cases), the correct expected value requires a computation that does not exist in the program; in L4b (8 cases), the function modifies no state variable, so there is no value to assert on.
These are not failures of precision but of abstraction level---the developer's true intent is about what the code should do (``split the swap at the crossing point'', ``update totalLocked''), not about what value a variable should hold.
Capturing such logic-level intent would require a fundamentally different formalism, such as temporal properties over execution traces or structural specifications of required code patterns, and lies outside the scope of a value-based interval-domain tool.
Recognizing this boundary is important: IntentChecker is effective when the bug manifests as a wrong value, and complementary tools are needed when the bug manifests as a missing or misplaced operation.

\subsection{Practical Annotation Guidelines}\label{sec:disc:guidelines}

The annotation grammar (§\ref{sec:design}) defines what can be written; the question that remains is when a developer should write which annotation.
The 20 mitigated cases and 14 L5 expressible cases reveal a recurring pattern: the most impactful annotations are not the ones that verify what the developer did write, but the ones that catch what the developer forgot to write.
We distill three non-obvious guidelines from this observation.

\smallskip
\noindent\textbf{Guideline 1: Enumerate all state variables a function should affect, not just those it does affect.}
Developers naturally reason about the code they wrote---the variables they explicitly assigned, the calls they explicitly made.
Bugs of omission (L5a, 7 cases) arise precisely from this cognitive bias: a state variable that should have been updated was simply never mentioned.
After writing a function, the developer should list every state variable whose value the function is expected to change and add at least a directional annotation (@Post var(Entry\,<\,Exit) or @Post changed(var, true)) for each.
In our data, this single practice---checking what should change rather than what does change---would have caught 7 of the 14 L5 expressible cases and 5 of the 8 mitigated @Post cases, all without requiring any knowledge of the specific bug.

\smallskip
\noindent\textbf{Guideline 2: When two state variables should move together, annotate their relationship, not each one in isolation.}
Several benchmark cases involve accounting pairs (e.g., a per-user balance and a global total, a deposit ledger and a reward tracker) that should stay in sync.
Annotating each variable independently catches only missing-update bugs; annotating their relationship (e.g., @Post globalTotal(Entry\,-\,Exit) >= userBalance(Entry\,-\,Exit)) catches bugs where both variables are updated but by inconsistent amounts.
This pattern recurs in 4 of the 20 mitigated cases (all Erroneous Accounting) and is the dominant form in L4d (invariant-masked), where independent annotations on each variable succeed but the cross-variable invariant fails.

\smallskip
\noindent\textbf{Guideline 3: For multi-step arithmetic, annotate the result against the mathematically ideal expression, not the code as written.}
Solidity's integer division truncates at every intermediate step, and the resulting precision loss depends on the order of operations.
Code that reads amount.div(12).mul(5) may look correct, but the developer's actual intent is the mathematical value $\lfloor\text{amount} \times 5 / 12\rfloor$.
Writing the intent annotation in the ideal form---@During result >= amount * 5 / 12---causes IntentChecker to compare the truncated code path against the non-truncated reference, surfacing the discrepancy automatically.
This pattern accounts for 7 of the 20 mitigated cases (Div In Path, Operator Order Issue, Exchange Problem, and Precision Loss Trend), all of which were caught by annotations that express the mathematically correct expression rather than restating what the code already does.

\section{Related Works}\label{sec:related}
\subsection{Numeric Logic Error Detection in Solidity}
Logic error detection focuses on identifying discrepancies between developer intentions and actual program behavior in smart contracts.

\citep{highguard} addresses business logic violations in smart contracts by using Dynamic Condition Response (DCR) graphs
to model expected behaviors including temporal constraints, role-based access control, and inter-function dependencies.
The system monitors runtime transactions against user-provided DCR models and their function mappings,
generating violation reports when execution activities deviate from the specified business logic patterns.

\citep{smartpulse} verifies temporal properties of smart contracts by accepting user-specified Linear Temporal Logic (LTL) formulas
and attack models to check both safety and liveness properties.
The system not only detects violations but also generates concrete attack scenarios that demonstrate how the temporal properties can be violated,
providing developers with actionable insights into potential logic errors.

\citep{consolidating} enables developers to specify function and address behaviors using the ConSol syntax alongside their Solidity code,
then verifies whether the implementation adheres to these behavioral specifications and generates behavior-compliant Solidity programs without annotations.

\citep{smartinv} leverages multimodal learning to automatically infer invariants and detect machine unauditable bugs (MUBs)~\citep{exploitablebugs}
by analyzing both source code and natural language artifacts including comments, function signatures, and documented transaction scenarios.
The system employs a fine-tuned model with Tier of Thought (ToT) prompting that progressively predicts transaction contexts,
generates and ranks invariants, and ultimately identifies vulnerabilities through three-tier reasoning.

\citep{accountingerrors} proposes a novel type system for Solidity variables defined as tuples of $\langle$Financial Type, Scaling Factor, Token Unit, Address$\rangle$
to detect accounting errors through type checking.
The system reinterprets Solidity code based on detection patterns such as incorrectly adding balances with fees,
enabling systematic identification of numeric logic errors that arise from mismatched financial operations.

Furthermore, there are also approaches that address multiple transaction logic errors such as price manipulation~\citep{defiranger,defiguard,pomabuster,secplf,defitainter}
and flash loan attacks~\citep{defitail,midnight}.

The numeric logic error detectors above and IntentChecker occupy distinct points along the development--auditing timeline rather than competing on the same axis.
NumScout, GPTScan, SmartInv, and the type-system approach of \citet{accountingerrors} are all designed to run over completed code and recover developer intent indirectly through pattern catalogs, language-model inference, or financial type assignments.
IntentChecker is positioned earlier in time and lets the developer declare intent explicitly through annotations evaluated inside the editor.
Because the two approaches see different inputs (code only vs.\ code with declared intent) and run in different workflow stages (post-hoc audit vs.\ edit-time validation), their coverage is necessarily complementary, and §\ref{sec:rq3} characterizes that complementarity rather than arguing numerical superiority.

\subsection{Specification-based Smart Contract Verification}
Specification-based verification approaches focus on verifying general properties and correctness requirements of smart contracts rather than specific developer intentions.

\citep{scribble} provides a framework that transforms developer annotations into Solidity assertion code,
enabling testing with existing tools like MythX~\citep{mythx} and Mythril~\citep{mythril}.
The framework supports multiple annotation types including if\_succeed (conditions for successful function returns),
invariant (contract-level properties that must always hold), if\_updated (conditions checked when state variables change),
and assert (validations at specific execution points), making formal specifications accessible through familiar testing pipelines.

\citep{smartace} builds upon Scribble~\citep{scribble} to verify whether Solidity code satisfies specifications written in the Scribble language,
leveraging C-based verification tools like SeaHorn~\citep{seahorn}, libFuzzer~\citep{libfuzzer}, and KLEE~\citep{klee} by transforming smart contracts into LLVM-IR based harnesses.
The framework abstracts the $2^{160}$ possible user addresses into a small set of representative users (implicit, transient, and explicit),
enabling verification of properties that must hold for arbitrary numbers of users, such as accounting properties like
"the contract balance equals the sum of all user deposits."

\citep{idealist} verifies Solidity code using two types of annotations: specification annotations (loop invariants, call invariants, and call modifies) that developers declare as assumptions,
and verification annotations (ensures, reverts\_if, and contract invariants) that the tool checks against the implementation.
The system assumes the truth of specification annotations and uses them to verify whether the code satisfies function post-conditions,
correctly handles revert conditions, and maintains contract invariants throughout execution.

\citep{solvent} focuses on verifying liquidity properties of smart contracts through formal methods
by converting both the contract code and user-defined liquidity properties into SMT constraints.
The system then checks whether the contract satisfies these properties using SMT solvers,
generating counterexamples when violations are detected to help developers understand potential liquidity issues.


While specification-based approaches formalise contract-level properties in dedicated specification languages---Scribble's annotation language, Idealist's loop and call invariants, Solvent's SMT-encoded liquidity properties---and discharge verification obligations over completed code, IntentChecker's intent model occupies a different point in the design space with three distinguishing characteristics.
First, its annotation language targets value-level numeric intent on individual variables at specific program points, not contract-level invariants or temporal properties.
Second, its denotational semantics (§\ref{sec:intent-semantics}) maps each clause form to a tri-valued validation outcome over the abstract states produced by interval-domain analysis, giving the annotation language a formal foundation comparable in rigor to the specification languages above while remaining cheap enough to evaluate at edit time.
Third, because IntentChecker performs interval-domain analysis that tracks actual value ranges through library function calls (e.g., SafeMath operations) rather than treating libraries as black boxes, it can validate intent over step-by-step numeric computations rather than only over post-condition-style abstract properties.
The two approaches are therefore complementary in workflow stage (edit-time vs.\ audit/verification-time), in granularity (value-level vs.\ contract-level), and in the specification style they support.

\subsection{Tools for Strengthening Security During Development Phase}
Development-phase security tools integrate vulnerability detection directly into the coding workflow, enabling developers to identify and address security issues as they write code rather than in post-development analysis.
\citep{making} presents an integrated development environment for smart contract development that combines natural language model-based code autocompletion with security validation.
The platform integrates existing static analysis tools including Oyente~\citep{oyente}, Mythril~\citep{mythril}, and Securify~\citep{securify} to provide comprehensive security reports during development workflow.

\citep{solhint} provides a Solidity linter that detects predefined vulnerability patterns including low-level calls, reentrancy, and deprecated function usage during development.
The tool enforces security best practices by checking for patterns such as proper visibility declarations, send result validation, and secure compiler version usage.

While these development-phase tools rely on predefined detection patterns for known vulnerabilities,
IntentChecker enables developers to specify their intended numeric behaviors through annotations and validates whether the actual program execution matches these specified intentions.
IntentChecker also extends SolQDebug's analysis scope beyond a single contract to a multi-contract single-transaction scope that includes inheritance, libraries, interfaces, and an arithmetic Yul subset, which is what makes intent validation feasible on realistic DeFi code.

\section{Conclusion}\label{sec:conclusion}

We presented IntentChecker, a development-time intent validation tool that extends SolQDebug with (i) an intent model---two annotation types (@During/@Post) equipped with a formal denotational semantics that maps each clause to a tri-valued outcome against abstract states, (ii) a validation engine whose interval comparison primitive is proved sound against that semantics and cross-validated against brute-force ground truth, producing graded Satisfied/Warning/Violated signals with separately computed risk scores and violated regions, and (iii) a scope extension to multi-contract single-transaction analysis covering inheritance, libraries, interfaces, and an arithmetic Yul subset.

On 75 effective benchmark instances (89 collected, 14 excluded) from Web3Bugs and NumScout, IntentChecker surfaced 20 bugs via Violated verdicts at edit-time speeds (mean 3.69\,s per case).
RQ2's expressibility analysis showed that 14 of the 34 intent-model limitation cases are expressible under bug awareness, while 20 represent a hard grammar ceiling---identifying concrete extension points for the intent model.
IntentChecker's positioning relative to existing detection tools is complementary: it fills the edit-time gap that auditing-time tools structurally cannot occupy.

The primary practical limitation is the annotation authoring burden, which future work can address through LLM-assisted annotation suggestion (lowering the L5 bug-awareness ceiling) and auto-repair from violated regions.
On the analyzer side, extending Yul support and multi-transaction reasoning would close the remaining technical limitations.
More broadly, this work adds ``edit-time intent validator'' as a third category alongside pattern-based detectors and formal verifiers in the design space for numeric logic error tools.
