## New feature: snapshot-qualified references, `varRef(Entry/Exit/Before/After/Assign)`

**Motivation**: three independently-analyzed cases (`web3bugs_83_H_01`, `web3bugs_42_H_01`, `web3bugs_35_H_11`) each hit the same wall in R1-3: the true reported intent was of the form `new_value == f(old_value, some_independent_third_quantity)`, and the grammar's only cross-state constructs — `(before relOp after)` ($D_{\text{ba}}$), `(assign relOp current)` ($D_{\text{ac}}$) under `@During`, and `(entry relOp exit)` ($P_{\text{ee}}$) under `@Post` — all compare the *same* single expression at two timepoints, with no way to inject a third, independently-scoped term. R1-3 had to fall back to a weaker relation each time (e.g. `debts >= details[_id].debt` instead of the exact `debts == old_debts + increasingDebt`), recorded as `Intent coverage: Partial` after the field was added (see the `web3bugs_83_H_01` RQ2-A-correction entries below in this doc's history / `phase_reviews/README.md` §3/§4/§10).

**Decision**: rather than keep documenting this as a permanent grammar limitation, extend the grammar. User's call, made explicitly aware of the cost (new grammar production, new formal semantics, new engine implementation, re-litigating cases already analyzed under the old grammar) and choosing to do it now, early in the 35-case pass, rather than after all 35 are done.

**Design**: one new `arithFactor` alternative, `varRef '(' snap ')'` where `snap ∈ {Entry, Exit, Before, After, Assign}` — a variable reference tagged to evaluate against a specific state snapshot ($\sigma_{\text{entry}}$/$\sigma_{\text{exit}}$/$\sigma_{\text{before}}$/$\sigma_{\text{pt}}$/$\sigma_{\text{assign}}$, per `main.tex`'s existing $\Gamma$ table) instead of the ambient reference point. Crucially, this is a single new *term*, usable anywhere inside an arithmetic expression (nested under `+`, `-`, `*`, ...), not a new clause-level rule — which is what makes `debts == debts(Entry) + increasingDebt` and `feeGrowthOutside1 == feeGrowthGlobal - feeGrowthOutside1(Before)` expressible as ordinary `(C_cmp)` comparisons. The old $D_{\text{ba}}$/$D_{\text{ac}}$/$P_{\text{ee}}$ clause forms are now strictly subsumed by this (e.g. `x(Before) < x(After)` says the same thing `x(Before < After)` used to) and were **removed from the grammar entirely**, not kept alongside the new form — a deliberate choice (user: "다 고쳐서 하자", "논문에 syntax semantics 적을 때도 더 깔끔할 것 같아") over keeping both for backward compatibility, since keeping both would have meant explaining two ways to say the same thing in the paper.

**Grammar restriction (`Entry`/`Exit` → `@Post`-only, `Before`/`After`/`Assign` → `@During`-only)**: NOT enforced by making `arithFactor` itself take a rule parameter — ANTLR4 doesn't allow parameters on left-recursive rules (`arithExpr`/`arithAdd`/`arithTerm` are all left-recursive; `error(169): rule ... is left recursive but doesn't conform to a pattern ANTLR can handle` when first attempted). Fixed by using a **parser member variable** instead (`@parser::members { inDuring = False }` at the top of `Parser/Solidity.g4`), set by an action at the top of `duringIntent`/`postIntent` (`{self.inDuring = True/False;}`), and read by semantic predicates on `arithFactor`'s new alternatives (`{not self.inDuring}? varRef '(' ENTRY ')'`, etc.) — this avoids parameterizing the left-recursive rules at all. `Entry` was originally going to be legal in *both* kinds (since $\sigma_{\text{entry}}$ is genuinely in `@During`'s $\Gamma$ too, needed internally by `changed()`) but was deliberately restricted to `@Post`-only per the user's design call, keeping `{Entry, Exit}` and `{Before, After, Assign}` as two clean, non-overlapping, self-contained sets rather than an asymmetric one.

**Files changed**:
- `Parser/Solidity.g4` — grammar changes above. User regenerated the ANTLR parser themselves (established pattern this session).
- `Analyzer/EnhancedSolidityVisitor.py` — (a) removed dead/now-crashing references to the deleted `PostEntryExitContext`/`DuringBeforeAfterContext`/`DuringAssignCurrentContext` classes in `_build_post_clause_dict`/`_build_during_clause_dict` (these would otherwise `AttributeError` on *every* `@Post`/`@During` annotation immediately after regeneration, since the classes no longer exist — found and fixed before it could bite); (b) added 5 new visitor methods (`visitVarRefAtEntry`/`Exit`/`Before`/`After`/`Assign`), each wrapping the inner `varRef`'s `Expression` with a context tag (`'VarRefAtEntry'` etc.) for the evaluator to dispatch on.

### `Domain/Interval.py`'s `Interval.copy()` dropping `type_length` (RESOLVED 2026-09-01)

User asked a targeted diagnostic question about `web3bugs_29_H_11`'s Group G crash (`Cannot join intervals of different type lengths` on `_blockTimestampLast`, a `uint32`) — floated type-casting (`uint32(block.timestamp % 2**32)`) or `&&`-evaluation as hypotheses, while noting they seemed unlikely. Both were ruled out by instrumenting `Utils/Helper.py._merge_by_mode` (join failure site) and `Interpreter/Semantics/Refine.py`'s `_update_comparison_condition`/`refine_intervals_for_comparison` (condition-narrowing site) with temporary probes (removed after diagnosis, `git diff` confirmed clean).

**Root cause**: `refine_intervals_for_comparison` opens with `A, B = a_iv.copy(), b_iv.copy()` (`Refine.py:311`). `Interval.copy()` (`Domain/Interval.py:54-55`) was `return type(self)(self.min_value, self.max_value)` — omitting `type_length` entirely. Since `IntegerInterval`/`UnsignedIntegerInterval.__init__` default `type_length=256`, any interval narrower than 256 bits (here, `uint32`) silently got promoted to 256 bits on every `.copy()`. The narrowing arithmetic itself (min `0`→`1` on the `!=` branch) was correct — only the bit-width tracking broke, causing the join against the untouched-branch's still-32-bit value to fail.

**Same bug, independently confirmed for `web3bugs_52_H_04`/`web3bugs_52_H_34`**: their crash had been provisionally attributed to a *different* cause in `engine_run_triage.md` ("likely a different root cause, may need a separate fix" — this was wrong). Direct tracing showed the failing variable is `roundID` (`uint80`, from a Chainlink `AggregatorV3Interface.latestRoundData()` tuple-unpack), corrupted via the identical `.copy()` path during `require(answeredInRound >= roundID, ...)`'s `>=` narrowing. One bug, three cases.

**Fix**: `Interval.copy()` now preserves `type_length` — but not via a third positional constructor argument (`type(self)(min, max, self.type_length)`), because `BoolInterval.__init__` only accepts 2 params and would break. Instead: construct with 2 args, then set `new_obj.type_length = self.type_length` as an attribute afterward — safe for every subclass.

**Verification**: `web3bugs_29_H_11` now runs to completion (exit 0), though with new downstream issues (see the `varRef(Before)` note above and `engine_run_triage.md`'s 단발성 entry). `web3bugs_52_H_04`/`web3bugs_52_H_34` clear their join crash and hit a new, unrelated one (`sumNative` identifier not found during the debug re-interpretation flush, despite being declared earlier in the same function — not yet diagnosed). `.copy()` is called from several files (`Refine.py`, `Evaluation.py`, `Domain/Variable.py`, `Utils/Helper.py`, `Interpreter/Semantics/DebugInitializer.py`), so blast radius was a real concern — checked via the full 20-case baseline (`evaluation/RQ1/run_all.py`, unchanged 17 VIOLATED/3 ERROR) plus a spot-check re-run of all ~20 cases touched earlier this session (every error signature matched exactly what was already documented, no new regressions or unexpected fixes elsewhere).

**Why:** User asked a direct diagnostic question instead of asking for a fix outright, giving room to actually trace the bug before proposing a change; approved applying the fix once the root cause and its shared nature across all three Group G cases were confirmed.
**How to apply:** `engine_run_triage.md`'s Group G entry (moved to §고쳐진 것들) has the same write-up; its 단발성 section has the three cases' new downstream issues. If auditing other `.copy()`-adjacent code for similar bugs, the pattern to watch for is any place that reconstructs a `Variables`/`Interval` object via its constructor using fewer positional args than the original had, relying on defaults.

## 1. `temp/preprocess_contraction.py` — single-line `if` expansion regex bug

**File**: `temp/preprocess_contraction.py`, function `expand_single_line_blocks` (originally used `RE_SINGLE_IF`).

**Bug**: `RE_SINGLE_IF = re.compile(r"^(\s*)(if\s*\(.*\))\s+(.+;)\s*$")` — the `.*` inside the condition group is greedy and matches through to the *last* `)` on the line. When the statement after the `if` condition itself contains parentheses (e.g. `if (cond) result = (a * b) >> 128;`), the regex misidentifies where the condition ends, producing corrupted output like:
```solidity
if (cond) result = (a * b) {
    >> 128;
}
```

## 3. `Domain/Variable.py` — struct member initialization crashed on enum-typed fields

**Symptom**: Analyzing `Perpetuals.Order` (a struct with a field `Side side;`, `Side` being an enum in the same library) crashed 3 of `Perpetuals`' 5 functions (`orderId`, `canMatch`, `getExecutionPrice` — every function taking an `Order`-typed parameter) with:

(Reproduced with a full traceback via a standalone script bypassing `Dependencies/main.py`'s `except Exception: pass`, which was swallowing this into a one-line `[ERR]` log.)

**Root cause**: `StructVariable.initialize_struct`'s inner helper `_make_var` was a **separate, incomplete reimplementation** of the type-dispatch logic that `VariableEnv.top_from_soltype` (`Utils/Helper.py`) already implements generically (array/mapping/struct/interface/enum/elementary). `_make_var` had branches for array/mapping/struct/interface but **no `enum` branch**, so an enum-typed member fell through to the elementary branch, where `et = sol_t.elementaryTypeName` is `None` for an enum type (only `enumTypeName` is set for enums) — `None.startswith(...)` crashes. `top_from_soltype` already had a correct enum branch; `_make_var` was simply never updated when that support was added elsewhere, which is exactly the kind of drift two independent copies of the same dispatch logic invite.

Added `enum_defs` as a new keyword parameter to `initialize_struct` (mirroring the existing `struct_defs` parameter), defaulting to `{}` if not supplied so no call site is required to change.

**Local import note**: `VariableEnv` is imported inside the function body (not at module top), because `Utils/Helper.py` imports several classes from `Domain/Variable.py` — a top-level import would be circular.

**Call sites updated to also pass `enum_defs=`** (mechanical, low-risk additions — previously these all passed `struct_defs=` but never `enum_defs=`, so enum-typed struct members would fall back to the empty-default `EnumVariable` instead of crashing, but without the enum's actual member list):

## 4. Cross-library qualified-enum-type reference (`Library.EnumName`, e.g. `Perpetuals.Side`) — 3 of 4 layers fixed

Surfaced while building `web3bugs_16_H_04`'s contraction: `Balances.Trade.side` is typed `Perpetuals.Side`, and `applyTrade` compares `trade.side == Perpetuals.Side.Long`. Every layer that touches a dot-qualified library-scoped enum reference had the same latent assumption baked in — "a `Library.X` qualified name always resolves to a struct" — because structs were the only qualified-name case exercised before this case.

**Layer 1 — `Analyzer/EnhancedSolidityVisitor.py`, `visitUserDefinedType`'s dot-qualified branch (`elif '.' in type_name:`)**: always treated the resolved symbol as a `StructDefinition`. Fixed by importing `EnumDefinition` (alongside `StructDefinition`) from `Domain/Variable.py` and branching on `isinstance(resolved, EnumDefinition)` vs `isinstance(resolved, StructDefinition)`:
```python
if isinstance(resolved, EnumDefinition):
    type_obj.typeCategory = "enum"
    type_obj.enumTypeName = type_name
    if contract_cfg and type_name not in contract_cfg.enumDefs:
        contract_cfg.enumDefs[type_name] = resolved
elif isinstance(resolved, StructDefinition):
    ... # existing struct logic, unchanged
```

**Layer 2 — `Interpreter/Semantics/Evaluation.py`, `evaluate_member_access_context`'s `isLibrary` dict-handling branch (~line 1014-1022)**: `Library.EnumName` fell through to a generic `f"symbolic({lib_name}.{member})"` string fallback (meant for genuinely-opaque library members), which then broke the subsequent `.Member` access on the enum value. Fixed by checking `lib_cfg.enumDefs` before falling back:
```python
if lib_cfg and member in getattr(lib_cfg, 'enumDefs', {}):
    return lib_cfg.enumDefs[member]
if lib_cfg and member in getattr(lib_cfg, 'globals', {}):
    return lib_cfg.globals[member].value
```
**Note**: this is the same error signature/site (`ValueError: member 'X' is not a recognised global-member.`) as the still-open `web3bugs_51_H_02` regression above (§ Open issue). Strongly suspected shared root cause, but not chased further — both remain in the deferred batch.

**Layer 4 — deferred**: fixing Layer 3 exposed a deeper error in the same condition-refine continuation logic (`'dict' object has no attribute 'identifier'`) when actually narrowing on the qualified-enum comparison. **This is the layer explicitly deferred by the user** ("에러난건 나중에 한꺼번에 고치자"), to be batched together with the `web3bugs_51_H_02` regression later. ## 5. Enum-valued `@LocalVar`/`@StateVar` debug annotations — new feature, implemented and verified

Motivated by `web3bugs_16_H_04`'s need to debug-annotate `trade.side` (an enum-typed struct field) with a value like `Perpetuals.Side.Long`. Previously, debug annotations only supported numeric/boolean/array literal values — no enum support existed end-to-end.

**Grammar**: the user themselves changed `Parser/Solidity.g4`'s `DebugEnumLiteral` production from `identifier ('.' identifier)?` to `identifier ('.' identifier)*` (arbitrary-depth qualified enum literals, e.g. `Long`, `Side.Long`, or `Perpetuals.Side.Long`) and regenerated the ANTLR parser themselves — not done by the assistant.

**`Analyzer/EnhancedSolidityVisitor.py`, `_parse_debug_value`'s `DebugEnumLiteralContext` branch (~line 2892)**: previously only joined the first 1-2 identifier tokens (written for the old `?`-cardinality grammar); fixed to join *all* identifier tokens to match the new `*` grammar:
```python
if isinstance(iv_ctx, SolidityParser.DebugEnumLiteralContext):
    return ".".join(ident.getText() for ident in iv_ctx.identifier())
```

**`Interpreter/Semantics/DebugInitializer.py`, `_patch_var_with_new_value_for_debug`**: had no enum-specific branch at all — a debug value string for an enum target fell through to a generic `isinstance(target_var, VarClass)` path that doesn't know how to set an enum's `valueIndex`. Added a new explicit branch, checked before the generic fallback:
```python
if isinstance(target_var, EnumVariable) and isinstance(new_value, str):
    member_name = new_value.rsplit(".", 1)[-1]
    if member_name not in target_var.members:
        raise ValueError(f"Debug annotation value '{new_value}' for enum '{target_var.typeInfo.enumTypeName}': "
            f"member '{member_name}' not found (known members: {list(target_var.members.keys())}). ...")
    target_var.valueIndex = target_var.members[member_name]
    target_var.value = member_name
    return
```
Accepts any qualification depth (`Long`, `Side.Long`, `Perpetuals.Side.Long`) by taking only the last dot-segment as the member name, so it works regardless of how fully-qualified the user's annotation happens to be.

**Verification**: (a) unit test directly against `_patch_var_with_new_value_for_debug` — `Long`, `Side.Long`, `Perpetuals.Side.Long` all correctly produced `valueIndex=0, value='Long'`; `Short` produced `valueIndex=1`; an invalid member name raised the clear `ValueError` above. (b) full-pipeline test through the real grammar/visitor/`ContractAnalyzer`, using a throwaway scratchpad `.sol` file (`debug_enum_test.sol`, **not** the real `web3bugs_16_H_04` contraction — contraction files stay annotation-free per convention, debug annotations belong only in the case JSON) with `// @LocalVar trade.side = Long` and friends inside a `// @Debugging BEGIN/END` block matching `applyTrade`'s real signature — confirmed working end-to-end through the actual parser, not just the isolated unit.

## 6. Confirmed architectural finding: loop-body `@During` is never evaluated by the engine

Not a bug fix — a confirmed fact about existing engine behavior, established by direct source inspection while investigating an external critique of `web3bugs_71_H_11`'s classification (see `phase_reviews/README.md` §4/R1-7's new exception paragraph and `phase_reviews/02_web3bugs_71_H_11/analysis.md` for the case-level consequences).

**Finding**: `Interpreter/Engine.py`'s `fixpoint()` (line 409) computes a loop's fixpoint using `transfer_function` (lines 267-277) internally — `transfer_function` never calls `_process_node_intents`. Separately, `reinterpret_from()` (line 1006) treats loop-head nodes specially: it calls `self.fixpoint(n)` and then `continue`s directly to the loop-exit's successors, entirely skipping the `_process_during_annotations` call (line 1108) that normal (non-loop) nodes go through. The net effect: a `@During` annotation textually placed on a statement inside a loop body is **never evaluated by the engine, in any iteration** — not evaluated once per iteration, not evaluated imprecisely via join — simply never invoked. This is an architectural/control-flow fact, verifiable from the source without running any case, independent of any question about join-over-iterations precision or ⊤-widening (a separate, genuinely engine-precision concern that remains correctly out of scope for R1-7's Expressibility decision).

**Consequence for the methodology**: led to the new `delta` tag (README §4/R1-7) — a case where a relation's content and referenced values are otherwise fine, but the only viable attachment point is a location this specific engine's architecture never evaluates. Two confirmed instances so far: `web3bugs_71_H_11` (this is the case's primary/first blocker) and `web3bugs_34_H_01` (checked as a secondary alternative, found to be equally blocked, but not the case's primary blocker — that case is independently blocked by `beta` first).

## Case-JSON authoring: the correct record order is code → intent → debug, not visual/final-file order — found and fixed across every case JSON built this session

**Not an engine bug** — a methodology/tooling-usage mistake in how this session built every case JSON up to this point, found by user-directed tracing of `Analyzer/SolidityAnalyzer.py`'s `update_code`/`_insert_lines`/`_is_during_inline` after the user noticed `web3bugs_3_H_05.json`'s structure looked wrong. Documented here because it will recur for every future case build unless followed deliberately — it is *not* what running `soltotestjson.py` naively on a single, already-fully-annotated `.sol` file produces.

**The mechanism** (`main.py`'s `simulate_inputs()`): every JSON record is replayed sequentially into a live line buffer via `sa.update_code(s, e, code, ev)`. `// @Debugging BEGIN` calls `batch_mgr.reset()`; `// @Debugging END` calls `batch_mgr.flush()`, which re-interprets the debug scenario against **whatever CFG and intent annotation are already registered at that point in the replay**. So the record order must be: (1) the full real code of the containing file, in full — not just the target function — so the target function's CFG is completely built; then (2) the `@During`/`@Post` intent annotation, inline in that code at its natural position; then (3) the debug block, **last**. Every case JSON built earlier this session (`web3bugs_83_H_01`, `web3bugs_3_H_05`, `web3bugs_35_H_11`) had the debug block placed immediately after the target function's (empty, header-only) skeleton record — i.e. *before* the real body and the intent annotation were ever added — which means `batch_mgr.flush()` was firing against an incomplete/un-annotated function every time. This is exactly what a naive single-pass `soltotestjson.py` run over an already-fully-written `.sol` file (debug block physically at the top of the function, for human readability) produces: top-to-bottom slicing puts the debug block first in array order, matching its visual position — which is the wrong array order even though it's the *right* visual/final position.

**Why the wrong-order files still "looked right" when read as a `.sol` file**: because the debug block's own `startLine` values, in a correctly-built file, are deliberately numbered as if the block were inserted right after the function's opening line — using the header record's own `endLine` as the starting line number for the whole block — and then the whole block is *appended at the end of the array*. Replaying "code, then intent, then debug-with-small-line-numbers-appended-last" reproduces the debug block sitting visually at the top once all inserts are applied (each debug-line insert pushes the already-registered code+intent further down the buffer), *without* the array order needing to match final visual order at all. Confirmed by reverse-engineering `web3bugs_101_H_01.json` (a pre-existing, correctly-built baseline case never touched this session) byte-for-byte: header record `startLine=42 endLine=43`; the function's first real body statement independently gets `startLine=43` (an exact reuse of the header's own `endLine`, not `+1`); the debug block, appended at the very end of the array, starts at `startLine=43` too and counts up from there.

**`@During` inline vs. standalone** (also traced from source, `SolidityAnalyzer._is_during_inline`, lines ~219-226): `@During` — and *only* `@During*, per its own docstring — may be written *inline*, meaning it attaches to an already-existing code line without shifting anything, by giving its record the **exact same `startLine`** as the statement it's about. `update_code`'s `add` handler checks this before calling `_insert_lines` at all: if the During record's `startLine` already has non-empty code sitting there, `_insert_lines` (which is what actually writes into `full_code_lines` and shifts subsequent lines) is skipped entirely, and only `analyze_context` runs — so an inline During never appears as its own visible line in the reconstructed source at all, it's purely a CFG-attachment action. Any other `startLine` (i.e. an empty line at that position) makes it standalone: a genuinely new line, shifting everything below it down by one. `@Post` is always standalone (never inline) per the same docstring. A plain top-to-bottom `slice_solidity()` run can never produce two different physical source lines with the same `startLine`, so building an inline During record requires a manual override — copy the target statement's own `startLine`/`endLine` onto the During record after slicing, then shift every later record back by the resulting gap (confirmed necessary against `web3bugs_101_H_01.json`: the `return` statement immediately after that case's inline During sits at exactly one less line than a naive slice would give it, since the inline During occupies no real line slot at replay time).

**Fix applied**: wrote a small reusable builder script (`build_case_json.py`, kept in this session's scratchpad, not checked into the repo) that (a) slices a code+intent-only `.sol` file (no debug block) via the existing `soltotestjson.py:slice_solidity`, (b) locates the target function's header record and takes its own `endLine` as the debug block's anchor line, (c) slices the debug block as its own tiny fragment numbered from that anchor, (d) optionally overrides a named `@During` record's `startLine`/`endLine` to match a named target-statement record (closing the resulting gap in every later record) for inline attachment, and (e) concatenates code+intent records with the debug records appended last. Validated byte-for-byte against `web3bugs_101_H_01.json` before use. Applied to rebuild all three previously-built case JSONs in place (`web3bugs_83_H_01`, `web3bugs_3_H_05`, `web3bugs_35_H_11` — content/annotations unchanged, confirmed via a multiset diff of `code` fields before/after; only the array order and line numbers changed) and to build `web3bugs_52_H_04` fresh from the start using the correct process.

**Two things initially misdiagnosed as bugs while investigating this, both retracted after re-reading `analysis.md` more carefully**: (1) `web3bugs_35_H_11`'s `@During` checks `feeGrowthOutside1` while textually sitting inside the `zeroForOne` branch, which never writes that field — this looked like a branch/scenario mismatch, but it is in fact exactly the point: the reported bug **is** "this branch writes the wrong field," so checking the field that *should* have been touched (and wasn't) from inside the branch that fails to touch it is the correct construction, not an error. (2) Relatedly, the same During was assumed to need inline attachment (per the "During's default is inline" framing) — but there's no statement to inline-attach it to in the first place, since the field it checks is never written in this branch; standalone was already correct.

**Loop-array debug-annotation convention, confirmed against `web3bugs_58_H_02.json`** (an already-working, previously-executed baseline case with a real `for` loop over a parameter array, untouched this session): set individual array indices directly (`arr[0]`, `arr[1]`, ...); **no `.length` annotation anywhere in that file at all**. Applied to `web3bugs_3_H_05` (extended `account.borrowTokens`/`account.holdingTokens` from 1 element to 2 each) and the fresh `web3bugs_52_H_04` build (`_pairs[0]`/`_pairs[1]`, one matching the queried token and contributing to `sumNative`/`sumUSD`, one not) — 2 elements chosen deliberately (per user direction) so the target function's loop actually needs to fixpoint-join over a genuine multi-iteration body rather than trivially "loop" once, in case that ever matters for RQ1-B precision later. `web3bugs_83_H_01` was left on its existing `poolInfo.length = [2, 2]` annotation — a different situation, since that array's *pre-call* length is itself a load-bearing entry-state precondition for a function that doesn't loop over the array at all, not a parameter being iterated by the current call.

## Open issue: same-file contraction functions must be declared callee-before-caller — the engine does not resolve forward references, confirmed live-broken in a pre-existing baseline case (`web3bugs_45_H_01`)

## Open issue: infeasible loop-exit produces an *empty* env, not a bottom-flagged one — `_is_bottom_env({})` returns `False` — found while re-examining `web3bugs_45_H_02` (not yet built)

**Symptom, traced by source read (no case run needed to see it — confirmed by reading `Interpreter/Engine.py` and `Utils/Helper.py` directly)**: when a `for`/`while` loop's *normal-completion* exit path has no feasible predecessor flow under a concrete debug scenario (e.g. every iteration is forced, via decisively-true/false branch conditions, to exit early through a `return` inside the loop body instead), `fixpoint()`'s exit-env computation (`Interpreter/Engine.py:608-615`) leaves `exit_env = None` and falls back to:
```python
exit_node.variables = VariableEnv.copy_variables(exit_env or {})   # → {} (a genuinely empty dict)
```
This is a **different representation of "unreachable" than the one used everywhere else in the engine**. An infeasible `if`/`else` branch is marked via `_set_bottom_env` (`Engine.py:1161-1163`), which keeps every variable *key* from the entry environment but sets each value to its domain's `bottom()` — and `_is_bottom_env` (`Engine.py:1141-1146`) correctly detects that. But a loop-exit env built from *zero* feasible predecessors is a dict with **no keys at all**, and:
```python
def _is_bottom_env(self, env: dict) -> bool:
    for v in env.values():
        if self._is_bottom_var(v):
            return True
    return False
```
iterates zero times over an empty dict and returns `False` — an infeasible loop-exit is **not recognized as unreachable** by the one check (`_run_worklist`, `Engine.py:853`) that's supposed to gate whether a node's statements actually execute.

**Why this doesn't (yet) cause an observable failure in the case checked**: `web3bugs_45_H_02`'s `getLockedAmount` reaches its final `return 0;` (L77) only after the `if (isIncrease) {...} else {...}` block's two branches rejoin. In the concrete `isIncrease==false`, match-at-`array[0]` scenario, the `isIncrease==true` sibling branch is infeasible at the *outer if/else* level, so it correctly gets a real, key-bearing bottom env via `_set_bottom_env`. At the join point before L77, `Utils/Helper.py:344`'s `_merge_by_mode` — `if not right: return copy_variables(left)` (and the symmetric case: an empty `left` degenerates to a plain copy of `right`'s keys, values included) — treats the empty dict from the loop-exit as an *identity* element and the properly-bottom dict from the sibling branch "wins" the merge, so the combined env reaching L77 is still correctly bottom-flagged and L77 is correctly skipped. **This is incidental, not designed**: it only works because there happens to be a sibling branch supplying a real bottom env at the same join point.

**Where it would actually bite**: any function where a loop's normal-completion exit is infeasible under the debug scenario *and* there is no sibling infeasible branch to merge with before the next statement — e.g. a bare `for (...) { ...; if (match) return x; }` followed directly by `return 0;` with nothing else in between. There, `nxt.variables = copy_variables(exit_node.variables)` (`Engine.py:912`, or the equivalent at `Engine.py:952` for the non-loop successor-propagation path) would hand the post-loop node a plain empty dict, `_is_bottom_env({})` would return `False`, and the post-loop `return 0;` (or whatever statement follows) would **actually execute** — with a variables dict missing every entry the function normally has in scope. Depending on what that statement reads, this could silently fabricate a spurious `return_vals` entry (contaminating any `@Post returnExpression` join per `_extract_return_value`, `Engine.py:957-999`) or crash on a missing-key lookup.

**Not yet fixed, not yet confirmed against a real running case** — found via source inspection while double-checking whether `45_H_02`'s planned `@Post returnExpression == array[0].lockedAmount - amount` annotation (see `phase_reviews/15_web3bugs_45_H_02/analysis.md`) could get contaminated by the function's other `return 0;` statements (L33, L77) at σ_exit. It does not, for the reason above, but the underlying representational gap (`{}` vs. a real bottom-flagged dict) is real and worth fixing at the root — e.g. by having `fixpoint()`'s exit-env fallback build a proper bottom-flagged dict (mirroring `_set_bottom_env`'s approach, using the loop head's own entry env as the key template) instead of `{}`, or by making `_is_bottom_env` treat an empty dict as bottom when a non-empty env was expected at that CFG position.

**Proposed fix (not yet applied)**: in `fixpoint()` (`Engine.py:608-615`), when `exit_env` stays `None`, build the fallback from the loop head's own `in_vars[head]` (or the head's entry `.variables`) run through `_set_bottom_env`, instead of falling back to `{}`. This keeps the "infeasible = bottom-flagged dict with real keys" representation consistent everywhere in the engine, not just at `if`/`else` nodes.

## RESOLVED (2026-08-31): the "@During comment chunk immediately followed by real-code chunk" crash (Group 1a above) was a case-JSON/`.sol` authoring-convention bug, not a `get_current_block()` search-algorithm bug — plus two real engine bugs found and fixed along the way

Confirmed by rebuilding all 3 known instances (`numscout_EthereumGod`, `web3bugs_31_H_01`, `web3bugs_112_H_01`) from scratch and re-running them clean. **Root cause**: the contraction `.sol` files had `@During`/`@Post` physically embedded as their own comment line, and the case JSON mirrored that (comment gets its own record, own line). The established, baseline-proven convention (cross-checked against all 20 working `evaluation/RQ1/run_all.py` cases) is different:

- **`@During`**: array position = after all real code, immediately before `@Debugging BEGIN`; `startLine` tag = the target statement's own line (the statement whose effect it checks, or — for a `changed(x, false)` guarding upcoming code, confirmed via `web3bugs_112_H_01` — the *following* statement's line). This hits `SolidityAnalyzer._is_during_inline`'s no-shift fast path since the tagged line already has real content.
- **`@Post`**: same array position (after all code, before `@Debugging BEGIN`), but `startLine` tag = **its own original (unshifted) line**, not the target's — confirmed byte-for-byte against the untouched original `web3bugs_16_H_06.json` and re-derivable from every baseline case. `@Post` deliberately goes through the real `_insert_lines` shift path (`_is_during_inline` excludes it, unchanged from before).
- **`@Debugging BEGIN`**: `startLine` tag = the enclosing function's own header pseudo-`endLine` (i.e. right at function entry, before its first real statement) — confirmed against 5 baseline cases (WANGMI/Nokon/HIT/`101_H_01`/`5_H_07`), all with `Debugging BEGIN`'s `startLine` exactly matching the target function header's `endLine`. Each subsequent debug line increments by 1. This session's earlier builds (`numscout_EthereumGod`, `web3bugs_113_H_05`, etc.) had used "sequentially after all code" instead — wrong, silently didn't crash in most cases but is not the actual established convention.

**Two genuine engine bugs found and fixed while chasing this**, both real, both verified against the full 20-case baseline with no regressions (`evaluation/RQ1/run_all.py`, still 17 VIOLATED / 3 ERROR throughout):

1. **`main.py`'s `simulate_inputs` called `sa.update_code(...)` twice for every `@During`/`@Post` record** — once unconditionally at the top of the loop, once again in the annotation-specific branch. For a multi-line-merged target statement (e.g. `web3bugs_31_H_01`'s `currentLockRatio = ...` spanning 2 source lines), the *first* call saw a blank `full_code_lines` slot at the During's tagged line (since multi-line-merged records write their real text at the span's last line, not its first — see `_insert_lines`'s "앞쪽 빈 슬롯 채우기" step) and fell through to a real shifting insert, corrupting every downstream line/CFG registration before the *second* call ever got a chance to take the safe inline path. Fixed: removed the redundant second call (`main.py`, the `// @During`/`// @Post` branch inside `simulate_inputs`).
2. **`SolidityAnalyzer._is_during_inline` only checked `full_code_lines` (the incrementally-rebuilt text buffer), not `line_info` (the actual CFG-node registry)** — so a `@During` tagged at a multi-line target's own `current_start_line` was wrongly judged "not inline" (blank buffer slot there) even though a real CFG node *was* registered at that exact line (`build_variable_declaration`/`insert_new_statement_block` key off `current_start_line`, independent of where the text buffer physically wrote the statement's content). Fixed: `_is_during_inline` now also accepts a line as inline if `line_info[start_line]['cfg_nodes']` is non-empty, not just if the text buffer is non-blank.

**Verified**: `numscout_EthereumGod` — both `@During` members now report correctly (`toMarketing` VIOLATED matching the reported bug, `newBalance` SATISFIED matching the case's own already-documented `swapTokensForEth`-balance-tracking caveat). `web3bugs_31_H_01` — `currentLockRatio` reports WARNING (legitimate — `totalCVXBalance` mixes in an unbounded `wantToCVX()` call). `web3bugs_112_H_01` — both `changed(...)` members correctly VIOLATED, matching the reported ordering bug. All three previously crashed on `DynamicCFGBuilder.py:1403`; none do now.

## RESOLVED (2026-08-31): `GuardianVerificationEngine._preds` queried the wrong exit node for `@Post` checks whenever the function actually has a `return` — root cause of `web3bugs_16_H_06`'s "not declared" error, previously mis-suspected as a JSON-placement issue

`DynamicCFGBuilder.build_return_statement` wires a `return` statement's block to `fcfg.get_return_exit_node()` — a **separate** node from `fcfg.get_exit_node()`. `GuardianVerificationEngine._preds` (feeding `_exit_env` → `_eval_on_exit_value`, used by nearly every `verify_post_*` check) queried `fn_cfg.get_exit_node()` directly, so for any function with a real `return`, it found **zero predecessors** (nothing was ever wired to that node) and fell back to `fn_cfg.related_variables` — a generic set containing only global/state names (`block.*`, `msg.*`, `tx.*`, declared state vars), no locals. Evaluating a `@Post` clause referencing a local (e.g. `web3bugs_16_H_06`'s `result == ...`) against that fallback env raised `This 'result' is may be elementary variable but may not be declared`.

Confirmed by instrumenting `_exit_env` directly: `preds count=0` for `web3bugs_16_H_06`'s `latestAnswer()`, even with the During/Post-placement convention above already fixed and the JSON matching the original file byte-for-byte. Ruled out as a placement issue by testing every combination (target-line vs. own-line, shift vs. no-shift) — all produced the identical error, isolating this to a pure engine bug.

The correct selector, `_get_post_exit_node` (return_vals non-empty → `return_exit`, else the general `exit_node`), already existed and was already used by `verify_post_return_expression`'s dedicated `_get_post_exit_node` call — but not by `_preds`. **Fix**: `_preds` now calls `self._get_post_exit_node(fn_cfg)` instead of `fn_cfg.get_exit_node()` directly (`Analyzer/GuardianVerificationEngine.py`).

**Verified**: `web3bugs_16_H_06` now reports `[POST INTENT WARNING]` with `RHS = 15000000000000000000000` — the exact value of `gasPrice * 1e9 * ethPrice * 1e12 / 1e18` for the seeded scenario (`gasPrice=5e9, ethPrice=3e9`). No regression on the 20-case baseline (still 17 VIOLATED / 3 ERROR) or on `web3bugs_29_H_08` (still the same two `WARNING`s as before).

## New open issue: `web3bugs_192_H_01`'s `KeyError: None` crash likely has a different trigger than `62_H_03`/`62_H_10` — a `/** ... */` NatSpec block comment, not a `//` line comment

## RESOLVED (2026-08-31): Group B — `struct_defs`/`enum_defs` backfill pattern was silently clobbering already-correct, comprehensive struct definitions with a narrower one, corrupting struct field access on mapping/array values built from file-level structs

**Symptom**: `web3bugs_113_H_05` crashed with `'valuation' not in struct 'params'` (reading `tokenLoanParams[tokenId]`, a `mapping(uint256 => TokenLoanParams)` where `TokenLoanParams` is a **file-level** struct); `web3bugs_52_H_04`/`web3bugs_52_H_34` crashed with `'token0' not in struct 'pairData'` (reading `_pairs[i]`, a `PairData[]` state array). In both cases the struct's `.members` dict was empty — the value was never `initialize_struct`'d.

**Root cause, found by instrumenting `MappingVariable.__init__`/`_make_value` to trace object + dict identity across the whole `113_H_05` run**: the *initial* construction of `tokenLoanParams`'s `MappingVariable` (via `ContractAnalyzer.process_state_variable`) correctly unions contract + file-level + parent-chain struct defs and assigns it — confirmed via direct trace, all 4 structs present including the file-level `TokenLoanParams`. But **13 separate call sites** (`Interpreter/Semantics/{Update.py,Evaluation.py,DebugInitializer.py}`) contained the exact same defensive-looking pattern:
```python
if not callerObject.struct_defs or not callerObject.enum_defs:
    ccf = self.an.contract_cfgs[self.an.current_target_contract]
    callerObject.struct_defs = ccf.structDefs      # ← only the CURRENT CONTRACT's own structs
    callerObject.enum_defs = ccf.enumDefs
```
This looks like a harmless "backfill if missing" guard, but the condition is `or`, not `and` — since `TokenLoanParams` has no enum members, `callerObject.enum_defs` is legitimately `{}` (falsy) even though `struct_defs` was already fully correct. That alone was enough to trigger the branch, which then **unconditionally overwrites** `struct_defs` with `ccf.structDefs` — the current contract's own structs only, missing every file-level struct (`TokenLoanParams`) and every parent-chain struct. Traced with object-identity + dict-identity prints: the *same* `MappingVariable` instance's `struct_defs` dict-id changed from the correct 4-key dict to a different, 1-key (`'TokenLoan'` — the contract's own, unrelated struct) dict between construction and the crash, confirming an in-place reassignment, not a stale copy. This pattern is exercised extremely often (every mapping-key access with a global/literal/computed key going through `copy_variables`-heavy CFG join/require/branch machinery), so once triggered once it silently propagates forward via `copy_single_variable`'s `struct_defs=v.struct_defs` (reference-preserving, not a fresh rebuild).

**Also found while fixing this**: two related, narrower gaps in the same "propagate struct/enum defs to composite values" family, hit by `52_H_04`/`52_H_34`'s `PairData[] private _pairs` (array-of-struct state variable, not a mapping):
- `EnhancedSolidityVisitor.visitStateVariableDeclaration`'s array branch constructed `ArrayVariable(...)` with no `struct_defs`/`enum_defs` at all (unlike the mapping branch a few lines below it, which already built the correct union) — so any struct-typed array element, lazily created via `ArrayVariable._create_new_array_element`, found `self.struct_defs` empty and silently skipped `initialize_struct`. Same gap existed in `ContractAnalyzer._create_variable_object`'s array branch (used for local array declarations).
- `ArrayVariable._create_new_array_element`'s nested-mapping and nested-array cases (`Domain/Variable.py`) didn't forward `self.struct_defs`/`self.enum_defs` to the child `MappingVariable`/`ArrayVariable` they construct — so an array-of-mapping-of-struct or array-of-array-of-struct would lose struct defs one level down even after the above fix.

**Fix** (all root-cause, no fallback/workaround):
1. Added `ContractAnalyzer.get_full_struct_enum_defs(contract_name=None)` — the single correct union logic (contract + file-level + parent chain), extracted from `process_state_variable`'s already-correct mapping branch so every caller shares one implementation instead of five slightly-different inline copies.
2. Replaced all 13 buggy call sites' `callerObject.struct_defs = ccf.structDefs` with `callerObject.struct_defs = {**all_structs, **callerObject.struct_defs}` (via the new helper) — merges in anything missing without ever discarding what was already there, so a legitimately-empty `enum_defs` can no longer trigger loss of a correct `struct_defs`.
3. `visitStateVariableDeclaration`'s array *and* mapping branches now construct with `struct_defs=`/`enum_defs=` from the new helper at construction time (mapping branch was already fixed downstream in `process_state_variable`, but doing it at construction too closes the gap for any read that happens before that runs).
4. `ContractAnalyzer._create_variable_object`'s array branch (local array declarations) — same fix.
5. `ArrayVariable._create_new_array_element`'s nested-mapping/nested-array construction — now forwards `struct_defs=self.struct_defs, enum_defs=self.enum_defs`.

**Verified**: `web3bugs_113_H_05`, `web3bugs_52_H_04`, `web3bugs_52_H_34` — the struct-field crash is gone in all three; each now runs further into different, pre-existing, unrelated territory (matches what the triage already expected — these cases have other independent blockers beyond this one). `web3bugs_83_H_01` (a related one-off, `poolInfo[1]` losing `struct_defs` in an array branch) also progresses past its old crash site, though it now hits a separate downstream issue not covered by this fix. No regression on the 20-case baseline (still 17 VIOLATED / 3 ERROR) or on any of this session's other rebuilt cases. **None of these 4 cases pass end-to-end yet** — `113_H_05` now hits `'str' object has no attribute 'multiply'`, `52_H_04`/`52_H_34` now hit the same interval-`join()` type-length crash as `web3bugs_29_H_11` (Group G), tracked as new entries in `engine_run_triage.md`'s "지금 안 되는 케이스" section (Group G/Group I), not silently dropped.

## RESOLVED (2026-08-31): Group F — bound library method resolution failed when `using Lib for Lib.Struct;` registers a *qualified* type key but the struct value's inferred type name is *bare*

**Symptom**: `web3bugs_70_H_05` crashed with `'decode144' not in struct 'temp_uq144x112_...'` — `FixedPoint.decode144()` (a library function attached via `using FixedPoint for FixedPoint.uq144x112;`) called on a synthesized intermediate value (the result of a chained `.mul(1)` call) fell through to plain struct-member lookup instead of resolving as a library call.

**Root cause**: the source uses the qualified-target form of `using`, e.g. `using FixedPoint for FixedPoint.uq144x112;` — a real, valid Solidity idiom (`using Lib for Lib.Struct;`, referencing a struct declared inside the library itself). `process_using_directive`/`ContractCFG.add_using_library` registers this into `using_libraries["FixedPoint.uq144x112"]` — keyed by the literal qualified text from the source. **Fix**: `ContractCFG.find_library_function` and `LibraryCFG.find_library_function` (`Utils/CFG.py`, both copies of the method) now also try the opposite qualification when the direct key lookup fails — a bare `target_type` additionally checks every `using_libraries` key whose last `.`-segment matches it (`"FixedPoint.uq144x112"` matches lookup for `"uq144x112"`), and a qualified `target_type` additionally checks the bare form. This is a pure fallback (only runs when the direct match already failed) so it can't change behavior for any case that was already resolving correctly.

**Verified**: `web3bugs_70_H_05` — the struct-field crash is gone; the case now progresses to a separate, unrelated `@IReturn` debug-annotation issue further down (`ContractAnalyzer.process_ireturn`, "'oracle' is not an interface-typed variable" — not diagnosed, tracked as a new entry in `engine_run_triage.md`'s Group I). **Does not pass end-to-end yet.** No regression on the 20-case baseline or any other rebuilt case.
