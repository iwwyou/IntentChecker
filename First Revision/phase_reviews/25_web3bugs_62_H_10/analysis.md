## R1-1 — Reported Behavior Reconstruction

**Contract/function role.** `Stream` (Locke Streaming Protocol) lets depositors lock a `depositToken` for a fixed duration in exchange for a continuously-streamed `rewardToken`; `isSale` is an immutable per-stream flag: when `true`, deposited tokens are a one-way sale to `streamCreator` rather than something depositors can later reclaim (no receipt tokens are minted, `claimDepositTokens` is unreachable). `depositTokenAmount` (state, `uint112`) is the contract's running internal ledger of "deposit tokens currently owed to someone" — incremented on `stake` (L431), decremented on `withdraw` (L469, only reachable while the stream is still active). `redeemedDepositTokens` (state, `uint112`) is a *separate* running ledger, meant to track how much of `depositTokenAmount` has already been paid out post-stream — the only place it is ever written is `claimDepositTokens` (L544, `redeemedDepositTokens += amount;`, the non-sale reclaim path).

**The two functions this bug spans:**
- `creatorClaimSoldTokens(address destination) public lock` (L583–600) — callable once (`!claimedDepositTokens` guard, then `claimedDepositTokens = true;`), only when `isSale`, only after `block.timestamp >= endStream`, only by `streamCreator`. Transfers the *entire* `depositTokenAmount` to `destination` in one shot (L594–597):
  ```solidity
  uint112 amount = depositTokenAmount;
  claimedDepositTokens = true;

  ERC20(depositToken).safeTransfer(destination, amount);

  emit SoldTokensClaimed(destination, amount);
  ```
  **It never writes to `redeemedDepositTokens` (or to `depositTokenAmount`) at all** — confirmed by reading the entire function body; no other statement in it touches either variable.
- `recoverTokens(address token, address recipient) public lock` (L646–691), `token == depositToken` branch (L650–660) — lets `streamCreator` sweep any deposit-token balance sitting in the contract beyond what is still owed:
  ```solidity
  uint256 excess = ERC20(token).balanceOf(address(this)) - (depositTokenAmount - redeemedDepositTokens);
  ERC20(token).safeTransfer(recipient, excess);
  ```
  This line's own inline comment (L639, the function's doc block) states the intent directly: `excess deposit tokens defined as (balance - depositTokenAmount)` for the non-sale case, generalized here to `balance - (depositTokenAmount - redeemedDepositTokens)` once partial redemptions are possible.

**Relevant locals/state:**
- `depositTokenAmount` (state, `uint112`) — total deposit tokens the contract still considers "allocated" (not yet reclaimed/paid out).
- `redeemedDepositTokens` (state, `uint112`) — cumulative deposit tokens already paid out of that allocation. **Structural fact, provable directly from the source, not merely a scenario assumption**: for any stream with `isSale == true`, `redeemedDepositTokens` can *never* become nonzero before `creatorClaimSoldTokens` runs, because its only writer, `claimDepositTokens`, is gated by `require(!isSale, "sale")` (L533) — categorically unreachable for a sale stream. So `redeemedDepositTokens(Entry) == 0` at the moment `creatorClaimSoldTokens` executes is not a chosen scenario value but a provable invariant of `isSale == true` streams.
- `amount` (local, L594, `creatorClaimSoldTokens`) = `depositTokenAmount` at the moment of the claim — the exact quantity physically transferred out at L596.
- `depositToken` (state, immutable) — the token address `creatorClaimSoldTokens` and `recoverTokens` both operate on.

**The disputed omission (L594–599, `creatorClaimSoldTokens`)**: the function reads `depositTokenAmount` into `amount`, transfers `amount` tokens out, and stops — it never records that this `amount` has now left the "still owed" ledger. `depositTokenAmount` itself is also left untouched. Both of the two variables `recoverTokens`'s excess formula subtracts (`depositTokenAmount - redeemedDepositTokens`) are therefore exactly the *same* after a full sale-claim as they were before it, even though the contract's actual `depositToken` balance has just dropped by `amount`.

**Variable-value intent.** After `creatorClaimSoldTokens` transfers out the sold allocation, the ledger quantity `depositTokenAmount - redeemedDepositTokens` — the accounting value `recoverTokens` treats as "still owed to someone, not recoverable as excess" — must shrink by exactly `amount`, the amount just paid out. Currently it does not shrink at all.

**Statement/line-level intent.** `creatorClaimSoldTokens` is conceptually the sale-stream counterpart of `claimDepositTokens` (the non-sale reclaim path) — both represent "deposit tokens leaving the contract to their rightful owner post-stream," and the contract's own established convention for recording that (`claimDepositTokens`, L544: `redeemedDepositTokens += amount;`) already exists in this same file. `creatorClaimSoldTokens` is supposed to uphold the same ledger invariant `claimDepositTokens` upholds, for the sale case.

**Reported erroneous behavior** (H-10, verbatim, primary source): *"In `recoverTokens`, the logic to calculate the excess number of deposit tokens in the contract is: `uint256 excess = ERC20(token).balanceOf(address(this)) - (depositTokenAmount - redeemedDepositTokens);` This breaks in the case where isSale is true and the deposit tokens have already been claimed through the use of `creatorClaimSoldTokens`. In this case, `redemeedDepositTokens` will be zero, and `depositTokenAmount` will still be at its original value when the streaming ended. As a result, any attempts to recover deposit tokens from the contract would either revert or send less tokens than should be sent... Notice that `creatorClaimSoldTokens` does not change `depositTokenAmount` or `redeemedDepositTokens`, so the excess calculation will be incorrect in the case of sales."* Judge (`0xean`) upgraded to High: *"assets would be lost in the case outlined by the warden."*

**Recommended Mitigation Steps** (verbatim): *"I would recommend setting `redeemedDepositTokens` to be `depositTokenAmount` in the function `creatorClaimSoldTokens`, since claiming the sold tokens is like 'redeeming' them in a sense. This would fix the logic issue in `recoverTokens`."* This anchors the defect's location squarely at `creatorClaimSoldTokens` (not at `recoverTokens`'s own formula, which the report never proposes changing) — `recoverTokens` is only where the consequence of the missing update surfaces.

**Concrete scenario (constructed — the report gives no numeric PoC).** A sale stream (`isSale == true`) accumulates `depositTokenAmount = 1000` (arbitrary round number, deposit-token smallest-unit terms) through `stake` calls during the stream; `redeemedDepositTokens(Entry) = 0` at the moment `creatorClaimSoldTokens` is called (provable invariant, above, not a scenario choice), post-`endStream`, by `streamCreator`, for the first (only allowed) time.
- **Buggy**: `creatorClaimSoldTokens` transfers `1000` deposit tokens out, leaves `depositTokenAmount = 1000` and `redeemedDepositTokens = 0` unchanged. A subsequent `recoverTokens(depositToken, recipient)` computes `excess = balanceOf(this) - (1000 - 0) = balanceOf(this) - 1000`; since the sold `1000` tokens already left the contract, `balanceOf(this)` is now `<=` its pre-claim value minus `1000` (any residual is whatever else, if anything, the contract holds of that token) — in the common case where the contract's deposit-token balance is now `0`, the subtraction `0 - 1000` underflows a `uint256` under Solidity >=0.8's default checked arithmetic and **reverts**, exactly matching the report's "would either revert... " clause; in a case where some unrelated deposit-token balance remains (e.g. a stray donation), `excess` is undercounted by `1000`, matching "...or send less tokens than should be sent."
- **Intended** (recommended fix applied at `creatorClaimSoldTokens`): `redeemedDepositTokens` becomes `1000` after the claim; `recoverTokens`'s subsequent computation uses `depositTokenAmount - redeemedDepositTokens = 1000 - 1000 = 0`, so `excess = balanceOf(this) - 0 = balanceOf(this)` — correctly recoverable in full, without spuriously reverting or undercounting.

**Bug-relevant intended numeric behavior**: by the time `creatorClaimSoldTokens` returns, the ledger quantity `depositTokenAmount - redeemedDepositTokens` must have decreased by exactly `amount` (the quantity just transferred out) relative to its value at function entry — the current code leaves it completely unchanged.

## R1-2 — Intent Abstraction

Distinguishing property (no patch diff exists to drop syntax from; the recommendation's own literal wording — "set `redeemedDepositTokens` to `depositTokenAmount`" — is treated as evidence of the *mechanism* to correct, not transcribed verbatim; see R1-3 for why a more general form was selected instead): the function must record, in the contract's own redemption-ledger accounting, that `amount` deposit tokens have left the "still owed" pool — currently it records nothing.

**Intent-level orientation: Effect/state-transition-centered.** This is not a constraint on one already-computed value's magnitude (R1-2's value-centered category); it is a constraint on what *effect* `creatorClaimSoldTokens` must have on persistent contract state — specifically, on the accounting relationship between two state variables — mirroring the `weiRaised -= amount` / `totalCredit += delta` precedent R1-4 (below) explicitly points to.

## R1-3 — Select the least implementation-specific sufficient relation

**Preliminary check — does the natural statement of intent need a function call inside `intentValue`?** No. Every quantity involved (`depositTokenAmount`, `redeemedDepositTokens`, `amount`) is a state variable or already-materialized local, directly `varRef`-able with snapshot qualifiers. `ERC20(depositToken).safeTransfer(destination, amount)` (the statement whose missing accounting counterpart is the actual defect) is **not** needed inside the relation itself — see Alternative 4 below for why a relation that *does* need a call (attached instead to `recoverTokens`) was considered and rejected.

1. **Directional (weakest tier)**: `redeemedDepositTokens(Exit) > redeemedDepositTokens(Entry)`. **Rejected — fails the required negation check.** A "fix" that increments `redeemedDepositTokens` by an arbitrary wrong amount (e.g. `+= 1`, or `+= amount/2`) satisfies this directional relation while leaving `recoverTokens`'s excess computation still wrong (under- or over-counting the true remaining balance) — exactly the reported defect, just less severe. A bare direction is not sufficient.
2. **Single-field exact equality, mirroring the recommendation's literal wording**: `redeemedDepositTokens == depositTokenAmount(Entry)` (**review-corrected on a third pass, see Review Notes** — the candidate must pin `depositTokenAmount` to its *entry* snapshot for the rejection argument below to actually hold; a bare exit-exit reading, `redeemedDepositTokens == depositTokenAmount` with no snapshot qualifier at all, is a *materially different, even weaker* candidate that does **not** catch the alternative fix described below — under `depositTokenAmount -= amount`, both operands equal `0` at exit and that bare form is vacuously satisfied, not falsely rejected). **Considered, and rejected as unnecessarily implementation-specific** — not because it's an equality (per README's explicit caution, operator strength alone doesn't measure implementation-specificity), but because of what it depends on: it hard-codes *which* of the two ledger variables must move, and pins the untouched one (`depositTokenAmount`) to the one snapshot value that only happens to still equal its exit value under the buggy code's own particular behavior. A legitimate alternative correct fix — decrementing `depositTokenAmount` by `amount` instead of incrementing `redeemedDepositTokens` (verified below to be an equally valid fix, since neither variable has any other load-bearing use inside `creatorClaimSoldTokens`, and `recoverTokens`'s formula only ever consumes the *difference* `depositTokenAmount - redeemedDepositTokens`, never either variable alone) — would be flagged as a false Violated by this (Entry-qualified) relation, which is a real cost given README §3's discipline: prefer program-native, non-patch-specific terms unless the exact patch expression is genuinely the only correct specification, which it is not here.
3. **Relational invariant over the ledger difference (SELECTED)**: `(depositTokenAmount - redeemedDepositTokens) == (depositTokenAmount(Entry) - redeemedDepositTokens(Entry)) - amount`. This states the actual semantic content of the fix — "the still-owed ledger shrinks by exactly the amount just paid out" — independent of which specific state variable the implementation chooses to move. **Verified to accept both legitimate fix strategies and reject every tested defect-retaining alternative** (arithmetic below).
4. **A `@Post` relation attached to `recoverTokens` itself**, e.g. checking that `excess` (or the underlying `ERC20(token).balanceOf(address(this))`) reflects the corrected ledger. **Rejected — alpha, no rescue available.** `ERC20(token).balanceOf(address(this))` is a live external-contract state read with no fixed formula: it depends on every other token movement into/out of the contract (other stakers' `stake`/`withdraw` calls, `flashloan`, `createIncentive`, arbitrary donations) that has occurred by the time of the call — not deterministic from in-scope arguments plus contract-lifetime-fixed constants, failing condition (a) of the exact-formula-inlining rescue (README §3), and not boundable by any protocol-enforced invariant either (no known-minimum/maximum exists on an arbitrary ERC-20's live balance), failing the Nokon-style known-bound rescue too. This is the same confirmed non-rescuable shape as `web3bugs_70_H_03`'s live Chainlink call and `web3bugs_59_H_05`'s external-contract state — alpha applies and is not closed. **This is why the target relation is instead attached to `creatorClaimSoldTokens`** (R1-4) — the missing-update defect's own root-cause location is fully expressible there without ever needing `balanceOf`.

**Winner: Alternative 3 (relational invariant, Entry/Exit-qualified).**

**Required negation check (§3/R1-3), verified with explicit numbers** (`depositTokenAmount(Entry) = 1000`, `redeemedDepositTokens(Entry) = 0`, `amount = 1000`):
- **Actual buggy code (no update at all)**: `depositTokenAmount(Exit) = 1000`, `redeemedDepositTokens(Exit) = 0`. LHS `= 1000 - 0 = 1000`. RHS `= 1000 - 0 - 1000 = 0`. `1000 == 0` -> **false -> Violated.** Correctly flagged.
- **Partial-fix alternative** (`redeemedDepositTokens += amount/2 = 500`): LHS `= 1000 - 500 = 500`. RHS `= 0`. `500 == 0` -> **false -> Violated.** Correctly flagged — this is exactly the "still wrong, just less severe" alternative that defeated Alternative 1.
- **Double-move alternative** (a hypothetical over-fix that both increments `redeemedDepositTokens` by `amount` *and* decrements `depositTokenAmount` by `amount`, double-counting the reduction): `depositTokenAmount(Exit) = 0`, `redeemedDepositTokens(Exit) = 1000`. LHS `= 0 - 1000 = -1000` (an unbounded/mathematical difference, for negation-check comparison purposes). RHS `= 0`. `-1000 == 0` -> **false -> Violated.** Correctly flagged. **Correction (review pass, see Review Notes): the real-world consequence stated below was wrong.** `depositTokenAmount`/`redeemedDepositTokens` are both `uint112`, and `recoverTokens`'s own excess line (L654) computes `depositTokenAmount - redeemedDepositTokens` as an actual `uint112` Solidity subtraction *before* combining with `balanceOf`; under this variant that subtraction is `0 - 1000`, which underflows a `uint112` under Solidity `^0.8.0`'s default checked arithmetic and **reverts** — confirmed directly against the engine's own arithmetic semantics too (`Domain/Interval.py`'s `UnsignedIntegerInterval.subtract()`, lines 634-647, returns `bottom()` — the engine's infeasible/reverting-execution result — whenever `max_diff < 0`, exactly this case). This is a worse instance of the same "would... revert" failure mode already described for the unpatched buggy code (R1-1), **not** an over-payment (`excess` is not silently inflated; the computation never completes). The relation's own Violated verdict is unaffected and still correct — only the previously-stated real-world consequence ("over-pay") was inaccurate and has been corrected here.
- **Intended fix, as literally recommended** (`redeemedDepositTokens = depositTokenAmount = 1000`, `depositTokenAmount` unchanged): LHS `= 1000 - 1000 = 0`. RHS `= 1000 - 0 - 1000 = 0`. `0 == 0` -> **true -> Satisfied.**
- **Legitimate alternative fix** (`depositTokenAmount -= amount`, i.e. `depositTokenAmount(Exit) = 0`, `redeemedDepositTokens` left at `0`): LHS `= 0 - 0 = 0`. RHS `= 0`. `0 == 0` -> **true -> Satisfied.** Confirms the relation is not overfit to the report's one specific suggested mechanism — a materially different, equally-correct implementation is accepted, not spuriously flagged.

No gap found: every tested variant that retains the reported "ledger not updated" defect (in whole or in part, in either direction) is caught, and both tested variants that actually fix it are accepted. **Intent coverage: Full.**

## R1-4 — During vs Post

**Selected scope: Post**, on `creatorClaimSoldTokens`. `depositTokenAmount` and `redeemedDepositTokens` are both persistent state variables, and the relation concerns their net change across the *entire* function call (entry-vs-exit), not an intermediate statement-time value or a same-statement self-reference — R1-4's own listed Post criterion ("a persistent state transition") applies directly. This is the same shape README explicitly calls out as a common pattern in this benchmark: *"`SwordCrowdsale`'s patch is the single assignment `weiRaised -= amount`, and `CDP.update`'s patch is `totalCredit += delta` — both assignment-shaped, and both ended up as Post with a directional/Entry-Exit relation."* Not chosen merely because the recommendation names one single-statement fix (R1-4's explicit caution) — chosen because the constrained quantity is a state-ledger relationship that only has meaning compared across the function's entry and exit.

**During considered and rejected.** Could the relation instead be attached to the specific point of the (currently-absent) update statement, e.g. immediately after `uint112 amount = depositTokenAmount;`? No natural attachment exists — there is no existing statement whose "before/after" value the relation needs to compare (unlike `web3bugs_29_H_11`'s `amount1 += ...`, where the same statement both reads and writes `amount1`). The relevant before/after pair here is the *whole function's* entry and exit state of two separate variables, not one statement's self-reference — Post's `(Entry)`/`(Exit)` vocabulary is the correct fit, not During's `(Before)`/`(After)`.

**Required explicit delta-exception check (README §4/R1-7).** `creatorClaimSoldTokens` contains no loop. More broadly, **the entire `Stream` contract (and `Governed`/`ExternallyGoverned`/`StreamFactory`) contains no `for`/`while` loop of any kind anywhere** — confirmed by reading the full 857-line file. There is no candidate loop-body `@During` attachment point to even consider, for this or any other statement in the file. **Delta confirmed not applicable, trivially** — the same clear-cut "no loop anywhere in the contract" situation `web3bugs_16_H_06` recorded.

## R1-5 — Relation form

**Relational invariant, Entry/Exit-qualified**, via the grammar's general `RelationalCmp` common-form rule (`intentValue relOp intentValue`, `Parser/Solidity.g4` line 325), reached through `postIntent -> commonClause`. Unqualified references (`depositTokenAmount`, `redeemedDepositTokens`, `amount` on the LHS-side of the relation) take their exit/final value by default under `@Post`; the RHS's `(Entry)`-qualified references (`depositTokenAmount(Entry)`, `redeemedDepositTokens(Entry)`) pin those two operands to their function-entry snapshot, per the confirmed grammar production `varRef '(' ENTRY ')' #VarRefAtEntry` (only legal outside `@During`, i.e. exactly the `@Post` context used here). Not an Entry-Exit *pairing of the same identifier* (contrast `web3bugs_42_H_01`'s `debts == debts(Entry) + increasingDebt`) but structurally identical in kind — a current-vs-entry comparison mixing two different state variables' entry and exit values in one arithmetic expression, which the snapshot-qualifier extension supports without restriction to a single-identifier pair (README §4: "usable anywhere inside an arithmetic expression, not only as one whole side of a dedicated clause"). Not forced to equality by the recommendation's assignment-shaped wording (R1-5's explicit caution) — equality was selected in R1-3 on independent, arithmetic-verified discrimination grounds (only equality catches every tested defect-retaining variant while still accepting both tested legitimate-fix variants).

## R1-6 — Construct the target annotation

**Attachment point**: `@Post` on `creatorClaimSoldTokens`, placed after the function's last statement (`emit SoldTokensClaimed(destination, amount);`) — the textual-placement convention used elsewhere in this batch even though `@Post` semantically evaluates at `sigma_exit` regardless of exact line.

**No synthetic constant is introduced** — `amount`, `depositTokenAmount`, `redeemedDepositTokens` are all live program values (a local and two state variables); no scenario-derived magic number appears (contrast README's `900`-style derived-constant guidance, which does not apply here).

**Target annotation:**
```solidity
function creatorClaimSoldTokens(address destination) public lock {
    require(isSale, "!sale");
    require(!claimedDepositTokens, "claimed");
    require(msg.sender == streamCreator, "!creator");
    require(block.timestamp >= endStream, "stream");

    uint112 amount = depositTokenAmount;
    claimedDepositTokens = true;

    ERC20(depositToken).safeTransfer(destination, amount);

    emit SoldTokensClaimed(destination, amount);
    // @Post (depositTokenAmount - redeemedDepositTokens) == (depositTokenAmount(Entry) - redeemedDepositTokens(Entry)) - amount
}
```

**Preconditions, stated explicitly (scenario-conditioning, per §4's general note):**
1. **`redeemedDepositTokens(Entry) == 0`** — not an assumed scenario value but a proven structural fact for `isSale == true` streams (R1-1: the only writer of `redeemedDepositTokens`, `claimDepositTokens`, is unreachable whenever `isSale`). Stated here as the concrete instantiation this relation is exercised against, even though the relation's own form does not require it (it holds generally for any `redeemedDepositTokens(Entry)`, per the algebra above).
2. **`amount > 0` (equivalently `depositTokenAmount(Entry) > 0`)** — a stream with zero deposits is a degenerate case with nothing to claim or recover; the reported bug is only observable/meaningful when there is a nonzero sold allocation.
3. **No underflow in `depositTokenAmount - redeemedDepositTokens`, on either the entry or exit side, in the scenarios where the relation is meant to hold (Satisfied)** — required for the relation's own subtraction to be well-defined under `uint112`/Solidity >=0.8 checked-arithmetic semantics; holds by construction in both tested legitimate-fix executions (the report's literal recommendation and the `depositTokenAmount`-decrement alternative) and in the unpatched-buggy/partial-update Violated cases. **Correction (review pass, see Review Notes)**: this precondition does *not* hold for R1-3's double-move alternative (`depositTokenAmount(Exit) = 0 < redeemedDepositTokens(Exit) = amount`) — the original wording overstated it as holding "in every variant exercised," which is false for that one variant. This is not a defect in the relation: the double-move is itself a rejected (Violated) alternative, not one this precondition needs to hold for, and its own violation of this exact non-negativity is additional, independent confirmation that it is defective (per the R1-3 correction above, `recoverTokens`'s real excess computation would itself revert on it).

**Quantification note**: not applicable. `depositTokenAmount`/`redeemedDepositTokens` are two individually-named contract-level state variables (one `Stream` instance, one sale), not elements of an array/mapping the annotation ranges over — no representative-element instantiation issue (contrast `web3bugs_83_H_01`'s `poolInfo[1]`).

**Outcome: Expressible = YES.**

## §5 — Value/Algorithm and Usable/Unusable

- **Algorithm-level.** Per the paper's own definition ("operation ordering, an absent state update, or a missing procedure call"), this is the most direct instance of "absent state update" in this batch: the intended computation for `creatorClaimSoldTokens` is (1) transfer `amount` deposit tokens to `destination` [present], (2) mark the single-claim guard [present], (3) record, in the contract's own ledger, that `amount` tokens have now left the still-owed pool [**entirely absent** — no code for this step exists anywhere in the function, not merely a wrong operand within an existing line]. This is a stronger case than `web3bugs_16_H_06`'s (which at least called a wrong/unscaled value into an otherwise-present multiplication) — here there is no candidate statement to point to as "the buggy line" at all; the fix is a pure insertion. **Corroborating, not sole, evidence**: `claimDepositTokens`'s own parallel line (`redeemedDepositTokens += amount;`, L544) shows the exact shape of the missing step already exists as an established convention elsewhere in this same contract — cited here per §5's explicit guidance as corroboration that the missing step has a well-defined shape in this codebase, not as the reason for the Algorithm-level classification itself (which rests on the missing step being absent from the intended computation's own sequence, independent of whether a directly-reusable sibling line happens to exist).
- **Usable.** Every value the relation needs (`depositTokenAmount`, `redeemedDepositTokens`, `amount`) is directly referenceable, in both its entry and exit forms as needed, at the annotation's `@Post` program point — no external-contract boundary, no semantic-unit ambiguity, no missing proxy. (Per README §4's note on delta: not applicable here since this case does not carry a delta tag at all — but the general point that Usable is assessed independently of any rescue/attachment difficulty holds; here there was no rescue needed in the first place.)
