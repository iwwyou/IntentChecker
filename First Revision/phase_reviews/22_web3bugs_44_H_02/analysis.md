## R1-1 — Reported Behavior Reconstruction

**Contract/function role.** `Swap` lets a caller execute a token swap by filling an off-chain-sourced 0x protocol quote. `swapByQuote(...)` is the external entry point: it optionally pulls the sell token into the contract (`safeTransferFrom`, L128, only when `zrxAllowanceTarget != address(0)`, i.e. an ERC20 sale - an unwrapped-ETH sale instead arrives via `msg.value`), then calls the internal helper `fillZrxQuote(...)` to actually fill the quote and report back how much of the buy-side asset (ERC20 and/or refunded ETH) was received, then deducts a swap fee from whichever proceeds arrived and forwards the rest to `msg.sender`. `fillZrxQuote`'s own doc comment states its contract precisely: "@return any **positive** `zrxBuyTokenAddress` ERC20 balance change, as well as any **positive** ETH balance change" - i.e. it must report the *actual, net-new* proceeds of the one `zrxTo.call{value: ethAmount}(zrxData)` it performs, isolated from any of the contract's own pre-existing or freshly-deposited balance.

**Relevant locals/state (`fillZrxQuote`, L200-225):**
- `ethAmount` (parameter, L204) - forwarded verbatim from `swapByQuote`'s own `msg.value` at the one call site (L135-140: `fillZrxQuote(IERC20(zrxBuyTokenAddress), zrxTo, zrxData, msg.value)`). Every unit of `ethAmount` was already credited to `address(this).balance` at the very start of the enclosing transaction (ordinary EVM/Solidity semantics: a `payable` call's `msg.value` is added to the receiving contract's balance before any of its code runs), i.e. *before* `fillZrxQuote`'s own body executes at all.
- `originalERC20Balance` (local, L206, initialized `0`; conditionally overwritten L207-209) = `zrxBuyTokenAddress.balanceOf(address(this))`, read only when the buy side is a real ERC20 (`!signifiesETHOrZero(...)`).
- `originalETHBalance` (local, L210) = `address(this).balance` - **the first disputed value**.
- `(bool success,) = zrxTo.call{value: ethAmount}(zrxData);` (L212) - the one opaque external call this function exists to perform; it can move both ETH (spending up to `ethAmount`, possibly refunding some of it) and the buy-side ERC20 in ways this contract cannot predict or bound from the caller's side.
- `ethDelta` (local, L215) = `address(this).balance.subOrZero(originalETHBalance)` - **the value the report's ETH-side complaint is about**.
- `erc20Delta` (local, L216, declared; assigned L218 only inside the `!signifiesETHOrZero` branch) = `zrxBuyTokenAddress.balanceOf(address(this)).subOrZero(originalERC20Balance)` - **the value the report's ERC20-side complaint is about**.
- **The two disputed statements** (per R1-1's "variable-value intent" sub-question, each is its own defect, both reported under the same H-02 finding - see R1-3 for why they are analyzed as two independent members rather than one relation):
  - L210: `uint256 originalETHBalance = address(this).balance;`
  - L206-209 (specifically the *absence* of any `- amountToSell`-shaped adjustment when `zrxBuyTokenAddress == zrxSellTokenAddress`): `originalERC20Balance = zrxBuyTokenAddress.balanceOf(address(this));`

**Variable-value intent, ETH side (L210).** `originalETHBalance` is used later (L215) as the "before" snapshot subtracted from the post-call balance to isolate *only the ETH this one `.call` produced*. Because `ethAmount` is already resident in `address(this).balance` by the time L210 executes (it was credited at the top of the transaction, several statements - and one function call - before this line), `originalETHBalance` as currently computed captures *more* than "the contract's balance before this swap's own proceeds arrived" - it also captures the very `ethAmount` about to be spent. The intended value is the balance **excluding** the amount about to be spent on this call: `address(this).balance - ethAmount`.

**Variable-value intent, ERC20 side (L206-209).** Symmetric problem, one function-boundary removed: when a user arbitrages a token against itself (`zrxSellTokenAddress == zrxBuyTokenAddress`, e.g. WBTC->WBTC), the sell-side `amountToSell` of that same token was already transferred into the contract by `swapByQuote` (L128, `safeTransferFrom`) *before* `fillZrxQuote` - and therefore `originalERC20Balance` - is ever computed. `originalERC20Balance` (L206-209) is therefore inflated by exactly `amountToSell` in this scenario, the ERC20-side mirror of the ETH-side problem. The intended value, for this scenario, is `zrxBuyTokenAddress.balanceOf(address(this)) - amountToSell`.

**Statement/line-level intent (both).** Both statements exist to establish a clean "before" baseline so that a later `subOrZero(after, before)` isolates *only* the net-new proceeds of the one `.call` this function performs - matching the doc comment's own "positive... balance change" framing. Neither baseline may include any amount the *caller* is separately responsible for having already deposited into the contract as part of the same transaction (the sell-side ERC20 transfer, or the forwarded `msg.value`).

**Reported erroneous behavior** (H-02, verbatim, primary source `Web3Bugs/reports/44.md`): *"When a user tries to swap unwrapped ETH to ERC20, even if there is a certain amount of ETH refunded, at L215, `ethDelta` will always be `0`. That's because `originalETHBalance` already includes the `msg.value` sent by the caller."* Worked example: contract holds 1 ETH; user swaps 10 ETH to USDC (`originalETHBalance` becomes 11 ETH); if 1 ETH is refunded, new balance is 2 ETH, so `ethDelta = subOrZero(2, 11) = 0` instead of the correct `1`. *"Similarly, `erc20Delta` is also computed wrong. Consider a special case of a user trying to arbitrage from `WBTC` to `WBTC`, the `originalERC20Balance` already includes the input amount, `erc20Delta` will always be much lower than the actual delta amount. For example, for an arb swap from `1 WBTC` to `1.1 WBTC`, the [erc20Delta - the report's own text says "ethDelta" here, an evident copy-paste slip, corrected per the surrounding "erc20Delta" framing and the arithmetic itself, which only makes sense for the ERC20 amounts quoted] will be `0.1 WBTC` while it should be `1.1 WBTC`."*

**Impact** (primary source only, absent from the truncated scattered excerpt): *"User can not get ETH refund for swaps from ETH to ERC20 tokens; Arb swap with the same input and output token will suffer the loss of almost all of their input amount unexpectedly."* Sponsor (`Shadowfiend`) confirmed: *"This doesn't allow explicit stealing by an attacker, but does leak value."* Judge (`0xean`) bumped to High: *"This results in a user losing assets that they will never be able to recover."*

**Recommendation** (primary source only): *"Consider subtracting the input amount from the originalBalance."* Used below as evidence that "subtract the already-deposited input" is the correct general shape of the fix for *both* halves of the finding - not transcribed as annotation syntax (the recommendation gives no code, only this one sentence).

**Bug-relevant intended numeric behavior**:
- ETH side: `originalETHBalance` must equal `address(this).balance - ethAmount` at L210, not the raw, unadjusted `address(this).balance`.
- ERC20 side: `originalERC20Balance` must equal `zrxBuyTokenAddress.balanceOf(address(this)) - amountToSell` when `zrxBuyTokenAddress == zrxSellTokenAddress`, not the raw, unadjusted balance - but see R1-3: `amountToSell` is a value from a *different function* (`swapByQuote`), not visible inside `fillZrxQuote` at all, which turns out to be decisive for expressibility.

## R1-2 — Intent Abstraction

Distinguishing property, both halves (no literal patch code exists to drop - the recommendation is one sentence, not a diff): the "before" balance snapshot must exclude whatever the *caller's own transaction* had already deposited as this swap's input, so that the later `subOrZero(after, before)` isolates only the swap's own net-new proceeds. **Intent-level orientation: Value-centered** for both - a constraint on one local variable's assigned value at one statement (`originalETHBalance` / `originalERC20Balance`), not a state-transition claim (`fillZrxQuote` mutates no persistent state of its own; the ETH/ERC20 that actually move do so via the opaque `.call`, not via any state variable this contract tracks).

## R1-3 — Select the least implementation-specific sufficient relation

Analyzed as **two independent members of the same H-02 finding** (the multi-annotation-set provision), since the report itself frames "wrong calculation of `erc20Delta` **and** `ethDelta`" as one finding with two distinct, separately-worked-out mechanisms (two separate worked examples, one per side) - the same shape of "check whether a second, independently-derived target annotation closes the gap" that governed `web3bugs_29_H_11`/`web3bugs_70_H_04`. Each is run through its own full R1-1-R1-7 below, **not** assumed to succeed together just because they're textually adjacent.

### Member A — ETH side (`originalETHBalance`, L210)

**Preliminary check — can the natural statement of intent even be written?** The natural relation is `originalETHBalance == address(this).balance - ethAmount`. This requires referencing `address(this).balance` as a term inside `intentValue`. **Checked directly against the grammar, not assumed:** `intentValue -> arithExpr -> ... -> arithFactor -> varRef`, and `varRef: identifier subAccess*` (`Parser/Solidity.g4` line 379-381), where `subAccess` is only `'.' identifier` or `'[' expression ']'` (lines 383-386). The *cast* syntax `address(this).balance` begins with the token sequence `address(` - not a bare `identifier` - so it cannot be parsed as a `varRef`; there is no production anywhere in `arithFactor`/`arithExpr` that accepts a parenthesized cast. So far this matches what an initial check would conclude.

**REVIEW CORRECTION (this is the load-bearing error in the original analysis): the bare, uncast form `this.balance` *is* a well-formed `varRef` and *is* reachable from `intentValue` - it was not checked, and the case's central claim ("can never be referenced inside a `@During`/`@Post` relation's own arithmetic") is wrong.** `this` is never declared as a reserved keyword anywhere in `Parser/Solidity.g4` (no `ThisKeyword`/`THIS` token exists among the grammar's keyword literals, `PureKeyword`/`ConstructorKeyword`/etc.) - it lexes as an ordinary `Identifier` (`IdentifierStart IdentifierPart*`, line 734). So `this.balance` parses cleanly as `varRef: identifier subAccess*` with `identifier = "this"` and one `subAccess = '.' 'balance'` (`#IntentMemberAccess`) - exactly the same production every other member-access term in this batch's annotations already uses. This is not merely a syntactic curiosity; it resolves to the *same value* as the source statement's own `address(this).balance`, confirmed by tracing the actual evaluator, not assumed:
- `Analyzer/EnhancedSolidityVisitor.py`'s `visitNormalVarRef` (L1175-1199) builds this as `Expression(identifier="this", context="VarRefBase")` with a chained `Expression(base=..., member="balance", operator=".", context="VarRefMemberAccess")` - the identical `Expression` shape any ordinary `x.y` varRef produces.
- `Analyzer/GuardianVerificationEngine.py`'s `evaluate_guardian_expression` (L42-100) delegates both `"VarRefBase"`/`"VarRefMemberAccess"` (via its `NormalVarRef`/`IntentMemberAccess` branch, L91-94) straight to `self.analyzer.evaluator.evaluate_expression` - i.e. `Interpreter/Semantics/Evaluation.py`, the **same** evaluator that interprets ordinary Solidity source statements (not a separate, annotation-only code path).
- `Evaluation.py`'s `evaluate_identifier_context` (L909, L927) special-cases `ident_str == "this"`, returning the sentinel string `"this"` regardless of whether `"this"` is a declared variable (it isn't).
- `Evaluation.py`'s `evaluate_member_access_context` (L1055-1079, its own comment literally reads "this 키워드 처리 (this.foo(), this.balance, address(this).balance 등)" - "handling the `this` keyword (`this.foo()`, `this.balance`, `address(this).balance`, etc.)") then matches `baseVal == "this"` and `member == "balance"`, and calls `self._get_address_this_balance(variables)` (L2642-2647) - the **same** helper that looks up the `@GlobalVar address(this).balance = ...`-seeded value under the literal key `"address(this).balance"` (the exact key `visitGlobalVarAddressBalance` writes, per the original analysis's own correct observation about that production).

So the cast syntax `address(this).balance` cannot be written inside `intentValue` (that half of the original claim is correct), but the semantically identical `this.balance` can be, and it resolves through the identical `@GlobalVar`-backed lookup - there is **no** unreachable value here, and **no** rescue is needed. (An arithmetic binary-op node like `this.balance - ethAmount`, produced by `visitAddSub`'s generic `"AddSubContext"` Expression, is likewise not one of `evaluate_guardian_expression`'s named branches, but falls through to the same delegation to `evaluator.evaluate_expression`, whose own generic binary-operator fallback - `Evaluation.py` L496-497, "이항 연산자" - recursively calls `self.evaluate_expression` on `expr.left`/`expr.right`, so `this.balance` and `ethAmount` are each independently resolved correctly before the subtraction. Traced end to end, not assumed.)

**This changes the rest of Member A's derivation: no scenario-constant substitution is needed at all.** The relation can reference `this.balance` live, exactly like any other in-scope value:

1. **Directional/inequality (weakest tiers)**: e.g. `originalETHBalance < this.balance - ethAmount`. **Checked and rejected - fails the required negation check**, for the same reason as before: an alternative buggy implementation computing e.g. `originalETHBalance = this.balance - ethAmount - 1 wei` (an off-by-an-arbitrary-amount defect, not the reported "forgot to subtract `ethAmount`" defect at all) would also satisfy the bound and be wrongly accepted as `Satisfied`. Under-discriminating, same reasoning as any case where the intended value is a single exactly-determined quantity, not a range.
2. **Exact equality (SELECTED)**: `originalETHBalance == this.balance - ethAmount` - both operands live, ordinary in-scope references (`this.balance` via the `varRef`/evaluator path just confirmed; `ethAmount` an ordinary parameter). Every alternative wrong-adjustment implementation considered (subtracting a fixed constant instead of `ethAmount`; subtracting half of `ethAmount`; not subtracting at all - the actual bug) fails this equality and is correctly flagged `Violated`; only the intended computation satisfies it. Unlike the withdrawn literal-`B` version, this form is not tied to one constructed scenario's numbers at all - it holds for *any* execution, not just the report's worked `(1 ETH pre-existing, 10 ETH ethAmount)` example (that example remains useful as an illustrative, concrete instantiation for an eventual RQ1-B run, where `this.balance`/`ethAmount` would need concrete `@GlobalVar`/argument seeding to get a non-`Warning` result - but it is no longer required to state the target annotation itself).

**Required negation check, explicit.** Does this equality's negation catch a plausible *different* implementation that still retains the reported "originalETHBalance already includes msg.value" defect but produces it differently - e.g. one that captures `originalETHBalance` *after* an unrelated intervening statement, or that forgets the subtraction only in a nested branch? Any implementation whose L210-equivalent statement does not compute exactly `(pre-call balance) - ethAmount` is caught, regardless of surface syntax, because the relation is checked against the *value* `originalETHBalance` ends up holding at that program point, not against the statement's literal form. **No gap found for this member's own mechanism.**

**Winner: exact equality, Member A.**

### Member B — ERC20 side (`originalERC20Balance`, L206-209)

**Preliminary check — can the natural statement of intent be written at all?** The natural relation is `originalERC20Balance == zrxBuyTokenAddress.balanceOf(address(this)) - amountToSell` (scoped to the `zrxBuyTokenAddress == zrxSellTokenAddress` self-arb scenario the report's own worked example uses). Two independent blockers, checked in turn:

1. **`zrxBuyTokenAddress.balanceOf(address(this))` is a function call inside `intentValue`.** Unlike `address(this).balance`, there is **no dedicated grammar production of any kind** for an arbitrary ERC20 `balanceOf` call - `visitGlobalVarAddressBalance` (above) explicitly restricts its one supported form to `address(this).balance` only (`if addr_identifier != "this": raise ValueError(...)` is the *address* argument check; the member is hard-coded to `.balance`, there is no analogous `.balanceOf(...)`-shaped debug-annotation production for any ERC20 token at all). Checked against both rescues: the **known-bound rescue** doesn't apply (no protocol-enforced minimum/fixed value for an arbitrary buy token's balance exists anywhere in this contract); the **exact-formula-inlining rescue** doesn't apply either (`balanceOf` reads another contract's own storage - condition (a) of the rescue, "deterministic given in-scope arguments plus only contract-lifetime-fixed constants, no other state read," fails outright: an ERC20's balance mapping is exactly the kind of external, mutable state the rescue's own text excludes). **This is `alpha`, with no rescue.**
2. **Independent of (1), `amountToSell` is not referenceable inside `fillZrxQuote` at all.** `amountToSell` is a *parameter of `swapByQuote`* (L108), a different function; `fillZrxQuote`'s own signature (`IERC20 zrxBuyTokenAddress, address payable zrxTo, bytes calldata zrxData, uint256 ethAmount`) has no analogous "sell amount" parameter, and nothing in `fillZrxQuote`'s body ever reads or derives it. **Checked (review-corrected framing) whether Member A's `this.balance`-style path rescues this too - it does not**: `this.balance` resolves the way it does specifically because the evaluator (`Evaluation.py`'s `evaluate_identifier_context`) special-cases the *literal identifier `"this"`* as a sentinel, independent of `variables`/scope lookup, then routes its `.balance` member access to the `@GlobalVar`-seeded `"address(this).balance"` key - a mechanism that exists *only* for `this`/global environment values (`msg`, `tx`, `block`, `this`), not a general "pin any name to a debug value" facility. `amountToSell` is an ordinary function parameter with no such sentinel treatment anywhere in the evaluator, and it belongs to a *different function's* scope besides - there is no debug-annotation form (`@StateVar`/`@LocalVar`/`@GlobalVar`) that pins a value for a name not in the current function's own variable environment, and no `"this"`-style special-cased identifier for it either. **This is `beta`.**

**Checked whether re-scoping the relation to `swapByQuote` (where `amountToSell` *is* in scope) rescues Member B.** `swapByQuote` does have `amountToSell`, `zrxSellTokenAddress`, `zrxBuyTokenAddress` in scope, and receives `fillZrxQuote`'s return values as `boughtERC20Amount`/`boughtETHAmount` (L135). But `originalERC20Balance` and the post-call `zrxBuyTokenAddress.balanceOf(address(this))` are **both** internal to `fillZrxQuote` and never exposed across the function boundary (only the already-computed, already-buggy `erc20Delta`/`ethDelta` tuple crosses it) - so at `swapByQuote`'s scope there is no independent, already-materialized "true bought amount" to compare `boughtERC20Amount` against; constructing one would require calling `zrxBuyTokenAddress.balanceOf(address(this))` a second time from *within the annotation*, which is the same alpha blocker as (1), now with no rescue available at this scope either (the balance-before-the-`fillZrxQuote`-call value is also a call result, and is not deterministic/formula-derivable - it depends on prior transaction history). **Re-scoping does not rescue Member B - confirmed `alpha_and_beta` regardless of which function the relation is attached to.**

**Outcome for Member B: no candidate relation of any tier (directional, inequality, or equality) can even be constructed** - the alternatives-tier procedure does not reach the point of comparing candidates, since the first step (state a distinguishing relation using in-scope values) already fails for both operands the correction needs. Recorded in §7 as a single blocked row rather than a populated alternatives table.

**Considered and rejected (second review pass): scenario-constant substitution of the entire RHS.** A candidate of the form `@During originalERC20Balance == <literal>` (fixing a constructed pre-existing-balance and `amountToSell`, then writing the resulting arithmetic difference as a bare number) was proposed and checked against precedent, not adopted by assumption. Contrast `web3bugs_16_H_06` (`GasOracle`, folder `19`), where an analogous-looking scenario-fixed constant (`oracle.decimals()`, itself an uncalled, un-rescuable value in the buggy code) *is* legitimately substituted - but there, the constant only fixes a *supporting/parametric* term (a scaling exponent), and the resulting relation still relates three other, still-live, in-scope values (`result`, `gasPrice`, `ethPrice`) to each other; its discriminating power survives independently of which concrete `gasPrice`/`ethPrice` execute. Member B's proposed literal-RHS form has no such surviving structure: eliminating `balanceOf(...)` and `amountToSell` leaves nothing else observable in the relation at all - it collapses to `lvalue == literal`, with the literal standing in for the very quantity whose unavailability constitutes the alpha/beta blocker itself. Also checked against `web3bugs_59_H_05` (README §1) - a same-project precedent with the identical shape (another contract's own opaque state, no in-scope proxy) - which was *not* rescued this way and remains `alpha`-tagged. Generalizing the collapse-to-literal move here would make it available to any alpha/beta case in the dataset (construct some scenario, assert the number the intended formula would have produced), which would make the alpha/beta tags non-discriminating as a classification - so it is not applied here. **Member B's Inexpressible/`alpha_and_beta` verdict stands.**

**Is this a genuine multi-relation-set case?** Checked, not assumed: the combining rule requires "each mechanism, run through its own full R1-1-R1-7 pass, is independently Expressible=Yes." Member B fails R1-7 (below) - so, per the rule's own text, **the target annotation set cannot include Member B**; only Member A qualifies. This is a different outcome from `29_H_11`'s two-member set (both members there passed independently) and from `70_H_04`'s two-member set (same) - this case's multi-mechanism check was performed with the same rigor but returns an asymmetric result, which is itself methodologically informative (see Intent coverage in the Summary).

## R1-4 — During vs Post

**Member A: During, selected.** `originalETHBalance`'s value is a statement-time local, defined once at L210 and never reassigned; the relation's subject is exactly "the value this one assignment produces," matching the During criterion ("a statement-time value") directly - not chosen merely because the defect is a single-statement omission. **Post considered and rejected**: `originalETHBalance` is neither `fillZrxQuote`'s return value (the returns are `erc20Delta`/`ethDelta`, computed later from it) nor persistent state, so Post's own listed criteria (function exit, return value, persistent-state transition) do not describe this relation's actual subject; attaching at function exit would add no semantic difference (the value is already settled at L210) while obscuring that the checked quantity is an intermediate, not the function's own output.

**Required explicit loop-body/`delta` check.** `fillZrxQuote` contains **no loop of any kind** - confirmed by reading the full function body (L200-225: two conditional balance reads, one external call, one `require`, one more conditional balance read, one `return`). The only loop anywhere in `Swap.sol` is `sweepFees`'s `for` loop (L250-256), an unrelated function, not part of this finding. **Delta does not apply, trivially** - there is no loop to even consider.

**Member B**: moot (Inexpressible at R1-3 already; no candidate relation exists to assign a scope to). For completeness: had a relation existed, it would face the identical "no loop in `fillZrxQuote`" fact, so delta would not have been the blocker regardless.

## R1-5 — Relation form

## R1-6 — Construct the target annotation

**Attachment point, Member A: inline with L210** (`uint256 originalETHBalance = address(this).balance;`), following the same inline-During convention used elsewhere in this batch (a `@During` checking the very statement it's about attaches inline, sharing that statement's line - precedent: `web3bugs_101_H_01`, `web3bugs_29_H_11`'s two members) rather than as a standalone following line.

All referenced identifiers are in scope at L210: `originalETHBalance` is the statement's own freshly-assigned local; `ethAmount` is a function parameter, in scope throughout the function body; `this.balance` is a live `varRef` reachable at any program point (R1-3, review-corrected), not scenario-substituted.

**REVIEW CORRECTION: no concrete constant is needed.** The original pass derived a literal `B = 11 x 10^18` (wei) to stand in for `address(this).balance`, believing the value was otherwise unreferenceable inside `intentValue`. Per the R1-3 correction, `this.balance` is directly referenceable, so the target relation uses it live instead of a hard-coded literal. The report's worked numbers (`1 ETH` pre-existing + `10 ETH` `ethAmount`) remain useful only as an illustrative instantiation for an eventual RQ1-B run (where `this.balance` would need a concrete `@GlobalVar address(this).balance = [11000000000000000000, 11000000000000000000]` seed to get a non-`Warning`, non-⊤ result) - not as something the target annotation itself needs to encode.

**Target annotation (Member A, the case's actual target annotation - Member B is not part of the set, see R1-3/R1-7):**
```solidity
uint256 originalETHBalance = address(this).balance;  // @During originalETHBalance == this.balance - ethAmount
```

**Quantification note**: not applicable. `originalETHBalance`/`ethAmount` are ordinary scalar locals/parameters of a single call, not elements of a collection the annotation ranges over (contrast `web3bugs_83_H_01`'s `poolInfo[1]`).

**Precondition, stated explicitly (scenario-conditioning)**: unlike the withdrawn literal-`B` version, this relation is **not** scenario-conditioned as stated - `originalETHBalance == this.balance - ethAmount` holds for any execution reaching L210, since both sides are live references to the same program state. (A concrete *run* of this annotation through the engine would still need concrete values for `this.balance`/`ethAmount` to resolve to something other than `Warning`/⊤ - that is an RQ1-B execution concern, deferred, not a limitation of the relation's own generality.)

## Third Review Pass — Finding-level completeness rule adopted; case-level verdict revised from Yes to No

This case is the one that prompted README §4/R1-3's finding-level completeness rule (added this session). The underlying facts above are **unchanged** — Member A remains independently Expressible=Yes with a genuine, sound relation; Member B remains independently Expressible=No (`alpha_and_beta`); the gap between them remains non-closable, exactly as the Second Review Pass established. What changed is **how the case-level (finding-level) verdict is derived from those two facts**.

**Prior framing** (superseded, both original and this file's own history above): "Expressible: Yes, for Member A only," with the finding's incomplete coverage of the full reported defect recorded as a separate `Intent coverage: Partial (non-closable)` flag alongside the Yes verdict.

**Why this was revised.** On review of this case together with the rest of the 35-case batch, three considerations argued for retiring the separate `Intent coverage` field and folding its information directly into the Expressible verdict instead: (1) by the time of this review, every *other* case in the batch that had ever carried a `Partial` coverage flag had been resolved to `Full` — either by the snapshot-qualified-reference grammar extension (`05_web3bugs_42_H_01`, `07_web3bugs_35_H_11`, `09_web3bugs_52_H_34`) or by a second independently-derived member closing the gap (`12_web3bugs_70_H_04`, `21_web3bugs_29_H_11`) — leaving this case as the sole standing exception, and a field that varies on exactly one case out of thirty-five carries little independent information as a *separate axis*; (2) unlike those other cases, this case's gap is structurally different in kind — it is not a single relation with a disclosed weakness that a second relation could close, it is a report with two independently-reportable mechanisms where one is *categorically* Inexpressible, which is precisely the situation README §4's multi-annotation-set provision was already written to handle for the *all-succeed* branch (`70_H_04`, `29_H_11`, both closed to Full) but had never addressed for the *mixed-result* branch; (3) reporting "Expressible: Yes" for a finding where a full third of its independently-reported numeric mechanisms cannot be represented risks overstating what the intent language actually captures for this finding, in a way a bare Yes/No split does not once the completeness rule is stated precisely (§4) — a strictly more conservative standard than the retired field implied, consistent with this project's general preference for not inflating a headline success metric.

**What is preserved, not lost.** Nothing about Member A's derivation, Member B's blockers, or the non-closability finding was altered by this revision — every fact re-verified in the First and Second Review Passes above stands exactly as re-confirmed there. Member A's relation remains a real, sound, independently-checkable annotation for the ETH-side mechanism; it is simply no longer sufficient, on its own, to mark *this finding* Expressible for RQ1 purposes. See the Summary section above for the current (finding-level) verdict and both members' individual outcomes.

**Consistency check performed**: before adopting this rule, the other 34 cases in the batch were swept for any other instance of a multi-mechanism report where only some members were pursued, to confirm this rule does not silently change any other case's verdict. Every other multi-member case in the batch (`web3bugs_70_H_04`, `web3bugs_29_H_11`, `web3bugs_35_H_08`, `web3bugs_29_H_08`, `web3bugs_35_H_12`, `web3bugs_112_H_01`, `web3bugs_70_H_09`) already has *every* required member's own outcome agreeing (all-Yes or all-No), so the rule reproduces each of their existing verdicts unchanged; this case remains the sole mixed-result instance in the dataset.
