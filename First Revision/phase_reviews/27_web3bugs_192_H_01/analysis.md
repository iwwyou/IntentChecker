## R1-1 — Reported Behavior Reconstruction

**Contract/function role.** `Lock` is Tigris Trade's bond-locking front-end: users lock a whitelisted `tigAsset` for `_period` days via `lock()`, receiving a bond NFT (minted by the separate `BondNFT` contract, which owns the actual per-bond accounting: principal, shares, expiry). `Lock.sol` itself keeps one piece of aggregate bookkeeping per asset — `totalLocked[address]` (state, line 19) — which exists solely to make `release()`'s underflow-checked subtraction (`totalLocked[asset] -= lockAmount;`, line 103) a meaningful sanity/accounting invariant: at all times, `totalLocked[_asset]` must equal the sum of every not-yet-released bond's currently-locked principal in that asset, since `release()` unconditionally subtracts a released bond's full locked amount from it. `extendLock()` (lines 84–92) is the second of two ways a user can increase how much of an asset is locked: it resets a bond's expiry and/or adds more principal (`_amount`) to an *existing* bond, as an alternative to creating a brand-new one via `lock()`.

**Relevant locals/state (within `extendLock`, lines 84–92):**
- `_asset` (local, line 89) = `claim(_id)` — a same-contract call that (a) distributes any pending gov-NFT rewards contract-wide (`claimGovFees()`, called internally), (b) claims bond `_id`'s own pending reward via `bondNFT.claim(_id, msg.sender)`, transferring it to the caller, and (c) returns the bond's `tigAsset` address. `_asset` is therefore the exact asset type of the bond being extended — read directly off `claim`'s own body (lines 34–41), not inferred.
- `_amount` (parameter) — the additional tigAsset principal the caller wants to add to the bond, per the function's own NatSpec (`@param _amount tigAsset amount being added`).
- `totalLocked[_asset]` (state, mapping `address => uint`, line 19) — the contract-wide running total for this asset. **Not referenced anywhere in `extendLock`'s body at all** — this absence is the entire defect.
- **The disputed statements — an entire missing statement, not a wrong existing one** (lines 89–91):
  ```solidity
  address _asset = claim(_id);
  IERC20(_asset).transferFrom(msg.sender, address(this), _amount);
  bondNFT.extendLock(_id, _asset, _amount, _period, msg.sender);
  ```
  Line 90 pulls `_amount` of `_asset` into the contract's custody exactly as `lock()`'s own line 72 does. Line 91 tells `BondNFT` to grow the bond's own `bond.amount` by `_amount` (confirmed directly from `BondNFT.sol`'s `extendLock`, line 117: `_bond.amount += _amount;`). Unlike `lock()` — which follows its own analogous `transferFrom` (line 72) with `totalLocked[_asset] += _amount;` (line 73) *before* calling `bondNFT.createLock(...)` (line 75) — `extendLock` has **no statement anywhere in its body that writes `totalLocked`**. This was confirmed by reading `extendLock`'s complete body (all three statements, lines 89–91) and the rest of `Lock.sol` (`totalLocked` is written only at line 73, inside `lock()`, and read/decremented only at line 103, inside `release()`).

**What `BondNFT.release()` returns, and why that makes the drift fatal, not merely cosmetic** (`Dataset/Web3Bugs/S3_1/contest_192_H_01/BondNFT.sol`, lines 137–159, read directly rather than assumed from the interface): `release()` returns `lockAmount = bond.amount` (line 155) — `bond.amount` being `BondNFT`'s own per-bond principal field, which *does* correctly accumulate every `_amount` ever added via either `createLock` (initial) or `extendLock` (line 117, `_bond.amount += _amount;`). So by the time a bond that has been extended is released, `Lock.release()`'s line 103 (`totalLocked[asset] -= lockAmount;`) subtracts the *full, extension-inclusive* principal from a `totalLocked[asset]` that only ever recorded the *original* (`lock()`-time) principal — an unconditional underflow (Solidity ≥0.8, no `unchecked` block at that line) once `lockAmount` exceeds the under-tracked `totalLocked[asset]`, reverting the entire `release()` call.

**Reported erroneous behavior** (H-01, verbatim, primary source `Web3Bugs/reports/192.md`): *"The issue is that the `Lock.extendLock` function does not increase the value in `totalLocked[_asset]`. This however is necessary because `totalLocked[_asset]` is reduced when `Lock.release` is called. Therefore only the amount of assets deposited via `Lock.lock` can be released again. The amount of assets deposited using `Lock.extendLock` can never be released again because reducing `totalLocked[_asset]` will cause a revert due to underflow. So the amount of assets deposited using `Lock.extendLock` is lost."*

**Proof of Concept** (verbatim numbers, primary source only — absent from the truncated scattered file): user locks `amount1 = 100` (tigAsset) for 9 days via `lock()`; then calls `extendLock` adding `amount2 = 10` more; after the bond expires, `release()` is called and reverts on `totalLocked[asset] -= lockAmount;` because `totalLocked[asset]` only ever reached `100`, not `110`. This concrete scenario is used directly below (R1-3) rather than an independently constructed one, since the report supplies real numbers.

**Recommended Mitigation Steps** (verbatim, primary source only): *"Add `totalLocked[_asset] += amount` to the `Lock.extendLock` function."* Sponsor (`TriHaz`) confirmed; judge (`Alex the Entreprenerd`) agreed on High severity (*"an issue with accounting that will cause principal deposits added via `extendLock` to be lost"*); sponsor later linked a mitigation PR.

**Expected/intended behavior**: `extendLock` must increment `totalLocked[_asset]` by exactly `_amount`, mirroring `lock()`'s own convention (line 73) — the missing statement is, verbatim, `totalLocked[_asset] += _amount;`, and its natural insertion point (matching `lock()`'s own statement ordering: transfer-in, then account, then notify `bondNFT`) is between line 90 (`transferFrom`) and line 91 (`bondNFT.extendLock`).

**Patch intent**: the recommendation is a literal one-line addition, syntactically identical to `lock()`'s own already-present line 73. Used below as R1-1 evidence only (§2/§3) — R1-2/R1-3 derive the target relation from `lock()`'s in-file convention and `BondNFT.sol`'s own confirmed semantics for what "the correct increment" must equal, not by transcribing the recommendation's literal syntax uncritically.

**Bug-relevant intended numeric behavior**: across any single `extendLock(_id, _amount, _period)` call, `totalLocked[_asset]` (for the bond's own asset) must increase by exactly `_amount`; the current code leaves it completely unchanged, regardless of `_amount`.

## R1-3 — Select the least implementation-specific sufficient relation

**Preliminary check — does this relation need a function call inside `intentValue`?** No. The relation's operands are `totalLocked[_asset]` (a state mapping), `_asset` (a local, already fully materialized by the time any post-entry point is reached — the value returned by `claim(_id)`, referenced opaquely, exactly as `29_H_11` referenced `balance0`/`balance1`), and `_amount` (a parameter). No call appears anywhere in the candidate relation itself.

1. **Directional (weakest tier)**: `totalLocked[_asset](Entry) < totalLocked[_asset](Exit)` (strict increase). **Considered, and this is the exact form README's own R1-4 precedent (`SwordCrowdsale`'s `weiRaised(Entry) > weiRaised(Exit)`, for the mirror-image missing-decrement bug) uses for this identical bug *pattern* — but rejected here on the required negation check below**, not out of habit.
   - **Discriminates the reported bug**: buggy code leaves `totalLocked[_asset]` completely unchanged (`Entry == Exit`), so `Entry < Exit` is false → Violated. Intended code (`_amount = 10 > 0`, per the report's own PoC) increases it → `Entry < Exit` true → Satisfied.
   - **Required negation check (§3/R1-3), performed explicitly**: does this relation's negation fail to catch some alternative implementation that retains the reported defect (an accounting drift between `totalLocked[_asset]` and the bond's true, extension-inclusive principal) but produces it differently? **Yes, it fails to catch one.** Consider a hypothetical implementation that adds only *part* of `_amount` — e.g. `totalLocked[_asset] += _amount / 2;` (a differently-shaped bug: partial, not zero, credit). Using the report's own PoC numbers (`Entry = 100`, `_amount = 10`): this alternative yields `Exit = 105`. `100 < 105` is **true** → the directional relation would incorrectly report Satisfied, even though the accounting drift (and the eventual `release()` underflow, once enough such partial-credit extensions accumulate) is still present. **Rejected** on this concrete, arithmetic-verified gap — the intended increment is not naturally a bound; it is a single, exactly-determined quantity (mirrors `lock()`'s own `+= _amount` verbatim), so weakening past equality loses real discriminating power, per README's explicit caution against treating operator strength as free.
2. **Inequality lower bound tied to the correct amount**: `totalLocked[_asset](Exit) >= totalLocked[_asset](Entry) + _amount`. **Rejected for the same reason as (1)** — this is strictly *more* implementation-specific than (1) (it names `_amount` explicitly) yet still fails to reject an alternative that *over*-credits (e.g., double-counts `_amount` due to a hypothetical re-entrant or duplicated call) while still retaining a real accounting-drift defect relative to `BondNFT`'s own `bond.amount` growth of exactly `_amount`. No net benefit over (1) and still an incomplete discriminator.
3. **Exact equality (SELECTED)**: `totalLocked[_asset](Exit) == totalLocked[_asset](Entry) + _amount`. Ties the increment to the one value R1-1 establishes (via direct inspection of `BondNFT.sol`'s own `_bond.amount += _amount;`) as the *exact* correct amount — not an approximation of it. Every operand is a pre-existing, semantically meaningful, in-scope value (the state mapping itself, a parameter, and — as an index — an already-materialized local); no synthetic constant.

**Required negation check, re-run against the selected equality (§3, mandatory)**: does the equality's negation fail to catch some alternative implementation that retains the reported "totalLocked doesn't track the true locked principal" defect but produces it differently?
- **No increment at all (the actual buggy code)**: `100 == 110`? False → Violated. Caught.
- **Partial credit** (`+= _amount/2`): `105 == 110`? False → Violated. Caught — this is exactly the alternative the directional/bound candidates above missed.
- **Over-credit** (e.g., a duplicated/double-counted increment, `+= _amount` applied twice): `120 == 110`? False → Violated. Caught.
- **Wrong-key credit** (a hypothetical implementation that increments `totalLocked[someOtherAsset]` instead of `totalLocked[_asset]`, e.g. a copy-paste of a different asset's handling): `totalLocked[_asset]` itself stays at `100`; `100 == 110`? False → Violated. Caught — a variant `29_H_11`-style "right operation, wrong operand" defect that a relation checking only "*some* `totalLocked[*]` entry changed" would miss, but this relation (fixed to the specific key `_asset`) does not.
- **Both fixed (intended)**: `110 == 110` → true → Satisfied.

No gap found. **Winner: Alternative 3 (exact equality).** This case does not need `Intent coverage: Partial` on R1-3's required-check ground (see Summary — Full).

## R1-4 — During vs Post

**Selected scope: Post.** The relation is exactly README's own listed Post criterion: "the relation concerns... final state, a persistent state transition, a function-level invariant" — `totalLocked[_asset]`'s entry-vs-exit delta across the *whole* `extendLock` call, not an intermediate expression or a single statement's before/after pairing (there is, in the buggy code, no single statement at all that produces the missing effect — see the During-alternative discussion below for why that rules out a `@During` construction here). **Directly matches this project's own already-published precedent for the identical bug pattern**: README §4/R1-4 cites `SwordCrowdsale`'s `refundMoney` (missing `weiRaised -= amount`) and `CDP.update` (missing `totalCredit += delta`) — both single-statement-shaped omissions that "ended up as Post with a directional Entry/Exit relation, not During-equality." This case is structurally the mirror image of `SwordCrowdsale` (missing *increment* rather than missing *decrement*), on the same kind of aggregate-accounting state variable — confirmed directly against the actual published case file, `evaluation/RQ1/cases/greedy_contract/SwordCrowdsale.json` (`"expr": "weiRaised(Entry) > weiRaised(Exit)"`), not merely inferred from the README's prose description.

**Why not `@During`, considered and rejected on a concrete construction ground (not a style preference).** A `@During (Before)/(After)` pairing (the mechanism `29_H_11`/`35_H_11` use for a same-statement self-reference) requires an *existing* statement in **both** the buggy and the intended code to attach to, so that `before_envs[line_no]` and the post-statement environment bracket the one effect being checked (as `29_H_11`'s `amount1 += _getAmountOut(...)` inline During does). **The buggy code has no such statement at all** — the entire increment operation is absent, not present-but-wrong. Attaching a *standalone* `@During` to an existing neighboring statement (e.g. line 91, `bondNFT.extendLock(...)`) does not help: that statement does not itself write `totalLocked` in either the buggy or the intended code (the fix's natural insertion point, mirroring `lock()`, is *before* line 91, between lines 90 and 91), so a Before/After pairing anchored on line 91 would show no change in either version and would not discriminate. A function-spanning Entry/Exit comparison — i.e., `@Post` — is the only scope that correctly brackets "the whole function's net effect on this state variable," independent of exactly which (possibly entirely absent) statement inside it is responsible.

**Required explicit delta-exception check (README §4/R1-7, mandatory per task instructions).** `extendLock` itself contains **no loop of any kind** — confirmed by reading its complete 3-statement body (lines 89–91). The call chain it reaches (`claim(_id)` → `claimGovFees()`) *does* contain a `for` loop (`claimGovFees`, lines 113–119, iterating `bondNFT.getAssets()`), but per the delta scope note (README §4): the question is whether **the reported defect's own value — here, `totalLocked[_asset]`'s entry-to-exit delta, and the (missing) statement that should produce it — is itself computed at a CFG node inside a loop body**. It is not: `totalLocked[_asset]` is never read or written inside `claimGovFees`'s loop at all (confirmed directly — that loop only touches `assets[i]`-keyed balances/approvals/`bondNFT.distribute` calls, never `Lock.sol`'s own `totalLocked` mapping), and the relation's own attachment point (`extendLock`'s function-level Entry/Exit) sits entirely outside that loop, two call-hops away, exactly the same structural situation `3_H_04` and `29_H_11` each confirmed did not trigger delta (a loop that exists elsewhere, in a called function, with no bearing on the annotation's own attachment point or the specific value it constrains). **Delta confirmed not applicable.**

## R1-6 — Construct the target annotation

**Attachment point**: `@Post` on `extendLock`, placed as a comment immediately after line 91 (`bondNFT.extendLock(...)`), the function's last statement — textual-placement convention matching this batch's other `@Post` cases (e.g. `3_H_04`, `16_H_06`); semantically evaluated at `σ_exit` regardless of exact placement.

**Target annotation**:
```solidity
function extendLock(
    uint _id,
    uint _amount,
    uint _period
) public {
    address _asset = claim(_id);
    IERC20(_asset).transferFrom(msg.sender, address(this), _amount);
    bondNFT.extendLock(_id, _asset, _amount, _period, msg.sender);
    // @Post totalLocked[_asset] == totalLocked[_asset](Entry) + _amount
}
```

**Values in scope**: `totalLocked` is a contract state variable, always in scope; `_asset` is a local, declared at line 89 and never reassigned, so it is settled and in scope at function exit; `_amount` is a parameter, in scope throughout. All three are ordinary `varRef`s at `σ_exit`.

**A source-verified engine detail worth recording precisely (not merely assumed), though it is an RQ1-B/build concern, not an R1-7 blocker (see R1-7's explicit scoping note below).** `Analyzer/GuardianVerificationEngine.py`'s `_evaluate_snapshot_var_ref` (`VarRefAtEntry` branch, lines 212–216) evaluates the **entire** inner expression — including any index sub-expression — against `target_env = fn_cfg.entry_env`, not just the outermost identifier. Since `_asset` is a mid-function local (not a parameter, not a state variable), `totalLocked[_asset](Entry)` requires `_asset` to itself be resolvable *within* `entry_env` for the index lookup to succeed. Traced directly: `fcfg.entry_env = VariableEnv.copy_variables(fcfg.related_variables)` (`Interpreter/Engine.py` line 749), and `related_variables` is exactly the dict that `@LocalVar`/`@StateVar` debug annotations write into (`Analyzer/ContractAnalyzer.py`'s `process_local_var_for_debug`/`process_state_var_for_debug`, both calling `apply_debug_directive_enhanced(..., variables=self.current_target_function_cfg.related_variables, ...)`). **Conclusion**: this is not a gap — it is a concrete, standard build requirement, no different in kind from every other case in this batch that pins a call-derived local via a debug annotation (`3_H_04`'s `cumulativeYield`, `29_H_11`'s `balance0`/`balance1`): the RQ1-B build for this case must include a `@LocalVar _asset = <the extended bond's tigAsset address>` debug annotation (alongside `@StateVar totalLocked[<that address>] = ...`, `@LocalVar _amount = ...`, etc.) so that `entry_env` — and therefore `totalLocked[_asset](Entry)` — resolves correctly. Recorded here in full because it was source-verified this session for this exact snapshot-qualifier-on-a-mapping-index combination (not previously exercised by `3_H_04`/`16_H_06`/`29_H_11`, none of which qualify a *mapping index that is itself a local* with `(Entry)`), not because it changes the Expressible verdict.

**Quantification note**: **Not applicable.** `_asset` is the one specific asset of the one specific bond (`_id`) the call operates on — a function parameter-derived value, not a representative element chosen out of many co-existing candidates in a collection the annotation itself has to range over (contrast `web3bugs_83_H_01`'s `poolInfo[1]`). The relation's subject (`totalLocked[_asset]`) is exactly analogous to `3_H_04`'s per-`(issuer, holder)` bond scoping — the function's own natural single-asset parameterization, not a chosen instantiation.

**Preconditions, stated explicitly (README §4's scenario-conditioning note):**
1. **`_amount > 0` for discrimination** (not for the relation's own validity — it holds, trivially, on both buggy and intended code when `_amount = 0`, since a zero-principal extend, per the function's own NatSpec, "extends the period and/or amount," is a legitimate call). The report's own PoC (`_amount = 10`) is used directly.
2. **No reentrant callback into `Lock.lock()`/`Lock.release()` during `extendLock`'s external calls** (`transferFrom`, `bondNFT.claim`/`extendLock`, `IGovNFT.claim` inside `claimGovFees`). `totalLocked` can only be written by `Lock.sol`'s own `lock()`/`release()`, and neither `extendLock` nor anything it calls carries a reentrancy guard — a malicious `_asset` token or a malicious `govNFT` could in principle reenter `lock()`/`release()` mid-call and change `totalLocked[_asset]` for reasons unrelated to this relation. This is a standard, unstated-but-necessary assumption for any Entry/Exit invariant that spans external calls (not specific to this case), stated explicitly per README's discipline of naming preconditions rather than leaving them implicit.
3. **`claim(_id)` (and everything it calls) does not itself write `totalLocked`** — confirmed directly (R1-1/RQ2-A below), not assumed; this is what makes the Entry snapshot of `totalLocked[_asset]` correctly represent "before this function's own (missing) increment" rather than being corrupted by an intervening side effect from the reward-claim step that runs first.

## R1-7 — Expressibility decision

**Values referenceable at a legal program point**: Yes. `totalLocked` (state), `_asset` (local, settled from line 89 onward), and `_amount` (parameter) are all ordinary in-scope `varRef`s at `extendLock`'s exit. No function call inside `intentValue` — `_asset` is referenced as an already-materialized opaque value (exactly as `29_H_11` referenced `balance0`/`balance1`), not by re-invoking `claim(_id)`.

**Arithmetic/logical relation representable**: Yes. `totalLocked[_asset](Entry) + _amount` is ordinary `arithAdd` over a snapshot-qualified indexed `varRef` and a plain `varRef`; `totalLocked[_asset] == ...` is the grammar's `RelationalCmp` common form. The mapping-index construction (`identifier '[' expression ']'`, `#IntentIndexAccess`) composing with the `(Entry)` snapshot qualifier (`varRef '(' ENTRY ')'`) is syntactically ordinary — `varRef` is defined as `identifier subAccess*`, and the `(Entry)` production wraps the *whole* `varRef`, so `totalLocked[_asset](Entry)` parses as a single, well-formed `arithFactor`.

**Observation point supported**: Yes — `@Post`, evaluated at `extendLock`'s exit, which is not inside any loop (R1-4's explicit delta check: `extendLock` itself contains no loop; the loop reachable via `claim(_id)` → `claimGovFees()` neither touches `totalLocked` nor contains this annotation's own attachment point). **Delta confirmed not applicable**, per the explicit check in R1-4.

**A genuine engine-mechanics detail was identified and recorded (R1-6) rather than glossed over — but per README's explicit R1-7 scoping rule ("do not consider... whether the engine can validate it"), it is not treated as a blocker here.** The finding (evaluating `totalLocked[_asset](Entry)` requires `_asset` to be resolvable within `entry_env`, which in turn requires an RQ1-B-time `@LocalVar _asset = ...` debug annotation) is about **whether the engine will successfully evaluate** the already-well-formed, already-in-scope relation at validation time — not about whether `_asset`/`totalLocked` are referenceable in the ordinary Solidity-scoping sense used by R1-7 (they manifestly are). This is the same category of caution `3_H_04` (call-return propagation through a loop-containing callee) and `29_H_11` (the confirmed `abi.decode` crash) recorded for their own cases without it overriding their Expressible=Yes verdicts — flagged below for RQ1-B, not folded into this decision.

**Outcome: Expressible = YES.**

## §5 — Value/Algorithm and Usable/Unusable

- **Algorithm-level**: per the paper's own classification (Algorithm-level = "operation ordering, an absent state update, or a missing procedure call"), this is the textbook case — `extendLock`'s intended computation is (1) resolve the bond's asset, (2) pull in `_amount` more tokens, (3) **account for the increase in `totalLocked`**, (4) notify `BondNFT` of the extension; the actual code has (1), (2), (4) only. Step (3) — an entire statement, not a wrong operand within one — is completely absent, mirroring `lock()`'s own presence of the analogous step (line 73) exactly. This is a cleaner instance of "absent state update" than `16_H_06`'s (there, a missing *normalization* stage inside an otherwise-single formula; here, a missing *statement* in an otherwise-linear three-statement function, immediately adjacent to where it belongs) — not a wrong/extra operator inside an existing expression (contrast `3_H_04`'s Value-level "extra `+ bond.amount` term," or `29_H_11`'s Value-level swapped-identifier argument).
- **Usable**: every value the relation needs (`totalLocked`, `_asset`, `_amount`) is referenceable, in-scope, at the annotation's program point. No representational gap, no semantic-unit/type distinction to preserve (this is a plain token-amount accounting fact, not a units/share-vs-amount distinction of the kind README §5 discusses for `29_H_08`). The one representational subtlety identified (§R1-6/R1-7's `entry_env`/`@LocalVar` finding) is an engine-evaluation concern, not a referenceability concern — `_asset` *is* referenceable as an ordinary local; whether the engine's debug-scenario setup remembers to pin it is a build-process fact, addressed and resolved above, not a §5 Usable/Unusable question.

## RQ2-A — Specification Requirements profile

**Relevant statements** (within `extendLock` itself; the call to `claim`/`bondNFT.extendLock` is treated atomically per README §6 — see "Additional functions/contracts required" below):
