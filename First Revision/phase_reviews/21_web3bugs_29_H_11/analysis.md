## R1-1 — Reported Behavior Reconstruction

**Contract role** (brief — clarifies why "reserve" and "balance" are two distinct quantities here, which the whole bug turns on): `ConstantProductPool` is Trident's Uniswap-v2-style constant-product AMM pool. It tracks two *cached* reserve figures (`reserve0`, `reserve1`, state, `uint112`) that are synced to the pool's actual Bento-share balances only when `_update(...)` runs (at the end of `mint`/`burn`/`burnSingle`/`swap`/`flashSwap`). Between syncs, the pool's *actual* current balance (queryable live via `_balance()`, which calls Bento's `balanceOf`) can exceed the cached reserve — e.g. if tokens are donated directly to the pool, or a prior step in the same call already changed the balance without yet calling `_update`. The report's own framing ("For a burn, usually the reserve should equal the balance, however if any new tokens are sent to the contract and balance > reserve...") is exactly this reserve/balance drift.

**Function role**: `burnSingle` lets an LP burn pool (LP) tokens and receive a *single* output token. Per the function's own doc comment and the report's first sentence, it is conceptually "`burn` followed by a `swap`, in one call": first compute the balanced two-token amounts the burned liquidity is worth (`amount0`, `amount1`, based on the pool's actual **balance**, not reserve — lines 167–168), then convert the unwanted token's share into more of the wanted token via the same constant-product formula (`_getAmountOut`) the standalone `swap` function uses.

**Relevant locals/state** (within `burnSingle`, lines 156–193):
- `tokenOut` (local, L157, decoded from `data`) — which token the caller wants to receive; gates the `if (tokenOut == token1) { ... } else { ... }` branch (L172/L180) that determines which of `amount0`/`amount1` is the "swap-in" leg and which is the "swap-out" leg. (`recipient`, `unwrapBento` — also decoded at L157 — play no role in either branch's arithmetic and are not tracked further.)
- `_reserve0`, `_reserve1` (locals, L158, from `_getReserves()`) — the pool's **cached** reserve figures as of the *last* `_update()` call. **Not used anywhere in the corrected computation** — this is the crux of the bug (see below).
- `balance0`, `balance1` (locals, L159, from `_balance()`) — the pool's **actual current** Bento-share balances, queried live.
- `amount0`, `amount1` (locals, L167–168) — `amount0 = (liquidity * balance0) / _totalSupply`, `amount1 = (liquidity * balance1) / _totalSupply`: the balanced two-token value of the liquidity being burned, computed against the fresh **balance**, per the function's own stated design (its doc comment: "calculate `amountOut` as if the user first withdrew balanced liquidity and then swapped").
- **The disputed statements**:
  - L175 (`tokenOut == token1` branch): `amount1 += _getAmountOut(amount0, _reserve0 - amount0, _reserve1 - amount1);`
  - L183 (`tokenOut == token0` branch, mirror): `amount0 += _getAmountOut(amount1, _reserve1 - amount1, _reserve0 - amount0);`
- `_getAmountOut(amountIn, reserveAmountIn, reserveAmountOut)` (L330–337) — the pool's constant-product-with-fee swap formula: `amountInWithFee = amountIn * MAX_FEE_MINUS_SWAP_FEE; amountOut = (amountInWithFee * reserveAmountOut) / (reserveAmountIn * MAX_FEE + amountInWithFee);`. Declared `internal view` (not `pure`) but reads only the immutable `MAX_FEE_MINUS_SWAP_FEE` and the constant `MAX_FEE` — both fixed for the pool's entire lifetime — so it is deterministic given its three parameters, exactly the situation `web3bugs_3_H_04`'s `applyInterest` was in.

**Variable-value intent (L175/L183, the buggy statements).** After withdrawing the balanced `amount0`/`amount1` (computed on **balance**), the *remaining* pool token holdings available for the internal "swap" leg are `balance0 - amount0` / `balance1 - amount1` — the actual, current post-withdrawal token holdings. The code instead passes `_reserve0 - amount0` / `_reserve1 - amount1` — the **stale, pre-withdrawal-and-possibly-pre-drift** reserve figures minus the same withdrawn amounts. Because `amount0`/`amount1` were themselves computed against `balance`, subtracting them from `_reserve` (a different base) rather than `balance` (the base they were actually drawn from) is an internally inconsistent mix of two different bases for the same quantity.

**Statement/line-level intent.** The function is trying to uphold the invariant its own doc comment states: `burnSingle` should behave identically to calling `burn` (which uses balance-based reserve figures throughout, since it calls `_update(balance0, balance1, ...)` unconditionally) followed by `swap` on the resulting, freshly-synced state. The swap leg's `_getAmountOut` call should therefore see the same post-withdrawal balances a real, separate `swap()` call would see after `burn` had run — i.e., balance-based, not reserve-based.

**Reported erroneous behavior** (H-11, verbatim, primary source `Web3Bugs/reports/29.md`): *"The token amounts to redeem (`amount0`, `amount1`) are computed on the **balance** (not the reserve). However, the swap amount is then computed on the **reserves** and not the balance. The `burn` function would have updated the `reserve` to the balances and therefore `balance` should be used here: `amount1 += _getAmountOut(amount0, _reserve0 - amount0, _reserve1 - amount1);`"* Footnote: *"⚠️ The same issue occurs in the `HybridPool.burnSingle`"* (a different contract, not in this case's target file — out of scope).

**Impact** (verbatim, primary source only — **absent from the scattered `Dataset/Web3Bugs` excerpt**, §0.5): *"For a burn, usually the `reserve` should equal the `balance`, however if any new tokens are sent to the contract and `balance > reserve`, this function will return slightly less swap amounts."* Sponsor (`maxsam4`) confirmed and requested the High bump quoted above (loss of pool funds).

**Recommended Mitigation Steps** (verbatim, primary source only, **also absent from the scattered excerpt**): *"Call `_getAmountOut` with the balances instead of the reserves: `_getAmountOut(amount0, balance0 - amount0, balance1 - amount1)`."*

**Expected/intended behavior**: for the `tokenOut == token1` branch, `amount1`'s update should use `_getAmountOut(amount0, balance0 - amount0, balance1 - amount1)`, not `_getAmountOut(amount0, _reserve0 - amount0, _reserve1 - amount1)` — i.e., every occurrence of `_reserve0`/`_reserve1` inside the swap-leg call should be `balance0`/`balance1`. By the same recommendation's own general framing ("the swap amount is then computed on the reserves") and the function's own doc comment, this applies to *both* branches of the `if (tokenOut == token1) {...} else {...}` structure — the report excerpts only L175, but L183 is the textually identical pattern for the opposite token, using the same `_reserve0`/`_reserve1` variables in the same wrong role.

**Patch intent**: the recommendation is a literal one-line substitution scoped to the one excerpted branch. Used below as evidence only (§2/§3) — R1-2/R1-3 derive the general relation from `_getAmountOut`'s own definition and the function's balance-vs-reserve design intent, not by transcribing the recommendation's exact code.

**Concrete scenario (constructed — the report gives no numeric PoC for H-11, so this is independently built and verified below, matching the style of `59_H_04`/`70_H_04` when no report PoC exists)**: `swapFee = 30` (0.3%, so `MAX_FEE = 10000`, `MAX_FEE_MINUS_SWAP_FEE = 9970`); `_reserve0 = _reserve1 = 1000` (last-synced cached reserves); `balance0 = 1000`, `balance1 = 1100` (token1's actual balance has drifted 100 above its cached reserve — e.g. an external donation, or a fee/yield accrual not yet synced); `totalSupply = 1000`, `liquidity = 100` (10% of supply being burned); `kLast = 0` (so `_mintFee` mints nothing and `_totalSupply` stays `1000` — an early-lifecycle call, before any bar-fee accrual has occurred, realistic and reachable).

- `amount0 = (100 × 1000) / 1000 = 100`. `amount1 = (100 × 1100) / 1000 = 110`.
- **Branch A (`tokenOut == token1`, L175)**:
  - **Buggy**: `_getAmountOut(100, 1000 − 100, 1000 − 110) = _getAmountOut(100, 900, 890)`. `amountInWithFee = 100 × 9970 = 997,000`. `amountOut = ⌊(997,000 × 890) / (900 × 10000 + 997,000)⌋ = ⌊887,330,000 / 9,997,000⌋ = 88`. `amount1` (final) `= 110 + 88 = 198`.
  - **Intended** (per the recommendation): `_getAmountOut(100, 900, balance1 − amount1) = _getAmountOut(100, 900, 990)`. `amountInWithFee = 997,000` (unchanged). `amountOut = ⌊(997,000 × 990) / (900 × 10000 + 997,000)⌋ = ⌊987,030,000 / 9,997,000⌋ = 98`. `amount1` (final) `= 110 + 98 = 208`.
  - **Buggy (198) < intended (208)** — matches the report's "returns slightly less swap amounts" for this branch/scenario.
- **Branch B (`tokenOut == token0`, L183, mirror), same underlying pool state**:
  - **Buggy**: `_getAmountOut(110, 1000 − 110, 1000 − 100) = _getAmountOut(110, 890, 900)`. `amountInWithFee = 110 × 9970 = 1,096,700`. `amountOut = ⌊(1,096,700 × 900) / (890 × 10000 + 1,096,700)⌋ = ⌊987,030,000 / 9,996,700⌋ = 98`. `amount0` (final) `= 100 + 98 = 198`.
  - **Intended**: `_getAmountOut(110, balance1 − amount1, 900) = _getAmountOut(110, 990, 900)`. `amountInWithFee = 1,096,700` (unchanged). `amountOut = ⌊(1,096,700 × 900) / (990 × 10000 + 1,096,700)⌋ = ⌊987,030,000 / 10,996,700⌋ = 89`. `amount0` (final) `= 100 + 89 = 189`.
  - **Buggy (198) > intended (189)** here — the *opposite* direction from Branch A on the same underlying drift. This is a genuine, arithmetic-verified finding of this pass, not asserted from the report: because Branch A's drift sits on the swap's `reserveOut` side (increasing it increases output) while Branch B's *same* drift sits on the swap's `reserveIn` side (increasing it decreases output), "buggy is always ≤ intended" does **not** hold in general — it depends on which token has the balance/reserve drift relative to which leg of that call's swap direction. This directly informs R1-3's rejection of any inequality-bound candidate below (§3).

**Bug-relevant intended numeric behavior**: for either branch, the swap-leg `_getAmountOut` call's second and third arguments must be the pool's **current balance** minus the withdrawn amount for each token, not the **cached reserve** minus the withdrawn amount.

## R1-2 — Intent Abstraction

Distinguishing property (patch's literal one-line substitution not transcribed beyond using it as evidence of "balance, not reserve"): the swap-leg computation's post-withdrawal reserve arguments must be derived from the pool's live balance, not its cached reserve. **Intent-level orientation: value-centered** — a constraint on `amount1`'s (resp. `amount0`'s) updated value at the disputed statement, in terms of other already-materialized in-scope values (`amount0`, `balance0`, `balance1`, and `amount1`'s own pre-statement value). ## R1-3 — Select the least implementation-specific sufficient relation

**Preliminary check — does this relation need a function call inside `intentValue`?** The natural statement of intent is "`amount1`'s new value equals its old value plus `_getAmountOut(amount0, balance0 - amount0, balance1 - amount1)`," and `intentValue`'s grammar has no call syntax. This is the **exact-formula-inlining rescue** (README §3, now formalized as a named, criteria-bearing rescue distinct from the Nokon-style known-*bound* rescue — surfaced for explicit formalization by this exact case, alongside its three already-established prior uses this session: `web3bugs_3_H_04`'s `applyInterest`, `web3bugs_16_H_06`'s `PRBMathUD60x18.mul`, `web3bugs_70_H_05`'s `FixedPoint.mul`/`.decode144()`). Checked against the rescue's three conditions: (a) `_getAmountOut` is deterministic given its three parameters (all already in scope at the call site) plus two contract-lifetime-fixed constants (`MAX_FEE_MINUS_SWAP_FEE` immutable, `MAX_FEE` constant) — no other state read; (b) its body contains no further call (opaque or otherwise) and no loop; (c) its entire body is `*`/`/` over those in-scope terms — no branch at all (a cleaner case than `3_H_04`'s `applyInterest`, which needed an explicit scenario condition to avoid its own internal hourly-compounding loop executing; `_getAmountOut` has no such branch to condition around). All three conditions hold, so the rescue applies cleanly and the relation stays an *exact* equality, not an approximation.

**Explicit methodological caveat (README §3, added this session, prompted by a review question on this exact case): using this rescue does not, by itself, make the case Algorithm-level.** Needing to inline `_getAmountOut`'s formula is a specification-requirements fact (captured in RQ2-A below as "Additional functions required: 1"), not evidence about what's structurally wrong in `burnSingle`'s own code — see §5 for why the actual defect (a swapped-identifier argument-source error, the same call still running unchanged) is Value-level despite the annotation needing to inline another function's body to state it.

1. **Directional/monotonicity**: e.g. "`amount1` after the statement is `≥`/`≤` its value using the buggy formula." **Rejected — not a stable direction.** The R1-1 scenario shows the buggy-vs-intended sign is **scenario- and branch-dependent**: Branch A's buggy value (198) is *less than* intended (208), but Branch B's buggy value (198) is *greater than* intended (189) on the exact same underlying pool drift — because the drifted token plays the `reserveOut` role in one branch and the `reserveIn` role in the mirror branch, and `_getAmountOut` is increasing in `reserveOut` but decreasing in `reserveIn`. No single directional inequality can be asserted as an intended-behavior invariant without being falsifiable by a legitimate (non-buggy) execution in the opposite drift configuration. Rejected on this concrete, arithmetic-verified ground — not merely "equality is stronger," matching the README's caution against assuming direction without checking.
2. **Inequality bound tied to the correct formula**: e.g. `amount1 ≥ amount1(Before) + [balance-based formula]`. **Rejected, same reason as (1)** — since the sign of the deviation is not fixed, no bound (upper or lower) can be asserted as a sound characterization of intended behavior; a bound picked to fit Branch A's scenario would be *violated by the intended, non-buggy code itself* on a Branch-B-shaped drift, which would make the annotation unsound (a false positive on correct code), not merely weak.
3. **Exact equality (SELECTED, both branches)**: `amount1 == amount1(Before) + (amount0 * MAX_FEE_MINUS_SWAP_FEE * (balance1 - amount1(Before))) / ((balance0 - amount0) * MAX_FEE + amount0 * MAX_FEE_MINUS_SWAP_FEE)` (Branch A); mirrored for Branch B. This is the only relation form that both discriminates the reported defect (below) and is sound on the intended/correct code regardless of which token's balance has drifted — precisely because the intended quantity is a single, exactly-determined arithmetic result (`_getAmountOut`'s own formula), not naturally a bound. Matches `59_H_04`/`3_H_04`'s precedent for exact-equality selection: operator strength here is not chosen out of habit but because it is the *only* sound option once the sign-instability in (1)/(2) is checked directly.
4. **Report's literal branch-scoped fix, Branch A only**: `amount1 == amount1(Before) + _getAmountOut(amount0, balance0-amount0, balance1-amount1)`, restated with the call inlined — this is essentially Alternative 3 for Branch A, and is not, by itself, "more implementation-specific" than 3 (both reference the identical inlined RHS; README's caution that operator strength/patch-likeness alone does not measure implementation-specificity applies here too — using the exact corrected formula is not a defect when it is genuinely the correct specification, §3). **What is rejected here is scope, not form**: selecting Branch A's relation *alone*, with no counterpart for Branch B, is addressed by the required negation check immediately below.
5. **Call-argument relation, `identifier.arg[n]` form (considered on review, rejected — not merely "less direct," genuinely inapplicable to this statement's shape).** An external critique proposed checking the swap-leg call's arguments directly — e.g. `@During _getAmountOut.arg[1] == balance0 - amount0` — instead of inlining `_getAmountOut`'s full formula, on the reasoning that this would be strictly less implementation-specific (immune to any future change in `_getAmountOut`'s own formula) and would use the grammar's dedicated `identifier.arg[n]` construct (`duringClause: identifier '.' 'arg' '[' numberLiteral ']' relOp intentValue`, `Solidity.g4`) instead of a general relation. **Checked directly against the engine's actual implementation and found inapplicable to this case's specific statement shape**: `Analyzer/GuardianVerificationEngine.py`'s `verify_during_function_arg` locates the target call via `for stmt in cfg_node.statements: if stmt.statement_type == 'functionCall': ...` — it only scans statements whose own top-level type is a **bare call statement** (`Domain/IR.py`: `statement_type == "functionCall"`, holding just a `function_expr`). The disputed statements here (L175/L183) are **compound-assignment statements** (`statement_type == "assignment"`, with `left`/`operator`/`right` fields, `right` holding the `_getAmountOut(...)` call) — a categorically different `Statement` shape that this scan loop skips entirely, regardless of what call is nested inside its `right` expression. Confirmed against the only existing precedent for this construct in the project (`indivisible_amount/BoostToken`'s `// @During transfer.arg[0] > 0`): it attaches to `_devWalletAddress.transfer(amount.div(4));`, a genuine bare call statement — not an assignment. `amount1 += _getAmountOut(...)` is not that shape, and (per this session's confirmed rule) the target statement cannot be rewritten into a bare-call shape to make it fit. **Rejected on this concrete, source-verified implementation ground, not on style/directness grounds** — full-formula inlining (Alternative 3) is not a detour around a more elegant available form; given this statement's shape, it is the only form the current grammar/engine combination can actually evaluate.

**Winner: Alternative 3, as a target-annotation set of two members — one relation per branch.**

**Is this a genuine README §4 multi-relation-set case, or "one bug restated twice"?** Flagged explicitly, since this case's two members are structurally more symmetric than `web3bugs_70_H_04`'s A/B (which differed in *kind* — a persisted state total vs. a returned array). Here, both members are the *same* formula shape, differing only in which token is `amountIn` vs. which pair of `_reserve/balance` terms is used — mutually exclusive per call (`tokenOut` selects exactly one branch), never both violated by the same execution. This is best described as **branch-symmetric duplication of one defect pattern**, not two independently-*reported* mechanisms in the `70_H_04` A/B sense (the report's own code excerpt shows only Branch A; Branch B is inferred here from direct code symmetry and the recommendation's function-general phrasing — "the swap amount is *then* computed on the reserves," and the finding's own title, "swap amount **computations**," plural). It still clears README's stated bar for a set: (1) each member independently passes its own full R1-1–R1-7 below; (2) it is not a different, separately-numbered finding — both branches are inside the one function this H-11 finding names, and the footnote ("the same issue occurs in `HybridPool.burnSingle`") shows the *reporter's own* framing already treats "the same defect pattern occurring in a mirrored/sibling location" as part of the one finding; (3) Intent coverage is judged against the combined set's negation, immediately below. Recorded as a set, with this caveat stated explicitly rather than silently presented as identical in kind to `70_H_04`.

**Required R1-3 negation check (§3, mandatory) — run against the combined set.** Does the set's negation fail to catch some alternative implementation that retains the reported "reserve-instead-of-balance" defect but produces it differently?
- An implementation that fixes Branch A (uses `balance0-amount0`/`balance1-amount1` at L175) but leaves Branch B unfixed (still `_reserve1-amount1`/`_reserve0-amount0` at L183): **caught** — the Branch B member is violated on any call with `tokenOut == token0` and nonzero drift.
- Symmetric case, Branch B fixed / Branch A unfixed: **caught** by the Branch A member.
- Neither fixed: both members violated — caught twice over.
- Both fixed (the actually-intended behavior): both members hold with equality — correctly accepted.
- **A single-relation selection (Branch A alone) would leave a real gap** — an implementation fixing only the excerpted line would satisfy Branch A's relation while silently retaining the identical defect in Branch B, undetected. This is exactly the required-check scenario the README's negation check exists to surface; the second, independently-derived member (Branch B) closes it, per §4's explicit guidance to check for a second relation before settling for `Intent coverage: Partial`.
- **No alternative implementation retaining the reserve-instead-of-balance defect in either branch escapes the combined set.**

**Discrimination check (explicit arithmetic, per §9 checklist item 1)**: already carried out in full in R1-1's concrete scenario for both branches — Branch A: buggy `198 == 208` false (Violated), intended `208 == 208` true (Satisfied); Branch B: buggy `198 == 189` false (Violated), intended `189 == 189` true (Satisfied).

## R1-4 — During vs Post

**Selected scope, both members: During.** The relation's subject, `amount1` (resp. `amount0`), is read *and* written within the same statement (`amount1 += _getAmountOut(...)`, which Solidity desugars to `amount1 = amount1 + _getAmountOut(...)`) — the RHS's `balance1 - amount1` term reads `amount1`'s pre-statement value, while the assignment target is its post-statement value. `amount1`/`amount0` are locals declared *mid-function* (L167/L168), not present at function entry, so the `@Post`-only `(Entry)`/`(Exit)` snapshot pair (tied to `σ_entry`/`σ_exit`, i.e., function start/end) cannot express "the value this same identifier had immediately before this one statement" — that specific same-statement old/new self-reference is exactly what the `(Before)`/`(After)` snapshot-qualified extension under `@During` was added for (README §4/R1-3; precedent: `web3bugs_35_H_11`'s `ticks[...].feeGrowthOutside1 == feeGrowthGlobal - ticks[...].feeGrowthOutside1(Before)`, `evaluation/RQ1/cases/web3bugs_35_H_11/web3bugs_35_H_11.json`). Not chosen merely because the patch is a single-statement `+=` (R1-4's explicit caution) — chosen because no `@Post` Entry/Exit pairing can reach a value that does not exist at function entry.

**Post considered and rejected as an alternative for the same value.** Could the relation instead be phrased at `@Post` on `amountOut` (the named return variable, since `amountOut = amount1;` at L178/L186 with no further modification)? No: `@Post`'s snapshot vocabulary only offers `σ_entry`/`σ_exit` for the *whole function*, and `amount1`'s own pre-`+=`, mid-function value has no `σ_entry` representation (it is not a parameter or persistent state, and it does not exist until L168) — there is no way to state "the increment added to `amount1` equals the balance-based formula" using only Entry/Exit. During, with the statement-local `(Before)` qualifier, is the only viable scope, matching exactly the reasoning documented in the grammar-extension note (README §4/R1-3).

**Required explicit check: does this case hit the confirmed loop-body-`@During`-never-evaluated exception (`delta`, README §4/R1-7)?** **No — checked directly on this case's own control flow, not by analogy.** `burnSingle` contains **no `for`/`while` loop anywhere in its body** (confirmed by direct reading of lines 156–193 above — the function is a linear sequence of statements plus one `if`/`else`). The `@During` attachment point (immediately after L175, resp. L183) is inside an `if`/`else` conditional block, not a loop body; conditionals are not covered by the confirmed exception at all (README §4's fixpoint/`reinterpret_from()` finding is specifically about loop heads jumping straight from `fixpoint()` to the loop's exit successors — an `if`/`else` has no such fixpoint/loop-exit jump; `_process_during_annotations` is reached normally for any non-loop statement, including one inside a conditional). **Delta confirmed not applicable, for both members** — unlike the old `L1a`-labeled cases (`71_H_11`, `34_H_01`) that genuinely do attach inside a `for` loop body, this case's disputed statements were never inside one to begin with.

## R1-5 — Relation form

**Exact equality, both members**, via the grammar's general `RelationalCmp` common-form rule (`intentValue relOp intentValue`, `Parser/Solidity.g4` — same production `web3bugs_35_H_11`'s `(Before)`-qualified relation uses), reached through `duringClause -> commonClause`. ## R1-6 — Construct the target annotation

**Target annotation is a set of two `@During` clauses** (README §4's multi-annotation note), one per branch, each attached **inline** — sharing the exact same line as its own disputed statement, not a standalone line after it.
