## R1-1 — Reported Behavior Reconstruction

**Contract role** (brief, since it clarifies the semantics of the values involved): `Router` is Vader's user-facing trading/lending aggregator. It does not hold pool reserves itself — actual AMM state (token/base reserves per pair) lives in a separate `POOLS` contract, and pure swap-math formulas (`calcSwapOutput`, `calcSwapSlip`, etc.) live in a separate `UTILS` contract, both reached exclusively through the `iPOOLS`/`iUTILS` interfaces. `Router` orchestrates multi-leg calls into those contracts and does its own slippage gating around them.

**Function role**: `swapWithSynthsWithLimit` is the single general-purpose swap entry point (all of `swap`, `swapWithLimit`, `swapWithSynths` delegate to it). It has four routing branches based on whether `inputToken`/`outputToken` are the protocol base asset (`isBase`, i.e. `VADER`/`USDV`): Token→Base, Base→Token, and — the branch this finding concerns — **Token→Token** (lines 162–176), which is implemented as two sequential legs through the common base asset: leg 1 sells `inputToken` for `_base`, leg 2 buys `outputToken` with the resulting `_base`. Each leg is preceded by its own `require(calcSwapSlip(...) <= slipLimit)` slippage gate.

**Relevant locals/state (Token→Token branch, lines 162–176):**
```solidity
} else if (!isBase(inputToken) && !isBase(outputToken)) {
    // Token||Synth -> Token||Synth
    require(iUTILS(UTILS()).calcSwapSlip(inputAmount, iPOOLS(POOLS).getTokenAmount(inputToken)) <= slipLimit);   // L164 — leg-1 gate
    if(!inSynth){
        iPOOLS(POOLS).swap(_base, inputToken, POOLS, true);                                                    // L166 — leg 1, return discarded
    } else {
        iPOOLS(POOLS).burnSynth(_base, inputToken, POOLS);                                                      // L168 — leg 1 (synth variant), return discarded
    }
    require(iUTILS(UTILS()).calcSwapSlip(inputAmount, iPOOLS(POOLS).getBaseAmount(outputToken)) <= slipLimit);   // L170 — leg-2 gate, THE BUGGY STATEMENT
    if(!outSynth){
        outputAmount = iPOOLS(POOLS).swap(_base, outputToken, _member, false);                                  // L172 — leg 2
    } else {
        outputAmount = iPOOLS(POOLS).mintSynth(_base, outputToken, _member);                                    // L174 — leg 2 (synth variant)
    }
}
```
- `inputAmount` (function parameter) — the amount of `inputToken`, in `inputToken`'s own unit, the caller wants to sell. Fixed for the whole call; never updated between the two legs.
- `_base` (local, set L141–145) — `VADER` or `USDV`, chosen by whether either `inputToken`/`outputToken` is an anchor asset.
- `iPOOLS(POOLS).getTokenAmount(inputToken)` (L164, leg-1 gate's second argument) — the **token**-side reserve of the `inputToken` pool, the correct comparison depth for a trade whose *input* is `inputAmount` units of `inputToken`.
- `iPOOLS(POOLS).getBaseAmount(outputToken)` (L170, leg-2 gate's second argument) — the **base**-side reserve of the `outputToken` pool, the correct comparison depth for leg 2 (since leg 2's actual input is `_base`-denominated).
- Leg-1 swap/burn (L166/L168) — moves `inputAmount` of `inputToken` into `POOLS` and (internally, inside `POOLS`) credits `POOLS` with some amount of `_base`. **Its return value — the actual `_base` amount leg 1 produced — is discarded in both sub-branches** (`iPOOLS(POOLS).swap(...)` and `iPOOLS(POOLS).burnSynth(...)` are called as bare statements, not assigned to anything). No local variable anywhere in this function captures this quantity.
- `outputAmount` (named return, first assigned L172/L174) — leg 2's actual output; not yet assigned at the time the buggy L170 `require` executes.

**Variable-value intent (L170, the buggy statement's first `calcSwapSlip` argument).** `calcSwapSlip(x, X)` (`iUTILS.sol` L32; implementation confirmed elsewhere in this dataset's own `web3bugs_5_H_07`/`5_H_08` variants of this same file, `x*10000/(x+X)`) computes a basis-points slippage figure for *trading `x` units against a pool whose relevant-side depth is `X`*. For this to be a meaningful slippage check on leg 2 (a `_base → outputToken` trade with depth-side `X = getBaseAmount(outputToken)`, itself `_base`-denominated), `x` must likewise be **the `_base`-denominated amount actually being traded into pool 2** — i.e. leg 1's actual output. The code instead passes `inputAmount`, which is denominated in `inputToken` (leg 1's *input* unit, not leg 2's input unit) and has no fixed numeric relationship to leg 1's `_base`-denominated output at all (different token, potentially different decimals, and a magnitude that depends on leg 1's own AMM curve, not a simple scalar of `inputAmount`).

**Statement/line-level intent.** The Token→Token branch is trying to uphold: *each leg's own slippage check gates that leg's own actual trade inputs against that leg's own actual trade depth* — the same invariant the (correct) leg-1 gate at L164 already upholds (`inputAmount` vs. `getTokenAmount(inputToken)`, both `inputToken`-side quantities). L170 breaks this invariant for leg 2 by reusing leg 1's input quantity instead of leg 2's actual (base-denominated) input quantity.

**Reported erroneous behavior** (H-15, verbatim): *"The slippage protection of the second trade (base to token) is computed wrong: ... It compares the **token** input amount (of the first trade) to the **base** reserve of the second pair. Slippage protection fails and either the trade is cancelled when it shouldn't be or it is accepted even though the user suffered more losses than expected."* Sponsor (`strictly-scarce`) confirmed the finding (disputing only severity, not validity): *"Valid, although disagree with severity, the wrongly compute slip amount would just fail the trade or allow the second trade to go thru with no protection."*

**Expected/intended behavior**: the report's recommendation is qualitative, not a code diff: *"it should use the base output from the first trade to check for slippage protection."* It also flags, as a secondary observation not part of the core defect, that this is still a per-leg check, not a joint two-leg slippage bound: *"Note that this still just computes the slippage protection of each trade individually. An even better way would be to come up with a formula to compute the slippage on the two trades at once."* This per-leg framing is adopted below (matching what the current code already structurally attempts) rather than the more ambitious "joint formula" the report explicitly calls out as a separate, unimplemented improvement, not the reported defect itself.

**Patch intent**: no literal code patch is given anywhere in the report (§0.5 cross-check confirms both copies agree on this — there is no PoC/Recommendation code block for this finding). The recommendation sentence is read as evidence of the intended quantity (leg 1's actual `_base` output), not transcribed as annotation syntax — there is no syntax to transcribe.

**Bug-relevant intended numeric behavior**: at L170, `calcSwapSlip`'s first argument should equal the actual `_base`-denominated amount leg 1 produced (the discarded return value of the L166/L168 call) — not `inputAmount` (leg 1's `inputToken`-denominated *input*).

**Concrete scenario (constructed — the report gives no PoC numbers for this finding, only the qualitative description above).** Token→Token trade, `!inSynth`/`!outSynth` sub-branch (the `swap`/`swap` pair; the `burnSynth`/`mintSynth` sub-branches share the identical discarded-return structure, so the scenario generalizes without needing to model synth mechanics). Let `inputAmount = 1000` (units of `inputToken`). Pool 1 (`inputToken`/`_base`) reserves at the time of leg 1: `getTokenAmount(inputToken) = 10000`, `getBaseAmount(inputToken) = 5000`. Using this dataset's own confirmed `calcSwapOutput(x, X, Y) = x·X·Y/(x+X)²` formula (`web3bugs_5_H_08.sol` L211–216, the pure AMM-output formula `iPOOLS.swap` uses internally):
- **Leg 1's actual `_base` output** (not captured by the buggy code, computed here only to construct the scenario): `calcSwapOutput(1000, 10000, 5000) = (1000·10000·5000)/(11000)² = 50,000,000,000 / 121,000,000 ≈ 413` (floor).
- **Leg-1 gate (L164, correct as written)**: `calcSwapSlip(1000, 10000) = 1000·10000/11000 ≈ 909` bps (9.09%) — legitimately compares `inputAmount` against `inputToken`'s own pool depth.
- Pool 2 (`_base`/`outputToken`) reserves at the time of leg 2: `getBaseAmount(outputToken) = 2000`, `getTokenAmount(outputToken) = 8000`.
- **Leg-2 gate, buggy (L170, as actually computed)**: `calcSwapSlip(inputAmount=1000, 2000) = 1000·10000/3000 ≈ 3333` bps (33.3%).
- **Leg-2 gate, intended (using leg 1's actual output, 413, in place of `inputAmount`)**: `calcSwapSlip(413, 2000) = 413·10000/2413 ≈ 1711` bps (17.1%).
- With `slipLimit = 2000` (20%, a realistic caller-supplied tolerance): **buggy** `3333 <= 2000` → **false, require reverts** — the trade is cancelled; **intended** `1711 <= 2000` → **true, require passes** — the trade should have gone through. This reproduces the report's first named failure mode verbatim: *"the trade is cancelled when it shouldn't be."*
- The reverse failure mode (*"accepted even though the user suffered more losses than expected"*) is equally reachable with different reserve/`inputAmount` magnitudes — since `inputAmount` (an `inputToken`-denominated quantity) has **no fixed ordering** relative to leg 1's actual `_base`-denominated output (it depends on the two pools' independent, unrelated token economics), the buggy comparison can land on either side of `slipLimit` relative to where the intended comparison lands, in either direction. This absence of a fixed sign is used again in R1-3 below to rule out any inequality-shaped rescue.

## R1-2 — Intent Abstraction

Governing question: `calcSwapSlip`'s first argument at L170 must equal the amount actually being traded into pool 2 on this leg (leg 1's realized `_base` output) — a quantity that is computed by the L166/L168 call but never assigned to anything — not `inputAmount`, a quantity from a *different* leg, denominated in a *different* token.

**Orientation: value-centered** — a constraint on one specific call argument (the first argument of the `calcSwapSlip` invocation at L170), matching README R1-5's explicitly-listed "call-argument relation" form category. Not a state-transition claim (nothing about *whether* the require fires as a boolean gate is the point — `require feasible`/`D_req` would only check reachability, not correctness of the comparison; see R1-3).

## R1-3 — Select the least implementation-specific sufficient relation

**Natural syntactic vehicle**: the grammar has a dedicated call-argument clause, `duringClause → identifier.arg[n] relOp intentValue` (`D_arg`, `paper/first_revision/main.tex` line 486; `Parser/Solidity.g4` line 306, `# DuringFunctionArg`), whose semantics (`main.tex` line 630) is `V[[f.arg[n] op e]](Γ) = Cmp*(eval(σ_before, arg_n(f, K)), op, eval(σ_before, e))` — exactly "compare the n-th argument of the call named `f` found at the annotated line against an arithmetic expression `e`." This is the right-shaped construct for the reported defect (a wrong call argument), so every alternative below is phrased as `calcSwapSlip.arg[0] relOp e` for some `e`, at L170. What varies is `e` and the comparator.

1. **Directional relation** — e.g., "as `inputAmount` grows, `arg[0]`'s value should track leg 1's output growing too" (a monotonicity claim). **Rejected — not meaningfully statable.** There is no second execution/iteration to compare against within a single call (unlike a loop), so a monotonicity claim would have to be encoded as a bound on the single value itself anyway; it collapses into alternative 2/3 below, not a genuinely weaker independent tier here.
2. **Inequality bound using only already-in-scope, call-free quantities** — e.g. `calcSwapSlip.arg[0] <= inputAmount` or any other bound built purely from `inputAmount`, `slipLimit`, or numeric constants. **Rejected — not sound, and not discriminating.** As shown in R1-1's scenario, leg 1's actual `_base` output has no fixed ordering relative to `inputAmount` (different token, independent pool economics) — a bound like "`arg[0] <= inputAmount`" is not even always true of the *intended* value (leg 1's output can exceed `inputAmount` numerically if `outputToken`'s implied price is high relative to `inputToken`'s), so it would misclassify correct implementations as violations on some inputs, and — separately — even where it happens to hold, it says nothing about *which* base-denominated quantity was used, so it would equally "pass" other wrong choices (e.g., a hard-coded `0`, or `getBaseAmount(inputToken)` itself). Both an unsoundness problem and a discrimination problem, either one independently disqualifying.
3. **Exact equality (SELECTED, notionally)** — `calcSwapSlip.arg[0] == <leg 1's actual _base output>`. Ties the check directly to the one quantity the report identifies as the fix ("the base output from the first trade"), is exact by nature (there is no legitimate partial-credit value between `inputAmount` and the real leg-1 output — either the correct base amount is used or it isn't), and — per R1-1's scenario — discriminates cleanly (3333 bps buggy vs. 1711 bps intended, on the same reserves).

**Winner (notionally): Alternative 3.**

**Required known-bound/call rescue check (README §4/R1-3, mandatory before concluding a call-blocked relation is Inexpressible — explicitly performed for this case's own facts, not inherited from the old `L2a` label).** The needed quantity, "leg 1's actual `_base` output," exists **only** as the return value of `iPOOLS(POOLS).swap(...)`/`iPOOLS(POOLS).burnSynth(...)` (L166/L168) — a call, and specifically a **state-modifying** one (re-invoking it inside an annotation is not merely a grammar violation but would also double-execute a state-changing trade, which is not what any annotation semantics in this grammar does — annotations are never executed, only evaluated over already-computed program state, so this is moot for the grammar question but confirms there is no live-recomputation escape hatch either). Checking for a Nokon-style rescue (`numscout_Nokon`'s `amountToBuy * ethRateFix >= msg.value * 250000`, which substitutes a *known configured constant* for an unknown call's result) **explicitly, against this case's own facts**:
   - Is there a **fixed, protocol-configured constant** standing in for leg 1's output, the way Nokon's `ethRateFix` does for `calculateRate()`? No — leg 1's output is a live AMM-computed quantity (`calcSwapOutput(inputAmount, X, Y)` over *pool 1's own current reserves*), not a rate the protocol fixes or bounds anywhere; `Router`/`POOLS` expose no configured minimum/maximum for it.
   - Is there an **in-scope, call-free upper or lower bound** that would still discriminate the specific reported defect (a token/unit mismatch, not merely "too large" or "too small")? The only conceivable candidates — `getTokenAmount(inputToken)`/`getBaseAmount(inputToken)` (pool 1's own reserves, which would at least give a same-pool magnitude bound on leg 1's output) — are **themselves calls** (`iPOOLS(POOLS).getTokenAmount(...)`/`getBaseAmount(...)`, both `external view`), so substituting either one *inside* `e` reproduces the exact same call-in-`intentValue` problem one level removed; it isn't a rescue, it's the same blocker restated. And even setting that aside, R1-1 already shows `inputAmount` itself has no fixed ordering against the true value, so no bound built from what's actually reachable would be sound in the first place.
   - Could the **already-present call in the very same statement** be reused — i.e., could `e` reference `getBaseAmount(outputToken)` (already appearing as `calcSwapSlip`'s *second* argument at L170) or `calcSwapSlip.arg[1]`? No: `intentValue`'s grammar (`arithFactor → number | [n,n] | varRef | varRef(snap) | (arithExpr)`, `main.tex` line 507; `Solidity.g4` lines 341–385) has no production that embeds an `identifier.arg[n]` reference *inside* an `arithExpr` — `f.arg[n]` only ever appears as the entire left-hand side of a `D_arg` clause (`Solidity.g4` line 306), never as a sub-term of `e`. So even a same-statement cross-argument reference is syntactically unavailable, independent of whether it would have been semantically useful.
   - **No rescue closes the gap. This is squarely alpha, not a case where the rescue check was skipped.**

**Required snapshot-qualified `varRef(Entry/Exit/Before/After/Assign)` check (README §4/R1-3, the other named rescue mechanism — explicitly checked, capitalized keywords, against this case's own facts).** This extension pins one `varRef` to a specific *state snapshot of an in-scope, non-call variable* (e.g. `debts == debts(Entry) + increasingDebt`) — it does not manufacture a value that has no `varRef` at all. `Router` holds **no** state variable or local that gets written by, or otherwise reflects, leg 1's `_base` output: the `_base` tokens land in `POOLS`'s own (different-contract) balance, not in any `Router`-owned mapping, and `Router` never reads `iERC20(_base).balanceOf(POOLS)` before/after leg 1 the way `moveTokenToPools` (same file, L447–460) does for its own *different* before/after-balance bookkeeping. Since there is no underlying `varRef` to begin with, `(Before)`/`(After)` has nothing to qualify. **Not applicable — confirmed no rescue.**

**Discrimination check (explicit arithmetic, per §9 checklist item 1)** — already shown in R1-1: buggy `calcSwapSlip(1000, 2000) ≈ 3333` bps vs. intended `calcSwapSlip(413, 2000) ≈ 1711` bps, on identical pool-2 reserves; with `slipLimit = 2000`, the two diverge on opposite sides of the threshold. The notional relation (Alternative 3), stated directly on `arg[0]` itself: buggy `arg[0] = 1000`, intended `arg[0] = 413`; `1000 == 413` is false → **Violated** on the buggy code; on a hypothetically patched execution where leg 1's output is correctly captured and passed, `arg[0] = 413 == 413` → **Satisfied**. Confirms the relation, if it could be constructed, would correctly discriminate.

**Required R1-3 negation check (§3/R1-3).** Does this relation's negation fail to catch some alternative implementation that retains the reported defect but produces it differently? The reported defect is "leg 2's gate uses the wrong `_base`-denominated input quantity"; the selected (notional) equality pins the *specific, unique* correct quantity, so **any** wrong substitute — `inputAmount` (the actual bug), a stale cached value, a hardcoded `0`, an unrelated pool's reserve — would equally violate it. No coverage gap was found for *this* relation against *this* reported mechanism. (The report's own secondary observation — that a joint two-leg formula would be "even better" than two independent per-leg checks — describes a strictly *more ambitious*, un-implemented improvement, not an alternative implementation of the *reported* per-leg defect, and is out of scope for R1-3's negation check, which is about alternative implementations of the reported defect, not about a different, more general defect the report explicitly flags as future work rather than the finding itself.)

## R1-4 — During vs Post

**Relation-driven scope (before the R1-6/R1-7 blocker): During.** `D_arg` is grammatically a During-only clause (`main.tex` fig:intent-grammar shows `identifier.arg[n] relOp intentValue` only under `duringClause`, with no `postClause` counterpart) — and this matches the relation's own nature independent of that syntactic fact: the constrained quantity is a call *argument* at one specific statement (L170), evaluated against `σ_before` (state immediately before that statement executes), not a function-exit/return-value property.

**Post alternative considered and rejected.** Could a `@Post` relation on `outputAmount` (the function's own named return, first assigned L172/L174) capture the same defect instead? `outputAmount` *is* legitimately referenceable at `σ_exit` as an ordinary named-return local (the same "already-materialized value, regardless of how it was computed internally" treatment applied to `59_H_04`'s `total` or `3_H_04`'s `cumulativeYield` — referencing it is not itself a call-in-`intentValue` problem). But constructing a *meaningful* relation with it fails on two independent grounds: **(a) content** — the report's mechanism is specifically "the gate's own argument is wrong," a property of one `require` statement, not a claim about the eventual `outputAmount` value (the report frames the consequence as *either* an unwarranted revert *or* an accepted-but-excessive-loss trade — a disjunction, not a single numeric relationship `outputAmount` could witness on its own); a Post bound on `outputAmount` would at best be a downstream, probabilistic symptom, and per the R1-3 negation-check discipline this would risk `Intent coverage: Partial` even if it were expressible. **(b) availability** — stating what `outputAmount` *should* have been (to compare against what it *was*) requires the same fair-value AMM computation over pool 2's reserves that R1-3's rescue check already showed needs calls (`getTokenAmount(outputToken)`/`getBaseAmount(outputToken)`/`calcSwapOutput`), so the same alpha blocker resurfaces one level downstream rather than being avoided. **Post does not rescue this case.**

**Explicit delta-exception check (required by task instructions, performed on this case's own facts).** `swapWithSynthsWithLimit` contains **no loop of any kind** — every statement in the function, including L164–176, is straight-line/branching code, never inside a `for`/`while` body. The confirmed `delta` exception (README §4: `fixpoint()`/`reinterpret_from()` in `Interpreter/Engine.py` never evaluating a `@During` whose only viable attachment is inside a loop body) is therefore **trivially not applicable** — there is no loop for any candidate relation in this case to be attached inside of. This case's blocker (below) is unrelated to observation-point support entirely; it is a value-availability problem that would exist regardless of what kind of statement L170 sat inside.

## R1-5 — Relation form (notional)

**Call-argument relation**, the grammar's dedicated `D_arg` form: `duringClause → identifier.arg[n] relOp intentValue` — not a return-value, Entry/Exit, or before/after form, because the constrained quantity is literally one argument of one call at one statement, which is exactly what `D_arg` exists to express (README R1-5's own listed form category, "call-argument relation"). Not forced into this shape by the patch's syntax (there is no patch syntax — R1-5's caution about patch-shape-driven form selection is moot here by construction); the form follows directly from R1-2's identification of the constrained value as a specific call argument.

## R1-6 — Attempted construction of the target annotation (blocked — see R1-7)

**Attachment point (would-be).** Immediately after L170 (the buggy `require`), inside the Token→Token branch — the point at which `D_arg`'s `arg_n(f, K)` lookup (`main.tex` line 630; corroborated by how the reference implementation locates a call by name within a statement, `Analyzer/GuardianVerificationEngine.py` lines 604–657's `_find_function_call_in_expr`, which recursively searches a statement's call tree for a member/direct call matching the target identifier — cited here only to confirm the grammar's own stated semantics for `D_arg`'s call lookup are unambiguous about *which* `calcSwapSlip` invocation a clause at this line would target, not as an R1-7 engine-validatability check) unambiguously resolves to the L170 `calcSwapSlip` call (not the L164 one, since each `@During` is scoped to its own annotated line).

**The construction fails**, for exactly the reason identified in R1-3's mandatory rescue check: the correct right-hand side, "leg 1's actual `_base` output," has:
- no non-call in-scope `varRef` (no local, no state variable, no struct field anywhere in `Router` holds it — R1-3's snapshot-qualifier check);
- no known-bound/constant substitute that both avoids a call and still discriminates the reported defect (R1-3's Nokon-style rescue check); and
- no way to reach it via a call embedded in `intentValue` at all, since the grammar's `arithFactor` production has no call syntax (`Parser/Solidity.g4` lines 341–385, confirmed by direct read: only `number`, `[number, number]`, `varRef`, `varRef(snap)`, and parenthesized `arithExpr` are legal factors — nothing resembling a function invocation).

**Notional annotation (would be, if the grammar allowed a call or a rescue existed):**
```solidity
require(iUTILS(UTILS()).calcSwapSlip(inputAmount, iPOOLS(POOLS).getBaseAmount(outputToken)) <= slipLimit);
// @During calcSwapSlip.arg[0] == <leg 1's actual _base output — no legal expression for this exists>
```
No legal `intentValue` can replace the placeholder — this is the dispositive fact, not a stylistic gap.

**Conclusion**: R1-6 cannot produce a fixed target annotation, at any legal program point, that is both (a) grammatically legal and (b) faithful to the R1-2/R1-3 relation.

## R1-7 — Expressibility decision

- **Values referenceable at a legal program point**: **No**, for the one operand that matters. `inputAmount`, `slipLimit`, and `outputToken` are ordinary in-scope parameters; `calcSwapSlip` itself is correctly locatable as the L170 call. But the relation's actual right-hand side — leg 1's realized `_base` output — has no in-scope, call-free reference of any kind (R1-3/R1-6). No Nokon-style known-bound rescue and no snapshot-qualified-`varRef` rescue closes the gap; both were checked explicitly against this case's own facts, not assumed absent.
- **Arithmetic/logical relation representable**: Not reached — moot, since the operand itself cannot be referenced. (In isolation, a bare `calcSwapSlip.arg[0] == x` for some in-scope `x` would of course be syntactically legal; the problem is exclusively that no legal `x` denotes the correct quantity.)
- **Observation point supported**: Not the blocker here. `D_arg`'s natural scope (During, at L170) is an ordinary non-loop statement — the confirmed `delta` exception was checked explicitly (R1-4) and is inapplicable; this function contains no loop at all.

**Outcome: Expressible = NO.**

**Tag: alpha** — the relation needs the return value of a call (`iPOOLS(POOLS).swap(...)`/`burnSynth(...)`, L166/L168) to supply its right-hand-side operand, `intentValue`'s grammar disallows calls, and no known-bound/constant rescue (Nokon-style) nor snapshot-qualified-`varRef` rescue closes the gap — both checked explicitly against this case's own facts (R1-3), not skipped and not inherited from the old `L2a interface-call-return-top` label. Not `beta`: the needed value is not "unreachable by any means" in the abstract — it is the direct, already-computed result of a call that already executes in this exact statement sequence; the value genuinely could be captured with one additional line of source (`uint _actualBase = iPOOLS(POOLS).swap(...)`, mirroring the file's own `moveTokenToPools` before/after-balance convention elsewhere), which is precisely the alpha pattern (call-shaped blocker), not a beta pattern (no path to the value under any circumstances). Not `gamma`: the blocker is squarely about the unavailability of one single operand, not about the relation being inherently multi-statement/accounting-structural in a way no single-relation grammar form could express (a `D_arg` clause is exactly the right single-relation shape for this defect — see R1-5 — the only problem is what can legally appear on its right-hand side). Not `delta`: confirmed in R1-4 — there is no loop anywhere in this function, so the confirmed loop-body-`@During` exception cannot be the mechanism (or even a candidate mechanism) here.

## §5 — Value/Algorithm and Usable/Unusable

- **Algorithm-level.** At first glance this looks like `59_H_04`'s "swapped operand" pattern (Value-level: wrong identifier chosen from among *already-existing* in-scope values). It is not the same pattern: in `59_H_04`, both the buggy divisor (`auctionAverageLookback`) and the correct divisor (`count - initialIndex`) were already-materialized, referenceable quantities — the defect was purely *which existing value* got selected. Here, the correct value (leg 1's actual `_base` output) **does not exist as a program value at all** in the buggy code — it is the paper's own listed Algorithm-level marker, "an absent state update" (or, equivalently, a missing capture of an already-executing procedure call's own return value): the call happens (L166/L168), but nothing stores its result, so the defect is not merely "wrong operand picked" but "the correct operand was never brought into existence." This is the same distinguishing logic `70_H_03`'s analysis (`First Revision/phase_reviews/11_web3bugs_70_H_03/analysis.md`, §5) used for its own alpha-tagged, call-blocked defect.
- **Unusable** — the value the relation needs (leg 1's realized `_base` output) is not referenceable in any form the intent model can use: it exists only as the discarded return of a call the grammar disallows referencing inside `intentValue`, and no bound substitutes for it (§5, purely a representational-resources fact, independent of whether a developer would know to add the missing capture).
