## R1-1 — Reported Behavior Reconstruction

**Contract role**: `MyStrategy` is a Badger Vault strategy that manages a position in Convex's `CVX` governance/reward token on behalf of depositors. It splits its CVX holdings between two states: **locked** (deposited into Convex's vote-escrow-style locker, `LOCKER : ICvxLocker`, to accrue voting power/boosted rewards) and **liquid/vaulted** (deposited into a companion Badger vault, `CVX_VAULT : ISettV3`, whose shares are this strategy's own `want` token, referred to in-code as "bCVX"). Only contract- and function-role detail actually needed for the bug is included; the strategy's harvest/withdraw machinery is not relevant here and is skipped.

**Function role**: `manualRebalance(uint256 toLock)` is a governance-only (`_onlyGovernance()`) function letting an admin manually decide what fraction of the strategy's **total** CVX holdings (locked + liquid CVX + liquid `want` converted to CVX-equivalent) should end up locked, expressed as `toLock`, a basis-points fraction of `MAX_BPS = 10_000` (per its own doc comment: "`toLock = 0`, lock nothing... `toLock = 100`, lock everything"). It then either deposits everything into the vault (if the target is already met or exceeded) or locks the shortfall.

```solidity
function manualRebalance(uint256 toLock) external whenNotPaused {
    _onlyGovernance();
    require(toLock <= MAX_BPS, "Max is 100%");
    // ... optional processExpiredLocks / harvest calls (L448-455) ...

    uint256 balanceOfWant = IERC20Upgradeable(want).balanceOf(address(this));      // L458-459
    uint256 balanceOfCVX = IERC20Upgradeable(CVX).balanceOf(address(this));        // L461
    uint256 balanceInLock = LOCKER.balanceOf(address(this));                       // L463: CVX currently locked
    uint256 totalCVXBalance =
        balanceOfCVX.add(balanceInLock).add(wantToCVX(balanceOfWant));             // L464-465

    // Ratios
    uint256 currentLockRatio =
        balanceInLock.mul(10**18).div(totalCVXBalance);                            // L468-469: BUGGY
    uint256 newLockRatio = totalCVXBalance.mul(toLock).div(MAX_BPS);               // L471
    uint256 toWantRatio =
        totalCVXBalance.mul(MAX_BPS.sub(toLock)).div(MAX_BPS);                     // L473-474

    if (newLockRatio <= currentLockRatio) {                                        // L477: nonsensical comparison
        // deposit remainder into vault, return                                    // L478-485
    }

    uint256 cvxToLock = newLockRatio.sub(currentLockRatio);                        // L488
    // ... lock cvxToLock (bounded by maxCVX), deposit any remainder (L490-507) ...
}
```

**Relevant locals**:
- `balanceInLock` (L463) — the strategy's current CVX amount held inside `LOCKER`, read directly from `ICvxLocker.balanceOf(address(this))`. `ICvxLocker.sol`'s own interface comment (`evaluation/RQ1/target_contracts_original/dependencies/ICvxLocker.sol` L15) documents this precisely: *"BOOSTED balance of an account which only includes properly locked tokens as of the most recent eligible epoch,"* returned as a named `uint256 amount` — i.e., an ordinary CVX token amount, not a normalized fraction. `MyStrategy`'s own inline comment at the call site (L462, `// Locked CVX in the locker`) states the same thing.
- `totalCVXBalance` (L464-465) — the strategy's total CVX-equivalent holdings across all three forms (liquid CVX, locked CVX, and `want` converted to CVX via `wantToCVX`), a CVX amount.
- `currentLockRatio` (L468-469, **the disputed statement**) — intended (per its own comment, "Ratios") to represent "how much of the total is currently locked." As written, it computes `balanceInLock * 10**18 / totalCVXBalance` — a value normalized into an 18-decimal-fixed-point **fraction** of `totalCVXBalance` (bounded above by `1e18`, i.e. 100%), not a CVX amount.
- `newLockRatio` (L471) — despite its name, this is **not** a fraction: `totalCVXBalance * toLock / MAX_BPS` is a plain CVX **amount** (the target amount to have locked, given the admin's chosen `toLock` fraction of the total). The report explicitly confirms this is the correctly-computed quantity ("newLockRatio ... is a CVX token amount. It's unbounded and just depends on the totalCVXBalance amount") — only `currentLockRatio` is named as wrong.

**Variable-value intent (L468-469)**: `currentLockRatio`'s value at this line must be the CVX **amount** currently locked — i.e., exactly `balanceInLock`, the value already computed two lines above for precisely this purpose. There is no reason for a `10**18`-scaled percentage normalization to appear here at all.

**Statement/line-level intent**: `manualRebalance` is trying to uphold "lock exactly enough CVX (or unlock/redirect the difference) so that the locked amount reaches the admin's requested target fraction (`toLock`) of total holdings." This requires comparing **two same-unit quantities** — "amount currently locked" vs. "amount that should be locked" — and, on the branch that proceeds, computing their **difference** as the additional amount to lock (`cvxToLock`). Both the comparison (L477) and the subtraction (L488) are only meaningful if `currentLockRatio` and `newLockRatio` share units.

**Reported erroneous behavior** (H-01, verbatim, primary source): *"The `veCVXStrategy.manualRebalance` function computes two ratios `currentLockRatio` and `newLockRatio` and compares them. However, these ratios compute different things and are not comparable: `currentLockRatio = balanceInLock.mul(10**18).div(totalCVXBalance)` is a percentage value with 18 decimals (i.e. `1e18 = 100%`). Its max value can at most be `1e18`. `newLockRatio = totalCVXBalance.mul(toLock).div(MAX_BPS)` is a CVX token amount. It's unbounded and just depends on the `totalCVXBalance` amount. The comparison that follows does not make sense: `if (newLockRatio <= currentLockRatio) {...}`."*

**Impact** (verbatim, primary source only — **absent from the scattered excerpt**, §0.5): *"The rebalancing is broken and does not correctly rebalance. It usually leads to locking nearly everything if `totalCVXBalance` is high."* — because `currentLockRatio` is capped at `1e18` while `totalCVXBalance` (and hence `newLockRatio`, for any nonzero `toLock`) is typically far larger in raw wei terms (CVX has 18 decimals, so any holding above roughly 1 CVX already exceeds `1e18`), the `newLockRatio <= currentLockRatio` early-return branch is almost never taken when it should be, and `cvxToLock = newLockRatio - currentLockRatio` ends up nearly equal to the full `newLockRatio` (since the subtracted `currentLockRatio` is comparatively tiny), driving the strategy to over-lock.

**Recommended Mitigation Steps** (verbatim, primary source only — **absent from the scattered excerpt**): *"Judging from the `cvxToLock = newLockRatio.sub(currentLockRatio)` it seems the desired computation is that the 'ratios' should actually be in CVX amounts and not in percentages. Therefore, `currentLockRatio` should just be `balanceInLock`. (The variables should be renamed as they aren't really ratios but absolute CVX balance amounts.)"*

**Sponsor response** (primary source): acknowledged ("Agree with the finding, the math is wrong"), then confirmed the mitigation would be to **delete and rewrite** `manualRebalance` entirely rather than apply the literal one-line substitution — used below only as confirmation the defect is real and agreed-upon, not as evidence for the specific target relation (the deployed fix's exact final shape is not in scope; R1-3 independently re-derives why `balanceInLock` is the correct substitution from the function's own downstream usage, not from trusting the recommendation's prose alone).

**Expected/intended behavior**: on any execution of `manualRebalance`, `currentLockRatio`'s value, at the point it is assigned (L468-469), must equal `balanceInLock` — the CVX amount currently locked — not a `1e18/totalCVXBalance`-normalized fraction of it.

**Patch intent**: the recommendation names an exact target value (`balanceInLock`, already an in-scope, already-computed local) for the single disputed statement, used below as *evidence for which value is correct*, not transcribed as annotation syntax by itself — R1-3 independently re-derives this primarily from `MyStrategy`'s own in-function inline comment at the call site (already-in-repo, same-function evidence — see the RQ2-A discussion for why this alone is sufficient and no cross-contract dependency is load-bearing), corroborated by `ICvxLocker.balanceOf`'s own interface doc-comment and by (not derived from) `cvxToLock`'s own downstream dimensional-consistency requirement, matching README §2's "use the patch as an anchor, not as a literal source" discipline, and directly following the task's explicit instruction to independently justify this substitution rather than merely reproduce it.

**Bug-relevant intended numeric behavior**: for every call to `manualRebalance`, `currentLockRatio` at its defining statement must equal `balanceInLock` (a CVX amount); the current code instead computes an 18-decimal-fixed-point fraction of `totalCVXBalance`, which is unit-incompatible with `newLockRatio` (itself already a correctly-computed CVX amount) — corrupting both the branch decision at L477 and the subtraction at L488, and (per the report's Impact statement) generally causing the strategy to lock far more CVX than the admin's requested `toLock` fraction calls for.

## R1-3 — Select the least implementation-specific sufficient relation

**Preliminary check — does this relation need a function call inside `intentValue`?** No. The relation's two candidate operands, `currentLockRatio` and `balanceInLock`, are both already-materialized `uint256` locals by the time execution reaches L469 (`balanceInLock` was assigned via a call at L463, but that call has already completed and its *result* is bound to an ordinary local — referencing `balanceInLock` inside the annotation is a plain `varRef`, not a call token). No alpha-style blocker to check.

Alternatives considered, in the README's suggested order:

1. **Directional/state-change relation — inapplicable, not merely rejected.** A directional relation (`x(Exit) >= x(Entry)`-shaped) requires a *before* value of the same variable to compare against. `currentLockRatio` is a `uint256` freshly declared and assigned in a single statement (L468-469) — it has no prior value within this function, and it is not persistent state, so there is no "before" snapshot to pair it with at all. This tier does not apply to this defect's shape (a single fresh-local mis-assignment), unlike `web3bugs_65_H_01`'s `lastFee` (persistent state with a genuine entry value).
2. **Inequality/bound — considered and rejected.** E.g. `currentLockRatio >= balanceInLock.mul(9).div(10)` (a loose tolerance band around `balanceInLock`). Rejected on two independent grounds: (a) README §6's requirement that any introduced constant be traceable to a specific derivation — a `9/10` tolerance here would be arbitrary, invented for no reason other than "looser than equality," with no scenario or source fact backing it; (b) it buys nothing, since the correct value is not approximate but an *exact*, already-in-scope local (`balanceInLock`) — introducing slack only weakens discrimination without any compensating benefit (per R1-3's "don't weaken past the point of losing discriminating power," §4). A bound is the right tool when the intended value is inherently a range; here it is a single already-known quantity.
3. **Relational invariant tying `currentLockRatio` to `newLockRatio`/`totalCVXBalance` directly** (e.g., a generic sanity bound such as `currentLockRatio <= totalCVXBalance`). **Rejected — does not discriminate.** The buggy formula (`balanceInLock * 1e18 / totalCVXBalance`) is *already* `<= totalCVXBalance` in essentially every realistic scenario (it is capped at `1e18`, and `totalCVXBalance` — a raw CVX-wei amount — routinely exceeds `1e18` once holdings pass roughly 1 CVX), so this bound is satisfied by both the buggy and the intended code and catches nothing. This directly illustrates why an inequality built from the "wrong" quantities themselves, rather than from the correct in-scope substitute, is the wrong direction to generalize in.
4. **Downstream/effect-centered alternative — `cvxToLock == newLockRatio - balanceInLock` at `@During`, L488 — considered and rejected as the attachment point, not as a value.** This would check the *consequence* (the corrected amount-to-lock) rather than the *root cause* (`currentLockRatio`'s own value). Rejected for two reasons: (a) **path asymmetry** — L488 executes only on the branch where `newLockRatio > currentLockRatio` is *not* taken to early-return; because the defect itself corrupts which branch is taken (per the Impact statement, the buggy comparison routes execution into the locking branch far more often than intended), the buggy and intended executions frequently **diverge in whether L488 is even reached** for the same input — an annotation placed there cannot be exercised comparably across both versions of the code on a single shared scenario, unlike an attachment point that both versions reach unconditionally. `currentLockRatio`'s own defining statement (L468-469), by contrast, executes identically and unconditionally in every call, on both the buggy and the intended code — the correct place to attach a relation whose job is to check the value at its origin, before any branch-dependent divergence. (b) It is also strictly more implementation-specific: it would tie the relation to the exact shape of `cvxToLock`'s formula (an extra subtraction with two operands the same as the target relation's) rather than the single, minimal, root-cause fact.
5. **Exact equality (SELECTED): `currentLockRatio == balanceInLock`.** Matches the value R1-1 establishes as correct — independently re-derived (not merely copied from the recommendation's prose) **primarily from `MyStrategy`'s own inline comment at the call site** (L462, `// Locked CVX in the locker`, same-function, in-repo evidence — see RQ2-A below for why this alone is sufficient and no cross-contract dependency needs to be counted), **corroborated by `ICvxLocker.balanceOf`'s own interface doc-comment** (*"BOOSTED balance of an account which only includes properly locked tokens..."*) — both directly state that `balanceInLock` *is* "the CVX amount currently locked," which is exactly the quantity `currentLockRatio`'s own name and R1-1's statement-level intent (§ "Statement/line-level intent" above) say it must equal. The in-function comment alone, without needing to inspect any code downstream of the attachment point or any cross-contract interface, already fully establishes the target value.
   **Corroborating (not load-bearing) cross-check — reviewed and reframed to avoid circularity**: the dimensional-consistency requirement of `cvxToLock`'s own consumers (`cvxToLock = newLockRatio.sub(currentLockRatio)` passed as `LOCKER.lock`'s `_amount` argument and compared against `maxCVX = IERC20Upgradeable(CVX).balanceOf(address(this))`, both CVX amounts) independently points to the same conclusion — `currentLockRatio` must share `newLockRatio`'s CVX-amount unit for the subtraction to be dimensionally sound — but this downstream reasoning is used here only as a secondary sanity check, not as the derivation itself: it inspects code purely to confirm (not to establish) that the doc-comment-derived substitution is consistent with the rest of the function, and per README §6's "alternative-rejection inspection doesn't count" corollary, downstream code inspected this way is correctly excluded from RQ2-A's counted footprint (see RQ2-A below) — a framing that would be inconsistent if this downstream argument were instead treated as the relation's actual derivation.

**Required check (§3/R1-3)**: does this equality's negation fail to catch some alternative implementation that retains the *reported* defect (a unit-mismatched `currentLockRatio`) but produces it differently? Checked against two distinct alternative shapes:
- **The actual buggy code**: `currentLockRatio = balanceInLock * 1e18 / totalCVXBalance`. Caught (Violated) — shown numerically below.
- **A structurally different but equally defective miscalculation** — e.g., an implementation that instead computes `currentLockRatio = balanceInLock.mul(5000).div(MAX_BPS)` (a different, equally nonsensical normalization, scaling by an arbitrary 50%-style factor rather than by `1e18/totalCVXBalance`): also caught, since this value equals `balanceInLock` only in the coincidental degenerate case `balanceInLock == 0`, which is excluded by the discrimination scenario's own nonzero `balanceInLock`. No plausible unit-mismatched variant of `currentLockRatio` escapes the equality except by numerical coincidence in a specific execution, not systematically.
- Two genuine, narrower **edge cases worth flagging explicitly** (not a gap in the required check, but a scenario-choice caution — corrected on review, the earlier draft named only one and stated it too strongly): (1) `totalCVXBalance == 1e18` precisely (an extreme, non-representative edge where total holdings equal exactly `1e18` wei of CVX-equivalent, i.e. exactly 1 CVX) makes the buggy formula's normalization factor equal `1`, so it coincides exactly with `balanceInLock` at that single point; (2) more simply, **`balanceInLock == 0`** — the buggy formula is `balanceInLock * 1e18 / totalCVXBalance`, which is `0` whenever `balanceInLock` is `0`, for *any* nonzero `totalCVXBalance`, exactly matching the intended value `0` — a broader, more easily-hit coincidence than case (1), not requiring any special `totalCVXBalance` value at all. Both are **reachability/scenario-selection** concerns, not defects in the relation itself: the discrimination scenario below is deliberately chosen with `totalCVXBalance != 1e18` and `balanceInLock > 0` (as any realistic, actively-rebalancing strategy holding would be), and README's own scenario-conditioning discipline (§4) is the right place to note this, not a weakening of the selected relation. **No genuine gap found for any non-degenerate scenario** (`balanceInLock > 0` and `totalCVXBalance != 1e18`); this case does not need a coverage flag on this ground.

**Winner: Alternative 5 (exact equality), attached at `currentLockRatio`'s own defining statement.**

**Discrimination check (explicit arithmetic, per §9 checklist item 1).** Scenario constructed directly from the report's own stated formulas (no PoC narrative exists in this report to draw numbers from, per the header note): `balanceOfCVX = 100e18` (100 CVX free/liquid), `balanceInLock = 400e18` (400 CVX currently locked), `wantToCVX(balanceOfWant) = 0` (no liquid `want`-form holdings, to keep the scenario minimal) leading to `totalCVXBalance = 100e18 + 400e18 + 0 = 500e18` (500 CVX total; not equal to `1e18`, satisfying the non-degeneracy caution above).

- **Buggy** (current code, L468-469): `currentLockRatio = balanceInLock * 10**18 / totalCVXBalance = 400e18 * 1e18 / 500e18 = 0.8e18` (i.e., "80%," a normalized fraction). Check: `currentLockRatio == balanceInLock` gives `0.8e18 == 400e18` -> **false, Violated.**
- **Intended** (per the independently re-derived substitution): `currentLockRatio = balanceInLock = 400e18`. Check: `400e18 == 400e18` -> **true, Satisfied.**

**Corroborating the report's own "locks nearly everything" Impact claim** (context only — not part of the annotated relation itself, since it requires values downstream of the attachment point that R1-3's alternative-4 analysis already excluded as non-load-bearing/path-asymmetric): with `toLock = 8000` (80% target), `newLockRatio = totalCVXBalance * toLock / MAX_BPS = 500e18 * 8000 / 10000 = 400e18`. **Buggy**: is `newLockRatio(400e18) <= currentLockRatio(0.8e18)`? False, so does *not* early-return; `cvxToLock = 400e18 - 0.8e18 = 399.2e18`, exceeding `maxCVX = balanceOfCVX = 100e18`, so the strategy locks **all** of its free CVX (100 CVX) — even though the target (80% of 500 CVX = 400 CVX) is already met by the 400 CVX already locked. **Intended**: is `newLockRatio(400e18) <= currentLockRatio_intended(400e18)`? True (equal), so it early-returns, depositing the free CVX into the vault instead of locking it. This concretely reproduces the report's "locking nearly everything" Impact claim and confirms the root-cause relation's discrimination is not merely formal but tracks the reported real-world consequence.

## R1-4 — During vs Post

**Chosen: During.** The relation concerns a single intermediate local's statement-time value (README's own During criterion: "an intermediate expression... a statement-time value... tied to one statement" applies directly) — `currentLockRatio` is not persistent state, has no meaningful "entry" value, and is not the function's return value or a final-state quantity; it is consumed later within the *same* function call by the branch condition (L477) and the subtraction (L488), both downstream of its own assignment. This is the same shape as `web3bugs_29_H_11`'s `amount0`/`amount1` locals-checked-at-their-own-definition pattern, not `web3bugs_65_H_01`'s persistent-state `@Post` pattern (there was no analogous local to check there; here there is, and it is exactly what's disputed).

**No snapshot-qualifier syntax (`(Entry)`/`(Exit)`/`(Before)`/`(After)`/`(Assign)`) is needed.** Both operands (`currentLockRatio`, `balanceInLock`) are read at the *same* single program point (immediately after L468-469), with no before/after or entry/exit pairing involved — an ordinary unqualified `@During` comparison of two locals current at that point.

**Required explicit delta-exception check (README §4/R1-7).** `manualRebalance` contains **no loop of any kind** — confirmed by reading its entire body (L444-508: a `require`, two optional `if`-guarded single calls, a sequence of local assignments, one `if`/early-return branch, and a final `if`/`else` lock dispatch — no `for`/`while` anywhere). The disputed statement (L468-469) is a plain sequential assignment, not inside any conditional or loop construct at all — the most clear-cut "no loop, no branch, unconditionally reached" case encountered in this batch, more clean-cut even than `web3bugs_65_H_01`'s (which at least needed a branch to be reached). `manualRebalance` does call `harvest()` (L454) conditionally, and `harvest()` (defined elsewhere in `MyStrategy`) may itself contain loop-adjacent logic, but that call, if taken, completes and returns *before* the target statement executes and is unrelated to `currentLockRatio`'s own CFG location — it does not place L468-469 inside any `loop_nodes` member of `manualRebalance`'s own CFG. **Delta confirmed not applicable.**

## R1-6 — Construct the target annotation

**Attachment point**: immediately after the disputed `currentLockRatio` assignment (L468-469), before `newLockRatio`'s own assignment (L471) — this textual-placement convention matches this project's other `@During` write-ups (e.g. `web3bugs_29_H_11`), and is also the *only* point that is reached identically and unconditionally on both the buggy and the intended execution (R1-3's rejection of the downstream `cvxToLock`-based alternative established this explicitly).

**Scenario precondition this instantiation relies on**: none beyond ordinary reachability — `manualRebalance` reaches L468-469 unconditionally on every non-reverting call (gated only by `require(toLock <= MAX_BPS, ...)`, a pure input-validity check unrelated to this defect). The only scenario-selection caution is the non-degeneracy note from R1-3 (`totalCVXBalance != 1e18`), which is a property of the chosen `balanceOfCVX`/`balanceInLock` inputs, not a precondition the annotation itself needs to encode.

**Target annotation**:
```solidity
function manualRebalance(uint256 toLock) external whenNotPaused {
    _onlyGovernance();
    require(toLock <= MAX_BPS, "Max is 100%");

    if (processLocksOnRebalance) {
        LOCKER.processExpiredLocks(false);
    }
    if (harvestOnRebalance) {
        harvest();
    }

    uint256 balanceOfWant = IERC20Upgradeable(want).balanceOf(address(this));
    uint256 balanceOfCVX = IERC20Upgradeable(CVX).balanceOf(address(this));
    uint256 balanceInLock = LOCKER.balanceOf(address(this));
    uint256 totalCVXBalance =
        balanceOfCVX.add(balanceInLock).add(wantToCVX(balanceOfWant));

    uint256 currentLockRatio =
        balanceInLock.mul(10**18).div(totalCVXBalance);
    // @During currentLockRatio == balanceInLock
    uint256 newLockRatio = totalCVXBalance.mul(toLock).div(MAX_BPS);
    ...
}
```
Both referenced identifiers (`currentLockRatio`, `balanceInLock`) are ordinary in-scope `uint256` locals at this exact program point — no synthetic constant is introduced (README's `900`-style derived-constant guidance does not apply; the relation's RHS is an already-computed local, not a scenario-specific literal).

**Quantification note**: the property is a plain scalar-local check (`currentLockRatio`/`balanceInLock` are single `uint256` values, not array/mapping elements) — not a claim quantified over a stored collection of co-existing elements. No representative-element instantiation issue applies.

## Section 5 — Value/Algorithm and Usable/Unusable

- **Algorithm-level** (revised on review — see below). The intended computation for `currentLockRatio` requires **zero** additional processing steps — its correct value is simply `balanceInLock`, a quantity *already fully computed* two lines earlier for exactly this purpose. The buggy code instead applies an entire spurious normalization procedure (`.mul(10**18).div(totalCVXBalance)`) that should not execute at all. That distinction is real, but it does not settle Value vs. Algorithm on its own — README §4's "missing/**extra**/misordered operation" phrasing does not require the extra operation to be the *mirror image* of a needed-but-absent one; a normalization pass that should not exist at all is still an extra operation, on the same footing as one that should exist but doesn't. `16_H_06` and this case are Algorithm-level for symmetric but not identical reasons — `16_H_06` is missing a needed step, this case contains an unneeded one — and README's own text already anticipates and names both.
