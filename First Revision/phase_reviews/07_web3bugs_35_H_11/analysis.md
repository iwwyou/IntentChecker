## R1-1 -- Reported Behavior Reconstruction

**Contract/function role**: `Ticks` is a library managing a linked list of initialized ticks (and their per-tick fee-growth-outside / seconds-per-liquidity-outside snapshots) for a Uniswap-v3-style concentrated-liquidity AMM pool. `cross(...)` is called by the pool contract when the swap's current price crosses a tick boundary, to (a) flip that tick's `secondsPerLiquidityOutside` snapshot, (b) update the running `currentLiquidity` in the swap's direction, (c) advance `nextTickToCross` to the next tick in the list, and (d) flip the newly-current tick's fee-growth-outside snapshot for the token whose fees are being accumulated on this swap.

**Relevant locals/params**: `zeroForOne` (param) -- swap direction; true means token0 is being sold for token1. `nextTickToCross` (param, **reassigned mid-function**, line 39/48) -- starts as the tick being crossed *from*, and is overwritten with the tick being crossed *into* before the fee-growth line executes. `feeGrowthGlobal` (param) -- the accumulator value the caller passes in. `ticks[.].feeGrowthOutside0` / `.feeGrowthOutside1` -- the two per-tick snapshots being rolled.

**The two branches**:
```solidity
if (zeroForOne) {
    ...
    nextTickToCross = ticks[nextTickToCross].previousTick;                                            // line 39
    ticks[nextTickToCross].feeGrowthOutside0 = feeGrowthGlobal - ticks[nextTickToCross].feeGrowthOutside0;  // line 40 -- BUGGY
} else {
    ...
    nextTickToCross = ticks[nextTickToCross].nextTick;                                                 // line 48
    ticks[nextTickToCross].feeGrowthOutside1 = feeGrowthGlobal - ticks[nextTickToCross].feeGrowthOutside1;  // line 49 -- BUGGY
}
```

**Cross-contract fact needed to fix which field is correct** (report, quoting the pool contract `ConcentratedLiquidityPool` -- not present in local `Dependencies/`, read via the report's quotation): swap fees are always taken from the *output* token, and the caller initializes the accumulator passed into `cross` as `feeGrowthGlobal = zeroForOne ? feeGrowthGlobal1 : feeGrowthGlobal0;` -- i.e. when `zeroForOne` is true, the `feeGrowthGlobal` argument **is** `feeGrowthGlobal1` (token1's global accumulator), and vice versa.

**Reported erroneous behavior**: `cross()`'s field selection is the reverse of this convention -- the `zeroForOne` branch (line 40) rolls `feeGrowthOutside0` and the else branch (line 49) rolls `feeGrowthOutside1`, when the caller's convention requires the opposite in each branch. Sponsor-confirmed. Impact: `feeGrowthOutside0`/`feeGrowthOutside1` for affected ticks end up permanently misattributed, corrupting downstream fee-owed calculations.

**Patch intent** (evidence only, not transcribed): swap which field (`0` vs `1`) each branch writes.

**Bug-relevant intended numeric behavior**: in the `zeroForOne` branch, after `nextTickToCross` has been advanced to the tick being crossed into (line 39), it is `feeGrowthOutside1` of that tick -- not `feeGrowthOutside0` -- that must be rolled (overwritten to reflect `feeGrowthGlobal` minus its prior snapshot). The bug writes the sibling field instead, leaving the field that should change untouched.

## R1-2 -- Intent Abstraction

Distinguishing property (patch syntax dropped), stated exactly: under `zeroForOne`, once `nextTickToCross` has been advanced to the post-crossing tick (line 39), that tick's `feeGrowthOutside1` must be updated to `feeGrowthGlobal - feeGrowthOutside1`(its own prior snapshot) -- that is the field, and the exact formula, the caller's fee-accounting convention says this branch is responsible for. The buggy code applies no such update to it at all -- it modifies a sibling field of the same struct instead, per a formula that never touches `feeGrowthOutside1`. **Intent-level orientation: Effect/state-transition-centered** (README Section 4, R1-2) -- the claim is about *which field the statement is required to modify and by what rule*, not a bound on an already-agreed-upon value. This is analogous to the paper's own `changed(previousPrices[0], true)` example only at the coarsest level (which field must move); R1-3 records the exact formula directly wherever the grammar allows it, per the same discipline followed in `web3bugs_42_H_01`.

## R1-3 -- Select the least implementation-specific sufficient relation (alternatives recorded, Section 7)

A structural note first, because it drives every option below: `nextTickToCross` is **reassigned on line 39**, strictly before the target line 40. Its function-*entry* value is the tick being crossed *from*; from line 39 onward it is the tick being crossed *into*. Any candidate relation that evaluates `ticks[nextTickToCross].feeGrowthOutside1` once using sigma_entry's binding of `nextTickToCross` and once using a later state's binding is silently comparing **two different ticks' storage** -- not a before/after of the same cell. This rules out sigma_entry-anchored forms outright (see options 1a and 4b below) and is the reason option 1b/selected is anchored the way it is.

**Bug-relevant intent, stated exactly (R1-2), before any weakening**: under `zeroForOne`, once `nextTickToCross` has been advanced to `Y` (line 39), the correct update is `ticks[Y].feeGrowthOutside1 == feeGrowthGlobal - ticks[Y].feeGrowthOutside1(Before)` -- the new value must equal `feeGrowthGlobal` minus the tick's *own prior* snapshot, not merely "some change happened" to the field. The alternatives below were originally organized around the fact that this exact form used to be grammar-inexpressible; that blocker is now resolved (see the correction to option 4 below), so it is the selected relation, not a fallback.

1. **Directional/state-change relation**:
   - **(a) `changed(ticks[nextTickToCross].feeGrowthOutside1, true)`** (rule C_chg): **rejected -- unsound for this variable, not just non-discriminating.** C_chg's definition fixes one side of every comparison to `eval(sigma_entry, e)`. Here sigma_entry's `nextTickToCross` is the pre-crossing tick (call it `X`), while every other state in Pi (from line 39 onward) has `nextTickToCross = Y` (the post-crossing tick, `Y = ticks[X].previousTick`). So this form would compare `ticks[X].feeGrowthOutside1` against `ticks[Y].feeGrowthOutside1` -- different storage cells, not a real "did it change" question. Excluded regardless of discrimination.
   - **(b) `ticks[nextTickToCross].feeGrowthOutside1 (before != after)`** (rule D_ba), @During, attached immediately after line 40: valid, expressible, discriminates (see below) -- but **superseded by option 4 below** now that the exact relation is expressible. Kept as the record of this case's original selection; see R1-7's Intent-coverage note for why it is no longer preferred. Placed this way, "the statement at the annotated line" is line 40 itself, so both sigma_before (immediately before line 40 runs) and sigma_pt (immediately after) fall *after* line 39's reassignment -- both bind `nextTickToCross = Y`, the same tick, on both sides of the comparison, which is exactly the stable-index property option 4's new form also relies on (below).

2. **Inequality/bound** -- e.g. `ticks[nextTickToCross].feeGrowthOutside1 (before < after)`: **rejected -- not supported by the reported behavior.** The report establishes *which field* must change, not that the new snapshot must exceed the old one; `feeGrowthGlobal` vs. the prior per-tick snapshot has no established ordering in the report or in `cross`'s own code (nothing prevents `feeGrowthGlobal` being less than `feeGrowthOutside1`'s old value on some path). Asserting a direction here would smuggle in an assumption condition (a) of R1-3 doesn't support -- it happens to hold in the numeric scenario below, but that's incidental to the scenario's chosen numbers, not something the report backs in general.

3. **Relational invariant** -- the paired form `ticks[nextTickToCross].feeGrowthOutside0 (before == after)` (asserting the *sibling* field is untouched), alongside 1(b): **not selected, not needed for sufficiency.** Recorded here as a legitimate companion, not part of the target annotation. Worth noting for completeness: this companion has the *same* kind of blind spot as 1(b) did -- if the buggy code's own assignment to `feeGrowthOutside0` happened to satisfy `feeGrowthGlobal == 2 * feeGrowthOutside0(Before)`, the buggy write would leave `feeGrowthOutside0` numerically unchanged too, and this relation would wrongly read "Satisfied" despite the wrong field still being written. Not a reason to add it as a second required annotation; recorded because it shows the "sibling unchanged" idea is not a free, unconditionally-sound alternative either.

4. **Exact equality** -- the literal intended formula, `ticks[nextTickToCross].feeGrowthOutside1 == feeGrowthGlobal - ticks[nextTickToCross].feeGrowthOutside1(Before)` (selected):
   - **(a) Via D_ba**: still not expressible through this specific rule -- D_ba's template rigidly compares `eval(sigma_before, e)` to `eval(sigma_pt, e)` for the *same* single expression `e`, with no way to inject a third free term (`feeGrowthGlobal`).
   - **(b) Via a plain common-form equality with a snapshot-qualified reference (selected)**: the grammar's snapshot-qualified-reference extension (README/`main.tex`) adds exactly the missing capability -- `varRef(Before)` lets any reference inside an arithmetic expression be pinned to $\sigma_{\text{before}}$ independently of the rest of the expression, without needing a dedicated D_ba-style clause. `ticks[nextTickToCross].feeGrowthOutside1 == feeGrowthGlobal - ticks[nextTickToCross].feeGrowthOutside1(Before)` is now an ordinary $(C_{\text{cmp}})$ instance: the left-hand `feeGrowthOutside1` and `feeGrowthGlobal` read the ambient reference point ($\sigma_{\text{pt}}$, i.e. post-line-40), while `feeGrowthOutside1(Before)` reads $\sigma_{\text{before}}$ explicitly -- no self-substitution collapse, because the two occurrences of `feeGrowthOutside1` are now genuinely pinned to different snapshots rather than both silently reading $\sigma_{\text{pt}}$. The stable-index property already established for option 1(b) carries over unchanged: `nextTickToCross` was already reassigned by line 39, strictly before this attachment point, so both the ambient and the `(Before)`-qualified occurrences of `ticks[nextTickToCross]...` index the *same* tick `Y` -- this relation does not reopen the two-different-ticks risk that ruled out sigma_entry-anchored forms.

**Selected**: `ticks[nextTickToCross].feeGrowthOutside1 == feeGrowthGlobal - ticks[nextTickToCross].feeGrowthOutside1(Before)` (option 4b). It states the exact reported update formula directly (R1-2), is now expressible without any grammar gap, and remains anchored to a single stable tick the same way option 1(b) was -- strictly more informative than 1(b) on every count that matters here, per R1-7's Intent-coverage note.

**Discrimination check (concrete scenario, numeric)**: let the tick crossed *from* be `X = 6`, with `ticks[6].previousTick = 4`, so after line 39, `nextTickToCross = Y = 4`. Let `ticks[4].feeGrowthOutside1 = 30` (pre-existing snapshot) and `feeGrowthGlobal = 100` (the value the caller passes in when `zeroForOne` is true, i.e. `feeGrowthGlobal1`).

- **Buggy code (as written, line 40 writes `feeGrowthOutside0`)**: `ticks[4].feeGrowthOutside1` is never touched by line 40. `feeGrowthOutside1(Before) = 30`, ambient `feeGrowthOutside1 = 30` (untouched). Check: `30 == 100 - 30` → `30 == 70` → **false ⟹ Violated** -- correctly flags the bug.
- **Intended code (hypothetical: line 40 rolls `feeGrowthOutside1` instead)**: `ticks[4].feeGrowthOutside1 = 100 - 30 = 70`. `feeGrowthOutside1(Before) = 30` (unchanged -- it's the pre-line-40 value regardless of what line 40 does), ambient `feeGrowthOutside1 = 70`. Check: `70 == 100 - 30` → `70 == 70` → **true ⟹ Satisfied** -- accepts the intended behavior.
- **On the `feeGrowthGlobal == 2 * feeGrowthOutside1(Before)` coincidence** (the same one that broke option 1(b), R1-2): this new relation is *unconditionally sound* on the accept side -- algebraically, `new == feeGrowthGlobal - old(Before)` holds for *any* `feeGrowthGlobal`/`old` combination whenever the intended code's own formula (`new = feeGrowthGlobal - old`) actually ran, so a genuinely correct implementation is never mis-flagged as Violated, unlike 1(b) (worked example: at `feeGrowthGlobal = 60, old = 30`, the intended code gives `new = 30`, and `before != after` is false even though the correct formula ran -- 1(b) would wrongly report Violated there; this relation reports `30 == 60 - 30` = true, correctly Satisfied). The relation is *not* claimed to be unconditionally complete on the reject side, though: at that same `feeGrowthGlobal = 60, old = 30` input, the *buggy* code (which leaves `feeGrowthOutside1` untouched at `30`) would also satisfy `30 == 60 - 30`, i.e. this specific coincidental input would fail to discriminate under either relation. This does not affect the case's own discrimination check above, which uses `feeGrowthGlobal = 100` specifically because it avoids the coincidence -- it is noted here only so the relation's guarantee is stated precisely: sound (no false violations) on any input, and discriminating (as demonstrated) on the constructed scenario, not claimed to catch the bug on every conceivable input.

## R1-4 -- During vs Post

**Chosen: During.** Beyond the general README guidance (an intermediate, statement-time value, not a function-wide invariant), this case has a specific, additional reason: `nextTickToCross`'s identity shifts partway through the function (line 39). Any Post form -- entry/exit (P_ee) or `changed(e,.)` (C_chg, which is defined for either kind but always anchors one side to sigma_entry) -- would evaluate `nextTickToCross` once at sigma_entry (still `X`) and once at sigma_exit/a later Pi state (already `Y`), producing a comparison across two different ticks' storage rather than a same-cell before/after (see R1-3, option 1a/4a). @During, anchored immediately around line 40 itself, is the only placement where both sides of the comparison are guaranteed to bind `nextTickToCross` to the same tick.

## R1-5 -- Relation form

**Exact equality**, via the common-form rule `intentValue relOp intentValue` ($C_{\text{cmp}}$), inside `@During` (`ref(Gamma) = sigma_pt` for the ambient/unqualified occurrences), with the snapshot-qualified reference `feeGrowthOutside1(Before)` reading $\sigma_{\text{before}}$ for the one term that must be pinned to the pre-line-40 value. Not $(D_{\text{ba}})$ any more -- that rule's `(before relOp after)` template only ever compares the *same* single expression at two timepoints, which cannot state "new equals a formula combining old and a third quantity"; the snapshot-qualified extension supersedes it here for exactly the reason R1-3 option 4 lays out. Not C_chg's `changed(.)` form despite the similar spirit, for the entry-anchoring reason in R1-4. Equality here is not a mechanical copy of the patch's assignment operator -- it is the literal reported formula (R1-2), which happens to be an equality regardless of what operator the patch's own statement used.
