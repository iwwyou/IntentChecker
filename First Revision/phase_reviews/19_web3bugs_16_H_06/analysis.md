## R1-1 — Reported Behavior Reconstruction

**Contract/function role.** `GasOracle` is a sample Tracer `IOracle` implementation that reports a gas-cost estimate denominated in USD. It composes two upstream Chainlink-style oracles: `gasOracle` (a "GAS in ETH"-style fast-gas feed) and `priceOracle` (a "quote/ETH" feed, e.g. ETH/USD). `latestAnswer()` is the sole externally consumed entry point (`IOracle.latestAnswer()`); its own doc-comment states the required output convention explicitly: *"Returned value is USD/Gas × 10^18 for compatibility with rest of calculations"* (L28-29) — i.e. the function must return a WAD (18-decimal) fixed-point USD/Gas price.

**Relevant locals/state (`latestAnswer()`, L31-37):**
- `gasPrice` (local, L32) = `uint256(gasOracle.latestAnswer())` — the fast-gas oracle's raw answer, cast from `int256` to `uint256`.
- `ethPrice` (local, L33) = `uint256(priceOracle.latestAnswer())` — the quote/ETH oracle's raw answer, same cast.
- `result` (local, L35) = `PRBMathUD60x18.mul(gasPrice, ethPrice)` — a WAD (18-decimal) fixed-point multiplication (`PRBMathCommon.mulDivFixedPoint(x, y)`, confirmed by direct read of `PRBMathUD60x18.sol`/`PRBMathCommon.sol`: for the realistic non-overflowing case, `= floor(x·y / 1e18) + (1 if (x·y mod 1e18) > 0.5·1e18 else 0)`) — i.e. `PRBMathUD60x18.mul` is only mathematically correct when **both of its inputs are already WAD-scaled (18-decimal) values**.
- **The disputed statement (L35-36)**:
  ```solidity
  uint256 result = PRBMathUD60x18.mul(gasPrice, ethPrice);
  return result;
  ```
- `toWad(uint256 raw, IChainlinkOracle _oracle)` (L45-52) — a helper **defined in the same contract but never called anywhere** (confirmed by reading the whole file — the only two call sites of `_oracle`/`IChainlinkOracle` are `gasOracle.latestAnswer()`/`priceOracle.latestAnswer()` in `latestAnswer()` itself; `toWad` has zero callers). Its own body: `_decimals = oracle.decimals(); require(_decimals <= MAX_DECIMALS, ...); scaler = 10**(MAX_DECIMALS - _decimals); return raw * scaler;` (`MAX_DECIMALS = 18`, contract-level constant, L20). **Scope caveat (added on review):** `toWad`'s own `require(_decimals <= MAX_DECIMALS, ...)` means this formula only *upscales* — it has no branch for an oracle reporting *more* than 18 decimals (which would need a downscaling division, not a multiplication). `toWad` is therefore the contract's existing normalization scheme for oracle precisions up to 18 decimals, not a fully general "any decimals" solution — worth stating precisely, since the report's own "could be anything" framing doesn't itself distinguish this. This doesn't affect the reported defect or the selected relation (the constructed scenario's decimals, 9 and 6, are both within `toWad`'s supported range) — it is a corroborating, not a defining, piece of evidence for what's missing in `latestAnswer()`; see the reframed Algorithm-level justification in §5 below.
- `IChainlinkOracle.decimals()` (interface, `IChainlinkOracle.sol` L27) — every Chainlink-conforming oracle exposes its own answer's decimal precision alongside `latestAnswer()`; nothing in the interface or in `GasOracle.sol` establishes that `latestAnswer()`'s raw integer is always already WAD-scaled — `decimals()` existing as its own accessor is precisely why a caller must consult it (or a stored assumption of it) before combining answers from different oracles.

**Variable-value intent (L35, `result`).** `result` must equal the USD/Gas price at 18-decimal precision — i.e. both `gasPrice` and `ethPrice` must be normalized to 18 decimals (via each oracle's own `decimals()`) *before* being passed into the WAD multiplication; the code currently passes each oracle's **raw** answer directly.

**Reported erroneous behavior** (H-06, verbatim): *"The `GasOracle` uses two chainlink oracles (GAS in ETH with some decimals, USD per ETH with some decimals) and multiplies their raw return values to get the gas price in USD. However, the scaling depends on the underlying decimals of the two oracles and could be anything. But the code assumes it's in 18 decimals... There is a `toWad` function that seems to involve scaling but it is never used. The impact is that, if the scale is wrong, the gas price can be heavily inflated or under-reported."* Sponsor (`raymogg`) confirmed the underlying issue (disputed only severity, noting production deployments would use "production Chainlink feeds for which the decimals are known at deploy time" — not disputing that the code is wrong for arbitrary/misconfigured oracles). Judge kept it High.

**Expected/intended behavior**: `result` should equal `PRBMathUD60x18.mul` applied to `gasPrice` and `ethPrice` **after each has been scaled to 18 decimals** relative to its own oracle's `decimals()` — i.e., the missing step is exactly `toWad`'s own (unused) formula, `raw × 10^(18 − oracle.decimals())`, applied to each of `gasPrice`/`ethPrice` individually before the multiplication.

**Patch intent**: the report gives **no diff/patch code**, only a qualitative recommendation ("check `chainlink.decimals()`... scale the answers to 18 decimals... no matter the decimals of the underlying oracles"). There is therefore no literal patch syntax to risk transcribing (§2/§3 moot by construction) — the correction below is derived directly from `toWad`'s own already-present (if dead) formula and the function's own 18-decimal doc-comment, not guessed at.

**Concrete scenario (constructed, not from the report — H-06 supplies no PoC/numbers at all beyond the qualitative argument quoted above).** `gasOracle.decimals() = 9` (a **source-hinted** value: `toWad`'s own body carries the inline comment `uint8 _decimals = oracle.decimals(); // 9`, L48 — read as the developer's own illustrative example, not an authoritative/enforced value); `priceOracle.decimals() = 6` (a **constructed** value, deliberately different from `gasOracle`'s to exercise both oracles' independent scale factors — not sourced from the report or the code, and not asserted to be a realistic real-world Chainlink decimals value, only an architecturally reachable one: `setGasOracle`/`setPriceOracle` accept *any* `IChainlinkOracle`-conforming address with no decimals check anywhere in `latestAnswer()`'s own execution path). Raw answers: `gasPrice = 5×10^9`, `ethPrice = 3×10^9` (arbitrary round numbers chosen so the arithmetic below has no fixed-point rounding remainder — verified explicitly).

- **Buggy** (current code, `PRBMathUD60x18.mul(gasPrice, ethPrice)`): `gasPrice·ethPrice = 5×10^9 × 3×10^9 = 1.5×10^19`. `1.5×10^19 / 10^18 = 15` exactly (`1.5×10^19 mod 10^18 = 0` ⟹ no rounding-up correction, and `1.5×10^19 ≪ 2^256` ⟹ no overflow branch). **`result = 15`.**
- **Intended** (scale each price to 18 decimals first, per `toWad`'s formula: scaler `= 10^(18−9) = 10^9` for `gasPrice`, `= 10^(18−6) = 10^12` for `ethPrice`): scaled `gasPrice' = 5×10^9 × 10^9 = 5×10^18`; scaled `ethPrice' = 3×10^9 × 10^12 = 3×10^21`. `gasPrice'·ethPrice' = 1.5×10^40`. `1.5×10^40 / 10^18 = 1.5×10^22` exactly (`1.5×10^40 mod 10^18 = 0` ⟹ no rounding correction; `1.5×10^40 ≪ 2^256 ≈ 1.16×10^77` ⟹ no overflow branch). **Intended `result = 1.5×10^22`.**
- Buggy (`15`) vs. intended (`1.5×10^22`): off by a factor of `10^21` — a massive under-report, matching the report's own "heavily... under-reported" characterization for the case where both oracles use fewer than 18 decimals.

**Bug-relevant intended numeric behavior**: for any execution where `gasOracle`/`priceOracle` are Chainlink-conforming oracles reporting at their own (potentially non-18) `decimals()`, `latestAnswer()`'s `result` must equal `PRBMathUD60x18.mul` applied to *decimals-normalized* `gasPrice`/`ethPrice`, not the raw values — a specific, derivable missing pair of scaling factors, not a vague "value might be off" claim.

## R1-3 — Select the least implementation-specific sufficient relation

**Preliminary check — does the natural statement of intent require a function call inside `intentValue`?** The most direct phrasing of the fix is "`result` should equal `PRBMathUD60x18.mul(toWad(gasPrice, gasOracle), toWad(ethPrice, priceOracle))`" — which nests **three** call layers (`toWad` ×2, each internally calling `oracle.decimals()`, plus `PRBMathUD60x18.mul` itself) inside what would be `intentValue`. The grammar's `intentValue` (`arithExpr`, `Parser/Solidity.g4` lines 341-376) has no call syntax at all — only literals, `varRef`s (with member/index/snapshot-qualifier access), parenthesized arithmetic, and `+ - * / % **`. Checked against README's required rescue before declaring this Inexpressible:

- **`oracle.decimals()` calls**: rescued the same way Nokon's `calculateRate()` is — for the *constructed scenario* above, `gasOracle.decimals()` and `priceOracle.decimals()` are treated as **fixed inputs to that scenario** (9 and 6 respectively), not values the annotation itself needs to query; the corresponding scalers (`10^9`, `10^12`) become ordinary number literals via `IntentExponentiation` (`arithFactor '**' arithExp`), not calls. This is a scenario-instantiation rescue rather than a Nokon-style "known minimum bound" rescue (there is no protocol-enforced decimals invariant here to bound against — see the explicit caveat in R1-6/R1-7 below on why this differs from `web3bugs_70_H_05`'s stronger, enforced-invariant version of the same rescue pattern).
- **`PRBMathUD60x18.mul` call**: **not** rescued the way `web3bugs_3_H_04`'s `applyInterest` was (there, the callee's *entire* behavior, for *all* inputs, was one unconditional arithmetic line, so inlining it was fully general). `PRBMathUD60x18.mul`/`PRBMathCommon.mulDivFixedPoint` is **not** unconditionally `⌊x·y/10^18⌋` — it has a conditional +1 rounding-up branch (confirmed by direct read of `PRBMathCommon.sol` L265-302: `roundUpUnit := gt(remainder, 499999999999999999)`, i.e. `remainder >= HALF_SCALE`, added when `prod1 == 0`) and a separate 512-bit-division branch (`prod1 != 0`) for `x·y` overflowing 256 bits. The rescue used here is narrower and must be stated honestly: the constructed scenario's *specific* numbers were chosen so that `(gasPrice·ethPrice) mod 10^18 = 0` and `(scaled gasPrice·scaled ethPrice) mod 10^18 = 0` **on both the buggy and the intended computation** (verified arithmetically above), and neither product approaches `2^256`, so for *this scenario only*, `PRBMathUD60x18.mul(x, y) = (x·y)/10^18` exactly, representable as ordinary `arithTerm` division. This is a scenario-conditioned inlining, not a general one — flagged explicitly, not glossed over (§4's non-negativity/casting-style caution: state each sub-claim at its actual precision). **Reviewer-added precedent note**: this is not a novel rescue pattern in this batch — `web3bugs_70_H_05`'s own R1-1 (L39 of that case's `analysis.md`) inlines `FixedPoint.mul()`/`.decode144()` the identical way, verifying `(2^112).mul(1e18).decode144() = (2^112 * 1e18) >> 112 = 1e18` is "exact — `2^112 * 1e18` is exactly divisible by `2^112`, so no truncation in this scenario," and that case's `External specification required: No` / `Expressible: Yes` verdicts were reached (and this project's Agent B review process did not flag the technique as a methodological problem) on a relation built the same way. This case's `PRBMathUD60x18.mul` rescue is therefore consistent with, not a departure from, existing accepted practice in this benchmark.

With both calls addressed this way, no call remains inside the final `intentValue`.

1. **Directional (weakest tier)**: e.g. "`result` increases as `gasPrice`/`ethPrice` increase." **Rejected — not discriminating.** True identically under the buggy and any correctly-scaled formula (both are monotonic products); says nothing about which scale is used.
2. **Inequality with an arbitrary/partial scale correction**: e.g. `result >= (gasPrice * (10**5) * ethPrice * (10**8)) / (10**18)`. **Rejected.** Per README's explicit caution (§4/R1-3), the exponents `5`/`8` here are not derived from anything (not `18 − gasOracle.decimals()`, not `18 − priceOracle.decimals()` for the scenario's own chosen decimals) — an arbitrary magnitude that happens to "look like" a partial fix. Worse, being *only* a lower bound, it fails the required negation check below.
3. **Pure lower bound tied to the correctly-derived scalers**: `result >= (gasPrice * (10**9) * ethPrice * (10**12)) / (10**18)`. **Considered and rejected** — see the required negation check immediately below; this specific, non-arbitrary form still fails to catch an "over-scaled" defect-retaining alternative, which the report's own language ("heavily inflated *or* under-reported") explicitly names as a possible manifestation of the same root defect.
4. **Two-sided bound accounting for `PRBMathUD60x18.mul`'s known ±1-wei rounding envelope**: `(gasPrice*(10**9)*ethPrice*(10**12))/(10**18) <= result <= (gasPrice*(10**9)*ethPrice*(10**12))/(10**18) + 1`. **Considered — a genuinely more general, rounding-robust form** (it does not depend on the scenario's numbers having zero remainder) that also passes the negation check below (verified: an over-scaled alternative violates the upper half). **Not selected**, in favor of (5): given the constructed scenario already has zero remainder in both the buggy and intended computations (verified above), the extra `+1` slack buys generality the scenario doesn't need, at the cost of a two-clause form that departs from every precedent case in this batch (`59_H_04`, `3_H_04`, `70_H_05`), all of which use a single relational clause. Recorded here as a legitimate, more-general alternative that a different scenario choice would make necessary.
5. **Exact equality (SELECTED)**: `result == (gasPrice * (10**9) * ethPrice * (10**12)) / (10**18)`. Ties the correction to the two concrete, `toWad`-formula-derived scalers for the constructed scenario's decimals (`10^(18−9)=10^9`, `10^(18−6)=10^12`), fully in-scope (`gasPrice`, `ethPrice`, `result` are locals; the RHS is ordinary arithmetic), and — because the scenario's remainder is verified zero on both sides — exact, not merely a bound. Matches `web3bugs_70_H_05`'s reasoning for the same category of defect: a scale/unit-conversion fact is not naturally a "bound," it is either applied correctly or not.

**Selected: Alternative 5.**

**Required negation check (§3/§4 R1-3)**: does this relation's negation fail to catch some alternative implementation that retains the reported defect but produces it differently? Checked against three distinct alternative-implementation shapes, all producing `result` values other than the buggy `15` or the intended `1.5×10^22`:
- **No scaling at all (the actual buggy code)**: `result = 15`. `15 == 1.5×10^22` → false → correctly flagged.
- **Partial scaling** (scales only `gasPrice`, leaves `ethPrice` raw): `result = ⌊(5×10^18 × 3×10^9)/10^18⌋ = 1.5×10^10`. `1.5×10^10 == 1.5×10^22` → false → correctly flagged.
- **Over-scaling** (uses a scaler one order of magnitude too large on `gasPrice`, e.g. `10^10` instead of `10^9` — the report's own "heavily inflated" branch): `result = ⌊(5×10^19 × 3×10^21)/10^18⌋ = 1.5×10^23`. `1.5×10^23 == 1.5×10^22` → false → correctly flagged. **This is exactly the case that motivated rejecting Alternative 3 (pure lower bound)** — `1.5×10^23 >= 1.5×10^22` is *true*, so a lower-bound-only relation would have missed this defect-retaining alternative; the exact equality does not.

No gap found for the selected relation *within the fixed-decimals (9, 6) scenario* — **Intent coverage is judged Full on that basis** (see the Summary and the explicit scenario-generality caveat in R1-7, which is a distinct, non-conflicting caution about *which decimals values* the relation is conditioned on, not about whether it tracks the reported mechanism once conditioned).

## R1-4 — During vs Post

**Selected scope: Post.** `gasPrice`, `ethPrice`, and `result` are all fully settled locals by the time `return result;` executes, with no further mutation — the relation concerns the function's return value at exit (README's own Post criterion: "the relation concerns... a return value"), not an intermediate statement-time value. Not chosen merely because the report describes a function-level consequence (R1-4's explicit caution) — chosen because `result` is only meaningful, and only fully computed, once, at the point immediately before `return`.

**Required explicit delta-exception check (README §4/R1-7, per task instructions — performed on this case's own facts).** `latestAnswer()` contains **no loop of any kind** — confirmed by reading the entire function body (4 statements: two oracle-call assignments, one `PRBMathUD60x18.mul` assignment, one `return`) and, for completeness, the entire `GasOracle.sol` file (67 lines total — `toWad`, the constructor, and the two setters are equally loop-free). There is therefore no candidate `@During` attachment point inside a loop body to even consider — this is a more clear-cut "not applicable" outcome than `web3bugs_59_H_04`/`web3bugs_70_H_05` (which had loops *elsewhere* in the function but not at the bug's own location): here there is no loop anywhere in the contract at all. **Confirmed: delta does not apply**, trivially.

## R1-5 — Relation form

**Exact equality via the ordinary relational common form** (`intentValue relOp intentValue # RelationalCmp`, `Parser/Solidity.g4` line 325) — **not** `returnExpression relOp intentValue` (`C_ret`). Per the same reasoning `web3bugs_70_H_05` used to choose between these two forms: `C_ret` is appropriate when the left-hand side is the function's own inline return-statement expression with no separate named local holding that value; here `result` **is** exactly such a named local (`uint256 result = PRBMathUD60x18.mul(...); return result;` is a bare pass-through of an already-named value), so the relation is stated directly over `result`. Not forced to equality by the assignment-shaped statement (R1-5's explicit caution) — equality was selected in R1-3 on independent discrimination grounds (a unit-scaling fact is not naturally a bound; see R1-3 Alternative 5's rationale).

## R1-6 — Construct the target annotation

**Attachment point**: `@Post` on `latestAnswer()`, placed immediately after `return result;` (textual-placement convention matching this batch's other `@Post` cases; semantically evaluated at `σ_exit` regardless of exact line). `gasPrice`, `ethPrice`, `result` are all ordinary locals, declared at the function's top level and never reassigned, so all three are in scope and settled at exit.

**Constant derivation.** `10^9 = 10^(MAX_DECIMALS − gasOracle.decimals())` and `10^12 = 10^(MAX_DECIMALS − priceOracle.decimals())`, using `MAX_DECIMALS = 18` (the contract's own constant, L20) and the constructed scenario's `gasOracle.decimals() = 9` (source-hinted, `toWad`'s own `// 9` comment), `priceOracle.decimals() = 6` (constructed, distinct from the gas oracle's value to exercise both scalers independently). `10^18` is the WAD scale `PRBMathUD60x18.mul` divides by internally (`PRBMathCommon.SCALE`) and matches `latestAnswer()`'s own documented output precision ("×10^18 for compatibility"). Written with `**` (`IntentExponentiation`, confirmed supported by the grammar and by the engine's `evaluate_binary_operator`, per this session's prior confirmation for `web3bugs_70_H_05`) rather than raw digit-string literals, for readability.

**Target annotation:**
```solidity
function latestAnswer() external view override returns (uint256) {
    uint256 gasPrice = uint256(gasOracle.latestAnswer());
    uint256 ethPrice = uint256(priceOracle.latestAnswer());

    uint256 result = PRBMathUD60x18.mul(gasPrice, ethPrice);
    return result;
    // @Post result == (gasPrice * (10 ** 9) * ethPrice * (10 ** 12)) / (10 ** 18)
}
```

**Preconditions, stated explicitly (scenario-conditioning, per R1-7's general note that most During/Post relations in this benchmark hold given stated preconditions, not as bare unconditional invariants):**
1. **Fixed decimals**: the relation holds specifically for executions where `gasOracle.decimals() == 9` and `priceOracle.decimals() == 6` at call time. `GasOracle` places **no constraint whatsoever** on these values at the `latestAnswer()` execution path (`setGasOracle`/`setPriceOracle` accept any `IChainlinkOracle`-conforming address; the only decimals check anywhere in the file, `toWad`'s `require(_decimals <= MAX_DECIMALS, ...)`, sits in the dead, never-called `toWad` function) — unlike `web3bugs_70_H_05`, where the analogous constant (`10^10`) was derived from a `require` **actually enforced on the buggy execution path** (`_addUSDVPair`'s `require(oracle.decimals() == 8, ...)`), here the (9, 6) pair is a pure scenario construction, not a protocol invariant. A different deployment (different oracle decimals) would need its own scenario-specific relation with its own derived scalers — this is a real generality gap, distinct from (and in addition to) the ordinary "one concrete scenario" conditioning every case in this batch carries, and is called out explicitly rather than implied away.
2. **No fixed-point rounding correction needed**: `PRBMathUD60x18.mul(x, y) = ⌊x·y/10^18⌋` exactly (no `+1`) for both the buggy and the intended computation in this scenario, verified directly above (`(x·y) mod 10^18 = 0` in both cases) — this is not a general property of `PRBMathUD60x18.mul` (see R1-3's Alternative 4 for the general, rounding-robust two-sided-bound form that does not need this precondition).
3. **Non-negative oracle answers**: `gasPrice`/`ethPrice` are obtained via a raw (non-reverting) `int256 → uint256` cast (`uint256(gasOracle.latestAnswer())`) — Solidity's plain cast always succeeds and is a bit-reinterpretation, so it does **not**, by itself, guarantee non-negativity; the scenario's chosen values (`5×10^9`, `3×10^9`) implicitly assume `gasOracle.latestAnswer()`/`priceOracle.latestAnswer()` return non-negative `int256` values in the first place (ordinary behavior for gas/price feeds, but not a fact enforced anywhere in this file). A negative raw answer would wrap to a near-`2^256` value under the same cast — a distinct, unreported behavior, outside H-06's scope (per README's non-negativity/casting-semantics caution, §4: this is a cast-dependent, execution-scoped fact, not a type-level guarantee, and is stated at its correct precision here rather than blanket-assumed).
4. **No overflow branch**: `gasPrice·ethPrice` and `(scaled gasPrice)·(scaled ethPrice)` are both far below `2^256`, so `PRBMathCommon.mulDivFixedPoint`'s `prod1 == 0` (no-overflow) branch is the one that executes — verified for the scenario's own magnitudes, not asserted for arbitrary inputs.

## R1-7 — Expressibility decision

- **Values referenceable at a legal program point**: Yes. `gasPrice`, `ethPrice`, `result` are all locals in scope, unmutated from their declaration through function exit — ordinary `varRef`s at `σ_exit`. **No function call inside `intentValue`**: confirmed via the R1-3 preliminary check — `oracle.decimals()`/`toWad`/`PRBMathUD60x18.mul` were all consulted only to *derive* the scenario's fixed constants and arithmetic form, never referenced live inside the annotation itself. The R1-3 alpha/known-bound-rescue question was explicitly raised and resolved (scenario-instantiation rescue for the decimals calls; scenario-conditioned inlining, honestly flagged as non-general, for `PRBMathUD60x18.mul`) rather than skipped.
- **Arithmetic/logical relation representable**: Yes. `(gasPrice * (10**9) * ethPrice * (10**12)) / (10**18)` is ordinary `arithTerm`/`arithExp` — multiplication, division, and `IntentExponentiation` (`**`) are all directly supported (`Parser/Solidity.g4` lines 346-376, confirmed by direct grammar read); `intentValue relOp intentValue` (`RelationalCmp`) is a first-class `commonClause` form (line 325).
- **Observation point supported**: Yes — `@Post`, evaluated at function exit. **Explicit delta-exception re-check** (per task instructions, since the old `L3` label gives no reliable signal either way): `latestAnswer()`, and `GasOracle.sol` as a whole, contain no loop of any kind (verified in R1-4) — the confirmed delta exception (a `@During` whose only viable attachment is inside a loop body, never evaluated by `fixpoint()`/`reinterpret_from()`) has no candidate attachment point to apply to here. **Not applicable, trivially.**

**Outcome: Expressible = YES**, under the fixed-decimals (9, 6) scenario constructed in R1-1/R1-6. This verdict is scoped to that concrete instantiation, per R1-7's own scope note — it does not claim the fully general, decimals-independent property ("correct for *any* pair of oracle decimals `GasOracle` could be deployed with") is expressible as a single fixed-constant relation; a different, differently-scaled relation would be needed for each distinct `(gasOracle.decimals(), priceOracle.decimals())` pair, since neither is a protocol-enforced constant in this contract (contrast `web3bugs_70_H_05`'s `oracle.decimals() == 8` `require`, which let that case's derived constant generalize across every reachable execution).

**Note on the old `L3 unsupported-construct-top` label**: not used as a starting assumption, and not confirmed or explained here (no prior-pipeline reasoning file was consulted, per the task framing) — but plausibly explained by the same grammar facts recorded across this batch's other reclassified cases: exponentiation (`**`) and the general discipline of rescuing an apparent function-call requirement via a fixed scenario constant were both only confirmed usable this session. Recorded as a plausible historical note, not as evidence for or against this case's fresh verdict.

## §5 — Value/Algorithm and Usable/Unusable

- **Algorithm-level** *(justification reframed on review — verdict unchanged, see below for why)*: per the paper's own definition (`main.tex` L239-240 — Algorithm-level = "operation ordering, an absent state update, or a missing procedure call"), the primary ground for this classification is that **the intended computation requires a distinct normalization stage — rescale each raw oracle answer to 18 decimals — applied once per operand, before the WAD multiplication, and this entire stage is absent from `latestAnswer()`**, not merely a single wrong/missing arithmetic factor inside one otherwise-complete expression: intended computation is (1) fetch `gasPrice`, (2) normalize `gasPrice`, (3) fetch `ethPrice`, (4) normalize `ethPrice`, (5) multiply the two normalized values; the actual code has (1), (3), (5) only — an entire processing step, not one operand, is missing. The already-implemented-but-uncalled `toWad` function *corroborates* this reading (it shows the missing stage has a concrete, well-defined shape in this codebase and was anticipated by the developer) but is **not itself the reason** for the Algorithm-level call — grounding the classification only in "a helper function exists and isn't called" would make the taxonomy contingent on an incidental implementation detail (an otherwise-identical bug with no spare `toWad`-style helper lying around should classify the same way, since the same processing stage would still be absent from the intended computation). Contrast the Value-level reclassifications elsewhere in this batch (`web3bugs_59_H_04`, `web3bugs_70_H_05`) — both of those are a wrong/missing single operand inside one continuous formula (a swapped denominator; a missing scale literal), not an entire missing processing stage.
- **Usable**: every value the relation needs (`gasPrice`, `ethPrice`, `result`) is referenceable, unmutated, in-scope at the annotation's program point. The scaling constants are scenario-fixed number literals, not calls — no representational gap. (Per README §4's note on `delta`: Usable is independently assessed and is not defaulted to "no" merely because a call-rescue was needed at R1-3 — here the rescue succeeded cleanly and Usable holds without qualification.)
