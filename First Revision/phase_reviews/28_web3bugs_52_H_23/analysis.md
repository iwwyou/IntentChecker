## R1-1 — Reported Behavior Reconstruction

**Contract/function role.** `VaderPoolV2` extends `BasePoolV2` (Uniswap-v2-style constant-product AMM pool tracking, per `(IERC20 foreignAsset) => PairInfo{totalSupply, reserveNative, reserveForeign, blockTimestampLast, priceCumulative}`) with a synthetic-asset system: `mintSynth`/`burnSynth` let a caller mint/burn a `Synth` token representing a claim on a `foreignAsset`, backed by depositing/withdrawing the pool's *native* asset (Vader/USDV) rather than the foreign asset itself. The contract's own module doc comment (lines 14-24) describes this as using "liquidity units as collateral for synthetic assets," and the report opens by quoting the project's own external documentation: *"It also is capable of using liquidity units as collateral for synthetic assets, of which it will always have guaranteed redemption liquidity for."* — i.e., the design intends every minted `Synth` token to be fully redeemable against the pool's actual foreign-asset holdings at all times.

**Relevant locals/state** (within `mintSynth`, lines 126-167):
- `foreignAsset`, `nativeDeposit`, `from`, `to` — parameters. `nativeDeposit` is transferred in unconditionally at line 138 (`nativeAsset.safeTransferFrom(from, address(this), nativeDeposit)`).
- `synth` (local, L140, `ISynthFactory.synths(foreignAsset)`, lazily created via `createSynth` at L142-145 if it doesn't yet exist) — plays no role in the numeric relation below; used only to reach the `synth.mint(to, amountSynth)` call at L166.
- `reserveNative`, `reserveForeign` (locals, L147-149, from the inherited `getReserves(foreignAsset)`) — the pool's cached native/foreign reserve figures as of the last `_update()` call.
- `amountSynth` (the function's **named return variable**, assigned at L151-155): `amountSynth = VaderMath.calculateSwap(nativeDeposit, reserveNative, reserveForeign)` — the constant-product "virtual swap" output: how much `foreignAsset` `nativeDeposit` would buy if it were actually swapped into the pool, computed by the same formula (`VaderMath.calculateSwap`, `dex_math_VaderMath.sol` L99-111: `amountOut = (amountIn*reserveIn*reserveOut) / (amountIn+reserveIn)^2`) the contract's own `swap()`/`doubleSwap()` functions use for real swaps.
- **The disputed statement (L157-164)**, immediately preceded by the developer's own `// TODO: Clarify` comment (L157) — direct in-file evidence that this exact call was already a recognized point of uncertainty, not a settled design choice:
  ```solidity
  // TODO: Clarify
  _update(
      foreignAsset,
      reserveNative + nativeDeposit,
      reserveForeign,
      reserveNative,
      reserveForeign
  );
  ```
  `_update` (inherited, `BasePoolV2.sol` L533-567) unconditionally executes `pair.reserveNative = uint112(balanceNative); pair.reserveForeign = uint112(balanceForeign);` using its 2nd/3rd parameters (`balanceNative`/`balanceForeign`) as the *new* persisted reserve values (plus a conditional, irrelevant-here TWAP price-cumulative update gated on `timeElapsed > 0 && reserveNative != 0 && reserveForeign != 0`). So the 3rd argument passed at the disputed call — `reserveForeign`, **unchanged from its pre-call value** — becomes the pool's new persisted `pairInfo[foreignAsset].reserveForeign` verbatim.
- `synth.mint(to, amountSynth)` (L166) — mints `amountSynth` new `Synth` tokens to `to`, each conceptually a claim on the pool's foreign-asset holdings.

**Reported erroneous behavior** (H-23, verbatim, primary source `Web3Bugs/reports/52.md`): *"However, in the current implementation, `Synth` tokens are minted based on the calculation result. While `nativeDeposit` be added to the reserve, `reserveForeign` will remain unchanged, not deducted nor locked. Making it possible for `Synth` tokens to get over-minted."*

**Proof of Concept** (verbatim, primary source only — **absent from the scattered `Dataset/Web3Bugs` excerpt**, §0.5): a newly created BTC-USDV pool with near-zero liquidity; Alice adds `100,000 USDV` and `1 BTC`; Bob calls `mintSynth()` with `100,000 USDV` and receives `0.25 BTC vSynth`; Alice then removes all her liquidity, withdrawing the full `200,000 USDV` and `1 BTC` — leaving Bob's `0.25 BTC vSynth` "backed by nothing and unable to be redeemed." The report separately describes a flash-loan variant (add lopsided liquidity, repeatedly call `mintSynth` to extract a large synth balance, remove the liquidity/repay the flash loan, then later drain real BTC via `burnSynth` once the pool is refilled by other LPs) as the same root cause scaled into a direct fund-theft path. Sponsor (`SamSteinGG`) commented (confirmed, on narrow policy grounds — findings on "mathematical accuracy" vs. the ported Thorchain reference implementation are only accepted if the code deviates from that reference or a test case demonstrates the problem); this does not dispute the report's own arithmetic, only the acceptance policy, and does not affect this analysis (per §2, sponsor/judge status is not itself evidence for or against the intended-behavior reconstruction).

**Arithmetic cross-check of the PoC's own numbers against `VaderMath.calculateSwap`'s formula** (verifies the report's `0.25 BTC` figure independently, and supplies this case's concrete scenario without needing to invent one): with `nativeDeposit = reserveNative = 100000` (USDV) and `reserveForeign = 1` (BTC) at the moment Bob calls `mintSynth`, `calculateSwap`'s formula gives `amountOut = (100000*100000*1) / (100000+100000)^2 = 10,000,000,000 / 40,000,000,000 = 0.25` — exactly matching the report's stated `0.25 BTC vSynth`. This scenario is used directly below rather than a separately constructed one.

**Variable-value intent (the disputed statement's 3rd argument).** The persisted `pairInfo[foreignAsset].reserveForeign` after `mintSynth` must reflect that `amountSynth` units of the pool's foreign-asset backing have now been earmarked to the newly minted `Synth` claim — i.e., it must be `reserveForeign - amountSynth`, not `reserveForeign` unchanged. This is not merely intuited from the report's prose; it is the same accounting `VaderPoolV2`'s own inherited `swap()` function performs for the identical formula: `swap()`'s native-in branch computes `foreignAmountOut = VaderMath.calculateSwap(nativeAmountIn, nativeReserve, foreignReserve)` (`BasePoolV2.sol` L471-475, the same three-argument shape and same callee `mintSynth` uses) and then calls `_update(foreignAsset, nativeReserve - nativeAmountOut + nativeAmountIn, foreignReserve - foreignAmountOut + foreignAmountIn, ...)` (L484-490) — for a native-only-in swap (`nativeAmountOut = 0`, `foreignAmountIn = 0`), this reduces to exactly `_update(foreignAsset, nativeReserve + nativeAmountIn, foreignReserve - foreignAmountOut, ...)`. `mintSynth` computes the identical `foreignAmountOut`-shaped quantity (`amountSynth`, via the identical `calculateSwap` call with the identical argument order) but then passes the *unmodified* `reserveForeign` as `_update`'s 3rd argument instead of `reserveForeign - amountSynth` — an internally inconsistent deviation from the contract's own established convention for "a native deposit that results in a foreign-asset-denominated output," not merely the report's own outside assertion.

**Statement/line-level intent.** `mintSynth` is conceptually "deposit native asset, virtually swap it for the foreign asset via the pool's own AMM curve, and hand the caller a synthetic claim on that virtual output" — the reserve bookkeeping must therefore treat the minted `Synth` amount exactly as `swap()` treats a real swap's output: removed from the available foreign-asset backing, so that the pool's `reserveNative x reserveForeign` accounting (and hence its guarantee of redemption liquidity, per the report's opening quote) stays consistent whether the "swap" was real (via `swap()`) or synthetic (via `mintSynth`).

**Patch intent**: none given (§0.5 — no `#### Recommendation` subsection for this finding in the primary source). The target relation below is derived entirely from `_update`'s own definition and `swap()`'s own established convention for the identical `calculateSwap` output, not from any patch text.

**Bug-relevant intended numeric behavior**: for any call to `mintSynth`, the `_update` call's 3rd argument (which becomes the pool's new persisted `reserveForeign` for that pair) must equal `reserveForeign - amountSynth`, mirroring exactly how `swap()` handles the same `calculateSwap`-computed output; the current code instead passes `reserveForeign` unchanged, so no foreign-asset backing is ever set aside for a minted `Synth` claim.

## R1-3 — Select the least implementation-specific sufficient relation

**Preliminary check — does this relation need a function call inside `intentValue`?** The natural statement is "the 3rd argument to `_update` equals `reserveForeign - amountSynth`." Both `reserveForeign` and `amountSynth` are already-materialized in-scope locals by the time the disputed statement executes (`amountSynth` is assigned at L151-155, strictly before the `_update` call at L158-164) — no call needs to appear inside the relation at all. (Whether `VaderMath.calculateSwap`'s own formula needs to be understood to justify *why* `amountSynth` is the right term is a separate R1-1 narrative point, not an expressibility requirement — see RQ2-A's Step 1 analysis below for why `calculateSwap` ends up not load-bearing to the selected relation's own *runtime evaluation*. **`_update`'s own definition, by contrast, is load-bearing to the relation's *derivation* — review-corrected, see RQ2-A/Review Notes**: without knowing that `_update`'s 2nd/3rd parameters become the persisted `reserveNative`/`reserveForeign`, there would be no way to know *which* call argument the defect concerns at all.)

1. **Directional/monotonicity** (e.g. "the argument is less than `reserveForeign`"): expressible, and would flag the actual buggy code (argument `== reserveForeign`, which is not `< reserveForeign`). **Rejected** — the intended value is a single, exactly-determined quantity (an exact reserve accounting decrement, mirroring `swap()`'s own arithmetic), not naturally a bound; a bare "less than" relation would also silently accept any implementation that decrements by the *wrong* amount (e.g. by only half of `amountSynth`, still leaving the mint partially unbacked — the same reported failure mode in degree, not in kind), understating the reported intent the same way README cautions against for `web3bugs_3_H_04`-style exactly-determined quantities.
2. **Inequality, upper bound** (`_update.arg[2] <= reserveForeign - amountSynth`): expressible, and does catch every *under*-deduction variant (no deduction at all — the actual bug — and any partial deduction), since all of those leave the argument strictly greater than the bound. **Considered, and rejected**, on the same "not naturally a bound" ground as (1): the pool's own `swap()` convention establishes a single correct value, not a range, and (per the required negation check below) using `<=` would silently accept a hypothetical over-deduction (e.g., subtracting `2*amountSynth`) as satisfying the relation even though it deviates from the `swap()`-consistent formula just as much as the reported under-deduction does, just in the opposite direction — not itself the *reported* failure mode, but not a property the constructed scenario needs to leave unchecked either, since the correct value really is exactly determined.
3. **Exact equality via the call-argument common form (SELECTED)**: `_update.arg[2] == reserveForeign - amountSynth`. Discriminates the actual reported defect exactly (arithmetic below) and is derived from `_update`'s own effect definition plus `swap()`'s own established convention, not from any patch syntax (there is none).
4. **Exact equality via a `@Post` state form** (considered as an alternative attachment, not a different value): `pairInfo[foreignAsset].reserveForeign == reserveForeign - amountSynth`, evaluated at `mintSynth`'s exit. Also expressible — `_update`'s only statement touching `pair.reserveForeign` is the single, unconditional assignment `pair.reserveForeign = uint112(balanceForeign);` (`BasePoolV2.sol` L564), so this is a clean instance of the exact-formula-inlining rescue (the assignment is deterministic given `_update`'s own 3rd parameter, no branch affects this specific field, no further call). **Not selected, in favor of (3)** — see the explicit comparison in R1-5/RQ2-A: the call-argument form targets the disputed statement's own argument directly (the literal locus of the defect) without needing to trace or rely on `_update`'s internal *assignment* at all. **(Review-corrected framing)**: both (3) and (4) equally depend on knowing *what `_update`'s 2nd/3rd parameters mean* (RQ2-A now counts `_update` as an Additional function for both); the genuine, remaining difference is that (4) additionally needs the exact-formula-inlining rescue on `_update`'s own body (tracing its specific assignment statement), while (3) only needs `_update`'s parameter *semantics*, not its implementation — still a real, checked reason to prefer (3), just a narrower one than originally stated.

**Winner: Alternative 3.**

**Required negation check (§3/R1-3)**: does this equality's negation fail to catch some alternative implementation that retains the reported "not deducted nor locked" defect but produces it differently?
- **No deduction at all (the actual buggy code)**: argument `= reserveForeign`. `reserveForeign == reserveForeign - amountSynth` is false whenever `amountSynth > 0` (true for any nonzero deposit) -> correctly flagged Violated.
- **Deducts the wrong quantity** (e.g., deducts `nativeDeposit` instead of `amountSynth` — a plausible "looks like a fix but uses the wrong operand" variant, since both are already in scope at the call site): argument `= reserveForeign - nativeDeposit`. Differs from `reserveForeign - amountSynth` whenever `nativeDeposit != amountSynth` (true in general — `calculateSwap`'s output is a nonlinear function of its inputs, not the identity) -> correctly flagged.
- **Deducts from the wrong reserve** (e.g., correctly subtracts `amountSynth` but from `reserveNative`'s argument slot instead, leaving the foreign-reserve argument at `reserveForeign` unchanged): identical to the "no deduction" case for this argument slot -> correctly flagged.
- **Partial deduction** (e.g., `reserveForeign - amountSynth/2`, a half-fix that still leaves the mint under-collateralized): differs from the exact target whenever `amountSynth != 0` -> correctly flagged.
- **The intended/corrected code** (argument `= reserveForeign - amountSynth`, matching `swap()`'s own convention): satisfies the equality exactly -> correctly accepted.

No alternative-defect gap found. **Intent coverage: Full** — the relation directly tracks the reported mechanism (the specific 3rd-argument value at the specific disputed call), not merely a symptom of it.

**Discrimination check (explicit arithmetic, per §9 checklist item 1)**, using the PoC-derived scenario from R1-1 (`reserveNative = nativeDeposit = 100000`, `reserveForeign = 1`, `amountSynth = 0.25`, all in the report's own stated units):
- **Buggy** (current code): `_update`'s 3rd argument `= reserveForeign = 1`. Check: `1 == 1 - 0.25 = 0.75` -> **false ⟹ Violated.**
- **Intended** (per the `swap()`-consistent formula): `_update`'s 3rd argument `= reserveForeign - amountSynth = 1 - 0.25 = 0.75`. Check: `0.75 == 0.75` -> **true ⟹ Satisfied.**

## R1-5 — Relation form

**Call-argument relation**, via the grammar's dedicated common form: `duringClause: identifier '.' 'arg' '[' numberLiteral ']' relOp intentValue # DuringFunctionArg` (`Parser/Solidity.g4` line 306). `identifier = _update` (an internal/inherited call, syntactically a bare `IdentifierExpContext` at the call site — `_update(...)`, no `this.`/member-access prefix), `arg_index = 2` (0-indexed: `[0]=foreignAsset, [1]=reserveNative+nativeDeposit, [2]=reserveForeign, [3]=reserveNative, [4]=reserveForeign`).

## §5 — Value/Algorithm and Usable/Unusable

- **Value-level**: per the paper's own classification, the defect is a **wrong argument value passed to an otherwise-complete, already-present call** — `_update(...)` is called, at the same point, with the same five-argument structure `swap()`'s own convention would produce; only the 3rd argument's *value* is wrong (`reserveForeign` where `reserveForeign - amountSynth` belongs). No procedure call is missing (`_update` is called exactly as it should be), no processing stage is absent (`amountSynth` is already correctly computed via the same `calculateSwap` formula `swap()` uses) — the sole defect is that one already-computed value (`amountSynth`) is never subtracted into one already-present call's argument slot.
