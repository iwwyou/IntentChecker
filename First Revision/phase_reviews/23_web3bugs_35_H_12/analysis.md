## R1-1 — Reported Behavior Reconstruction

**Contract role.** `ConcentratedLiquidityPool` is Trident's Uniswap-v3-style concentrated-liquidity AMM pool. Besides the constant-product/tick-range mechanics, it maintains a single pool-wide, Uniswap-v3-style oracle accumulator, `secondsPerLiquidity` (`uint160 internal secondsPerLiquidity; /// @dev Multiplied by 2^128.`, L49), together with a checkpoint timestamp `lastObservation` (`uint32 internal lastObservation;`, L50). This accumulator is the pool's own record of "cumulative seconds elapsed, weighted inversely by how much active liquidity was in the pool during each stretch of time" — the same purpose UniswapV3's `secondsPerLiquidityCumulativeX128` serves, and it is later read by `rangeSecondsInside()` (L635–658) to let external stakers/consumers compute time-in-range for incentive accounting.

**The one place the accumulator is correctly updated — `swap()` (L298–436), L312–319:**
```solidity
{
    uint256 timestamp = block.timestamp;
    uint256 diff = timestamp - uint256(lastObservation); /// @dev Underflow in 2106.
    if (diff > 0 && liquidity > 0) {
        lastObservation = uint32(timestamp);
        secondsPerLiquidity += uint160((diff << 128) / liquidity);
    }
}
```
This block runs unconditionally at the very start of every `swap()` call (before the swap's own price/tick-crossing loop, and before `swap()`'s own later mutation of `liquidity` at L422). Its logic: accrue `(diff << 128) / liquidity` — the elapsed seconds since the last checkpoint, scaled 2^128 and divided by whatever `liquidity` was **at the time that elapsed period was in effect** — onto the running accumulator, then move the checkpoint forward. The critical property, stated by the report and independently confirmed by reading this block: the division must use the *pre-existing* `liquidity` value, i.e., the accumulator update must happen **before** anything in the same call changes `liquidity`, or the wrong (post-change) liquidity would be credited for a time period during which the old liquidity was actually in effect.

**The two places `liquidity` is mutated without this checkpoint — `mint()` and `burn()`:**
- `mint()` (L141–228), L175–177: `unchecked { if (priceLower < currentPrice && currentPrice < priceUpper) liquidity += uint128(_liquidity); }` — the **only** statement in `mint()` that writes the state variable `liquidity`.
- `burn()` (L231–272), L241–243: `unchecked { if (priceLower < currentPrice && currentPrice < priceUpper) liquidity -= amount; }` — the **only** statement in `burn()` that writes `liquidity`.

**Confirmed by reading both functions in full (not merely the report's excerpted lines): neither `mint()` nor `burn()` contains any statement anywhere that writes `secondsPerLiquidity` or `lastObservation`.** `mint()` does *read* `secondsPerLiquidity` once, passing it (by value) as an argument into `Ticks.insert(...)` at L184 (used there, per the report, to initialize the newly-inserted tick's own `secondsPerLiquidityOutside` field) — but this is a read of whatever stale value the accumulator already holds, not a write. `burn()` does not reference `secondsPerLiquidity`/`lastObservation` at all. This asymmetry — `swap()` always checkpoints the accumulator before any liquidity change in the same call, `mint()`/`burn()` never checkpoint it despite each containing exactly one liquidity-changing statement of their own — is the entire defect, independently visible from the file's own write-sites alone; the report additionally narrates it directly (below).

**Reported erroneous behavior** (H-12, verbatim, primary source `Web3Bugs/reports/35.md`): *"`secondsPerLiquidity` is updated as such: `secondsPerLiquidity += uint160((diff << 128) / liquidity);` where `diff = timestamp - uint256(lastObservation)`. Hence, whenever liquidity changes, `secondsPerLiquidity` should be updated prior to the change. In particular, this affects the `mint()` and `burn()` functions, in the case where liquidity changes when `lowerTick <= currentTick < upperTick`. In fact, the latest `secondsPerLiquidity` value should be calculated and used in `Ticks.insert()`."*

**Recommended Mitigation Steps** (verbatim): *"The `secondsPerLiquidity` increment logic should be applied prior to liquidity addition in `mint()` and removal in `burn()`."*, followed by literal code showing the exact same accrual block (elided as `// insert logic before these lines`) placed immediately before each function's own `unchecked { if (priceLower < currentPrice && currentPrice < priceUpper) liquidity += / -= ... }` block — i.e., before *both* the liquidity mutation *and* (in `mint()`'s case) the subsequent `Ticks.insert(...)` call that reads `secondsPerLiquidity`. Sushi (`sarangparikh22`) initially disputed ("changing the order... will not affect anything, since it is not getting calculated at the mint or burn function"), then confirmed after the judge asked for elaboration: *"my apologies, this is an issue. I could confirm this."*

**Variable-value intent.** At the exit of either `mint()` or `burn()`, the persistent state variable `secondsPerLiquidity` must reflect one accrual step using the *pre-mutation* `liquidity` value (i.e., the value `liquidity` held at function entry, since neither function writes `liquidity` more than once) and the elapsed time since `lastObservation`'s pre-mutation value — the exact same formula `swap()` already applies, just relocated into these two sibling functions. `lastObservation` itself is a secondary, symmetric consequence of the same missing block (a checkpoint-timestamp update); this case's target relations, deliberately, check only `secondsPerLiquidity`'s final value — see R1-3 for why this is not scope-narrowing beyond what's needed.

**Statement/line-level intent.** `mint()` and `burn()` must uphold the same "any liquidity-affecting call must first checkpoint the seconds-per-liquidity accumulator using the *old* liquidity" invariant `swap()` already enforces on itself — a same-contract, cross-function (three-way: `mint`/`burn` vs. `swap`) consistency defect, not a wrong operand inside an already-complete formula.

**Expected/intended behavior**: for any call to `mint()`/`burn()` that reaches its own liquidity-mutating statement with `block.timestamp > lastObservation` (at entry) and `liquidity > 0` (at entry) — the exact same gating condition `swap()`'s own block already uses — `secondsPerLiquidity` at exit must equal `secondsPerLiquidity` at entry plus `((block.timestamp − lastObservation@entry) << 128) / liquidity@entry`. The current code leaves `secondsPerLiquidity` completely unchanged across both calls.

**Bug-relevant intended numeric behavior**: `secondsPerLiquidity` at `mint()`'s (resp. `burn()`'s) exit must equal `secondsPerLiquidity` at entry plus the elapsed-time accrual computed from the function's *own entry-time* `lastObservation`/`liquidity`, mirroring `swap()`'s own formula verbatim; the current code performs zero accrual in either function, regardless of how much wall-clock time has passed or how much liquidity was in effect during it.

## R1-3 — Select the least implementation-specific sufficient relation

**Preliminary check — does this relation need a function call inside `intentValue`?** No, and for a structurally different reason than every other case in this batch that had to invoke a rescue: `swap()`'s accrual block is not a function being *called* by `mint()`/`burn()` at all — it is an inline, unnamed block of arithmetic that exists verbatim inside a **sibling** function, never invoked from `mint()`/`burn()`. There is no call syntax anywhere in the buggy code to inline a bound around or substitute a formula for (contrast the alpha-rescue cases, where a literal call site had to be rewritten); the relation simply borrows `swap()`'s own already-fully-arithmetic formula as its RHS, exactly as any other in-scope arithmetic fact. This is closer in spirit to reading a sibling function purely for *semantic program context* (README §6, Step 2's first category) than to the exact-formula-inlining rescue (§4) used for `applyInterest`/`PRBMathUD60x18.mul`/`_getAmountOut` — those rescues exist specifically to defeat the grammar's "no call inside `intentValue`" restriction; here that restriction was never triggered in the first place.

**Is the target annotation a README §4 multi-annotation set?** Yes, and unusually cleanly so relative to this batch's other multi-member cases. The report's own Recommended Mitigation Steps section gives the fix for `mint()` *and* `burn()` side by side, under the same finding, explicitly ("this affects the `mint()` and `burn()` functions"); each function's own instance of the defect is independently derivable (own R1-1–R1-7 pass below) and, unlike `web3bugs_29_H_11`'s branch-symmetric pair (mutually exclusive per call, since one `if`/`else` selects between them), `mint()`'s and `burn()`'s instances are **not** mutually exclusive at all — they are two separate function bodies, each independently callable and independently checkable in the same analysis session, making this if anything a cleaner instance of the multi-annotation-set mechanism than either of this batch's prior two-member cases (`29_H_11`, `70_H_04`).

**1. `changed(secondsPerLiquidity, true)`** (the old L5a draft, rewritten in currently-valid grammar — `VarChangedEval`, `Parser/Solidity.g4`). **Discriminates the literal reported defect** (buggy code never writes `secondsPerLiquidity`, so `changed(..., true)` is false ⟹ Violated) **but fails the required negation check below** — rejected.

**2. Directional/strict inequality: `secondsPerLiquidity > secondsPerLiquidity(Entry)`.** Discriminates the literal reported defect (buggy: `Entry == Exit`, so `Exit > Entry` is false) for the same reason as (1), and is scenario-conditioned on the same `diff > 0 && liquidity(Entry) > 0` gate `swap()` itself uses (under which the correct accrual is always strictly positive). **Also fails the required negation check below** — rejected.

**3. Exact equality (SELECTED, both members):** `secondsPerLiquidity == secondsPerLiquidity(Entry) + ((block.timestamp - lastObservation(Entry)) << 128) / liquidity(Entry)`. Reproduces `swap()`'s own formula verbatim, using each function's own entry-time snapshots for the two "old" operands `lastObservation`/`liquidity` (the specific values the report's "prior to the change" language identifies as the ones that must be used).

**Required negation check (§3/R1-3, mandatory — actively checked against a concrete, plausible, differently-shaped alternative implementation, not merely asserted).** The report's own emphasis is squarely on *ordering*: "whenever liquidity changes, `secondsPerLiquidity` should be updated **prior to** the change." This directly suggests the most natural defect-retaining alternative to check: a developer who read the report, added the missing accrual block to `mint()`/`burn()`, but placed it **after** (not before) the liquidity-mutating statement — using whatever `liquidity` value is naturally in scope at that later point, which by then is already the *post*-mutation value. This is a single, coherent, highly plausible "partially fixed, still wrong" implementation, not a contrived one — it is exactly the mistake the report is explicitly warning against.

Concrete arithmetic, using a constructed scenario (the report supplies no PoC numbers for H-12, so — matching this batch's practice for numberless findings, e.g. `59_H_04`/`70_H_04` — one is built and verified here): `lastObservation(Entry) = 1000`, `block.timestamp = 1500` (so `diff = 500 > 0`), `secondsPerLiquidity(Entry) = 0` (early-lifecycle pool, no prior accrual), `liquidity(Entry) = 1000 > 0`. `mint()` call is in-range (`priceLower < currentPrice < priceUpper` holds) and mints `_liquidity = 200`, so `liquidity` becomes `1200` after L176 executes; the symmetric `burn()` scenario removes `amount = 200`, so `liquidity` becomes `800` after L242.

  - Alternative 1 (`changed`): `changed(0, true)` -> **false -> Violated** (correctly flagged).

- **"Right formula, wrong order" alternative** (block inserted *after* the liquidity mutation, using the naturally-in-scope, already-mutated `liquidity`):

**Alternatives 1 and 2 both fail this check; Alternative 3 (exact equality) closes it for both functions.** This also directly supersedes the old L5a draft's `changed(secondsPerLiquidity, true)` proposal — under this session's required negation-check discipline (which the retired L1–L5 taxonomy never applied), the old draft demonstrably does not discriminate a plausible, report-anticipated alternative implementation.

**A second, narrower, explicitly-considered-and-not-fully-closed alternative (mint() only): does the selected relation independently verify the report's separate remark that "the latest `secondsPerLiquidity` value should be... used in `Ticks.insert()`"?** `Ticks.insert(...)` (L180–192) reads `secondsPerLiquidity` by value as its 4th argument. Since nothing else in `mint()` writes `secondsPerLiquidity` again after this call, and the recommended fix's own placement is *before* line 175 (i.e., before *both* the liquidity mutation and the `Ticks.insert` call, which are quoted together in the same "insert logic before these lines" block) — a fix placed at the recommended location automatically supplies `Ticks.insert()` with the correct, freshly-accrued value, so an equality check at *function exit* is equivalent to checking correctness at the `Ticks.insert` call site too, **provided the fix is not artificially separated from its natural placement.** A contrived counter-scenario was checked: a developer who first *caches* `liquidity(Entry)` into a spare temporary, correctly computes the accrual formula, but writes it to `secondsPerLiquidity` only *after* `Ticks.insert()` has already read the stale value — this would satisfy the selected Exit-scoped equality (the final state is correct) while still violating the report's `Ticks.insert`-specific remark. Two attempted rescues for this narrower gap were checked and rejected on concrete grounds: (a) a `@During identifier.arg[n]` clause on the `Ticks.insert` call — inapplicable, since `nearestTick = Ticks.insert(...)` is an *assignment*-shaped statement (`statement_type == "assignment"`), and `verify_during_function_arg` only scans bare call statements (`statement_type == "functionCall"`), the identical, already source-confirmed limitation `web3bugs_29_H_11` found for its own `_getAmountOut` call; (b) a `@During` clause referencing `secondsPerLiquidity`/`liquidity`/`lastObservation` at the `Ticks.insert` statement's own program point — inapplicable, because by that point `liquidity` has *already* been overwritten by L176 in both the buggy and intended executions, so no snapshot qualifier legal under `@During` (`Before`/`After`/`Assign` only — `Entry`/`Exit` are Post-only, per the grammar's `{not self.inDuring}?`/`{self.inDuring}?` guards) can recover the pre-mutation `liquidity` value at that later point. Given (i) the recommended fix's own quoted placement inherently avoids this gap, (ii) closing it would require a genuinely awkward, unmotivated implementation (deliberately caching a value it has no other reason to cache) rather than a natural partial fix, and (iii) no grammar-legal construct closes it cleanly regardless — this narrower point is **not** treated as forcing a third annotation-set member or as reducing Intent coverage below Full; it is recorded here transparently as a considered-and-rejected edge case (per the task's explicit instruction to look for, not to manufacture, coverage gaps).

## R1-6 — Construct the target annotation

**Target annotation is a set of two `@Post` clauses** (README §4's multi-annotation-set mechanism), one per function, sharing the identical RHS formula.

**Attachment points**: `@Post` on `mint()`, placed after its final statement (`emit Mint(...)`, L227); `@Post` on `burn()`, placed after its final statement (`emit Burn(...)`, L271) — the textual-placement convention used elsewhere in this batch (`3_H_04`, `16_H_06`, `29_H_11`, `62_H_03`), semantically evaluated at `sigma_exit` regardless of exact line.

**Target annotations:**
```solidity
// mint()
...
emit Mint(mintParams.positionOwner, amount0Actual, amount1Actual, mintParams.positionRecipient);
// @Post secondsPerLiquidity == secondsPerLiquidity(Entry) + ((block.timestamp - lastObservation(Entry)) << 128) / liquidity(Entry)
```
```solidity
// burn()
...
emit Burn(msg.sender, amount0, amount1, recipient);
// @Post secondsPerLiquidity == secondsPerLiquidity(Entry) + ((block.timestamp - lastObservation(Entry)) << 128) / liquidity(Entry)
```

**No synthetic constant needed** — every operand (`secondsPerLiquidity`, `lastObservation`, `liquidity`, `block.timestamp`) is a pre-existing, live program value (three contract-level state variables, one global), and the shift amount `128` is copied directly from `swap()`'s own source line, not derived from a scenario (contrast README's `900`-style guidance, inapplicable here).

**Grammar note on the RHS's explicit parenthesization.** `arithExpr`'s shift operator (`IntentShiftOp`) sits at the *lowest*-precedence layer of the grammar (`arithExpr : arithExpr shiftOp arithAdd`, above `arithAdd`/`arithTerm`/`arithExp`), matching Solidity's own precedence (shift lower than `+ - * /`). Writing `... << 128) / liquidity(Entry)` therefore requires the explicit parenthesization shown (`arithFactor: '(' arithExpr ')'`) around `(block.timestamp - lastObservation(Entry)) << 128` to force the shift to bind before the division — an exact grammar-level mirror of the source's own explicit parens around `(diff << 128) / liquidity`.

**Preconditions, stated explicitly (scenario-conditioning, README §4's general note), both members:**
1. **Same gate `swap()`'s own block uses**: `block.timestamp(Entry) > lastObservation(Entry)` (so `diff > 0`) and `liquidity(Entry) > 0` — without these, `swap()`'s own analogous block would not accrue anything either, so the relation is not claimed to hold outside this gate.
2. **No overflow in the `uint160 +=`**: the un-`unchecked` accumulator addition (matching `swap()`'s own placement, not inside any `unchecked` block) would revert under Solidity >=0.8 checked arithmetic if the result exceeded `uint160`'s range; the constructed scenario's magnitudes (`~1.70e38`, `uint160` max `~1.46e48`) stay well clear of this, verified directly above, not assumed.
3. **Deliberately not checking `lastObservation`'s own exit value.** The same missing block also updates `lastObservation = uint32(timestamp);`; this is a symmetric, secondary consequence of the identical omission, but the report's own complaint is specifically about `secondsPerLiquidity`'s correctness (a stale `lastObservation` alone does not misstate the pool's oracle accumulator the way a stale `secondsPerLiquidity` does) — adding a `lastObservation`-checking third/fourth set member was considered and not included, to avoid the padding README §3 explicitly warns against ("not a license to pad every ... case with unrelated annotations"); the two `secondsPerLiquidity` members already achieve Full coverage of the reported mechanism (R1-3).

**Quantification note, both members: not applicable.** `secondsPerLiquidity`, `lastObservation`, and `liquidity` are each single, named, contract-level state variables — not elements of an array/mapping the annotation has to range over (contrast `web3bugs_83_H_01`'s `poolInfo[1]`). No representative-element instantiation issue applies.

## R1-7 — Expressibility decision

**Values referenceable at a legal program point, both members**: Yes. `secondsPerLiquidity`, `lastObservation`, and `liquidity` are all ordinary contract-level state variables, directly referenceable (bare and `(Entry)`-qualified) at `sigma_exit` of either function — no explicit `this.`/inheritance indirection or external-contract boundary is involved. `block.timestamp` is a `varRef` (`identifier` `block` + `subAccess` `.timestamp`), grammatically legal (`Parser/Solidity.g4`'s `varRef: identifier subAccess*`) and confirmed tracked end-to-end elsewhere in this codebase: `Analyzer/StaticCFGFactory.py` registers `"block.timestamp"` as a first-class `GlobalVariable`, `Analyzer/EnhancedSolidityVisitor.py`'s `READONLY_GLOBAL_BASES = {"block", "msg", "tx"}` recognizes `block` as a resolvable global base, and multiple existing case JSONs (`web3bugs_70_H_04`, `web3bugs_42_H_01`) already pin `block.timestamp`'s value via `@GlobalVar block.timestamp = [...]` debug annotations for their own scenarios.

**One genuinely novel-usage caution, flagged explicitly rather than silently assumed:** no prior case in this batch was found to reference `block.timestamp` *directly inside an `@During`/`@Post` relation's `intentValue`* (as opposed to only appearing in ordinary code, or being pinned via a `@GlobalVar` debug annotation). The grammar imposes no distinction between a global's `varRef` and a state/local's `varRef` inside `arithFactor`, and `NormalVarRef`'s evaluation delegates uniformly to `self.analyzer.evaluator.evaluate_expression` (`Analyzer/GuardianVerificationEngine.py`, `evaluate_guardian_expression`'s `NormalVarRef` branch) — the same evaluator that already resolves `block.timestamp` when it appears in ordinary source code — so there is no source-level reason to expect this to behave differently. This is recorded as a caution for RQ1-B (deferred, not this pass), matching how this project already flags an untested-but-plausible construct on first use (README §4's own precedent for the `varRef(Entry)`/`varRef(Before)` extension) rather than silently assuming it will run cleanly.

**No function call inside `intentValue`, both members**: confirmed in R1-3's preliminary check — `swap()`'s accrual block was never a call to begin with; its formula is reproduced as ordinary arithmetic, not inlined around a call site.

**Arithmetic/logical relation representable, both members**: Yes. `secondsPerLiquidity(Entry) + ((block.timestamp - lastObservation(Entry)) << 128) / liquidity(Entry)` uses only `+`, `-`, `<<`, `/`, all directly supported (`arithExpr`'s `IntentShiftOp`/`AddSub`/`MulDivMod` productions, `Parser/Solidity.g4` lines 346–359), plus the `(Entry)` snapshot qualifier (confirmed grammar-supported under `@Post`, capitalization double-checked per README's explicit caution after the `web3bugs_70_H_04` mis-capitalization incident) and ordinary parenthesization; `secondsPerLiquidity == ...` is the grammar's general `RelationalCmp` common form.

**Observation point supported, both members**: Yes — `@Post`, evaluated at function exit, on functions confirmed loop-free (R1-4). The confirmed `delta` exception is explicitly checked and does not apply — trivially, since there is no loop anywhere in either target function to attach inside, and the one loop that does exist in the file (`swap()`'s `while`) is never touched by either target relation's own attachment point or its operands (all four operands are read as already-materialized state/global values, the same treatment `29_H_11` gave `balance0`/`balance1` relative to `_balance()`'s own internal mechanism).

**Old-label engine-precision note, addressed but confirmed not to change this verdict.** The old pipeline's own note for this case additionally flags `abi.decode(data, (MintParams))` (`mint()`'s first statement, L142) / `abi.decode(data, (int24, int24, uint128, address, bool))` (`burn()`'s first statements, L232–235) as a secondary blocker ("concrete values cannot be set through debugging annotations"), i.e., an old-style `TOP`-resolution concern. Two things distinguish this from the actual R1-7 verdict here: (1) per README §4, engine-precision/`TOP` claims are out of scope for R1-7 in general (an RQ1-B question, deferred); (2) this case's selected relations' four operands (`secondsPerLiquidity`, `lastObservation`, `liquidity`, `block.timestamp`) are **none of them** derived from `abi.decode`'s output at all — they are pre-existing contract state and a global, entirely independent of what `mintParams`/`lower`/`upper`/`amount` decode to. The `abi.decode`-adjacent risk this case actually carries is a *stronger, already-confirmed-elsewhere* fact than the old label's `TOP` framing anticipated (see RQ1-B below), but it is an execution/reachability concern, not a representability one, and is deferred accordingly.
