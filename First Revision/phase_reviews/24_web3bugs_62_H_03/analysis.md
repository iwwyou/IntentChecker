## R1-1 — Reported Behavior Reconstruction

**Contract/function role.** `Stream` is Locke's token-streaming contract: depositors stake `depositToken` and, over `streamDuration`, earn `rewardToken` proportional to their staked (diluted) balance, tracked via an accumulator-ratio scheme (`cumulativeRewardPerToken`, per-user `lastCumulativeRewardPerToken`). Two `uint112` state variables act as the contract's own internal ledger of "how much of each token is spoken for": `rewardTokenAmount` (reward tokens funded and owed to depositors) and `depositTokenAmount` (deposit tokens staked). `recoverTokens(token, recipient)` is a non-protocol "sweep" function letting the stream creator recover any token balance the contract holds *in excess of* what it owes to depositors/governance — for `token == rewardToken`, that "owed" amount is computed as `rewardTokenAmount + rewardTokenFeeAmount`.

**Relevant locals/state (`claimReward()`, L555–578):**
- `ts` (local, L558) = `tokensNotYetStreamed[msg.sender]` — storage pointer to the caller's own `TokenStream` record.
- `cumulativeRewardPerToken` (state, L560) — updated via `rewardPerToken()` (accumulator convention; internals not load-bearing here, see R1-3/RQ2-A).
- `ts.rewards` (state, struct field, L563) — updated via `earned(ts, cumulativeRewardPerToken)`, the caller's newly-recomputed total accrued-but-unclaimed reward.
- `rewardAmt` (local, L569) = `ts.rewards` — the exact amount about to be transferred out to the caller.
- `ts.rewards = 0;` (L570) — zeroes the per-user record so the same accrual can't be claimed twice.
- **The disputed omission (no line number — this is an absent statement, not a wrong one)**: after `rewardAmt` is captured and before/after the transfer (L575), no statement anywhere in `claimReward()` decreases the global ledger variable `rewardTokenAmount` by `rewardAmt`.
- `ERC20(rewardToken).safeTransfer(msg.sender, rewardAmt);` (L575) — the actual token movement: `rewardAmt` reward tokens leave the contract's real balance at this point.

**The `rewardTokenAmount` ledger's own write sites (established by reading the whole file, not just `claimReward`):**
- `fundStream()` (L377–410): `rewardTokenAmount += amt;` (either branch of the `feeEnabled` conditional) — the **only** place `rewardTokenAmount` is ever incremented.
- `claimReward()` (L555–578): **no write to `rewardTokenAmount` at all** — confirmed by reading the full function body; the only state writes in the function are to `cumulativeRewardPerToken`, `ts.rewards` (twice), `ts.lastCumulativeRewardPerToken`, and `lastUpdate`.
- No other function in the file writes `rewardTokenAmount`.

This asymmetry — one function only ever increments the ledger, the actual-payout function never decrements it — is the entire defect; it is independently visible from the file's own write-sites alone, without needing the report's narration, though the report states it directly (see below).

**The consuming/symptom site, `recoverTokens()` (L662–677, the `token == rewardToken` branch):**
```solidity
if (token == rewardToken) {
    require(block.timestamp > endRewardLock, "time");
    // check what isnt claimable by depositors and governance
    uint256 excess = ERC20(token).balanceOf(address(this)) - (rewardTokenAmount + rewardTokenFeeAmount);
    ERC20(token).safeTransfer(recipient, excess);
    emit RecoveredTokens(token, recipient, excess);
    return;
}
```
This is the statement the report's code excerpt marks with `// @audit-issue`. Its own formula (`balance − (rewardTokenAmount + rewardTokenFeeAmount)`) is *not itself wrong* as arithmetic — it is the input `rewardTokenAmount` that is wrong (permanently inflated, since it is never decremented), so this formula computes an excess that is too low (frequently underflowing, since Solidity ≥0.8 checked subtraction reverts rather than wrapping — matching the report's own PoC, where excess becomes exactly `0`, not a revert, because `balanceOf` had also fallen to `0`, keeping the subtraction non-negative in that specific scenario). **The genuinely wrong statement — the one an intended-behavior fix must add — is in `claimReward()`, not `recoverTokens()`**: this is stated directly by the report's own Recommended Mitigation Steps (below), not inferred.

**Reported erroneous behavior** (H-03, verbatim, primary source `Web3Bugs/reports/62.md`): *"The `Streaming` contract allows recovering the reward token by calling `recoverTokens(rewardToken, recipient)`. However, the excess amount is computed incorrectly as `ERC20(token).balanceOf(address(this)) - (rewardTokenAmount + rewardTokenFeeAmount)`... Note that `rewardTokenAmount` only ever *increases* (when calling `fundStream`) but it never decreases when claiming the rewards through `claimReward`. However, `claimReward` transfers out the reward token. Therefore, the `rewardTokenAmount` never tracks the contract's reward balance and the excess cannot be computed that way."*

**Proof of Concept** (verbatim, primary source only — **absent from the scattered `Dataset/Web3Bugs` excerpt**, §0.5): *"Assume no reward fees for simplicity and only a single user staking. Someone funds `1000` reward tokens through `fundStream(1000)`. Then `rewardTokenAmount = 1000`. The stream and reward lock period is over... The user claims their full reward and receives `1000` reward tokens by calling `claimReward()`. The reward contract balance is now `0` but `rewardTokenAmount = 1000`. Some fool sends `1000` reward tokens to the contract by accident. These cannot be recovered as the `excess = balance - rewardTokenAmount = 0`."*

**Impact** (primary source only, absent from the scattered excerpt): *"Reward token recovery does not work."*

**Recommended Mitigation Steps** (primary source only, absent from the scattered excerpt): *"The claimed rewards need to be tracked as well, just like the claimed deposits are tracked. I think you can even decrease `rewardTokenAmount` in `claimReward` because at this point `rewardTokenAmount` is not used to update the `cumulativeRewardPerToken` anymore."* Sponsor `brockelmore` confirmed.

**Variable-value intent.** At the point `claimReward()` has finished paying out `rewardAmt` to the caller, the global ledger `rewardTokenAmount` must reflect that this amount is no longer outstanding — i.e., `rewardTokenAmount` at the function's exit must equal `rewardTokenAmount` at the function's entry, minus `rewardAmt`. The recommendation's own parenthetical ("at this point `rewardTokenAmount` is not used to update `cumulativeRewardPerToken` anymore") additionally confirms this decrement is safe to add with no knock-on effect on the accumulator math — `rewardTokenAmount` is read only inside `rewardPerToken()`'s `else` branch (L349), which already ran and produced `cumulativeRewardPerToken` *before* `rewardAmt` is even computed in this same call.

**Statement/line-level intent.** `claimReward()` must uphold the same "transfer out ⇒ decrement the corresponding ledger" invariant that the codebase already applies elsewhere for the deposit-token side: `claimDepositTokens()` (L532–550) transfers `depositToken` out and, in the same breath, does `redeemedDepositTokens += amount;` — an explicit tracking update paired with the transfer. `claimReward()`'s reward-token payout has no such paired update. This is a same-contract, cross-function consistency defect, not a value-level arithmetic mistake within one already-complete formula.

**Expected/intended behavior**: for any call to `claimReward()` that completes (i.e., `rewardAmt > 0` and the transfer succeeds), `rewardTokenAmount` must decrease by exactly `rewardAmt` — matching `fundStream()`'s own paired increment and `claimDepositTokens()`'s own precedent pattern.

**Bug-relevant intended numeric behavior**: `rewardTokenAmount` at `claimReward()`'s exit must equal `rewardTokenAmount` at its entry minus `rewardAmt` (the exact amount transferred at L575); the current code leaves `rewardTokenAmount` completely unchanged across the call.

Distinguishing property (no literal patch diff is given — only the qualitative recommendation "decrease `rewardTokenAmount` in `claimReward`" — used as evidence of *where* and *what*, not transcribed as annotation syntax): the state variable `rewardTokenAmount` must be decremented by the exact amount paid out on every completing call to `claimReward()`; the current code performs the payout with no corresponding ledger update at all.

## R1-3 — Select the least implementation-specific sufficient relation

**Preliminary check — does this relation need a function call inside `intentValue`?** No. The relation's operands are `rewardTokenAmount` (a state variable, referenced at two snapshots) and `rewardAmt` (an already-materialized local, captured at L569 before the transfer). Neither requires inlining or bounding any function's result — a structurally simpler starting position than every other case in this batch, which is worth noting explicitly rather than skipping past: there is no alpha-style call blocker to rescue here at all.

1. **Directional (weakest tier)**: `rewardTokenAmount(Exit) < rewardTokenAmount(Entry)` (equivalently, the old pipeline's own draft, `rewardTokenAmount(Entry > Exit)`, rewritten in currently-valid grammar — the bare clause-level `(entry relOp exit)` form is retired, see README §4). **Discriminates the literal reported buggy code** (which leaves `rewardTokenAmount` completely unchanged, so `Entry < Entry` is false ⟹ Violated) **but fails the required negation check below** — rejected.
2. **Exact equality tied to the actual payout amount (SELECTED)**: `rewardTokenAmount == rewardTokenAmount(Entry) - rewardAmt`. Discriminates the reported defect (below) and additionally survives the negation check that rules out (1).

**Required negation check (§3/R1-3, mandatory — actively checked, not asserted)**: does a *plausible, defect-retaining, differently-shaped* alternative implementation escape Alternative 1 but get caught by Alternative 2? Yes, concretely: consider an alternative buggy fix that *does* add a decrement statement to `claimReward()`, closing the report's literal complaint that "`rewardTokenAmount` never decreases" — but decrements by the wrong quantity, e.g. a scaling/timing bug that decrements by only half of `rewardAmt` (`rewardTokenAmount -= uint112(rewardAmt / 2);`), or by `ts.rewards` read *after* it was already zeroed at L570 (always decrementing by `0`, i.e., a statement is present but inert). Both variants still leave `recoverTokens()`'s excess computation wrong (a smaller, but still incorrect, `rewardTokenAmount` drift accumulates every claim) — the reported consequence ("reward token recovery does not work" / miscomputes) persists. **Alternative 1 (directional `<`) is satisfied by the half-decrement variant** (`rewardTokenAmount` still strictly decreases, just by the wrong amount) **— a false negative.** Alternative 2 (exact equality against `rewardAmt`) correctly flags both variants as Violated (`rewardTokenAmount(Entry) - rewardAmt/2 ≠ rewardTokenAmount(Entry) - rewardAmt`, and `rewardTokenAmount(Entry) - 0 ≠ rewardTokenAmount(Entry) - rewardAmt` whenever `rewardAmt > 0`, which `require(rewardAmt > 0, "amt")` guarantees on any completing call). This is the same category of check `29_H_11` performed (a bound that looks sufficient for the literal reported line but is falsified by a nearby differently-broken variant) — performed here directly against this case's own two concrete alternative shapes, not by analogy.

**Winner: Alternative 2 (exact equality).** Not selected merely "because equality is stronger" (README's explicit caution against defaulting to equality out of habit) — selected because the negation check concretely demonstrates the directional form has a real gap that the exact equality closes, and the exact quantity (`rewardAmt`, an ordinary already-computed local, not a synthesized constant) is no more patch-specific than the directional form — both reference the identical in-scope values, so there is no implementation-specificity cost to using the equality here (matching README's caution that operator strength alone doesn't measure implementation-specificity).

**Discrimination check (explicit arithmetic, per §9 checklist item 1), using the report's own PoC numbers directly** (no independently-constructed scenario needed — a rare case in this batch where the report supplies concrete numbers): `rewardTokenAmount(Entry) = 1000` (from `fundStream(1000)`, no fees), single staker claims their full accrued reward, `rewardAmt = 1000`.
- **Buggy** (current code): `rewardTokenAmount` is never written in `claimReward()`, so `rewardTokenAmount(Exit) = 1000`. Check: `1000 == 1000 - 1000 = 0` → **false ⟹ Violated.** (Matches the report's own stated consequence exactly: *"The reward contract balance is now `0` but `rewardTokenAmount = 1000`."*)
- **Intended** (recommended fix, `rewardTokenAmount -= uint112(rewardAmt);` inserted before/after the transfer): `rewardTokenAmount(Exit) = 1000 - 1000 = 0`. Check: `0 == 1000 - 1000 = 0` → **true ⟹ Satisfied.**
- **Half-decrement alternative** (from the negation check above): `rewardTokenAmount(Exit) = 1000 - 500 = 500`. Directional (`Entry < Exit`... i.e. `Exit < Entry`): `500 < 1000` → true → *incorrectly* Satisfied under Alternative 1. Exact equality: `500 == 0` → false → correctly Violated under Alternative 2.

## R1-4 — During vs Post

**Selected scope: Post.** There is no existing statement in `claimReward()` that writes `rewardTokenAmount` at all — the defect is a wholly *absent* statement, not a wrong one. This matters directly for the During/Post choice: a `@During` clause (with a `(Before)`/`(After)` snapshot pair, as used for genuine same-statement self-references, e.g. `29_H_11`'s `amount1(Before)`) requires attaching to *the statement whose own effect is being checked* — but no such statement exists here to attach to. The relation instead concerns the whole function's net effect on a persistent state variable between entry and exit — README's own Post criterion ("a persistent state transition, a function-level invariant") applies directly, and matches the two precedent cases README explicitly calls out for this exact shape: `SwordCrowdsale`'s `weiRaised -= amount` and `CDP.update`'s `totalCredit += delta`, both missing/wrong single-assignment ledger updates, both resolved as `@Post` with an Entry/Exit relation, not During. Not chosen by default because the fix would be "a single statement" (R1-4's explicit caution) — chosen because no During attachment point exists for a statement that was never written.

**Required explicit delta-exception check (README §4/R1-7, performed on this case's own facts, not assumed from the case's simplicity).** `claimReward()` contains no loop. For completeness (since the delta exception is about the *entire engine's* per-node checking machinery, not this function alone), the whole `web3bugs_62_H_03.sol` file was scanned for `for`/`while` at the top of this analysis and confirmed to contain none anywhere — `Stream` and `StreamFactory` are both loop-free contracts. There is therefore no candidate loop-body attachment point to even consider, for either a `@During` or a `@Post` reading. **Delta confirmed not applicable, trivially** — the most clear-cut version of this check in the batch so far (contrast `web3bugs_16_H_06`, which is also loop-free but needed the check stated explicitly because of an old label pointing at engine-precision reasoning; this case's own old label similarly cites an unrelated engine concern — `recoverTokens`' `balanceOf()` call resolving to `TOP` — which is addressed below, not conflated with the loop/delta question).

## R1-6 — Construct the target annotation

**Attachment point**: `@Post` on `claimReward()`, placed immediately after `emit RewardsClaimed(msg.sender, rewardAmt);` (the function's final statement) — the textual-placement convention used elsewhere in this batch (`3_H_04`, `16_H_06`, `29_H_11`), semantically evaluated at `σ_exit` regardless of exact line.

**No synthetic constant needed** — `rewardAmt` is an ordinary, already-computed in-scope local; no scenario-derived magic number is introduced (contrast README's `900`-style derived-constant guidance, inapplicable here).

**Target annotation**:
```solidity
uint256 rewardAmt = ts.rewards;
ts.rewards = 0;

require(rewardAmt > 0, "amt");

// transfer the tokens
ERC20(rewardToken).safeTransfer(msg.sender, rewardAmt);

emit RewardsClaimed(msg.sender, rewardAmt);
// @Post rewardTokenAmount == rewardTokenAmount(Entry) - rewardAmt
```

**Precondition, stated explicitly (scenario-conditioning, README §4's general note)**: the relation is conditioned on the call actually completing (`require(rewardAmt > 0, "amt")` already guarantees `rewardAmt > 0` on any non-reverting execution, matching the report's own PoC scenario — a single user claiming a nonzero accrued reward) and on `rewardTokenAmount(Entry) ≥ rewardAmt` (no underflow in the intended, fixed subtraction; not a strict inequality — the report's own PoC scenario has `rewardTokenAmount(Entry) = rewardAmt = 1000`, i.e. equality is a legitimate instance, not merely a boundary case to exclude). The latter is not independently re-proven here — it holds by the ledger's own accounting design (`rewardTokenAmount` is meant to track cumulative funded-but-unclaimed rewards, and `rewardAmt` is one claim's worth of that total), the same kind of design-level, not re-derived, precondition `29_H_11` recorded for its own `balance ≥ amount` subtraction.

**Quantification note**: not applicable. The relation is stated per-call, over `msg.sender`'s own claim — `msg.sender` is an ordinary global, not an element of a stored collection the annotation has to range over (contrast `web3bugs_83_H_01`'s `poolInfo[1]`). No representative-element instantiation issue applies.

## §5 — Value/Algorithm and Usable/Unusable

- **Algorithm-level**: per the paper's own classification (`main.tex` — Algorithm-level = "operation ordering, an absent state update, or a missing procedure call"), this is the most direct instance of "absent state update" in this batch: the intended computation's own sequence of steps for `claimReward()` is (1) compute the caller's accrued reward (`rewardAmt`), (2) reset the caller's own per-user accrual record (`ts.rewards = 0`), (3) **decrement the global outstanding-reward ledger by the same amount**, (4) transfer the tokens out. Step (3) does not exist anywhere in the actual code — not a wrong operand within an otherwise-complete formula (contrast `3_H_04`/`29_H_11`/`59_H_04`'s Value-level swapped-identifier/operator defects), a whole operation is missing. **Explicit note on the old label's divergent classification**: the prior pipeline's `l4_l5_classification.py` records `bug_category="value"` for this case (grouped under its own "Value (missing state update)" bucket in `l4_l5_case_review_(kor).md`). That older taxonomy used "value" more loosely, to mean roughly "a single state variable's tracked value is wrong" rather than the current paper's own operational Value-vs-Algorithm test (is a whole step present-but-wrong, or absent). Checked directly against the current methodology's own definition (the same check `16_H_06`'s review performed): the missing step here is not an implementation-detail accident of a spare unused helper (there is no unused `decrementReward`-style helper sitting in the file the way `16_H_06`'s `toWad` was) — it is a bare, structurally absent operation, which is precisely what the paper's own "absent state update" phrase names. This case is reclassified Algorithm-level under the current methodology, diverging from the old pipeline's own bucket for exactly this reason.
- **Usable**: every value the relation needs (`rewardTokenAmount`, `rewardAmt`) is directly referenceable, in-scope, at the annotation's program point — no representational gap, no semantic-unit distinction that fails to reduce to a numeric relation (§5's other caution, not triggered here at all — this is an ordinary ledger/balance quantity throughout).

## RQ2-A — Specification Requirements profile

**Relevant statements** (within `claimReward()` itself; §6 rule (a)/(b)/(c), inline notes where non-obvious):
1. `TokenStream storage ts = tokensNotYetStreamed[msg.sender];` (L558) — defines `ts`, the storage pointer needed to reach `ts.rewards`, the operand `rewardAmt` is copied from; per README §6's container/extracted-value rule (`msg.sender` is the meaningful, non-mechanical mapping key here — it *is* the representative-claimant element the relation is stated over, per R1-6's quantification note, not a discardable loop index — so it stays counted as a Global value below), the container `tokensNotYetStreamed` itself is also a load-bearing value reached by this statement (see Unique relevant program values, below).
2. `uint256 rewardAmt = ts.rewards;` (L569) — defines `rewardAmt`, the relation's own operand, directly. `ts.rewards`'s own upstream defining statement (`ts.rewards = earned(ts, cumulativeRewardPerToken);`, L563) is **excluded** here (see below, Step 1) — `rewardAmt` is treated as an opaque, already-materialized per-user reward figure, the same convention `3_H_04` applied to `cumulativeYield` and `29_H_11` applied to `amount0`/`amount1`'s own further-upstream operands (`liquidity`, `_totalSupply`).
3. `ERC20(rewardToken).safeTransfer(msg.sender, rewardAmt);` (L575) — **reinstated on second review pass** (see Review Notes): this statement is a (c)-type soundness-justifying statement, not merely narrative color. It is what establishes that `rewardAmt` — the relation's own decrement operand — *is* the real-world quantity that actually leaves the contract, i.e. it is the statement that grounds *why* `rewardAmt` (rather than some other in-scope quantity) is the correct amount to subtract from `rewardTokenAmount`. R1-1's own reconstruction already depends on this statement for exactly this purpose (its description of `rewardAmt`, L24 of this document's R1-1, is "the exact amount **about to be transferred out to the caller**" — a fact only established by reading L575). Applying README §6 Step 1 to the statement itself (not the `SafeTransferLib` call inside it): the call-site fact "this statement transfers `rewardAmt`, not some other quantity, to `msg.sender`" is load-bearing to the relation's own derivation, even though the *relation's runtime evaluation* at `σ_exit` never needs to inspect this statement's actual execution (that distinction is why "Additional functions required" stays 0 below — the statement counts as relevant context, but `SafeTransferLib`'s own internal implementation does not).

**Total: 3 relevant statements.** *(Corrected on second review pass — see Review Notes: the first review pass's removal of `ERC20(rewardToken).safeTransfer(msg.sender, rewardAmt);` is itself reverted; the statement counts as (c)-type context, not merely the "real-world event being tracked.")*

**Excluded, with reason (not merely omitted) — Step 1 (README §6):**
