## R1-1 — Reported Behavior Reconstruction

**Contract role** (brief, since the dual-mode ERC721/ERC1155 distinction directly explains why the bug is ERC1155-specific): `NFTXVaultUpgradeable` is an ERC20-wrapped vault that lets users deposit NFTs (`mintTo`) in exchange for fungible vault-share tokens, and later redeem or swap those shares back for NFTs (`redeemTo`/`swapTo`). A single vault instance is configured, once, as either an ERC721 vault or an ERC1155 vault (`is1155`, L51, set in `__NFTXVault_init`). ERC721 tokens are inherently one-of-a-kind (each `tokenId` exists at most once); ERC1155 tokens are semi-fungible (the vault can hold an arbitrary *quantity* of copies of the same `tokenId`).

**Function role**: `getRandomTokenIdFromFund()` (L413–416) is the internal helper `withdrawNFTsTo`'s loop (L373–400) calls, once per unit being withdrawn, whenever the caller did not specify which token ID they want for that slot (`i >= specificIds.length`, L374–376). It is supposed to hand back a token ID drawn "randomly" from the vault's current holdings such that every held *unit of inventory* has an equal chance of being the one returned — this fairness property is what `redeemTo`/`swapTo`'s non-direct-redeem path relies on to avoid systematically favoring any one asset.

**Relevant state** (only the variables the bug actually touches):
- `holdings` (`EnumerableSetUpgradeable.UintSet`, L61) — the set of *distinct* token IDs currently held by the vault. Populated in `receiveNFTs`: for ERC1155 (L332–352), a `tokenId` is added to `holdings` only the first time it's received (`if (quantity1155[tokenId] == 0) { holdings.add(tokenId); }`, L346–348) — repeat deposits of an already-held ID do **not** add a second entry. For ERC721 (L353–361), every received `tokenId` is added unconditionally (L358), since ERC721 IDs are inherently unique — one `holdings` entry per physical unit there. Removed in `withdrawNFTsTo`: for ERC1155, only when the *last* unit of that ID leaves (`quantity1155[tokenId] == 0` after decrement, L389–391); for ERC721, unconditionally per withdrawal (L398).
- `quantity1155` (`mapping(uint256 => uint256)`, L62) — for ERC1155-mode vaults only, tracks how many copies of each distinct `tokenId` the vault currently holds (incremented L349, decremented L388). **Never touched outside the `is1155` branches** — for an ERC721 vault this mapping stays entirely at its zero default; irrelevant there.
- `is1155` (bool, L51) — selects which of the two accounting regimes above governs a given vault instance.

**Variable-value intent (the return value of `getRandomTokenIdFromFund`, L415)**: for an ERC1155-mode vault, the returned `tokenId` should be drawn such that `P(return t) = quantity1155[t] / Σ_{t' ∈ holdings} quantity1155[t']` — proportional to how many units of `t` are actually held, not merely whether `t` is held at all.

**Statement/line-level intent**: `getRandomTokenIdFromFund` is meant to uphold "every currently-held *unit* of inventory is equally likely to be the one returned" — a fairness invariant over the vault's redeem/swap path. The actual code instead computes `randomIndex = getPseudoRand(holdings.length())` (L414) then `return holdings.at(randomIndex)` (L415) — uniform over `holdings`'s **cardinality** (the count of distinct IDs), which only coincides with "uniform over units" when every held ID has quantity exactly 1 (always true for ERC721; not generally true for ERC1155).

**Reported erroneous behavior** (H-03, verbatim, `Web3Bugs/reports/8.md` lines 94–108): *"`NFTXVaultUpgradeable.getRandomTokenIdFromFund` does not work with ERC1155 as it does not take the deposited `quantity1155` into account. Assume `tokenId0` has a count of 100, and `tokenId1` has a count of 1. Then `getRandomId` would have a pseudo-random 1:1 chance for token 0 and 1 when in reality it should be 100:1. This might make it easier for an attacker to redeem more valuable NFTs as the probabilities are off."* Recommendation (verbatim): *"Recommend taking the quantities of each token into account (`quantity1155`) which probably requires a design change as it is currently hard to do without iterating over all tokens."* Sponsor `0xKiwi` **acknowledged** (not "confirmed," and not disputed) — no code fix was ever supplied by either side. Judge (`cemozer`) raised it to High: *"Marking this as high risk as an attacker can weed out high-value NFTs from a vault putting other users funds at risk."*

**Expected/intended behavior**: `P(getRandomTokenIdFromFund() = t) = quantity1155[t] / Σ_{t' ∈ holdings} quantity1155[t']`, for ERC1155-mode vaults, instead of the code's actual `1 / |holdings|`. Using the report's own numbers: `tokenId0` (quantity 100) and `tokenId1` (quantity 1) should be selected in a 100:1 ratio; the code as written gives 1:1 (`|holdings| = 2`, uniform over the two distinct entries, quantity ignored entirely).

**Patch intent**: **none available** — this is not merely "no diff was pasted into the report" (several other cases in this dataset are in that position but still get a clear qualitative recommendation, e.g. `70_H_03`/`70_H_05`); here the report's own recommendation explicitly *disclaims* having a concrete fix ("probably requires a design change," "hard to do without iterating over all tokens"). There is therefore no formula anywhere in the source material — not even an informal one — describing what the corrected implementation would actually compute; only the qualitative weighting property itself (quantity-proportional, not uniform-over-distinct-IDs) is stated. This is the first fact that shapes R1-2/R1-3 below: unlike every prior case in this batch, R1-1 cannot produce even a candidate "intended formula" to check equality/inequality against — only a statistical *property* the intended distribution must have.

**Bug-relevant intended numeric behavior**: for ERC1155-mode vaults, the probability that `getRandomTokenIdFromFund()` returns a given token ID must be proportional to that ID's currently-held quantity, not merely to whether it is held at all (uniform-over-distinct-IDs, what the code actually implements).

## R1-2 — Intent Abstraction

Governing question: what numeric property distinguishes the reported buggy behavior from the intended behavior? Here the honest answer is that the distinguishing property is **a claim about a probability distribution** — the relative *frequency*, across the (unbounded) space of possible `(blockhash, randNonce)` pseudo-random inputs a call to `getRandomTokenIdFromFund()` might see, with which each distinct token ID is returned. This must be stated explicitly and up front, because it determines everything that follows in R1-3: this is **not** a value-centered constraint on a quantity computed at one program point in one execution (README's first orientation — e.g. `returnExpression >= X`), and it is **not** an effect/state-transition-centered claim about persistent state across one call (the second orientation — e.g. `holdings(Entry) != holdings(Exit)`) either. Every value realized by one concrete call to `getRandomTokenIdFromFund()` — the computed `randomIndex`, the returned `tokenId` — is a single deterministic sample, and that one sample is logically consistent with **both** a correctly quantity-weighted selection scheme and the current uniform-over-distinct-IDs one (any legal output of one scheme is also a legal output of the other, for *some* choice of blockhash/nonce). Nothing about one execution's trace can, by itself, witness this defect. This observation is carried forward as the decisive finding of R1-3, not treated as a mere framing note.

## R1-3 — Select the least implementation-specific sufficient relation

Tried in the README's stated order (directional → inequality/bound → relational invariant → exact equality), plus the two mandatory rescue checks:

**1. Directional/state-change**: e.g. `returnExpression ∈ holdings`, or "`holdings` changes across calls." **Rejected — vacuous.** `returnExpression ∈ holdings` holds unconditionally under both the buggy code and any conceivable fix (any correct or incorrect selection scheme must return *something* currently held); it says nothing about quantity at all and cannot discriminate.

**2. Inequality/bound, via the call-argument relation form (`duringClause: identifier '.' 'arg' '[' numberLiteral ']' relOp intentValue`, `Solidity.g4` line 306)**: e.g. `getPseudoRand.arg[0] == Σ_{t∈holdings} quantity1155[t]`, checking that the modulus passed to `getPseudoRand` reflects total quantity rather than `holdings.length()`. **[Reviewer B correction]** The original draft rejected this "on two independent grounds," treating (a) *partial discrimination* (a modulus-only check wouldn't catch every buggy-in-spirit implementation, e.g. one with a correct modulus but an unfair index-to-token mapping) as an independent rejection ground alongside (b) *inexpressibility*. That conflates two different questions per README §3: a candidate that discriminates the *reported* defect on the *reconstructed scenario* but not every conceivable variant is not automatically rejected — §3 requires recording `Intent coverage: Partial` for exactly this situation, not discarding the candidate. Checked directly: on the report's own scenario (`tokenId0` qty 100, `tokenId1` qty 1), the buggy code passes modulus `holdings.length() = 2`; any weighted-selection fix drawing from "how many total units are held" must pass modulus `Σ quantity1155[t] = 101` — so `getPseudoRand.arg[0] == 101` genuinely rejects the observed buggy call while accepting the reconstructed intended one. This candidate **would qualify as Expressible with `Intent coverage: Partial`** were its operand referenceable. **The sole actual blocker is (b): inexpressibility.** There is no in-scope value for "total quantity across held token IDs" — computing it requires `Σ_{t ∈ holdings} quantity1155[t]`, and the grammar's `intentValue` (`arithExpr`, `Parser/Solidity.g4` lines 341–376: literals, `varRef`s with `.member`/`[index]`/snapshot-qualifier access, parenthesized arithmetic, `+ - * / % ** << >> >>>`) has **no aggregation/summation construct, no loop, and no way for an annotation to range over a mapping's or set's contents** — confirmed by direct grammar read (verified independently by Reviewer B against the same production set). This is a genuine **beta**-type gap (no in-scope variable/expression represents the needed aggregate value at all); it is decisive on its own and requires no assistance from a separate "insufficiency" ground.

**3. Relational invariant relating two individual `quantity1155` lookups to relative selection frequency**: e.g. "if `quantity1155[t0] > quantity1155[t1]` then `t0` is returned more often than `t1`, over repeated calls." **Rejected — not a relation form the grammar has, in principle, not merely as an oversight.** Every `commonClause`/`duringClause` production the grammar defines (`ReturnExprCmp`, `ReturnIndexCmp`, `ReturnVarCmp`, `PercentOf`, `Ceil`, `Floor`, `RelationalCmp`, `Implication`, `VarChangedEval`, `DuringFunctionArg`, `Solidity.g4` lines 304–328) is evaluated exactly once, against the values one concrete execution's `σ_entry`/`σ_exit`/`σ_before`/`σ_after`/`σ_assign` actually realizes. None of them has any notion of frequency, expectation, or probability across a family of executions differing only in their random inputs — "returned more often than," by construction, is not a fact about any single execution at all.

**4. Exact equality, pinning one concrete pseudo-random draw**: fix `block.number`, `blockhash(block.number - 1)`, and `randNonce` to specific values, compute the resulting deterministic `randomIndex = keccak256(...) % holdings.length()`, and assert `returnExpression == <that specific tokenId>`. **Rejected on two independent grounds, either alone sufficient.** (a) `keccak256(...)` and `blockhash(...)` have no representation anywhere in `intentValue`'s grammar — no hash-function or `blockhash`-global production exists in `arithExpr`/`arithFactor` at all (not merely "disallowed," genuinely absent), so `randomIndex`'s own deterministic formula cannot even be written, independent of anything about `holdings`/`quantity1155`. (b) Even granting (a) away by some other means, there is still no way to state what the *correct* token ID would be for that fixed draw — R1-1 already established the report supplies no concrete corrected algorithm (a "design change... iterating over all tokens" is explicitly named as the likely shape of a real fix, with no formula given), so there is no "intended value" defined anywhere in the source material to assert equality against. This alternative fails even before reaching the question of whether one fixed draw could ever demonstrate a *distributional* property (it manifestly cannot, per R1-2 — a single draw's outcome, even if fully specified, would only be one sample, not a frequency).

**Required R1-3 negation check, adapted**: normally this check asks whether the selected relation's negation fails to catch some alternative implementation that retains the defect differently. Here it cannot even be posed in its usual form, because **no candidate relation survived R1-3 to be selected** — every tier failed either on soundness (2a), on grammar/value-availability grounds (2b, 4a), or on the relation form not existing at all for this kind of claim (3, 4b). This is recorded explicitly rather than skipped: the negation check presupposes a relation whose discrimination power can be interrogated, and this case never reaches that point.

**Known-bound/call rescue check (mandatory, Nokon-style, before declaring a function-call blocker decisive)**: is there a known bound on `holdings.length()`, `holdings.at(...)`, or `getPseudoRand(...)`'s results that would let some relation avoid needing the call itself? **No.** `holdings.length()` is not a call to a value with any knowable constant/bound — it is the live size of a set that grows on every first-deposit of a new ID and shrinks on zero-quantity removals, with no protocol-enforced floor or ceiling anywhere in this contract. And even a hypothetical bound on it would not help: as with candidate 2 above, a bound on the *set's size* says nothing about the *weighting-by-quantity* property that is actually in dispute. `getPseudoRand`'s output is, by design, meant to vary across calls; no fixed constant could stand in for "a fairly-weighted random draw" the way Nokon's `calculateRate()` minimum stands in for a rate. The rescue technique substitutes a known bound for an *unknown call result* while the underlying property remains a deterministic, single-execution fact — here the underlying property is not a deterministic single-execution fact to begin with (R1-2), so no substitution of any kind closes the gap. **Checked and confirmed inapplicable, not skipped.**

**Snapshot-qualified `varRef(Entry/Exit/Before/After/Assign)` extension check**: does this case need to compare an old value to a formula involving a third, independent term — the gap this extension exists to close? **No.** Nothing about this defect is a before/after or entry/exit comparison: `holdings`/`quantity1155` are only *read* by `getRandomTokenIdFromFund` itself (mutations happen in the separate caller-adjacent functions `receiveNFTs`/`withdrawNFTsTo`), and even where a snapshot comparison could in principle be constructed, the defect is a same-instant weighting-by-content property, not a state-transition one. **Checked and confirmed inapplicable.**

**A partial, worth-recording referencing finding (matching the discipline of checking whether a naively-alpha-looking reference actually has a workaround, per `70_H_03`/`70_H_05`'s precedent)**: `holdings` is declared without a visibility modifier (`EnumerableSetUpgradeable.UintSet holdings;`, L61 — default `internal`), and its type resolves, with no privacy modifiers of its own at any level, through `UintSet { Set _inner; }` down to `Set { bytes32[] _values; mapping(bytes32=>uint256) _indexes; }` (`evaluation/RQ1/target_contracts_original/dependencies/EnumerableSetUpgradeable.sol`, read directly this session, lines 39–46, 246–248). Since the intent grammar's `subAccess` supports chained `.identifier`/`[expression]` access (`Solidity.g4` lines 379–386), `holdings._inner._values.length` and `holdings._inner._values[i]` are syntactically legal `varRef`s that reach the set's raw backing array **without** going through the library's function-call interface (`.length()`/`.at()`) at all — the same "inline the call's underlying formula as raw field/arithmetic access" workaround `70_H_05` used for `FixedPoint.decode144()` and `70_H_03` used (unsuccessfully, for a different operand) for the same library call. This resolves the narrow sub-question of whether `holdings`'s size/contents can be referenced call-free — **it does not rescue the case**: it supplies no summation construct for `Σ quantity1155[t]` (beta, candidate 2b, is unaffected), and it does nothing about the decisive problem below. Recorded to show this avenue was checked, not skipped. **[Reviewer B verification]** Confirmed accurate against `dependencies/EnumerableSetUpgradeable.sol` directly: `UintSet { Set _inner; }` (line 246–248) and `Set { bytes32[] _values; mapping(bytes32=>uint256) _indexes; }` (line 39–46) are exactly as described, and `holdings._inner._values`/`.length`/`[i]` are legal chained `subAccess` per the grammar. One added nuance worth recording for completeness (does not change the conclusion): `UintSet.at(uint256 index)` (library, line 294–296) returns `uint256(_at(set._inner, index))` — i.e. it explicitly casts the raw `bytes32` element to `uint256` on the way out. A raw `holdings._inner._values[i]` reference bypasses that cast and yields the underlying `bytes32` representation, not a `uint256` — so this workaround is only exactly equivalent to `.at(i)` if the engine/grammar treats a `uint256`-valued set's `bytes32` backing slot as numerically interchangeable with `uint256` (true here, since `UintSet.add` stores `bytes32(value)`, a direct reinterpretation with no hashing, so the numeric value is preserved bit-for-bit — but this is worth stating explicitly rather than assuming the workaround is type-transparent by default, since for `AddressSet`/`Bytes32Set` the reinterpretation semantics differ). Does not affect this case's beta/epsilon verdict either way, since the referencing workaround was already established as non-rescuing.

**Decisive blocker, independent of every referencing question above**: even granting every referencing convenience considered — call-free access to `holdings`'s raw contents, a hypothetical aggregation construct for "total quantity," a hypothetical hash/`blockhash` production inside `arithExpr` — the reported property remains a claim about the *statistical distribution* of `getRandomTokenIdFromFund()`'s output across repeated, independently-randomized calls, not a fact realized within any single execution's state. As established in candidate 3 above, **no production in the grammar's `commonClause`/`duringClause` set has any notion of frequency or probability across executions** — every one of them is a fact about one execution's realized values. This is the primary, independently-sufficient reason this case is inexpressible, present even where none of the narrower value-availability gaps (candidate 2b/beta) would matter on their own.

## R1-4 — During vs Post (attempted, before the decisive blocker)

**Natural choice, notionally: Post.** The property concerns `getRandomTokenIdFromFund`'s return value — R1-4's own listed Post category ("the relation concerns... a return value") — not an intermediate, statement-time value; there is no meaningful "During" reading of a distributional claim about the function's *output*, only about individual local values mid-computation, which is not what the defect is about.

**Required explicit delta-exception check (per task brief), performed on this case's own facts**: does the only viable observation point sit inside a `for`/`while` loop body, hitting the confirmed loop-body-`@During`-never-evaluated exception (README §4)? `getRandomTokenIdFromFund` itself (L413–416) contains **no loop** — the check does not apply to the function under analysis directly. A secondary candidate is worth checking explicitly rather than dismissing by assumption: could a per-draw check be attached instead at the **call site**, inside `withdrawNFTsTo`'s loop (L373–400), where `getRandomTokenIdFromFund()` is actually invoked once per withdrawn unit? Such a `@During` **would** sit inside that loop body and **would** separately, independently hit the confirmed delta exception (`Interpreter/Engine.py`'s `fixpoint()`/`reinterpret_from()` never evaluating a loop-interior `@During`) — but this is moot: the relation itself is already rejected on content grounds (R1-3, gamma — a distributional claim, not a per-draw fact) before the observation-point question is even reached, exactly matching `70_H_03`'s R1-4 discipline for its own, differently-caused block. **This case's actual blocker is unrelated to delta**, and delta is not adopted as a tag here (see R1-7).

## R1-6 — Attempted construction of the target annotation (blocked — see below)

**Attachment point (would-be)**: `@Post` on `getRandomTokenIdFromFund()`, or alternatively a `@During` call-argument clause on the `getPseudoRand(holdings.length())` call site (L414) — either point was considered notionally viable for *some* relation, per R1-4.

**The construction fails, for the reasons developed in full in R1-3, summarized here against R1-6's own checklist**:
- No known constant is available anywhere in the source to fill in for "the correct weighted-selection outcome" — the report's own recommendation explicitly disclaims specifying one (R1-1).
- No in-scope aggregate value represents `Σ_{t ∈ holdings} quantity1155[t]` — the grammar has no summation/aggregation construct at all (R1-3, candidate 2b — **beta**).
- The reported property is naturally "quantified" in a sense the grammar's collection-instantiation workaround (README's R1-6 note: pick one concrete representative element when a property ranges over a collection) **does not cover**, because the quantification here is not over which element of a collection is examined — it is over the *space of random draws*, i.e., over repeated executions of the same call. Instantiating on "one representative draw" (R1-3 candidate 4) does not approximate the reported property the way instantiating on "one representative pool" approximates a collection-quantified property elsewhere in this dataset (e.g. `83_H_01`'s `poolInfo[1]`) — a single draw carries no information about a distribution at all, whereas a single pool genuinely does carry the full content of that pool's own state. This distinction is recorded explicitly so the (inapplicable) collection-instantiation workaround is not mistakenly invoked here.
- Even setting the above aside, no relation form in `commonClause`/`duringClause` evaluates a probability/frequency claim at all (R1-3, candidate 3 — the decisive, independently-sufficient blocker; tagged **epsilon**, not gamma — see R1-7 for why).

**Conclusion**: R1-6 cannot produce a fixed target annotation, at any legal program point, that is both (a) grammatically legal and (b) a faithful expression of the R1-1/R1-2 intended property — no aggregate operand exists (beta), and, decisively, no relation form the grammar defines is capable of stating a distributional/probabilistic claim in the first place (epsilon), independent of operand availability.

## R1-7 — Expressibility decision

- **Values referenceable at a legal program point**: Partially. Individual `quantity1155[t]` lookups (a concrete mapping index) are ordinary, legal `varRef`s. `holdings`'s raw contents/size are also referenceable call-free via its internal storage layout (R1-3's storage-layout finding). The one value with no in-scope reference of any kind is the **aggregate** `Σ_{t ∈ holdings} quantity1155[t]` (no summation construct exists — beta) and, separately, `getPseudoRand`'s internal `keccak256`/`blockhash` formula (no hash/`blockhash` production exists in `arithExpr` — a further, non-decisive alpha-shaped gap, not adopted as an independent tag since it is not what blocks the actually-attempted relation; see below).
- **Arithmetic/logical relation representable**: **No, not for the property actually needed** — this is the decisive point, not the value-availability question above. No production in `commonClause`/`duringClause` (`Solidity.g4` lines 304–328) evaluates a claim about the distribution of outcomes across repeated executions; every relation form is a single-execution fact. This is true independent of which operands would be referenceable.
- **Observation point supported**: Not reached — the relation-form blocker above is dispositive regardless of attachment point (R1-4's explicit delta check further confirms the case's real blocker is unrelated to loop-body observation-point limits).

**Outcome: Expressible = NO.**

**[Reviewer B — tag correction, the central finding of this review]** Agent A's original draft tagged this case `beta_and_gamma`, explicitly generalizing README §4's `gamma` — defined as *"the relation is inherently multi-point/structural (spans multiple statements or an accounting relationship the grammar's single-relation forms can't capture), independent of any single missing value"* — from "spans multiple statements" to "spans multiple **executions**," and flagged this generalization itself as needing scrutiny. Independent review, re-reading §4's text fresh (not deferring to Agent A's own flagged uncertainty) and cross-checking against every other case in this batch that discusses `gamma` (`02_web3bugs_71_H_11`, `03_web3bugs_83_H_01`, `11_web3bugs_70_H_03`, `16_web3bugs_5_H_15` — all of which describe or rule out `gamma` only in the "multi-statement/accounting-structural within one execution" sense, e.g. `16_web3bugs_5_H_15`: *"not about the relation being inherently multi-statement/accounting-structural in a way no single-relation grammar form could express"*), concludes: **this is not a legitimate reading of `gamma`, and this case needs a new tag.**

Reasoning: every example README gives for `gamma` — "spans multiple statements," "an accounting relationship the grammar's single-relation forms can't capture" — describes a relation that is still, in principle, a fact about *one execution's* trace; it just needs to relate values realized at *several distinct points within that one trace* (via the snapshot-qualified `varRef(Entry/Exit/Before/After/Assign)` machinery, or several `commonClause`s combined). The grammar's engine already provides exactly this kind of multi-point access within a single execution — `σ_entry`, `σ_exit`, `σ_before`, `σ_after`, `σ_assign` are all snapshots *of the same run*. What this case needs is categorically different: a claim about the *frequency distribution of outcomes across many independent runs* differing only in their random inputs. No number of within-execution snapshots — however many, however extended the grammar's snapshot machinery hypothetically became — could ever witness a frequency/probability fact, because a single execution realizes exactly one sample from that distribution, and (per R1-2) that one sample is logically consistent with *both* the buggy and the intended scheme. This is not "the grammar's single-relation forms can't capture an accounting relationship spanning several statements" (gamma); it is "the grammar's entire relation-evaluation model — one relation, checked once, against one execution's realized state — has no way to represent a fact that isn't a property of any single execution at all" — a different axis of inexpressibility than gamma addresses, present even hypothetically for a grammar with unlimited multi-statement/aggregation power.

This finding is well-grounded (a confirmed fact from direct reading of `Solidity.g4`'s `commonClause`/`duringClause` productions and their single-σ evaluation semantics, matching the evidentiary bar README §4 sets for `delta`, the last tag added under similar reasoning) — not a speculative or borderline call. Per the task brief's instruction to independently rule on this rather than defer, this review proposes and adopts a fifth tag:

**epsilon (new, proposed this review)** — the relation's content is inherently a probabilistic/distributional property over the outcomes of repeated, independently-randomized executions of the same function/call site (a frequency or probability claim), not a fact realized within any single execution's state, regardless of how many within-execution snapshots or statements the relation could draw on. Distinct from `gamma`: `gamma`'s multi-point/structural cases are still, in principle, single-execution facts that current single-relation forms merely can't stitch together; `epsilon` cases are not single-execution facts under *any* relation form, current or hypothetically extended, because the grammar's entire evaluation model checks one relation once per execution with no notion of frequency/expectation across a family of executions. **This tag is proposed pending README §4 formalization by the orchestrator/researcher — it is used provisionally in this case record.**
